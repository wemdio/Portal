# Portal repo — AI agent entrypoint

Этот файл подгружается Claude Code автоматически в начале каждой сессии.

Перед любыми действиями с Git, релизом или production обязательно прочитай и соблюдай [`AGENTS.md`](./AGENTS.md). Раздел про границы релиза и production — критический.

## Что это за репозиторий

Portal — внутренний инструмент студии: Next.js app, воркеры и production-БД на prod-сервере, интеграция с Instantly для cold outreach. Инфраструктура описана в [`.env.servers`](./.env.servers) (НЕ коммитить).

- Прод: `139.60.162.12` (Next.js, workers, main Supabase/Postgres, два instantly-postgres, analytics-датасет `instantly_dataset`, instantly-sync-bot, qualifier и т.д.)
- Старый DB/utility-сервер: `144.31.54.166` (временные rollback-копии после переезда и вспомогательные сервисы; не использовать как текущий endpoint БД)

Документация и архитектура: [README.md](./README.md), [DESIGN.md](./DESIGN.md), [PRODUCT.md](./PRODUCT.md).

## Когда работаешь с Instantly-датасетом (analytics, AI-агент по outreach данным)

**Сразу читай [`wiki/CLAUDE.md`](./wiki/CLAUDE.md)** — там полный контекст:
- структура `instantly_dataset` (23 таблицы + 6 lookup + 6 views, 2.1M+ писем (растёт еженощно), 167K лидов)
- паттерн `wiki/` для накопления знаний (Karpathy LLM-wiki)
- **обязательный self-improving eval loop**: каждая сессия логируется в `query_log`, раз в неделю ревьюим и улучшаем датасет/wiki (YC-style)

Связь и креды к датасету — в `.env` под `INSTANTLY_DATASET_DB_URL`.

## Когда работаешь с самим portal-приложением (Next.js, воркеры, миграции основной БД)

Это вне scope wiki — обычная разработка. Используй стандартные практики проекта.
- App код: `app/src/`
- Скрипты: `app/scripts/`
- Миграции основной БД: `supabase/migrations/`, `supabase/instantly-migrations/`

### Как деплоится ночной синк датасета (`app/scripts/instantly-dataset/`)

Синк живёт **вне** compose приложения: `/opt/instantly-dataset-sync` на 139, крон `docker run node:22-alpine node sync.mjs` в 00:00 МСК. Два пути на прод:
- **Код** (`sync.mjs`, лейблеры, `sync-portal-mirror.mjs`, `*.sql`) — автодеплой из main (`.semaphore/scheduled-deploy.yml`, шаг «Dataset sync»): триггер — изменения в `app/scripts/instantly-dataset/*` (кроме `wiki/`), `node --check` в образе крона, прежняя версия в `.prev/`, при ошибке приложение деплоится штатно, а в health-чат летит алерт и прогон красный. Список файлов в шаге должен совпадать с `deploy-sync.sh`.
- **Конфиг** (`.env` синка, crontab, `npm install`) и хотфиксы до мержа — руками `app/scripts/instantly-dataset/deploy-sync.sh` (см. шапку: он пересобирает прод-`.env` из локального — сверь `INSTANTLY_DATASET_DB_URL`).
- Доки для специалистов (`app/scripts/instantly-dataset/wiki/*.md`) → `node app/scripts/instantly-dataset/load-agent-wiki.mjs` (пишет в `agent_wiki` датасета).

## Что НЕ делать

- Не коммитить `.env*` файлы — там креды.
- Не дёргать Instantly /emails API больше 10 RPM пока `portal-worker-instantly-leads` контейнер запущен на prod — общий workspace rate limit, [инцидент 22 мая в `wiki/log.md`](./wiki/log.md).
- Не модифицировать `query_log` строки post-hoc для подкрутки метрик loop'a. Loop работает только если данные честные.
- Не добавлять тесты «за компанию» с правкой и не проверять текст уже применённых миграций и конфигов — см. «Правило: тесты пишем скупо» ниже.
- **Не создавать новые `*.test.ts` / `*.test.tsx` файлы** — набор уже сокращён до 1987 проверок в 176 файлах и обратно не отращивается. Если хочется закрыть баг регрессионным тестом, спросить пользователя; по умолчанию — фиксим код и всё.

## Правило: тесты пишем скупо

**Новых тестов в этом проекте не пишем.** Набор уже урезан до предела
(1987 проверок в 176 файлах) и обратно не отращивается: правки, тянущие
`it()` в существующий файл, согласовываются отдельно; правки, требующие
**нового** `*.test.ts` / `*.test.tsx` — по умолчанию отклоняются. Спросить
пользователя, прежде чем добавлять.

Прогон тестов в ветке — единственный барьер перед мержем (на `main` тесты не
гоняются вовсе), и одновременно он оплачивается временем разработчика на каждом
пуше. Поэтому набор держим маленьким и быстрым намеренно.

**Бюджет: прогон в ветке не дольше 3 минут.** Если правка его превышает —
проблема в правке, а не в CI.

Второй бюджет — деньги. Semaphore считает минуты **суммой по всем джобам**, а
не временем «от и до»: каждая лишняя джоба заново платит за пролог (checkout
репозитория и подъём node_modules — 1,3 ГБ, 88 тысяч файлов, около минуты).
Поэтому веточный блок намеренно состоит из одной джобы, и раскладывать его на
параллельные — значит менять ожидание на счёт. 31.08.2026 набор сокращён с
8423 проверок до 1987 в 176 файлах: остались деньги, доступы, жизненный цикл
воркеров и ядро аутрича. Обратно не отращиваем.

Проверить, во что обошёлся конкретный файл:

```bash
npx jest --silent --json --outputFile=/tmp/j.json && node -e "const r=require('/tmp/j.json').testResults.map(t=>[t.endTime-t.startTime,t.name]).sort((a,b)=>b[0]-a[0]).slice(0,15);console.table(r)"
```

### Не писать тест, если он не может упасть в будущем

Тест обязан ловить **будущую** ошибку, а не протоколировать сегодняшний код.
Если единственный способ его завалить — переписать проверяемый файл руками,
он не тест, а копия этого файла.

Так делать **нельзя**:

```ts
// tests/migrations/amoTasks.test.ts — удалён 31.08.2026 вместе с 57 такими же
const SQL = fs.readFileSync('.../20260803_0001_amo_tasks.sql', 'utf8');
it('создаёт таблицу amo_tasks', () => {
  expect(SQL).toMatch(/create table if not exists public\.amo_tasks/);
});
```

Миграция уже применена и по определению неизменна; SQL здесь не выполняется и
база не проверяется. Такой файл не поймает ни одной будущей ошибки.

Проверять конфиги и SQL можно — но **правилом по всем файлам**, а не текстом
одного. Живые примеры такого в репозитории:
- [`tests/migrations/grants.test.ts`](./app/tests/migrations/grants.test.ts) —
  у каждой новой таблицы обязан быть `grant ... to service_role` (ловит класс
  ошибки из инцидента мая 2026);
- [`tests/migrations/noTransactionMigrations.test.ts`](./app/tests/migrations/noTransactionMigrations.test.ts) —
  миграции `no-transaction` обязаны быть идемпотентны и без долларовых кавычек;
- [`tests/lib/nextBuildTypecheckConfig.test.ts`](./app/tests/lib/nextBuildTypecheckConfig.test.ts) —
  обязательные проверки не должны выпасть из `.semaphore/semaphore.yml`.

### Логику проверять напрямую, а не через отрисовку экрана

Замер на этом проекте (31.08.2026): **одна проверка через рендер интерфейса
стоит примерно как тридцать обычных**. 3% проверок съедали четверть времени
всего набора.

Рендер оправдан там, где проверяется именно поведение экрана — что кнопка
разблокировалась, что чужие данные не показаны. Всё остальное — расчёт суммы,
формат даты, ветвление, сортировка — выносится в функцию и проверяется без
`render()`.

### Не пережидать паузы

Если код спит (backoff, кулдаун, пауза между лидами) — тест обязан прокрутить
время, а не прожить его. Иначе один файл стоит секунды: так набор проседал на
46 секунд на ровном месте.

```ts
// Виртуальные часы: см. tests/lib/baseConstructorWorkerRetry.test.ts
beforeAll(() => jest.useFakeTimers());
afterAll(() => jest.useRealTimers());
const pending = updateJobWithRetry(...);
await jest.advanceTimersByTimeAsync(10_000);
const result = await pending;
```

Если пауза настраивается снаружи — просто задай 0 (`min_delay: 0`).
`jest.setTimeout(30_000)` в файле — почти всегда признак, что тест спит.

### Один сценарий — одна проверка, и лучше в существующем файле

Каждый **файл** стоит ~90 мс независимо от содержимого (766 файлов — это
больше минуты только на подготовку). Новый файл заводим на новый модуль, а не
на новый случай: случай добавляется в соседний `it()`.

Не покрывать одно и то же дважды — если логика уже проверена на уровне
функции, повторная проверка через API-роут и через экран не добавляет защиты.

### Перед добавлением теста ответь себе

1. Какая **будущая** ошибка его завалит? Не можешь назвать — не пиши.
2. Эту ошибку уже ловит соседний тест, типы или линтер? Тогда не пиши.
3. Нужен ли здесь рендер экрана, или хватит вызова функции?
4. Можно ли дописать `it()` в существующий файл вместо нового?

Отдельно для агентов: **новые тесты в этом проекте не пишем** — см. правило
в начале раздела. Правка формулировки, переименование, перенос кода тестов
не требуют.

## Правило: после правки compose обязателен `--force-recreate`

**Любая правка `docker-compose*.yml`** (`docker-compose.prod.yml`, `deploy/main-db-prod/docker-compose.yml`, `deploy/instantly-db/docker-compose.yml`) требует **явного** пересоздания затронутых сервисов:

```bash
docker compose -p <project> -f <file> up -d --force-recreate --no-deps <service1> <service2>
```

Без `--force-recreate` Docker хранит конфигурацию контейнера в собственной БД с момента `create` и при рестарте берёт её оттуда, а не читает compose. Правки лежат мёртвым грузом до пересоздания.

**Особенно критично для полей** `healthcheck`, `deploy.resources.limits`, `restart` — compose diff-detection иногда их пропускает.

**Прецедент 23.07.2026:** правка `healthcheck: disable: true` для двух distroless postgrest контейнеров была сделана 22.07, но `--force-recreate` не запустили → 15 часов loop failed exec → миллионы closed FIFO в dockerd → hang сервера. Post-mortem — коммит `f4cc524e`.

## Post-mortem от 23.07.2026 — что защищает от повторения

Уровни защиты, применённые после hang'а сервера:

1. **`/etc/docker/daemon.json` на 139** — log rotation (50 MB × 3 файла на контейнер) + `live-restore: true` (рестарт docker без падения контейнеров) + `nofile: 1M`.
2. **`/etc/systemd/journald.conf` на 139** — `SystemMaxUse=10G`, `RateLimitBurst=10000/30s` — journal не съест диск, спам-контейнер обрезается на уровне журнала.
3. **`services/health-check/main.py`** — TG-алерт при broken healthcheck (Health.Status=unhealthy + FailingStreak ≥ 20) с типом причины + pids ≥ 80% cgroup-лимита.
4. **compose fixes**: `localhost` → `127.0.0.1` в healthcheck main-storage и portal-telegram-bot-api (IPv6 fallback → refused при IPv4-only сервисе).
