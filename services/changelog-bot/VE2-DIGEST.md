# Ежедневная сводка по базам VE2

После штатного деплоя сервис `changelog-bot` публикует отдельную сводку **каждый
день в 11:00 МСК (08:00 UTC, 12:00 Астрахань/Самара)** в существующий
«Polza Общий Чат», общий топик. Компьютер пользователя не участвует.
Существующий дайджест изменений Portal в 09:00 МСК остаётся самостоятельным.

Новый отчёт не использует LLM, платные API проверки контактов или application
GET с reconciliation. Читает production Postgres в согласованной read-only
транзакции, сохраняет только собственную историю `ve_daily_digests` и отправляет
Telegram. Никаких сборов или подготовок он не запускает.

## Формат и источник

- Завершённые с прошлого отправленного поста базы, включая завершённые ниже
  цели с явной пометкой. Письма должны быть готовы.
- Прирост контактов в ранее готовых базах, если такой прирост есть.
- Текущий сбор/подготовка и очередь. Ожидание следующего раунда — продолжение
  сбора, не новая база в очереди.
- Ошибки и зависания **не публикуются**. Их безопасные категории остаются в
  закрытом `snapshot.items` со `state=issue` и read-only preview. Отдельной
  автоматической отправки проблем в Telegram нет: разбор только владельцу в
  его задаче. Сервис не знает и не угадывает личный Telegram ID владельца.

Охват — выбранные, не отменённые подготовки VE2. Проверяются одновременно
base status/error, preparation, target progress, привязанный ready template и
последние jobs по трём стадиям. Running без обновления более двух часов не
объявляется действующим сбором. Числа — сохранённые проверенные
`target_progress.ready_contacts`, иначе `ready_rows`; это не кандидаты и не
сырой `row_count`. Достижение цели проверяется по `ready_rows`, поскольку
лимит адресов компании может уменьшать зачёт. Базы не суммируются как
уникальные получатели. Отсутствие доступного снимка не подменяется нулями.

Первая граница — подтверждённый пост 25.09.2026 12:06 МСК,
[message 33349](https://t.me/c/1665607826/33349). `ve2_baseline.json` содержит
компактный снимок 102 выбранных баз (90 уже готовых), сверенный с предшествующим
снимком и подтверждением публикации. Контактов, кандидатов и секретов в нём нет.
Дальше границу задаёт последняя полностью подтверждённая серверная публикация.
Если после этого пост отправят вручную вне сервиса, перед следующим запуском
понадобится явно согласованная сверка/обновление границы; бот не читает историю
группы задним числом.

## Доставка и сбои

- Требуется миграция `20260928_0002_ve_daily_digests.sql`. Без неё отчёт не
  отправляется, health показывает ошибку; существующий changelog продолжает
  работать.
- Расписание UTC фиксировано. Каждые пять минут проверяется пропущенная
  публикация. После рестарта позднее 11:00 пост догоняется один раз с актуальными
  данными, а не отдельным постом за каждый пропущенный день.
- Прямое подключение Postgres необходимо для session advisory lock; production
  проверен: main-postgres на порту 35434. Transaction-pooling сюда не подставлять.
- Уникальная дата/канал, локальная блокировка и PostgreSQL advisory lock
  защищают от параллельных запусков. В БД перед HTTP записывается `sending`.
- Для длинных сообщений хранятся подтверждения отдельных частей. Подтверждённая
  часть повторно не отправляется. Отклонённая часть может быть повторена;
  после принятия первой части остальные используют тот же снимок с указанным
  временем. До первой принятой части повтор снимает свежие данные.
- Явный Telegram 4xx с `ok=false` допускает повтор. Таймаут/обрыв сети, 5xx,
  некорректное подтверждение или потеря записи подтверждения в БД блокируют
  новые публикации как `uncertain`. Это ограничение Telegram: у sendMessage нет
  ключа идемпотентности, а таймаут не доказывает отсутствие сообщения.
- При `uncertain` владелец проверяет общий чат и точный текст частей. После
  отдельного разрешения на production-запись администратор сверяет message IDs,
  подтверждает доставленные части либо разрешает повтор доказанно неотправленных.
  Нельзя просто удалять историю или переводить весь отчёт в pending: это может
  повторить уже опубликованное. Автоматического таймаута снятия блокировки нет.
- `/health` содержит `ve2_digest.status`, schedule, безопасный код ошибки либо
  report_id. Названия проблемных баз и токены в health/логах не выводятся.

## Проверка и включение

Миграция и образ бота входят в обычный релиз через `main`; отдельный локальный
Codex heartbeat не нужен. Переменная `VE2_DIGEST_ENABLED=0` отключает только
новую сводку (по умолчанию `1`, переменные `.env` уже передаются сервису).
Нельзя включать вторую локальную публикацию параллельно серверной.
Канал проверяется против подтверждённого bootstrap и через Telegram getChat.

Предпросмотр после деплоя (только чтение, не создаёт даже запись истории):

```sh
docker exec portal-changelog-bot python /app/main.py --ve2-preview
```

Результат содержит `parts` для общего чата, снимок и отдельные `private_issues`.
Не отправлять весь JSON в общий чат. Полный production deploy и применение
миграции требуют разрешения пользователя согласно AGENTS.md.
