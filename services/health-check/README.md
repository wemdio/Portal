# Health-check сервис

Отдельный контейнер для мониторинга портала polza-portal.ru.

## Что делает

- **Health check каждые 5 минут** — проверяет доступность БД и сайта
- **При сбое** — сразу шлёт красный флаг в Telegram
- **Монитор парсеров каждые 5 минут** — алертит, если активная задача не
  обновлялась 15 минут, или если новый запуск завершился реальной ошибкой.
  Ручные остановки не считаются ошибкой; повторные алерты по одному запуску
  подавляются даже после перезапуска health-check.
- **Монитор суточных пайплайнов каждые 5 минут**:
  - *OutreachOS* (`outreachos_pipeline_runs`): 🔴 прогон завис (`running`
    дольше порога) или упал (`failed` + текст ошибки), 🟠 прогон не стартовал
    к дедлайну, 🟢 дневной OK-стат (parsed/new/valid/залито A+B) — чтобы
    «тихий» день отличался от тихой поломки. В алертах — хвосты логов:
    `tail /var/log/portal/outreachos-cron.log`, `docker logs portal-worker-hh`.
  - *Mailganer auto-pipeline* (`client_auto_pipeline_runs`): 🔴 прогон упал
    (с текстом ошибки), 🟠 завис (heartbeat старше порога). Исторические
    failed-прогоны при первом запуске помечаются baseline'ом — старый хвост
    не заспамит чат. Логи: `docker logs portal-worker-autopipeline`.
  - *ENG ночной добор* (`he_auto_pipeline_configs` / `he_auto_pipeline_runs`,
    крон `heAutoPipelineCron` в 03:20 UTC): 🟠 включённый us-конфиг без паузы
    не обходился дольше 26 ч (`last_run_at`, до первого обхода — `created_at`;
    напоминание раз в сутки простоя) — крон не запускался или обход проекта
    падает; 🟠 строка прогона стоит `collecting` дольше 14 ч (самый длинный
    честный путь стадии `base_collect` — 3 + 3 + 6 ч — плюс 2 ч запаса), текст
    различает состояние базы и джобы `base_collect`. Каждая строка — один раз;
    строки старше 7 суток не поднимаются. Без колонки `refill_paused_at`
    (миграция `20260930_0005` не применена) берутся все включённые конфиги.
- **Монитор упавших баз каждые 5 минут** (`ve_bases` — русские вертикали VE2,
  `he_bases` — ENG и старый движок гипотез): сообщение «БАЗЫ», когда база
  переходит в `failed`. В нём проект, гипотеза или вертикаль, текст ошибки и
  команда для логов воркера. Три и больше базы с одной ошибкой (например,
  кончился баланс Requesty) приходят одним блоком со списком проектов. Одна
  база с одной ошибкой — одно сообщение. Когда базу продолжили и она вышла из
  `failed`, следующее падение снова придёт в чат. Базы, упавшие до включения
  монитора, при первом запуске помечаются baseline'ом.
- **Монитор «2ГИС → VE2» каждые 5 минут** (план `docs/reports/2026-10-26-2gis-ve2-plan.md`).
  Проверки 🔓/🧵/📈/🗺 молчат, пока на main-postgres нет ни роли `twogis_ve2`, ни
  сборщика Ш5 `twogis_ve2_builder` со входом (LOGIN); без `twogis_ve2` проверяются
  только строки pg_hba сборщика. Проверка 🛌 от роли не зависит и молчит, пока у
  баз нет метки сна. Отдельное сообщение
  `⚠️ 2ГИС → VE2`; напоминание раз в сутки (`HEALTH_TWOGIS_VE2_REPEAT_MIN`, 1440):
  - 🔓 в `pg_hba_file_rules` нет запрета для `twogis_ve2` выше общих строк — файл
    живёт в контейнере и пропадает при его пересоздании. Вернуть строки из
    `app/scripts/2gis-dataset/README.md` («VE2 user») и обязательно
    `SELECT pg_reload_conf();`: монитор читает файл, а не загруженные правила;
  - 🔓 у `twogis_ve2_builder` включён вход, а запрета для него выше общих строк
    нет. Вернуть две строки из `app/scripts/2gis-dataset/README.md`
    («Builder login») и `SELECT pg_reload_conf();` — или, если окно Ш5 закрыто,
    выключить вход: `ALTER ROLE twogis_ve2_builder NOLOGIN;`;
  - 🧵 `twogis_ve2` занят (не idle) всеми своими соединениями 3 цикла подряд —
    модуль 2ГИС завис;
  - 📈 на инстансе соединений не меньше min(85, 85% `max_connections`);
  - 🗺 модуль 2ГИС на паузе или в серии ошибок (`ve_twogis_source_status`, строка
    свежее 15 мин, `mode ≠ off`): вид ошибки, с какого времени, как выключить чтение.
    Смена снимка паузы не ставит и видна как серия с третьей ошибки подряд; для неё
    в сообщении другое: близнецы баз закрываются на первом чтении, нужна пересборка
    Ш5 (`004_ve2_features.sql`: prepare `-v new_build=1` → сборщик → index → swap) и
    новые snapshot_id/features_version в настройках, а `reads_enabled = false` лишь
    заставит новых близнецов ждать. Устаревшая строка (старше 15 мин) — состояние
    неизвестно: эпизод не закрывается, напоминание остаётся раз в сутки;
  - 🛌 база с близнецом 2ГИС спит дольше суток (`HEALTH_TWOGIS_VE2_SLEEP_MIN`, 1440).
    Читается только `public_info.two_gis_sleep` (`collect_info` — никогда) у баз в
    `collecting` с активной задачей `base_collect`: пауза подготовки снимает задачу и
    оставляет метку, у `failed`-базы задачи нет. В сообщении — причина при засыпании
    (пробуждения её не переписывают), с какого времени, проект, гипотеза, `#id` базы
    и строка для лога задачи (`docker logs … --since 2h`); данных карточек нет. Ключ —
    база + `since` (эпизод), напоминание раз в сутки от `since`. Ключи эпизодов, которых
    в цикле нет, удаляются только старше окна напоминания + 60 мин: во время полного
    тика метка на секунды пропадает и возвращается с тем же `since`, и удаление по
    отсутствию повторяло бы тот же алерт; новый эпизод — новый `since` и новый ключ.
    Три и больше базы с одной причиной — один блок со списком проектов; не больше 6
    блоков и 2400 знаков, остальное — «…и ещё N баз». Закрытая выдача (`closed`) и сбои
    чтения (`read_failed`) закрывают близнеца сами через сутки, остальные причины — нет,
    нужен оператор. Срез `public_info` знает метку только после миграции части 5: до неё
    проверка молчит, а при `mode = on` раз в сутки приходит «сон баз 2ГИС не виден»
    (функция `ve_base_public_info` без `two_gis_sleep`). Базы, уснувшие до миграции, срез
    видит только со следующей записи `collect_info`; в сообщении — запрос, который
    пересчитывает срез только collecting-базам с меткой сна.
  Ключи — по эпизоду; когда проблемы нет, ключи эпизода удаляются.
- **Монитор «ДВИЖОК → РАССЫЛКА» каждые 5 минут** — запуски Движка вертикалей
  через свою «Рассылку» (кампании `source_kind = 've2'`) и карточки лидов
  проектов. Отдельное сообщение `⚠️ ДВИЖОК → РАССЫЛКА`, тег — из
  `HEALTH_VE2_SENDER_ALERT_MENTION` (по умолчанию никого). Не больше 6 блоков и
  3500 символов, остальное — хвостом «…и ещё N» с заголовками; сначала красное:
  - 🟡 *выключатели*: сообщение на каждое переключение (кто, когда, пометка) и
    напоминание раз в 12 ч от переключения, пока выключено: новые запуски рынка
    только в Instantly, подача контактов рынка выключена, отправка кампаний
    Движка остановлена (сколько на паузе), карточки лидов выключены (сколько
    лидов с тех пор без карточки); возврат (рынок, отправка, карточки) — тоже
    сообщением;
  - 🔴 *выключатель не держит*: отправка остановлена, а кампания Движка идёт;
    письмо кампании ушло позже чем через 10 мин после остановки; карточки
    выключены, а автопередача поставила письмо клиенту;
  - 🟠 отправку вернули, а остановленные ею кампании не продолжены 15 мин —
    «нажмите «Продолжить отправку» ещё раз»;
  - 🟠 идущая кампания Движка молчит 3 часа окна отправки, хотя есть кому писать
    с ящика с запасом лимита (с адресами отправки и временем их связи);
  - 🔴 у идущей кампании не осталось рабочих ящиков (пул не менялся 15 мин);
  - 🟠 подача контактов в кампанию «Рассылки» стоит: наблюдение запуска старше
    60 мин при включённой подаче (считая от включения подачи; у нового запуска —
    от его создания), с причиной (кампания удалена, завершена, чужая, пул изменён
    вручную, иначе — лог воркера VE2);
  - 🟠 строки подачи висят: `attempting` > 30 мин, `uncertain` > 1 ч;
  - 🔴 воркер лидов встал: ответы без оценки > 30 мин, лиды без карточки > 15 мин,
    карточки не берутся в доставку > 10 мин — одним блоком; после включения
    карточек отсчёт — от включения (и при «прислать пропущенных»);
  - 🟠 оценка ответов не проходит > 2 ч (по тексту ошибки);
  - 🟠 карточка лида не доставлена > 1 ч или сдалась (`undelivered`).

  Напоминания — раз в 2 ч от начала проблемы (не по календарю); разовые
  сообщения смотрят не дальше 7 суток, baseline не нужен. Каждый запрос — со
  своим тайм-аутом 5 с, ошибка запроса (в том числе нет таблицы — миграция
  `20261026_0020` не применена) печатается в лог каждый цикл, остальные
  проверки идут дальше.
- **Сводка каталога Яндекс.Карт каждый день в 08:00 МСК** — сколько сканов
  обхода прошло за сутки и сколько новых организаций нашлось, сколько карточек
  обновилось за вчера. 🔴 синк не прошёл (ни одного успешного скана, или
  обновление карточек дало 0 при ненулевом резерве, или обход не запускался),
  🟠 упало ≥ 50% сканов либо новых организаций 0, 🟢 норма. Упавшие сканы
  группируются по причине; при ошибке прокси в сообщении сразу команда для
  проверки пула воркера. Появилось после 28.08–02.09.2026, когда пул прокси
  Карт умер и пять дней каталог молча не пополнялся.
- **Разбор ночного синка датасета каждый день в 08:30 МСК** — что случилось
  с четырьмя ночными заданиями крона (`sync.mjs` 00:00, зеркало портала 01:00,
  разметка ответов 02:00, разметка ниш 02:30) и **с каким именно текстом ошибки**.
  По каждому заданию: прошло / упало (с последней строкой ошибки из лога) /
  оборвалось без финала (убит процесс) / этой ночью не запускалось. Плюс из
  самой БД датасета — чем кончился прогон `sync.mjs`, сколько залито и как
  давно был последний успешный синк; старше 30 ч — красный флаг с прямым
  указанием, что дашборды сейчас показывают неполный день. Сообщение уходит
  каждое утро, включая зелёное: тихая ночь должна отличаться от тихо умершего
  бота. Появилось после 06.08.2026 (синк молча стоял пять дней из-за крона) и
  16.09.2026 (упал на общем ограничителе чтений) — оба раза замечал человек.
  Требует смонтированной `/var/log/instantly-dataset-sync` (см. compose) и
  `INSTANTLY_DATASET_DB_URL` в `.env`.
- **Ответы клиентам каждый день в 21:00 МСК** — health-бот проверяет журнал
  отправок из кабинета за 24 часа: ошибки, отказы защитной проверки адресата,
  случаи, когда явный адресат отдельного письма не совпал с автором входящего,
  и старые отправки без сохранённого адресата (их нельзя подтвердить по журналу).
  Показывает число ответов с другим адресом автора и проверенным адресатом, а также
  последние проблемные письма по ID, без текста переписки. Красный или оранжевый
  отчёт приходит даже при отключённых обычных уведомлениях.
- **Статистика каждый час** — отчёт по БД (проекты, пользователи, парсеры, задачи и т.д.)

## Конфигурация (.env)

| Переменная | Обязательно | Описание |
|------------|-------------|----------|
| `DATABASE_URL` | да | Строка подключения к PostgreSQL |
| `TELEGRAM_HEALTH_CHAT_ID` | да | ID чата для алертов и статистики |
| `TELEGRAM_BOT_TOKEN` | да | Токен бота (или `TELEGRAM_HEALTH_BOT_TOKEN` для отдельного) |
| `HEALTH_PORTAL_URL` | нет | URL портала (по умолчанию `https://polza-portal.ru`). В prod-compose для контейнера задаётся `extra_hosts: polza-portal.ru → host-gateway`, чтобы с того же сервера проверялся именно публичный сайт. |
| `HEALTH_INTERVAL_SEC` | нет | Интервал проверки в секундах (по умолчанию 300) |
| `HEALTH_JOB_MONITOR_INTERVAL_SEC` | нет | Интервал проверки задач парсеров (по умолчанию 300 секунд) |
| `HEALTH_JOB_STUCK_MIN` | нет | Через сколько минут без обновлений считать задачу зависшей (по умолчанию 15) |
| `HEALTH_OUTREACHOS_STUCK_MIN` | нет | Через сколько минут `running` считать прогон OutreachOS зависшим (по умолчанию 180) |
| `HEALTH_OUTREACHOS_MISSING_AFTER_UTC_HOUR` | нет | С какого часа UTC алертить «прогон не стартовал» (по умолчанию 4, крон в 02:00 UTC) |
| `HEALTH_AUTOPIPELINE_STUCK_MIN` | нет | Через сколько минут без heartbeat считать прогон Mailganer auto-pipeline зависшим (по умолчанию 30) |
| `HEALTH_HE_REFILL_STALE_HOURS` | нет | Через сколько часов без обхода включённого us-конфига ночного добора ENG алертить (по умолчанию 26, минимум 25) |
| `HEALTH_HE_REFILL_STUCK_HOURS` | нет | Через сколько часов строку `he_auto_pipeline_runs` в `collecting` считать зависшей (по умолчанию 34, минимум 33: очередь дочернего сбора до 10 ч + работа до 3 ч) |
| `HEALTH_VE2_SENDER_ALERT_MENTION` | нет | Кого тегать в сообщении «ДВИЖОК → РАССЫЛКА» (по умолчанию никого) |
| `HEALTH_VE2_REPEAT_MIN` | нет | Напоминание «ДВИЖОК → РАССЫЛКА», пока проблема держится, раз в столько минут (по умолчанию 120, минимум 30) |
| `HEALTH_VE2_SWITCH_REMINDER_HOURS` | нет | Напоминание о выключенном выключателе раз в столько часов от переключения (по умолчанию 12, минимум 1) |
| `HEALTH_VE2_STOP_GRACE_MIN` | нет | Через сколько минут после остановки отправки идущая кампания Движка и после выключения карточек автопередача — «стоп не держит» (по умолчанию 5, минимум 1) |
| `HEALTH_VE2_STOP_LEAK_MIN` | нет | Письмо кампании Движка позже стольких минут после остановки — «стоп не держит» (по умолчанию 10, минимум 2) |
| `HEALTH_VE2_RESUME_STALE_MIN` | нет | Через сколько минут после возврата отправки открытые строки остановки — «продолжение не закончено» (по умолчанию 15, минимум 5) |
| `HEALTH_VE2_SILENT_WINDOW_HOURS` | нет | Сколько часов окна отправки идущая кампания Движка может молчать при готовых получателях (по умолчанию 3, минимум 1) |
| `HEALTH_VE2_NO_MAILBOX_MIN` | нет | Сколько минут пул без рабочих ящиков не меняется до алерта (по умолчанию 15, минимум 5) |
| `HEALTH_VE2_OBSERVE_STALE_MIN` | нет | Возраст наблюдения запуска «Рассылки», после которого подача считается вставшей (по умолчанию 60, минимум 20) |
| `HEALTH_VE2_ROWS_ATTEMPTING_MIN` / `HEALTH_VE2_ROWS_UNCERTAIN_MIN` | нет | Сколько минут строка подачи может быть `attempting` / `uncertain` (по умолчанию 30 / 60, минимум 15 / 30) |
| `HEALTH_VE2_QUALIFY_BACKLOG_MIN` | нет | Сколько минут ответ кампании Движка может ждать оценки (по умолчанию 30, минимум 10) |
| `HEALTH_VE2_CARD_MISSING_MIN` | нет | Сколько минут лид может быть без карточки при включённых карточках (по умолчанию 15, минимум 5) |
| `HEALTH_VE2_CARD_IDLE_MIN` | нет | Сколько минут карточка к доставке может не браться воркером (по умолчанию 10, минимум 5) |
| `HEALTH_VE2_QUALIFY_STUCK_MIN` | нет | Через сколько минут неоценённый ответ — «оценка не проходит» (по умолчанию 120, минимум 60) |
| `HEALTH_VE2_CARD_PENDING_MIN` | нет | Через сколько минут недоставленная карточка — алерт (по умолчанию 60, минимум 30) |
| `HEALTH_TWOGIS_VE2_REPEAT_MIN` | нет | Напоминание «2ГИС → VE2», пока проблема держится, раз в столько минут от её начала (по умолчанию 1440, минимум 60) |
| `HEALTH_TWOGIS_VE2_SLEEP_MIN` | нет | Сколько минут база с близнецом 2ГИС может спать до алерта 🛌 (по умолчанию 1440, минимум 60) |
| `STATS_INTERVAL_SEC` | нет | Интервал статистики в секундах (по умолчанию 3600) |
| `INSTANTLY_DATASET_DB_URL` | нет | Аналитический датасет `instantly_dataset` для утреннего разбора синка. Не задан — разбор идёт только по логам |
| `HEALTH_DATASET_SYNC_LOG_DIR` | нет | Каталог логов ночного синка (по умолчанию `/var/log/instantly-dataset-sync`, монтируется read-only) |

Пороги `HEALTH_VE2_*` и `HEALTH_TWOGIS_VE2_*` читаются безопасно: не число или меньше минимума — в лог
пишется имя переменной (без значения) и берётся значение по умолчанию или
минимум; контейнер из-за опечатки не падает. Новое значение в `.env` начинает
действовать только после `--force-recreate --no-deps health-check`.

## Команды в чате (чтобы не спамить)

В группе, куда приходят алерты, можно писать боту:

| Команда | Действие |
|---------|----------|
| `/mute`, `/тихо`, `/alerts_off`, `/выкл` | Отключить отправку в чат — проверки продолжают работать, сообщения не приходят |
| `/вкл`, `/unmute`, `/alerts_on`, `/on` | Снова включить уведомления |
| `/alerts`, `/статус`, `/status` | Показать, включены ли уведомления |

Состояние хранится в БД (таблица `health_check_settings`), переживает перезапуск контейнера.

## Как получить TELEGRAM_HEALTH_CHAT_ID

1. Напишите боту любое сообщение
2. Откройте в браузере: `https://api.telegram.org/bot<TOKEN>/getUpdates`
3. Найдите `"chat":{"id":123456789}` — это ваш chat_id

docker compose up -d health-check
