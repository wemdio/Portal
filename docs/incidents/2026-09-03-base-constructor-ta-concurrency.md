# Оценка ЦА: две параллельные пачки в production-конфигурации

## Объём изменения

Продолжение исправления `c0becbdc8` (обрезанные ответы, resume и замеры).
В production compose дефолт `BASE_TA_SCORING_CONCURRENCY` меняется с 1 на 2.
Двенадцать реплик по-прежнему берут по одной задаче: максимум 24 одновременных
TA-запроса, а не 24 задачи/полных базы в памяти.

Библиотечный дефолт остаётся 1. Модель `policy/gemini-flash`, критерии оценки,
порог 7, размер исходной пачки 10, лимиты токенов/попыток/времени,
дедупликация, порядок строк и `keepAllScored` не меняются. Другие шаги и
инструменты отдельную настройку параллельности не получают.

## Гонка, закрытая до включения параллельности

Воспроизведён случай: одна пачка ожидает сохранения checkpoint, вторая уже
завершилась и поставила отчёт в очередь. После отказа первой записи
`reportChain.then(report, report)` запускал следующую запись и progress.

Цепочка теперь не восстанавливается после ошибки. Отложенный отчёт проверяет
отмену/ошибку в момент исполнения и после сохранения. Этот же сигнал видят
внутренние HTTP-повторы второй пачки. После обнаружения ошибки сохранения
повторы останавливаются, не создаются технические оценки и не публикуется успех.
Уже выполняющийся HTTP-запрос может завершиться; его результат после остановки
не сохраняется. Исходная ошибка checkpoint остаётся причиной отказа шага.

## Что проверяется

Расширены существующие тесты, без добавления файлов/`it()`:

- максимум два HTTP-запроса, включая чтение тела, обратный порядок ответов;
- частичный/обрезанный ответ добирается без потери успешного соседа;
- строки/почты остаются на своих местах, записи checkpoint последовательны;
- 100% появляется только после финального сохранения;
- при 429 повторяется только неудачная пачка с прежним bounded backoff;
- ошибка сохранения блокирует отложенные отчёты и HTTP-повторы соседа.

Тест найденной гонки сначала падал на прежнем коде. Ожидания моделируются
виртуальными часами; production и платные AI-запросы не используются.

Проверка перед передачей:

- полный Jest после переноса поверх актуальной Sergey (`a7261bc58`):
  213 suites / 2344 tests passed, 79.1 s;
- TypeScript `tsc --noEmit`, ESLint изменённых TS-файлов — успешно;
- bundle `worker/baseConstructor.ts` через esbuild — успешно;
- `docker compose config --no-env-resolution --no-interpolate` — успешно;
- сравнение YAML с раскрытыми anchors: у всех 12 реплик меняется только
  дефолт TA с 1 на 2; остальные сервисы, настройки и ресурсы равны HEAD;
- независимый review и `git diff --check` — без блокирующих замечаний.

В полном Jest есть неблокирующие `MaxListenersExceededWarning` для process
exit/SIGTERM/SIGINT; падений тестов нет. Next.js production build и фактический
деплой в рамках этой правки не запускались.

## Ограничения

Это не распределённый регулятор Requesty. Другие потребители аккаунта не
входят в потолок 24. Существующие повторы ограничены бюджетом исходной пачки;
при исчерпании бюджета остаётся явная ошибка, а не гарантированная оценка.
Ни баланс аккаунта, ни его тариф не используются в приложении как настройка.

При параллельности `ta_scoring_telemetry.api_duration_ms` — сумма длительностей
HTTP-попыток, а не время ожидания специалиста. Для сравнения скорости нужен
`step_timings.steps[].active_ms` по TA и число уникальных компаний. Двукратное
ускорение теоретическое: реальные повторы, latency и записи БД могут снизить
выигрыш. Его нужно измерить после отдельного деплоя.

## Выпуск и возврат к прежнему темпу

Production не изменяется этим коммитом. При согласованном деплое нужно
пересоздать только согласованные base-constructor контейнеры с новым образом
и настройкой; не обрывать активные задачи ради проверки скорости.

Явный `BASE_TA_SCORING_CONCURRENCY=1` в окружении имеет приоритет над новым
дефолтом. При read-only проверке `/home/Portal/prod/.env` такого переопределения
не было; непосредственно перед деплоем проверить повторно и проверить
фактическое значение в запущенных контейнерах после него.

Для снижения темпа обратно: в рамках отдельно согласованного деплоя задать
`BASE_TA_SCORING_CONCURRENCY=1`. Исправления сохранения/отмены откатывать не нужно.
Не менять количество реплик, лимиты CPU/RAM, модель или порог отбора вместе
с этим сравнением. Следить за активным временем TA, 429/timeout/length,
оставшимися ошибками, повторными запусками контейнеров и public health.
