# SMTP на Timeweb: устаревший разрешённый адрес Portal

## Причина, подтверждённая 14.09.2026

Уточнение к [первичной диагностике VBI](2026-09-14-ve2-hidden-progress-smtp-unreachable.md).
Пользователь сообщил, что utility-сервер `144.31.54.166` не оплачен. Состояние
его биллинга независимо не проверялось. Резервный SMTP proxy на Timeweb
`89.19.209.252` тоже не отвечал на запросы Portal к TCP/3100.

Через авторизованную пользователем консоль Timeweb проверено:

- сервер «Звонилка VPS», ID `6646351`, IP `89.19.209.252`;
- `smtp-proxy.service` active/running, Python слушает `0.0.0.0:3100`;
- локальный `GET /health` возвращает HTTP 200;
- INPUT разрешал TCP/3100 только для loopback и `139.60.162.12/32`, затем DROP;
- краткий tcpdump только заголовков SYN к TCP/3100 показал запросы от текущего
  Portal `139.60.162.24`. Они доходили до Timeweb, но не проходили INPUT;
- старое разрешение восстанавливалось через `ExecStartPre` в
  `/etc/systemd/system/smtp-proxy.service`, а не через `/etc/iptables/rules.v4`.

В панели также были сообщения о сбое ноды и переносе сервера. Они сами по себе
не доказывают причину этой ошибки: рабочий процесс и конкретное блокирующее
правило подтверждены внутри гостевой ОС. Это не повтор DNS-инцидента июля.

## Согласованное исправление

После отдельного согласия пользователя добавлено разрешение только для
`139.60.162.24/32` на TCP/3100. Существующие правила, включая общий DROP этого
порта, сохранены. В unit добавлена одна строка `ExecStartPre`: копия прежней
идемпотентной проверки/установки разрешения, с новым адресом Portal.

Резервная копия на Timeweb:
`/etc/systemd/system/smtp-proxy.service.bak-20260914-portal-ip`.

Выполнены `systemd-analyze verify`, `systemctl daemon-reload` и установка
разрешения в действующий INPUT. Проверка diff показала ровно одну добавленную
строку. Unit enabled, `NeedDaemonReload=no`, ActiveEnterTimestamp остался
`2026-07-24 15:33:36 UTC`: сервис и сервер не перезапускались.
Перезагрузка для проверки не выполнялась; сохранение обеспечено проверенным
`ExecStartPre` в загруженном unit с включённым автозапуском.

## Проверка из рабочего контейнера Portal

- 01:59:20 UTC: `GET /health` через `portal-worker-baseconstructor-12` —
  HTTP 200, `status=ok`, 404 мс.
- 02:01:20 UTC: одна реальная проверка документированного контрольного адреса
  `postmaster@gmail.com` через `/smtp-check` — HTTP 200, SMTP `250`,
  `exists=true`, `greylist=false`, без ошибки, 511 мс. Письмо не отправлялось.
- 02:01:43 UTC: текущая задача конструктора
  `6340785f-1fc1-45d9-b7ac-36c157e96aa7` сохраняла 37 OK и 43 Catch-All.
- Пакет VBI `96b59207-defa-4e15-80c1-7fcfc54675a4` завершился в 01:59:37 UTC:
  27 Catch-All, 973 unknown. Это результаты email-проверки, а не число
  контактов, прошедших весь отбор по гипотезе. Ранее сохранённые unknown
  нельзя считать подтверждёнными только потому, что доступ восстановлен.

Другие proxy на неоплаченном utility-хосте не восстанавливались. Конфигурация
Portal, данные очередей, кампании и правила допуска email не менялись; новые
сборы не запускались. Продолжающиеся задачи обрабатывались штатными workers.

## Ошибка при работе с доступом

Во время предыдущей диагностики нативная вставка с восстановлением системного
буфера привела к попаданию скопированного root-пароля в командную строку
консоли. Пользователь уведомлён сразу и повторно в итоговом ответе; ему передана
смена пароля через панель Timeweb. Сам пароль и снимок этого экрана не сохранены
в репозитории. Факт ротации пока не подтверждён. История команд не очищалась.
Для дальнейших команд использовалась только браузерная `Tab.paste`;
не использовать нативную вставку с восстановлением буфера для этой web-консоли.
