# VBI: скрытый прогресс и недоступные SMTP-сервисы

## Проверено 14.09.2026, 01:09–01:17 UTC

Пользователь видел «0 готово» на шаге «Базы и объём» примерно через час после
начала сбора. Подготовка «Сетей частных клиник» действительно имела статус
collecting; база `a7d6c650-05f7-480d-8d87-196459c7b12f` создана в 00:07:33 UTC.
Цель — 500 готовых контактов, два начальных пакета по 100 компаний.

Подробный статус находился внутри свёрнутого превью. Общая карточка его не
показывала. Дополнительно presentation трактовал pending родительского job
как ожидание очереди даже при processing у дочернего конструктора. VE2 штатно
делает self-requeue между опросами, поэтому pending не доказывает простой.

Исправлено: статус незавершённой подготовки виден над объёмом базы; снимок дочернего
обработчика учитывается при pending родителя. Отдельно показаны текущий этап,
процент этого этапа, цель превью, сохранённые счётчики и время обновления базы.
Процент не выдаётся за готовность всего сбора; время окончания не выдумывается.
Терминальная ошибка родителя имеет приоритет над старым снимком дочерней работы.

## Реальная задержка за интерфейсом

Все 12 BaseConstructor-контейнеров и VE2 были без рестартов/OOM с 22:40 UTC.
Первый пакет `96b59207-defa-4e15-80c1-7fcfc54675a4` сохранял checkpoints на
validate_emails=99. Из 1052 уникальных сохранённых результатов проверки:
1000 unknown, 52 invalid; 995 ошибок соединения с proxy и 5 DNS-ошибок.
899 адресов имели одну попытку, 153 — две. Это моментальный снимок, не итог.

Второй пакет `00a748dc-3e96-4272-9359-9d4d445cac0e` завершился в 01:09:45 UTC;
validate_emails занял 3 415 386 мс (~57 минут). 541 сохранённая строка и
valid_count=0 не означают 541 готовый контакт. Родитель забрал этот пакет,
пока соседний ещё работал. Рабочий 99% сохраняется во время повторных проб;
само это число не позволяет отличить первичный проход от повторного.

GET /health по всем настроенным адресам завершился connect timeout из
BaseConstructor-контейнера, а затем timeout с самого хоста Portal:

- `http://144.31.54.166:3100`
- `http://144.31.54.166:3101`
- `http://89.19.209.252:3100`

Это документированные utility endpoints, не адреса текущей Portal DB.
Причина недоступности самих серверов/сети пока не установлена. Нельзя считать
это повтором DNS-инцидента июля: тогда /health отвечал, сейчас не соединяется.
Serper и SMTP-валидация — разные зависимости. Редеплой UI не восстановит SMTP.

Пользователь подтвердил, что серверы должны работать. Дополнительные GET /health
с Mac тоже завершились timeout. С Portal TCP/22 на 89.19.209.252 доступен, но
3100 не отвечает; на 144.31.54.166 не ответили ни 22, ни 3100/3101. Поэтому
данные не доказывают выключение всех серверов: нужны проверка служб и сетевых
правил на utility-хостах. SSH-диагностика с Mac на 144.31.54.166 остановилась
на timeout banner exchange, для 89.19.209.252 не было доверенного host key;
проверка host key не отключалась.

## Граница и проверка

Диагностика production была read-only; сбор не отменяли, сервера не меняли,
новые сборы и платные поиски не запускали. Правила допуска email не ослаблены.
Исправление интерфейса не является восстановлением SMTP-инфраструктуры.

Существующий тест collectionProgress покрывает pending родителя + processing
ребёнка, приоритет failed родителя и завершённый пакет, ожидающий отбора.
Локальная визуальная проверка компонента на 1150 и 390 px: без ошибок JS и
горизонтального переполнения. Использовались синтетические данные без API.
