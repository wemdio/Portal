# Яндекс.Карты: запуск #790ce9bf собрал 41 организацию вместо ~2000 (15.07.2026)

Job id: `790ce9bf-13da-422d-9b64-0d5c7bd70339` (9 запросов: СПб/Москва/Новосибирск × Кафе/Ресторан/Бар, лимит 250/запрос).

## Проверка гипотезы «собрал 41 из 1/9 ссылок, остальные скипнулись»

**Не подтверждается.** По логам `application_logs` все 9 поисковых запросов
отработали одинаково: каждый получил первую порцию **4–12 ссылок в первую
минуту**, дальше новых карточек не приходило, и через ~5 минут тишины каждый
запрос умер с `TypeError: terminated`. 41 = сумма первых экранов всех девяти
запросов, а не полный сбор одного. Ни один запрос не был скипнут — все они
были «обрезаны» одинаково.

## Две причины (обе воспроизведены)

### Причина 1 (главная): зарубежные прокси → международная выдача yandex.com

`yandex.ru/maps` с зарубежного IP отвечает `302 → yandex.com/maps`
(воспроизведено с зарубежного egress: `curl -L https://yandex.ru/maps/?text=…`
приходит на `https://yandex.com/maps/?text=…`). Международная версия отдаёт
только «первый экран» (4–12 карточек) и не подгружает список при скролле —
живой тест на проде: 5 ссылок за 11 секунд, дальше 6 минут скролла впустую.
Исторический бенчмарк (апрель–июнь, российская выдача): 80–230 организаций
на запрос.

Код теперь детектит редирект и сигналит:
- парсер: `intl_redirect_detected` + лог `[!] Яндекс перенаправил на …`;
- стрим: `{"done": true, …, "intl_redirect": true}`;
- воркер: warn `parser.yandexmaps.collect.intl_redirect` на каждый URL и
  `…intl_redirect_summary` при завершении — задача больше не выглядит
  «успешной» молча.

### Главный фикс: сбор через внутренний API /maps/api/search (обход скролла)

Российских прокси нет и не будет (мобильные ~200 КБ/с не тянут), значит
скролл на международной выдаче не починить. Но выяснилось, что **скролл и не
нужен**: SPA Карт подгружает список не «прокруткой», а подписанными запросами
к `/maps/api/search` с пагинацией `skip`/`results`. Мы повторяем их напрямую.

Как это разобрано (всё воспроизведено с зарубежного egress — та же ситуация,
что на прокси Германии/Нидерландов):
- `yandex.ru/maps` → 302 → `yandex.com/maps`, страница отдаёт полный конфиг
  инлайном: `sessionId`, `csrfToken`, центр карты `mapLocation.center`,
  и `totalResultCount` (для «Москва Кафе» — 62, а не 5!). Данные ЕСТЬ, SPA
  их просто догружает по мере скролла через API.
- `/maps/api/search` требует подпись `s` = djb2/XOR-хэш от `qs.stringify`
  отсортированных (case-insensitive) параметров + `csrfToken`, `sessionId`,
  `ajax=1`, `ll`, `spn`, `z`, `origin`. Разобрано из бандла front-maps
  (модуль 79409). Без `s` → 400; без `ll`/`sessionId` → 500.
- Пагинация `skip += 12` вытянула **120 уникальных организаций** по «Москва
  Кафе» (Яндекс продолжает отдавать сверх `totalResultCount`, расширяя зону)
  против 4–12 скроллом. Ответ содержит полные данные: адрес, категории,
  телефоны, координаты, рейтинг, сайт (`urls`), соцсети (vk/telegram/whatsapp/
  instagram/youtube), часы работы. `card_url` строится из `seoname`+`id`.

Реализация:
- `yandex_parser.py`: `collect_organization_links_via_api()` — грузит
  страницу (куки/сессия/csrf/центр карты), затем пагинирует подписанный API
  из browser-контекста (`context.request`, куки общие). Возвращает
  канонические `yandex.ru/maps/org/…` — downstream (парсинг карточек,
  нормализация) не меняется. Пульс `on_links` идёт и на страницах-дублях.
- `server.py`: `YANDEXMAPS_COLLECT_MODE` = `api` (по умолчанию) | `scroll`
  (фолбэк на старый скролл — только для российской выдачи).

Почему только этап сбора ссылок, а не парсинг карточек: карточки через
зарубежные прокси парсятся штатно (в этом же инциденте 41/41 успешно) —
ломался только сбор списка.

Проверено: подпись из кода парсера принимается живым сервером,
`_api_search_page` пагинирует (43 орг за 4 страницы в интеграционном тесте),
юнит-тесты подписи/bootstrap/дедупа зелёные, heartbeat-стрим работает в
api-режиме. Полноценная проверка через сами прокси Германии/Нидерландов —
на проде после деплоя (чек-лист ниже).

### Причина 2: стрим воркер↔парсер рвётся через 5 минут тишины

Undici (HTTP-клиент Node) по умолчанию: `bodyTimeout=300с` (стрим без единого
байта) и `headersTimeout=300с` (ожидание ответа). «Пульс» в парсере был
написан с ошибкой — слал сигнал жизни только когда число ссылок *изменилось*,
т.е. молчал именно в застое. Итог: ровно через ~5:10 после последней порции —
`TypeError: terminated` (воспроизведено локально с undici Agent: та же ошибка,
cause «Body Timeout Error»).

Фиксы (этот коммит):
1. **Heartbeat на сервере** (`server.py`): `generate()` шлёт
   `{"heartbeat": true, "total": N}` каждые `YANDEXMAPS_STREAM_HEARTBEAT_SEC`
   (20с) независимо от состояния парсера. Проверено интеграционно: при 7с
   тишины и пульсе 2с приходят 3 heartbeat, done-строка и семафор целы.
2. **Пульс в парсере** (`yandex_parser.py`): условие «только если изменилось»
   убрано — шлёт каждые 10 итераций скролла всегда.
3. **Undici-таймауты в воркере** (`yandexMapsServiceClient.ts`): dispatcher
   `Agent({headersTimeout: 0, bodyTimeout: 0})` — верхняя граница остаётся за
   AbortController (990с). Это закрывает и латентный баг `/parse-orgs`:
   не-стримовый POST думает до 900с, а headersTimeout убил бы его на 300с
   (чанк из 15 карточек через медленный прокси легко превышает 5 минут).
4. **Ретрай на любую ошибку** (`yandexMapsWorker.ts`): раньше не-блокировочная
   ошибка (обрыв стрима, 500, умерший прокси) сразу скипала URL; теперь URL
   ретраится через следующий прокси из пула (пул+1 попыток), уже собранные
   порции не теряются (пишутся в БД инкрементально). Это переимплементация
   недеплоенного фикса 8c3f009f.

## Побочная находка: playwright-stealth 1.0.6 частично сломан

На каждой загрузке страницы init-скрипты stealth кидают
`ReferenceError: opts is not defined` / `utils is not defined` (проверено
локально через `page.on("pageerror")`). `page.evaluate` и скролл они **не
ломают** (ошибка из отчёта диагностики — это pageerror, а не сбой evaluate),
но часть анти-бот маскировки молча не применяется → выше шанс капчи.
Отдельная задача: заменить на поддерживаемый форк (`tf-playwright-stealth`)
или выпилить битые эвазии.

## План тестирования на проде (чек-лист закрытия бага)

1. **Деплой** этой ветки: пересобрать `yandexmaps`-контейнер и воркер
   (`portal-worker-yandexmaps`). Не забыть non-blocking миграцию 9c37f79c,
   если ещё не задеплоена. `YANDEXMAPS_COLLECT_MODE` не задавать — дефолт `api`.
2. **Главный фикс (API-сбор) закрыт, если:** запуск с 1 запросом («Москва
   Кафе», лимит 250) на текущих зарубежных прокси собирает **60–120+
   организаций** (а не 4–12). В `application_logs` — `[OK] API-сбор: N
   организаций`. Если 0 и `api_collect: не нашли sessionId…` — Яндекс
   поменял конфиг страницы, чинить `_extract_api_bootstrap`. Если 400/500 в
   `[!] api/search skip=…` — поменялась схема подписи, сверить с бандлом
   front-maps (модуль с `csrfToken:n||s.csrfToken`).
3. **Причина 2 (обрыв стрима) закрыта, если:** нет `TypeError: terminated` в
   логах воркера; задача доходит до `done`. (В api-режиме риск почти снят —
   API отвечает за секунды, длинной тишины нет; heartbeat остаётся страховкой.)
4. **Фолбэк-режим:** при `YANDEXMAPS_COLLECT_MODE=scroll` работает старый
   скролл — оставлен на случай, если появятся российские прокси (тогда
   полная российская выдача) или API-схема сломается.
5. **Бенчмарк:** сравнить `links/запрос` с историей в БД (14.04: 22 346 ссылок
   на 192 запроса ≈ 116/запрос). API-режим должен дать сопоставимо.
6. **Проверка данных карточек:** этап парсинга карточек не менялся — убедиться,
   что `yandex_maps_organizations` заполняется как раньше (карточки
   yandex.ru/maps/org/… грузятся через зарубежные прокси штатно).

## Возможное развитие (не в этом коммите)

API уже отдаёт ВСЕ поля организации (адрес, телефоны, сайт, соцсети, часы,
рейтинг, координаты) в JSON сбора — можно заполнять `yandex_maps_organizations`
прямо из ответа сбора и **вообще отказаться от этапа парсинга карточек**
(экономия сотен page.goto, минус риск капчи на карточках). Требует расширения
контракта стрима (отдавать org-объекты, не только ссылки) и правок воркера —
отдельная задача.

`/root/ym_diag.py`, `/root/ym_diag.out` на 139.60.162.12.
