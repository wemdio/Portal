# VE2: восстановление контактов и параллельная подготовка

## Исправленные причины потерь и повторной работы

В проверенной сборке были повторно выбраны 1 071 строки HH без сайта и ИНН.
Контроль исключений знал ИНН, сайт и email, но не факт обработки исходной строки.
Теперь у каждой обработанной строки есть отдельная квитанция внутри этой базы.
Она включает географию и источник; старые квитанции без этих полей сопоставляются
только с однозначным исходником. Это не идентификатор компании для других гипотез.

Конструктор, успешно завершивший проверку с одной строкой заголовков, возвращает
ноль готовых контактов. VE2 больше не подменяет этот результат сырыми кандидатами
и не сообщает ложный сбой email-валидации. Незавершённый или повреждённый результат
по-прежнему не допускает контакты к отправке.

Email, попавший в колонку сайта, сохраняется как адрес для обычной проверки.
Исходное значение остаётся в происхождении строки. Домен email не объявляется
официальным сайтом. Для отсутствующих сайтов добавлен поиск по ИНН либо названию
и географии: результат подтверждается собственными страницами найденного сайта.
Известный ИНН сохраняет строгую проверку юридического лица. Без ИНН нужны полное
название бренда в title/h1 и география из исходника на страницах сайта. Каталоги,
HH и соцсети не принимаются за официальный сайт. Совпадение названия не объединяет
разные города в общем checkpoint проверки.

Поиск идёт по восемь компаний за волну, максимум две волны до освобождения очереди.
Результаты каждой волны сохраняются; сбой соседнего запроса не стирает успешные.
Отсутствие сайта — сохранённый исход, а не бесконечный повтор. Предельное число
поисков одной сборки — 10 000. Сначала используются строки с доступными контактными
данными, затем восстанавливаются пропуски. Подтверждённый сайт проходит обычные
поиск email, SMTP-валидацию и проверку гипотезы, без обхода этих этапов.

При возобновлении старого сбора сначала проверяются сохранённые адреса с пригодным
email. Новый поиск начинается после этого. На сайте классификатор выбирает номера
точных фрагментов; независимая проверка получает исходные цитаты. Версия проверки
сайтов повышена только для повторного рассмотрения неопределённых результатов;
готовые решения не инвалидируются массово.

## Параллельность и ограничения

- VE2: по умолчанию 8 одновременно работающих проектов, настройка
  `VE_JOB_CONCURRENCY` допускает 1–16. Один процесс остаётся владельцем очереди.
- Внутри проекта одновременно работает один родительский обработчик: это
  сохраняет порядок итоговых записей, учёт расходов и исключение дублей.
  Ожидание дочерних парсеров и конструктора освобождает слот. Разные гипотезы
  больше не ждут полного завершения всех предыдущих баз проекта.
- Две подготовки одной гипотезы по-прежнему выполняются последовательно.
- Проверка сайтов: 8 вместо 4 одновременно. Независимая проверка релевантности:
  до 8 компаний за запрос, с прежним изолированным повтором повреждённого ответа.
- Compose: предел VE2-контейнера 8 ГБ / 4 CPU, Node heap 6 ГБ. Число обработчиков
  общего конструктора этим изменением не увеличивается.

Тест очереди прогоняет 375 задач для 15 проектов при 8 слотах, проверяя завершение
всех задач и отсутствие двух родительских записывающих обработчиков одного проекта.
Это не нагрузочный тест сайтов, SMTP и ИИ и не доказательство получения 187 500
контактов за ночь. Реальную производительность нужно измерять после выпуска по
времени партий, выходу готовых адресов, возрасту очереди и сбоям провайдеров.

## Выпуск и проверка на сервере

Миграций и изменений HE/ENG нет. Нужен штатный выпуск приложения, VE2 worker и
Compose. После него — явное продолжение сохранённой подготовки через штатный
API/UI; не создание ещё одной базы и не сброс всех checkpoints.

Проверить новую concurrency, обработку сохранённого резерва, рост готовой части
и отсутствие новых повторов тех же исходников. Старые суммарные счётчики могут
включать повторные проходы: они не переписываются в производственной БД этим
изменением и не являются количеством уникальных компаний.

Остановка по-прежнему использует существующий drain/checkpoint протокол. Откат
на старый worker после перехода сборки за прежние пять раундов требует отдельного
разбора совместимости: старая проверка ограничений не знает нового режима поиска.
Слепой откат и массовый сброс очереди не предусмотрены.
