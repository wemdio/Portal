# Vertical Engine v2 — сезонность РФ и портфельная очередь запусков

- **Дата:** 2026-08-28
- **Статус:** реализовано в коде ветки `Sergey`; миграции не применены, deployment не выполнен
- **Область:** только внутренний Vertical Engine v2 (`verticalEngineV2`, `ve_*`, `VE_MODEL_*`)

## Коротко

Vertical Engine v2 оценивает сезонность каждой RU-гипотезы по проверенным источникам ещё
на evidence-stage, переводит её в понятное состояние московского календаря и строит очередь
подготовленных запусков. Кампании можно готовить заранее без ограничения: они создаются в
Instantly как `PAUSED`. После QA специалист вручную активирует из Portal только первый
допустимый bundle; один template launch с любым числом сегментных кампаний занимает один слот.

Для одного Instantly workspace и пересекающихся mailbox-наборов базовая ёмкость равна одному
активному bundle. Portal не вытесняет текущую отправку. Слот освобождается автоматически только
после свежего подтверждения `Completed` у всех кампаний bundle либо вручную после свежей
проверки, обязательной причины и фиксации автора.

## Почему старого пункта #5 было недостаточно

Первая правка сезонности добавила текущую дату и пример «образование → сентябрь» в промпты
анализа базы и писем. Это помогало сформулировать сезонный повод в copy, но не отвечало на
операционный вопрос Ани:

- факт сезонности не подтверждался источником;
- позитивный пик не отличался от периода, когда ЛПР недоступны;
- вывод появлялся слишком поздно, после сбора базы;
- не было календарной даты начала outreach с учётом прогрева до пика;
- сезонность никак не меняла порядок запусков и расход мощности.

Поэтому prompt hint больше не является источником решения. Источник истины — сохранённая
verified-оценка гипотезы, а текстовый промпт может только использовать уже известный контекст.

## 1. Контракт verified seasonality

Оценка сохраняется на RU-гипотезе после evidence-stage:

```json
{
  "version": 1,
  "classification": "seasonal",
  "confidence": "high",
  "rationale": "Почему окна важны именно для outreach этой ниши в РФ",
  "windows": [
    {
      "kind": "peak",
      "label": "Пик набора",
      "start_mm_dd": "09-01",
      "end_mm_dd": "09-30",
      "lead_days": 45,
      "evidence": [
        {
          "claim": "Проверяемое утверждение именно о пике",
          "source_url": "https://example.org/peak-source",
          "quote": "Точная цитата из загруженного источника"
        }
      ]
    },
    {
      "kind": "avoid",
      "label": "ЛПР в отпусках",
      "start_mm_dd": "07-01",
      "end_mm_dd": "07-14",
      "evidence": [
        {
          "claim": "Проверяемое утверждение именно о недоступности ЛПР",
          "source_url": "https://example.org/avoid-source",
          "quote": "Точная цитата о негативном окне"
        }
      ]
    }
  ],
  "evidence": [
    {
      "claim": "Каноническое объединение evidence сохранённых окон",
      "source_url": "https://example.org/peak-source",
      "quote": "Точная цитата из загруженного источника"
    }
  ]
}
```

### Классификация

- `seasonal` — есть проверенные годовые окна, влияющие на момент outreach.
- `neutral` — проверенные данные не показывают значимого сезонного ограничения; это тоже
  доказанный вывод, а не дефолт.
- `unknown` — данных недостаточно, источник/цитата не прошли проверку либо структура ответа
  некорректна. Никакой отраслевой догадки вместо данных не делается.

`confidence` принимает `low | medium | high`, но не заменяет evidence. Для полезного
`neutral` нужен хотя бы один URL и точная цитата, найденная в фактически загруженном
источнике. Для `seasonal` **каждое** `peak/avoid`-окно обязано иметь собственный evidence,
который доказывает именно его: цитата про пик не подтверждает отпуск ЛПР. Неподтверждённые
окна отбрасываются независимо; mixed-ответ сохраняет только доказанную часть. Если окон не
осталось, в persisted state пишется `unknown`. Top-level `evidence` — каноническое объединение
evidence выживших окон, а не разрешение распространить одну цитату на весь календарь.

### Что проверяет исследование рынка РФ

Evidence-stage ищет факты именно для конкретной ниши и российского рынка, а не применяет
словарь «образование всегда сентябрь». В оценке нужно различать как минимум:

- сезон конечного спроса и более раннее окно, когда надо начинать B2B outreach;
- доступность ЛПР и бюджетные/закупочные циклы;
- позитивные пики и негативные периоды отпусков, праздников или остановки принятия решений;
- федеральную закономерность и региональную особенность;
- устойчивый ежегодный паттерн и разовый инфоповод.

Для каждой гипотезы идут три отдельные поисковые линии: demand peak, negative availability
ЛПР и procurement/budget lead time. Round-robin и отдельная квота не позволяют первой богатой
выдаче вытеснить остальные сигналы; при наличии результатов загружается до двух страниц на
каждую линию (до шести seasonal sources плюс не более двух общерыночных). Discovery-дедуп
изолирован по линии, поэтому поздно замеченный market URL не «съедает» сезонную квоту;
фактическая загрузка затем дедуплицируется глобально по URL.

Если источник поддерживает только часть вывода, сохраняется только подтверждённая часть.

## 2. Московский календарь

Все RU-решения вычисляются по бизнес-дате `Europe/Moscow`, независимо от timezone хоста.
Годовые окна задаются как `MM-DD`; поддерживаются окна через границу года.

Date-derived state не замораживается в момент подготовки. Перед каждым чтением RU-очереди и
перед activation reservation Portal полностью и пагинированно читает допустимые RU bundle,
пересчитывает state по текущей московской дате из immutable seasonality snapshot, повторно
проверяет его SHA-256 и применяет изменения одной service-only транзакцией. `plan_version`
повышается один раз только если timing действительно изменился.

Для `peak` поле `lead_days` означает:

```text
дата начала outreach = дата начала peak − lead_days
```

Это принципиально: ждать начала спроса часто уже поздно. Например, для `peak=09-01..09-30`
и `lead_days=45` начало outreach — 18 июля.

### Производные состояния

| Состояние | Смысл |
|---|---|
| `launch_now` | Настало окно начала outreach или сам peak ещё идёт |
| `prepare_now` | 14-дневный буфер перед датой начала outreach; готовим PAUSED bundle |
| `neutral` | Проверенного сезонного ограничения нет |
| `unknown` | Проверенных данных недостаточно |
| `wait` | Сезонный запуск ещё рано активировать |
| `avoid` | Идёт проверенное отрицательное окно |

Для примера выше `prepare_now` длится 4–17 июля, `launch_now` — 18 июля–30 сентября,
а до 4 июля действует `wait`. При пересечении `peak` и `avoid` побеждает `avoid`:
неоднозначность закрывается в безопасную сторону.

`launch_now` и `neutral` делают bundle допустимым кандидатом для **ручной** активации.
Они не запускают кампанию в фоне. `prepare_now`, `wait`, `unknown` и `avoid` блокируют
обычную активацию; осознанный ручной override требует автора, причины и явного решения.

## 3. Единица планирования: launch bundle

Один template launch после аудита сегментации может создать основную и несколько сегментных
кампаний. Для бизнеса это один запуск, поэтому все такие кампании сохраняются как один bundle:

```text
launch bundle
├── project / vertical / hypothesis / base / template
├── segmentation audit snapshot
├── Instantly workspace + immutable mailbox set
├── seasonality + priority snapshot
└── 1..N child campaigns
```

Правила:

- N child campaigns потребляют ровно один слот вместе;
- scope workspace/mailbox фиксируется при подготовке и не меняется во время активации;
- успешная подготовка, terminal audit, bundle и все child campaign ID фиксируются одной
  DB-транзакцией;
- оборванная или неоднозначная подготовка не создаёт активируемый queue item;
- старые launch-записи читаются обратно совместимо, но не получают выдуманный scope.

## 4. Подготовка и ёмкость

Подготовка отделена от отправки:

```text
research/evidence → base/template/segmentation QA → PAUSED campaigns + queued bundle
                                                     ↓ ручная активация
                                      activating → active/uncertain → released
```

Количество PAUSED/queued bundle не ограничено. Слот держат только состояния:

- `activating`;
- `active`;
- `uncertain`.

`uncertain` удерживает мощность, потому что внешний API мог успеть активировать часть кампаний
до timeout или ошибки ответа. Автоматически считать такой запуск неактивным опасно.

### Область конфликта

Capacity применяется не глобально ко всему Portal, а к реальной отправочной мощности.
Два bundle конфликтуют, только если одновременно:

1. используют один Instantly workspace;
2. их immutable mailbox-наборы пересекаются.

Для RU-портфеля базовый лимит — `max_active_bundles=1` в такой области конфликта.
Наборы `{a,b}` и `{b,c}` конфликтуют; `{a}` и `{c}` — нет. Другой workspace также независим.

Preemption отсутствует: более срочный новый сегмент не останавливает уже активный. Он становится
первым ожидающим и получит возможность запуска после освобождения слота.

## 5. Объяснимая очередь

Порядок кандидатов стабилен и проверяем:

1. подтверждённый ручной порядок/pin;
2. ближайший сезонный дедлайн и наименьший запас времени;
3. более высокая confidence сезонного вывода;
4. более высокий `potential_pct`;
5. более раннее время постановки в очередь (защита от вечного голодания);
6. стабильный ID как последний tie-breaker.

Для positive peak его конец считается inclusive. Производный сезонный deadline — следующий
календарный день, а latest activation вычисляется как `deadline − ceil(estimated_run_days)`.
Иными словами, выше стоит не просто ближайший peak, а bundle с наименьшим реальным запасом,
чтобы успеть открутиться внутри полезного окна.

`estimated_run_days` считается консервативно по сумме лидов всех child campaigns bundle:
они делят один immutable mailbox pool. Использовать максимум одного сегмента означало бы
занизить длительность и слишком поздно поднять сезонный запуск в очереди.

Сезонность и потенциал не складываются в один «магический» процент. Специалист видит, почему
элемент выше: ручное решение, календарное окно, качество evidence, потенциал и возраст остаются
раздельными полями.

Ручной override может задать порядок, `not_before` и решение `activate_next | wait`, но:

- требует непустую причину, actor и timestamp;
- увеличивает plan version, чтобы устаревшая вкладка не активировала старый план;
- не освобождает занятый слот;
- не вытесняет активный bundle;
- не скрывает исходную seasonality/evidence.

Явный `wait` имеет приоритет даже над автоматически допустимым `launch_now/neutral`: такой
bundle исключён и из candidate gate, и из authoritative head до нового audited решения.

## 6. Ручная активация из Portal

Активация разрешена только после QA и явного подтверждения специалиста. Это fenced saga,
потому что DB-транзакция не может быть общей с внешним Instantly API:

1. UI до QA-confirm показывает полный список child campaigns, их сегменты, lead count и ссылки.
2. Portal заново получает точный paginated campaign set и проверяет live campaign ID,
   Instantly workspace и точное равенство immutable mailbox snapshot.
3. Portal атомарно резервирует bundle/слот с idempotency key.
4. В той же DB-границе проверяются plan version, актуальный head очереди, timing gate,
   пересечение mailbox-наборов и capacity.
5. Только после успешной reservation Portal активирует каждую child campaign.
6. Если все вызовы подтверждены, bundle становится `active`.
7. Частичный результат, timeout или неясный внешний ответ переводит bundle в `uncertain` и
   сохраняет слот до reconciliation.

Сохранённый capacity snapshot в UI не является причиной навсегда отключать кнопку: после QA
специалист может запустить authoritative preflight. Portal сначала сверит живые статусы
пересекающихся holder-кампаний, автоматически освободит только действительно Completed bundle
и лишь затем попытается резервировать следующий слот.

Повтор с тем же idempotency key не создаёт вторую активацию. Конкурентные запросы на
пересекающиеся mailbox-наборы сериализуются advisory locks и CAS-переходами. Проверка более
приоритетного ожидающего bundle выполняется внутри той же серверной reservation, а не только UI.

## 7. Reconciliation и освобождение слота

Portal сверяет каждый известный child campaign с живым статусом Instantly и сохраняет время
наблюдения. Observation set должен в точности совпадать со всем tracked child set: subset или
duplicate отклоняется. Bundle становится `active` только если **каждый** child свежо подтверждён
как `Active/RunningSubsequences/Completed`; смешанный active+paused/error остаётся `uncertain`.

Автоосвобождение разрешено только если:

- у bundle есть child campaigns;
- для каждой есть свежий live status;
- **каждая** кампания имеет статус `Completed`.

Fresh exact `Paused`/unhealthy set не доказывает completion и поэтому не освобождается
автоматически. Missing, stale, unknown или sending status вообще не дают release-proof. Это
fail-closed правило защищает от незаметного двойного расходования mailbox capacity.

Свежий exact all-`Completed` set автоматически ставит `released`, включая recovery; это не
manual release, поэтому manual actor не нужен. Иной fresh exact non-sending set позволяет
аварийное ручное освобождение только для `active | uncertain`. Оно запрещено в `activating`;
для свежего `uncertain` действует 10-минутный settling fence. Нужны новая live-проверка всех
child campaigns, точное совпадение campaign ID/mailbox snapshot, отсутствие отправки и
обязательные reason/actor. Решение и время сохраняются в queue item.

Освободить capacity не означает разрешить удалить ledger: `released` остаётся reconcile-able и
при внешней реактивации возвращается в `active | uncertain`. Source cascade разрешён только для
childless `released | skipped | cancelled`. Любой `prepared | queued | activating | active |
uncertain` запрещено удалять даже без children, а любой tracked child блокирует delete при любом
Portal status, включая cached `Completed`. Удаление потребует будущего отдельного fenced
remote-delete workflow.

### Прямая активация в Instantly

Пока права в Instantly позволяют ручной клик, это остаётся операционным bypass Portal.
Для уже отслеживаемых campaign ID reconciliation (включая вручную `released` ledger) замечает
фактический `Active`/`RunningSubsequences`, переводит bundle в удерживающее слот состояние и
не даёт Portal активировать конфликтующий следующий bundle. Но Portal не может физически
запретить внешний клик или гарантированно увидеть созданную вне него неизвестную кампанию;
для жёсткой гарантии нужна отдельная настройка прав Instantly.

## 8. Хранение и изоляция

Миграция `20260828_0002_vertical_engine_v2_ru_seasonality.sql` добавляет verified assessment
в `ve_hypotheses`.

Миграция `20260828_0003_vertical_engine_v2_launch_portfolio.sql` добавляет:

- `ve_launch_portfolio_settings`;
- `ve_launch_queue_items`;
- `ve_launch_queue_campaigns`;
- service-only транзакционные операции reservation/finalize/reconcile/manual release/override.

RLS включён; browser-клиент не получает прямой mutation-доступ. Все изменения находятся в
пространстве v2. Новые прогоны не пишут в `he_*`, код не импортирует бизнес-стадии
`hypothesisEngine`, настройки `HE_MODEL_*` и ENG `/client/eng` не меняются.

## 9. Проверки и release boundary

Контракт закрепляют отдельные тесты:

- seasonality schema, Moscow calendar, cross-year, peak/avoid/lead-time и fail-to-unknown;
- evidence-stage search, проверка URL+цитаты и persistence;
- one bundle/N campaigns, mailbox overlap, no-preemption, ranking и release rules;
- RLS/RPC/CAS/idempotency в обеих миграциях;
- queue, manual override/release и activation API;
- UI статусов сезонности и launch portfolio.

Итоговая проверка: **37 suites / 316 tests passed** для всего Vertical Engine v2; целевой
seasonality/portfolio-набор — **13 suites / 162 tests passed**; strict TypeScript — green.

Обе миграции `0002`/`0003` сейчас существуют только в коде ветки `Sergey`. Они не применены
к базе, приложение и воркер не развёрнуты. Push в `Sergey` — стоп-точка этой работы; migration,
merge и deployment требуют отдельного явного подтверждения.
