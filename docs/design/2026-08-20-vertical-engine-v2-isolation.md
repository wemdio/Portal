# Изоляция внутреннего Движка вертикалей v2 от ENG-портала

**Статус:** фундамент v2 реализован в ветке `vertical-engine-v2`, не задеплоен  
**Дата:** 20.08.2026  
**Область:** `/tools/hypothesis-engine`, `/client/eng`, `app/src/lib/hypothesisEngine`, воркеры и таблицы `he_*`

## Коротко

Текущий Hypothesis Engine нельзя свободно переделывать под внутренний инструмент: это production-backend ENG-портала. Внутренний Движок вертикалей v2 строится рядом как отдельный продукт со своими API, очередью, воркером, таблицами и модельными настройками.

### Реализованный фундамент

Первая фаза добавляет скрытый `/tools/vertical-engine-v2`, таблицы `ve_projects` и `ve_legacy_project_links`, отдельный internal API и SELECT-only архив проверенных legacy-проектов. Новый pipeline, `ve_jobs`, воркер, модели и переключение основного URL намеренно ещё не реализованы. До применения миграции и отдельного деплоя production не меняется.

После перехода специалистов на v2:

- обычный интерфейс показывает только новый внутренний движок;
- старый внутренний интерфейс исчезает из навигации и остаётся только как закрытая read-only диагностика;
- ENG-портал продолжает работать на существующем Hypothesis Engine;
- история старых внутренних прогонов показывается в новом интерфейсе в разделе «Архив», но не становится частью нового runtime.

## Почему это необходимо

Сейчас внутренний инструмент и ENG-портал выглядят как разные продукты, но используют одно ядро:

```text
/tools/hypothesis-engine ─┐
                          ├─ app/src/lib/hypothesisEngine
/client/eng ──────────────┘            │
                                      ├─ worker/hypothesisEngine.ts
                                      ├─ he_jobs
                                      └─ остальные таблицы he_*
```

У них отдельные UI и API-роуты, но общие стадии research, chain, collect, template, общий воркер, общая модельная конфигурация `HE_MODEL_*` и общая схема данных. Изменение стадии, промпта, модели, статуса джобы или таблицы может изменить либо сломать оба продукта.

Разные git-ветки защищают разработчиков от перезаписи файлов, но не защищают продукты после слияния изменений.

## Принятое решение

### 1. Существующий Hypothesis Engine закрепляется за ENG

Существующие компоненты остаются совместимым backend ENG-портала:

- `app/src/lib/hypothesisEngine/**`;
- `app/worker/hypothesisEngine.ts`;
- `/api/client/eng/**`;
- таблицы `he_*`;
- `HE_MODEL_*`;
- `worker-hypothesis-engine`.

Внутренний v2 не должен менять этот код ради собственного функционала. Изменения существующего Hypothesis Engine допустимы только как осознанные изменения ENG-продукта с проверкой ENG-сценариев.

Текущий внутренний `/tools/hypothesis-engine` считается legacy-клиентом этого backend до момента перехода на v2.

### 2. Внутренний Движок вертикалей v2 создаётся отдельно

Целевые границы нового продукта:

```text
Код:       app/src/lib/verticalEngineV2/**
API:       /api/tools/vertical-engine-v2/**
Очередь:   ve_jobs
Данные:    ve_projects, ve_verticals и остальные ve_*
Воркер:    worker-vertical-engine-v2
Модели:    VE_MODEL_RESEARCH, VE_MODEL_CHAIN, VE_MODEL_BULK, VE_MODEL_GATE
UI:        новый интерфейс специалистов
```

Пользовательский URL можно сохранить как `/tools/hypothesis-engine`: после переключения он должен открывать v2. Техническое имя v2 не обязано быть видно специалисту.

### 3. Направление зависимостей запрещает обратное сцепление

```text
ENG UI  → ENG API  → текущий Hypothesis Engine
Internal UI → Internal API → Vertical Engine v2

Оба продукта → только стабильные нейтральные библиотеки
```

Запрещено:

- импортировать бизнес-стадии `hypothesisEngine` в v2;
- импортировать v2 из ENG API, ENG UI или текущего воркера;
- писать новые внутренние прогоны в `he_*`;
- использовать `HE_MODEL_*` для настройки v2;
- добавлять в `he_jobs` новые стадии только ради внутреннего v2.

Разрешено разделять низкоуровневые pure-утилиты: безопасный fetch, клиент LLM, CSV, адаптер Instantly, валидацию URL. Такая библиотека должна иметь узкий стабильный контракт и тесты обоих потребителей; продуктовые промпты, статусы и orchestration общими не являются.

## Что делать со старым UI

Скрывать его прямо сейчас нельзя: пока v2 не готов, специалисты потеряют рабочий инструмент.

Порядок перехода:

1. Старый внутренний UI работает как сейчас, но не получает новый функционал v2.
2. v2 строится рядом и проходит приёмочные проверки.
3. Новый UI получает раздел «Архив старого движка».
4. `/tools/hypothesis-engine` переключается на v2.
5. Ссылка на legacy-интерфейс удаляется из обычной навигации.
6. Legacy-интерфейс остаётся только для администраторов в read-only режиме на время диагностики и сверки истории.

Backend и данные legacy-интерфейса не удаляются, потому что ими продолжает пользоваться ENG.

## История прогонов специалистов

Историю нельзя терять, но не нужно сразу физически копировать все `he_*` в `ve_*`.

Рекомендуемый вариант:

- новый UI показывает вкладку «Архив»;
- архив читает legacy `he_*` через отдельный read-only adapter;
- архивные записи маркируются как `legacy` и не редактируются;
- новые прогоны создаются только в `ve_*`;
- из архива можно открыть результат, скопировать входные данные или создать новый v2-прогон, но нельзя продолжить старую legacy-джобу.

Это сохраняет единый пользовательский интерфейс без двойной записи и рискованной миграции сложного графа `he_projects → hypotheses → verticals → bases → templates`.

### Как отделить внутреннюю историю от ENG

У старых строк `he_projects` нет надёжного продуктового признака: `market` и `autopilot` описывают поведение, а не происхождение проекта. Нельзя постоянно угадывать принадлежность по этим полям.

Перед включением архива нужен один проверенный реестр соответствий в пространстве v2, например:

```text
ve_legacy_project_links
  legacy_he_project_id
  legacy_kind = internal
  verified_at
  verified_by
```

Реестр заполняется одноразовым backfill с ручной проверкой спорных проектов. ENG-проекты в него не попадают. Это не требует менять production-семантику `he_projects`.

## Изоляция выполнения

Отдельного TypeScript-модуля недостаточно. Для независимого runtime нужны:

- отдельная очередь и claim-фильтр;
- отдельный процесс воркера;
- отдельные переменные моделей и API-бюджеты;
- отдельный heartbeat и healthcheck;
- отдельные лимиты CPU/RAM/pids;
- отсутствие каскадного изменения статусов между `he_*` и `ve_*`.

На первом этапе оба воркера могут собираться из одного Docker image. Это изолирует поведение, но не сборку и релиз. Если понадобится возможность выпускать продукты независимо, `worker-vertical-engine-v2` должен получить отдельный image/deploy pipeline.

Любая будущая правка compose требует `docker compose ... up -d --force-recreate --no-deps <service>` согласно корневому `CLAUDE.md`.

## Границы работы двух разработчиков

До завершения разделения:

- внутренний разработчик работает над новым v2 и внутренним UI;
- ENG-разработчик работает над `/client/eng`, `/api/client/eng` и существующим Hypothesis Engine;
- изменения `app/src/lib/hypothesisEngine`, `app/worker/hypothesisEngine.ts`, `he_*` и `HE_MODEL_*` считаются ENG-изменениями и требуют согласования;
- общие инфраструктурные утилиты меняются только с тестами обоих продуктов.

Отдельные ветки/worktree обязательны, но не заменяют эту архитектурную границу.

## Условия переключения специалистов на v2

Legacy UI скрывается только когда выполнены все условия:

- v2 создаёт проект и завершает свой основной пайплайн;
- новые прогоны не создают строк в `he_*`;
- worker v2 не claim'ит `he_jobs`, а ENG worker не claim'ит `ve_jobs`;
- модели v2 меняются независимо от `HE_MODEL_*`;
- в новом UI виден read-only архив проверенных внутренних legacy-проектов;
- есть тест, запрещающий импорты бизнес-модулей между ENG engine и v2;
- проходят отдельные smoke-тесты внутреннего v2 и `/client/eng`;
- возврат legacy-ссылки через feature flag проверен как rollback.

## Итоговая пользовательская картина

Специалист видит один «Движок вертикалей»: новый v2 плюс историю старых прогонов в архиве. Он не видит две конкурирующие версии и не может случайно создать новый прогон в ENG-backend.

ENG-клиент продолжает видеть свой Outreach-процесс и не зависит от того, насколько радикально меняются сущности, этапы, модели и интерфейс внутреннего v2.
