# Добор контактов OutreachOS из 2GIS (top-up)

Дата: 2026-08-11. Статус: **реализовано** (код+тесты в ветке Sergey, миграция
20260811_0001; прод-миграция и включение флага — после подтверждения владельца).
Отличие от первоначального дизайна: отдельная кампания C НЕ заводится — GIS-лиды
льются в общие кампании A/B (см. §7.2).

## 1. Контекст и цель

Дневной пайплайн OutreachOS (HH + SuperJob) вышел на steady state ~140 залитых
контактов в сутки. Это не лимит заливки (капа нет, `daily_limit=8000` не кусается),
а естественная ёмкость воронки: seen-окно 45 дней срезает ~92% кандидатов
(10.08: 4358 после ICP → 333 новых → 155 валидных → 144 залито). SuperJob как
второй источник даёт всего +4% к парсу (179 компаний к 4480 HH после дедупа
по домену) — выдача SJ сильно пересекается с HH.

Цель: **добирать контакты из 2GIS-датасета в те дни, когда HH+SJ не достаёт
до целевого объёма** (top-up), с качественным отбором по B2B-рубрикам и с
полным набором существующих фильтров качества.

Вне скоупа: «база баз» (реестровая база `companies_directory`, импорт СБИС v4) —
отдельный источник, здесь не рассматривается. Яндекс Карты — отдельный резерв
(~1M организаций), также вне v1.

## 3. Архитектура: фаза 2 внутри OutreachOS (top-up)

Реализуем **внутри `runOutreachOsDailyPipeline`** (app/src/lib/outreachos/pipelineRunner.ts),
а не отдельным пайплайном: режим «добирать только когда не хватает» — это по
определению ветка основного прогона. Отдельный always-on сегмент в
gisSignalOutreach (вариант «б») остаётся запасным путём, если топ-ап покажет
плохую экономику.

### 3.1. Конфиг (`outreachos_pipeline_config`, миграция)

| Поле | Тип | Дефолт | Смысл |
|---|---|---|---|
| `gis_topup_enabled` | bool | false | мастер-выключатель |
| `gis_topup_target_appended` | int | 200 | цель: суммарно залито A+B за прогон |
| `gis_topup_rubric_groups` | jsonb | см. §6 | рубрикатор, формат как у `gis_signal_segments.rubric_groups` |
| `gis_topup_daily_cap` | int | 500 | потолок кандидатов 2GIS за прогон (защита конструктора и бюджета валидации) |
| `gis_topup_measure_only` | bool | true при вводе | замер воронки добора без заливки и без seen |

### 3.2. Поток (вставка между шагом 7b и шагом 8 текущего runner)

```
HH+SJ → ICP/B2C/suppression → seen-дедуп → конструктор → LLM → keptLeads
                                                        │
        deficit = gis_topup_target_appended − (appended-прогноз по keptLeads)
        если gis_topup_enabled и deficit > 0:           ▼
   8t.1 pull 2GIS: latest snapshot, rubric_groups, hasWebsite=true,
        лимит = min(cap, ceil(deficit / 0.45 * 1.3))   // 0.45 = историч. yield конструктора
   8t.2 дедупы (§4) → структурный B2C-отсев (isOutreachOsB2cCompany) →
        suppression (isSuppressedCompany, fail-closed как у HH)
   8t.3 второй base_constructor_job (те же selected_steps/step_config),
        ждём тем же циклом опроса
   8t.4 gridToLeadPayloads → LLM-фильтр «наш ли покупатель» (тот же вызов,
        контекст: название+домен+рубрики 2GIS вместо HH-индустрий/вакансии)
   8t.5 объединить с keptLeads → общий markSeen (§4.3) → общий дедуп против
        своих кампаний → общий A/B-сплит → append
```

- Точка принятия решения — ПОСЛЕ LLM, а не до конструктора: дефицит считается
  точно, а не прогнозно. Цена — второй конструктор-джоб в «худые» дни
  (+~15–25 мин к прогону). В «сытые» дни топ-ап не запускается вовсе.
- Прогноз appended по keptLeads: keptLeads ≈ то, что реально уйдёт в Instantly
  (skipped~0 исторически) — используем keptLeads.length напрямую.
- `gis_topup_measure_only=true`: фазы 8t.1–8t.4 выполняются, счётчики пишутся
  в run, заливки и seen нет. Первые 2–3 прогона — только замер.

### 3.3. Телеметрия

Новые колонки в `outreachos_pipeline_runs` (миграция): `gis_pulled`,
`gis_after_dedup`, `gis_valid_contacts`, `gis_llm_kept`, `gis_appended`.
В audit-лог `outreachos.run.completed` — те же поля. На дашборд воронки —
отдельная строка «2GIS top-up».

## 4. Дедупы (ключевой раздел)

Общий ключ между мирами — **домен сайта** (deriveDomain). У 2GIS-карточки нет
hh_employer_id; у HH-работодателя нет twogis_id.

### 4.1. Что отсекаем на 8t.2 (новое)

1. Домены из `outreachos_seen_employers` за 45 дней — loader уже есть
   (`loadRecentlySeen`), возвращает `domains` — используем как есть.
2. **Домены из `gis_signal_seen_companies` (любые, не только свежие)** — НОВЫЙ
   loader. Иначе компания, которой edu/remont-пайплайн уже писал, получит второе
   письмо от OutreachOS. Это главный новый кросс-пайплайнный рубеж.
3. Домены сегодняшнего HH+SJ-батча (как сейчас SJ дедупается против HH по
   домену) — передаём `hhDomains` из шага 3a.
4. Suppression (клиенты AMO) — общий механизм, fail-closed.

### 4.2. Обратная сторона (отдельная задача, тоже нужна)

`gisSignalOutreach` сегодня не знает про `outreachos_seen_employers`: после
запуска топ-апа GIS-пайплайн сможет написать компании, которой OutreachOS
писал неделю назад. В `pullSegmentCandidates` добавить отсев по доменам
`outreachos_seen_employers` (45д). Маленькая правка, но обязательная —
без неё запускать топ-ап нельзя.

### 4.3. markSeen для GIS-компаний

Пишем контакт в ОБА журнала (минимальные изменения схем):
- `outreachos_seen_employers`: `hh_employer_id = NULL`, `domain` — требуется
  проверить nullable/индекс по domain (миграция при необходимости);
- `gis_signal_seen_companies`: `twogis_id`, `domain` — чтобы edu/remont-пайплайн
  тоже видел контакт.
Порядок не меняется: seen ДО append (шаг 8 текущего runner), at-least-once
семантика сохраняется. Статус для no-email/llm_noise — как у HH-ветки.

## 5. Качество

Рубежи те же, что у HH-потока, плюс специфика источника:

- Структурный B2C/ИП-отсев (`excludeB2c`) — без изменений.
- Suppression клиентов — без изменений (fail-closed).
- LLM «наш ли покупатель»: контекст 2GIS = название + домен + **рубрики
  карточки** (аналог HH-индустрий; описания компании в 2GIS нет — как и для
  HH-строк без описания, классифицируем по названию+домену+рубрикам).
- 6-сигнальную квалификацию сайта из gisSignalOutreach в v1 **не** вводим
  (это 15–20 мин на 500 сайтов и отдельный архив); кандидат на v2, если
  шум LLM по GIS-потоку окажется заметно выше HH-шного (~6–7%).
- Кап catch-all ≤20% — действует в `gridToLeadPayloads`, без изменений.

Отличие источника честно фиксируем: HH/SJ = сигнал «нанимает/растёт»,
2GIS = только «существует». Отклик ожидаем ниже; меряем по меткам в кампаниях
(§7, открытый вопрос про атрибуцию).

## 6. Рубрикатор v1 (стартовый набор)

Формат `gis_topup_rubric_groups` = формат `gis_signal_segments.rubric_groups`
(`category` + `includedSubcategories`). Старт — узкий, расширяем по замерам:

| Категория | Подход | Оценка карточек |
|---|---|---|
| Транспорт / Грузоперевозки | категория целиком, минус такси/пассажирские через excludedSubcategories | ~150–170k |
| Юридические / фин / бизнес-услуги | includedSubcategories: юр.услуги, бухгалтерия, аудит, консалтинг, регистрация, оценка, налоговое консультирование (исключить «помощь в банкротстве физлиц» и проч. B2C) | ~80–120k |
| Строительство / Недвижимость / Ремонт | includedSubcategories: генподряд, СМР, проектирование, инженерные системы, электромонтаж, кровля, фасады; исключить риелторов/ипотеку | ~80–100k |
| Строительные / отделочные материалы | категория целиком (опт/производство преобладает), исключить гипермаркеты | ~100k |
| Оборудование / Инструмент | категория целиком | ~90k |
| Металлы / Топливо / Химия | категория целиком | ~52k |
| Интернет / Связь / ИТ | только B2B-субрубрики (список из §2) | ~55–60k |
| Охрана / Безопасность | категория целиком (ЧОП, охранные системы) | ~20k |

Итого пул v1: **грубо 600–700k карточек** до has-website. Доля карточек с
сайтом неизвестна (полный count по 4,3M строк за 120 с не выполняется —
уточнить первым measure-прогоном); при доле 30–40% это 180–280k кандидатов.
Потребление: добор 60–150/день × выход из seen-окна — **пула хватает на годы**.

## 7. Открытые вопросы (решить до кода)

Статус на реализацию (2026-08-11, ветка Sergey):

1. **Цель `gis_topup_target_appended`**: 200? 250? (Сейчас HH+SJ даёт ~140.)
   → **Закрыт кодом**: стартовый дефолт 200 (миграция), меняется UPDATE'ом
   конфига без деплоя; финальное значение — по результатам live-наблюдения (§8.8).
2. **Атрибуция отклика**: лить GIS-лидов в те же кампании A/B (единый оффер,
   атрибуция по custom-переменной лида, если `appendLeadsToClientCampaign`
   её пробрасывает) или завести отдельную кампанию C «OutreachOS-GIS»
   (чистая статистика отклика, но третья кампания в ротации). Рекомендация:
   отдельная кампания C на первые 2–3 недели — решение об объёме потом будет
   опираться на честные цифры отклика; дедуп против своих кампаний уже
   умеет список.
   → **РЕШЕНО иначе (решение владельца при постановке)**: отдельная кампания C
   НЕ заводится. GIS-лиды льются в те же кампании A/B через существующий
   детерминированный сплит по домену компании (шаг 9 pipelineRunner) — все
   почты одной GIS-компании попадают в одну кампанию, сплит стабилен между
   прогонами. Атрибуция источника — по колонкам `gis_*` в
   `outreachos_pipeline_runs` (воронка) и по доменам лидов в кампаниях при
   необходимости разового анализа.
3. **Окно ре-контакта для GIS-компаний**: 45 дней как OutreachOS
   (рекомендация — единое окно) или 30 как в GIS-пайплайне.
   → **Закрыто кодом**: единое окно 45 дней (`RECONTACT_AFTER_DAYS`).
   GIS-компании пишутся в `outreachos_seen_employers` (hh_employer_id=NULL) и
   попадают под то же окно; обратный кросс-дедуп (§4.2) использует то же окно.
4. **Снапшот 2GIS**: сейчас 2026-07-26. График обновления снапшотов? Устаревание
   влияет только на «свежесть» пула, не на корректность.
   → **Остаётся открытым** (эксплуатационный вопрос, кодом не закрывается:
   топ-ап берёт latest snapshot каждый прогон через getLatestTwoGisSnapshotId).
