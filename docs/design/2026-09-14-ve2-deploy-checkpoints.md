# VE2: остановка перед редеплоем и сохранённые письма

## Остановка обработчиков

`scheduled-deploy.yml` пропускает выпуск, если `main` совпадает с
`last_deploy_sha`. При выпуске изменённых обработчиков скрипт вызывает
`drain-worker.sh`, а затем удаляет выбранные контейнеры через `docker rm -f`.
Поэтому одного `stop_grace_period: 5m` в Compose недостаточно.

Перед остановкой дочерних обработчиков drain явно останавливает VE2 через
`docker compose stop worker-vertical-engine-v2`. Это действует только при
выборе VE2 или полном drain. Ошибка команды останавливает скрипт до удаления
контейнеров. Очередь `ve_jobs` не переводится массово в pending при живом VE2.

После SIGTERM/SIGINT обработчик не берёт новые jobs, подготовки или следующие
проекты дозагрузки. Текущая операция сбора может сохранить результат; затем
`onCheckpoint` прерывает стадию. Её running job, дочерний task ID и checkpoints
остаются для существующего startup recovery. Остановка не увеличивает attempts
и не записывается как ошибка базы. Уже начатая дозагрузка завершает свой журнал.

Для нересёрчевых стадий ожидание точки сохранения ограничено четырьмя минутами,
затем срабатывает AbortSignal. Пять минут Compose остаются внешним пределом.
Research сохраняет прежнюю немедленную отмену и watchdog. Зависшая операция,
авария БД и SIGKILL всё ещё могут оставить неоднозначный результат внешнего
запроса; это не гарантия exactly-once. Новых повторов таких запросов не добавлено.

Резервирование semantic review/citation repair перед платным HTTP сохраняется
с `canYield: false`: штатная остановка не должна прерывать работу между записью
`started` и отправкой запроса. Следующая точка после сохранения результата уже
разрешает остановку. Отмена пользователя и общий deadline сохраняют приоритет.

## Письма и ошибки подготовки базы

Страница писем ищет текущую готовую цепочку по ID подготовки и базы. Если её
нет, показывает последнюю готовую непустую цепочку **той же гипотезы** из
истории обычных баз. Supply-базы исключены. Предыдущая версия доступна только
для просмотра: это не перепривязка к новой базе, одобрение или разрешение запуска.
Текущие письма сохраняют редактирование A/B и тем.

Ошибка failed-базы показывается на шаге «Базы и объём» вместе с продолжением
подготовки. На шаге писем объясняется зависимость от базы; настоящие ошибки
генерации писем остаются ошибками.

Основание: чтение VBI показало сохранённые четыре письма для «Сетей частных
клиник», тогда как сохранённая ошибка Serper относилась к базе «Эстетическая
медицина». Нельзя переносить письмо между ними по совпадению проекта/вертикали.

## Проверка и выпуск

Существующие сценарии проверяют остановку после создания дочерней задачи и
после relevance checkpoint, восстановление без повторной классификации,
завершение зарезервированного semantic review без повторной оплаты,
прекращение обхода проектов дозагрузки и порядок drain на заглушках Docker.
Проверки писем покрывают точное соответствие гипотезе и отделение ошибок базы.

Изменений схемы БД, ENG и `he_*` нет. Для применения нужен штатный выпуск
приложения и VE2 worker с новым drain-скриптом. Реальная остановка production
в рамках этой задачи не выполнялась; после выпуска нужна проверка продолжения
активного сбора через штатный редеплой.
