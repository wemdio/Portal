# Software Factory для Portal

В проект подключены семь навыков из
[michaelshimeles/skills](https://github.com/michaelshimeles/skills/tree/513f8a24aae6383b00356fa285144b1bc3730dc1).
Они задают процесс разработки: подготовить рабочую копию, внести изменение,
проверить результат и передать свою ветку на дальнейшее рассмотрение.
Это инструкции агентам и инструмент записи доказательств, а не фоновый
сервис или автоматический деплой.

## Как пользоваться

Обычного запроса достаточно: «Исправь сохранение фильтров в списке лидов».
Агент прочитает правила в `AGENTS.md` и выберет нужные навыки. Явный пример:

```text
Используй $new-feature для задачи сохранения фильтров. После реализации
проверь поведение через $evidence-driven-testing и покажи результат.
```

| Навык | Результат |
| --- | --- |
| `new-feature` | Своя рабочая копия и ветка с понятной базой; существующая рабочая копия задачи сохраняется |
| `code-structure` | Повторяемые операции вынесены без смешивания доменных правил |
| `evidence-driven-testing` | Проверяемые результаты, команды, ограничения и локальные артефакты |
| `before-and-after` | Сопоставимые снимки интерфейса до и после изменения |
| `unslop` | Понятные сообщения, документация и комментарии |
| `greploop` | Исправления по свежему ревью существующего PR, если этот этап запрошен |
| `greploop-apps` | Запасной триггер для подтверждённого ограничения Greptile по числу файлов |

Greptile не требуется для обычной разработки. Для него нужен подключённый
к репозиторию сервис и доступ к GitHub. Установка этих навыков не подключает
сервис и не подтверждает наличие подписки. Пример отдельной команды после
создания PR пользователем: «Запусти greploop для PR №123, максимум 3 цикла».
Цикл не разрешает переключаться на чужую ветку или выполнять деплой.

## Подключение в рабочих копиях

Канонические файлы находятся в `.agents/skills/`. Codex читает их в контексте
репозитория; Claude Code использует относительные ссылки из `.claude/skills/`.
Правила процесса находятся в `AGENTS.md`, а `CLAUDE.md` ссылается на них.
Остальные локальные настройки агентов и навыки остаются под прежними
правилами `.gitignore`. Общие пользовательские настройки не меняются.

После получения этой ветки навыки доступны со следующего сообщения в задаче,
открытой в этой рабочей копии. Если список не обновился, перезапусти Codex.
В других ветках набор появится после переноса изменений пользователем.
Механизм поиска описан в [официальной документации Codex](https://learn.chatgpt.com/docs/build-skills#where-codex-loads-local-skills).

Проверка установки из корня репозитория:

```bash
python3 scripts/software-factory-check.py
```

Она проверяет семь файлов `SKILL.md`, ссылки Claude Code, сохранённые
upstream-файлы по SHA-256 и доступность необязательных инструментов.
Не устанавливает пакеты, не читает секреты, не обращается к сети и не
запускает приложение. Код выхода 0 означает исправный набор файлов;
отсутствующий FFmpeg или GitHub CLI выводится отдельно как ограничение.
На Windows для ссылок нужен checkout с поддержкой symlink.

## Среда Portal

Перед установкой зависимостей проверь версии Node/npm в текущем
`app/package.json`, lockfile и Dockerfile. Не меняй lockfile ради настройки
навыков. Для задач, которым нужны Node-зависимости, в отдельной рабочей копии:

```bash
cd app
npm ci --ignore-scripts
npm exec -- patch-package
```

`--ignore-scripts` позволяет отдельно контролировать lifecycle-хуки.
Обычный `postinstall` также скачивает Chromium. При необходимости браузерных
проверок установи браузер через локальный Playwright:

```bash
cd app
npm exec -- playwright install chromium
```

Не копируй и не связывай production `.env` с новой рабочей копией.
`predev` и `prestart` вызывают `scripts/db/ensureDatabase.js`; `dev`
дополнительно запускает воркеры. Эти команды не являются безопасной
автоматической подготовкой к любой задаче.

Для визуальной проверки существует `npm run dev:ui` в `app/`. Он задаёт
`UI_ONLY=1`, чтобы Next.js не загружал корневой `../.env`. Это не сетевая
изоляция: переменные, унаследованные процессом, и локальные env-файлы всё
ещё нужно проверить. Используй чистую среду с тестовыми данными, свободный
порт и сервер своей рабочей копии. Такой режим проверяет отображение,
но не доказывает работу авторизации, БД или фоновых процессов.

Для интеграционных проверок нужны отдельная тестовая БД и тестовые учётные
записи. Недоступную проверку укажи в отчёте. Не запускай реальные рассылки,
миграции или workers ради получения доказательства.

## Какие проверки запускать

Выбирай проверки по изменённому поведению. Сначала прочитай тесты и их
настройки: отдельный скрипт может использовать внешнюю инфраструктуру.
Команды ниже запускаются из `app/`, с установленными зависимостями и
контролируемой средой. Подставляй реальные файлы вместо примеров.

| Изменение | Проверка |
| --- | --- |
| Навыки и документация Factory | Из корня: `python3 scripts/software-factory-check.py`; проверить ссылки и инструкции |
| TypeScript | `npm exec -- tsc --noEmit` |
| Конкретные JS/TS-файлы | `npm run lint -- src/path/to/changed.ts` |
| Поведение с Jest-тестами | `npm test -- --runInBand --runTestsByPath tests/relevant.test.ts` |
| Сборка Next.js, когда затронута | `UI_ONLY=1 npm run build`, только в чистой тестовой среде |
| Компиляция воркеров, когда затронута | `npm run build:workers`, без запуска собранных процессов |
| Пользовательский сценарий | Воспроизведение на тестовых данных и фактические результаты/снимки |

`UI_ONLY=1` не гарантирует отсутствие запросов при сборке: Next.js может
выполнять серверный код. Не запускай её с production-учётными данными.
Существующие сбои фиксируй отдельно от регрессий задачи. Не обозначай сборку
как успешную, если она завершилась ошибкой или была прервана.

Изменения legacy Hypothesis Engine могут затрагивать `/client/eng` и
внутренний legacy UI. Внутренний Vertical Engine v2 сохраняет отдельные
модули, `ve_*`, очередь, worker/API и `VE_MODEL_*`; новые v2-запуски не пишут
`he_*`. Перед работой прочитай утверждённый isolation design в текущем
контексте. Если его нет в ветке, найди актуальный документ через память
Portal; не делай вывод о состоянии продукта по одной старой рабочей копии.

Для памяти используй доступный `portal-memory` и сначала его команду
`where`. Общая память может находиться в основной рабочей папке. Factory
не переносит её целиком и не заменяет wiki Instantly. Сохраняй только новые
проверенные выводы задачи; память не меняет разрешения.

## Доказательства и завершение

Сохраняй логи, снимки, видео и отчёт в `.artifacts/<task>/`. Папка исключена
из Git. Для UI сравнивай одинаковые данные, viewport и состояние; для
backend приложи воспроизведение, результаты тестов или измерения.
Привязывай доказательства к ветке, SHA и незакоммиченным изменениям.

Видео необязательно. Встроенный `evidence.py doctor --json` проверяет
FFmpeg/ffprobe, кодек и источник захвата. Если инструментов нет, используй
доступные снимки и логи. Скриншоты и видео с клиентскими данными не публикуй.
В upstream `before-and-after --markdown` загружает изображения на внешний
хост; для локальной таблицы эта опция не нужна.

Перед commit проверь diff и добавь только файлы задачи. После push текущей
ветки сообщи SHA, результат проверок и ограничения. PR в `test`/`main`,
слияние и деплой остаются отдельными этапами по правилам `AGENTS.md`.

## Источник и обновления

Источник зафиксирован на коммите
`513f8a24aae6383b00356fa285144b1bc3730dc1`. Состав, сохранённые контрольные
суммы и адаптации перечислены в
[software-factory-upstream.json](software-factory-upstream.json).

Сохранены лицензии `before-and-after`, `greploop`, `greploop-apps`, `unslop`
и неизменённый recorder. У трёх остальных навыков в этом upstream-снимке
нет отдельных файлов лицензий; происхождение указано в manifest.
Убраны скрипты публичной загрузки снимков, неиспользуемые инструкции
GitLab/Perforce и дублирование API-справки. Инструкции адаптированы под
GitHub, локальные доказательства и границы Portal.

При обновлении сначала сравни upstream с зафиксированным SHA. Не заменяй
Portal `AGENTS.md` upstream-шаблоном и не перезаписывай адаптации слепым
установщиком. После осмысленного переноса обнови manifest, проверь навыки,
ссылки и поведение изменённых скриптов, затем используй обычный процесс
commit/push своей ветки.
