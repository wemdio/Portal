# Расходы новой базы Vertical Engine v2

Перед первым измеренным запуском worker сохраняет в `ve_jobs.payload.provider_usage_origin` ID этого запуска. Если его начало исчезло из журнала при очистке, отчёт считает историю неполной даже при наличии поздних успешных обращений. Пагинация сверяет точное число строк; изменение состояния задач/базы после `capturedAt` блокирует точный итог до следующей выгрузки.

Учёт работает после обычного деплоя версии с `withVeCostTelemetry` и обновления VE2 worker. Прошлые расходы он не восстанавливает: `ve_projects.cost_usd` и `ve_jobs.cost_usd` остаются оценками, а не счетами провайдера. Этот отчёт измеряет Requesty и Serper; инфраструктура, прокси, другие поставщики и отправка писем в сумму не входят.

Для контроля VBI откройте внутренний движок → VBI → «Частная медицина», выберите одну гипотезу и запустите обычный сбор. Проект `5520bec1-4f58-48e6-8094-c8340dfd5348`; принятые гипотезы: «Сети частных клиник» (`650dd54a-36c8-4225-8108-e9e09d789f66`) и «Эстетическая медицина» (`c5c81be3-ddef-470b-afed-63f9a6ae9bd9`). Цель — 1000 готовых контактов на базу; достижение зависит от данных и лимитов, существующие базы участвуют в дедупликации. Сохраните ID новой базы. Исследование для измерения сбора заново запускать не требуется.

CLI ниже выполняет только GET к `https://polza-portal.ru/rest/v1`. Он не запускает сбор, ИИ, поиск, рассылку или reconciliation API. Секрет `SUPABASE_SERVICE_ROLE_KEY` читается из локального env-файла либо окружения и не попадает в отчёт. Из каталога `app`:

```sh
./node_modules/.bin/esbuild scripts/ve2-cost-report.ts --bundle --platform=node --target=node20 --format=cjs --outfile=/tmp/ve2-cost-report.cjs
node /tmp/ve2-cost-report.cjs --project 5520bec1-4f58-48e6-8094-c8340dfd5348 --base BASE_UUID --mode collection --env-file /absolute/path/to/local.env --out /tmp/vbi-base-cost.json
```

Замените BASE_UUID на реальный ID. Когда известна цена пакета Serper, добавьте `--serper-usd-per-1000 PRICE`. Без тарифа деньги Serper и сумма ИИ + поиск остаются `null`, кредиты отображаются отдельно. Для исследований используйте `--mode research` без `--base`. Режим `all` показывает отдельные стадии в `byStage`; стоимость исследования не распределяется автоматически между базами. Режим collection включает только `base_collect`, без `base_analyze` и `template`.

- `requesty.reportedUsdKnownSubtotal` — сумма денежных значений, возвращённых Requesty. `estimatedUsdKnownSubtotal` — отдельная оценка; она не подменяет неизвестную фактическую стоимость.
- `serper.returnedCreditsKnownSubtotal` — возвращённые кредиты. Отсутствие ответа или credits остаётся неизвестным даже при успешном HTTP.
- `financialCoverageComplete` означает полноту наблюдаемого журнала в указанном scope. `collectionFinished` отдельно отражает терминальные состояния задач, в том числе failed/cancelled. У работающей базы стоимость промежуточная; стоимость контакта рассчитывается только после окончания.
- `issues`, `unmeteredJobs`, `childPlans` раскрывают начатые без финала стадии/запросы, неоднозначные ответы, старые прогоны и неизвестные дочерние планы. Неизвестное не равно нулю. Повторные записи одного attemptId не суммируются дважды; конфликтующие финалы дают пробел.
- `costPerReadyContactUsd` доступен только для одной завершившей сбор базы: нужны полный учёт, тариф Serper и положительное фактическое число ready. `row_count` не заменяет ready. Если сохранённые ready-счётчики расходятся, знаменатель неизвестен.

Снимки до/после каждого запуска стадии сохраняют ID дочерних задач между раундами. Проверенные текущие HH/Yandex/Google парсеры и шаги конструктора `find_emails`, `enrich_descriptions`, `split_emails`, `dedup_email`, `validate_emails`, `cap_emails_per_company` не вызывают Requesty/Serper: сайты читаются HTTP, валидация использует DNS/SMTP. Это не означает бесплатную инфраструктуру. Другие планы считаются неизвестными. При изменении реализации пересмотрите allowlist в `costReport.ts` и версию журнала.

Начало запроса сохраняется перед обращением к провайдеру, финал — после него. Сбой сохранения журнала завершает задачу технической ошибкой `Provider usage journal could not be saved.` без автоматического повтора, чтобы не оплатить работу повторно вслепую. Прерванный процесс оставляет явный пробел. Выгрузка во время работы не является транзакционным снимком: период журнала ограничен `capturedAt`, статус базы читается отдельно. Записи `application_logs` могут удаляться после 30 дней; экспортируйте итоговый JSON заранее.
