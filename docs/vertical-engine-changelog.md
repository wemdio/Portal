# Сводка изменений — Vertical Engine

Живой журнал для технического звонка (по средам). Пополняется по мере фидбека
специалистов и технических изменений.

Формат каждого пункта:
- **Проблема / репорт** — что сообщили или заметили (текст фидбека/наблюдение).
- **Вердикт** — `реальная` / `ложная` / `частично` / `улучшение (не репорт)`.
- **Что изменено** — конкретные правки и где (только v2 `verticalEngineV2`, если не указано иное).
- **Как теперь работает** — проверяемый результат (A/B, метрики, поведение).

## 2026-08-24

### 1. Репорт Ани (VBI): «LLM сужает гипотезы — в „Финансы для МСБ“ нет банков»

- **Проблема / репорт**: прогон VBI. Вертикаль «Финансы для МСБ» содержала только лизинг/факторинг, банки отсутствовали.
- **Вердикт**: **реальная** — подтверждено по данным. Причина тоньше, чем «LLM сужает»: VBI — это маркетинг-агентство, у него был кейс с лизинговой компанией («Интерлизинг»), и LLM заякорился на этом одном кейсе — сгенерировал только «Финансовый лизинг», а соседние подкатегории сектора (банки, МФО, страхование, брокеры) не раскрыл. Плюс единственную финансовую гипотезу потом вручную отклонили → вертикаль в 0%.
- **Что изменено**: промпт стадии гипотез, только v2 (`verticalEngineV2/prompts/hypotheses.ts`):
  - «кейс в секторе = семя для ВСЕГО сектора» — банки/МФО/страхование/брокеры/факторинг/лизинг это отдельные гипотезы;
  - «смежник внутри сектора — не риск/конкурент, а отдельная гипотеза»;
  - самопроверка в конце промпта: «каждый сектор с кейсом разложен на подкатегории полностью».
- **Как теперь работает**: A/B на реальных входных данных VBI (gpt-5.5). Было 1 финансовая гипотеза («Финансовый лизинг»), стало 4 — «Банки для МСБ» 76%, «Лизинг оборудования» 75%, «Страхование и НПФ» 70%, «Факторинг и МФО МСБ» 71%.

### 2. Репорт Ани (VBI): «В цепочке не тот TOV выпал, но есть опция поправить — удобно»

- **Проблема / репорт**: сгенерированная цепочка писем не попала в тон общения (TOV) клиента; при этом «опцию поправить» Аня оценила как удобную.
- **Вердикт**: **частично**. «Не тот TOV» объясним самим прогоном (v1 до брифа): эталона стиля (`style_override`) не было, цепочка писала дефолтным «живым» тоном, а не в голосе клиента — это не баг текущего v2, перепроверить на v2 с заполненным эталоном. «Опция поправить — удобно» — корректная похвала UX (инлайн-редактор письма «✎» + «Перегенерировать» + A/B в Step 3).
- **Что изменено**: ничего не меняли. TOV задаётся эталоном стиля (Step 1 → «Эталон стиля (необязательно)»), отдельно от структурного брифа.
- **Как теперь работает**: в v2 с заполненным `style_override` цепочка подражает манере/структуре/тону эталона; без него — дефолтный «живой» тон. Открытый вопрос на звонок: делать эталон обязательным или выводить TOV автоматически из брифа.

### 3. Репорт Ани: «Что значат % рядом с невыбранными базами?»

- **Проблема / репорт**: Аня не поняла, что означает процент-пилюля рядом с невыбранными (ещё не принятыми/отклонёнными) гипотезами-сегментами на шаге выбора вертикали. «Базы» в её формулировке = гипотезы/сегменты, под которые потом собирается база контактов.
- **Вердикт**: **реальная** (UX: цифра без подписи). Сам `%` — это `potential_pct`, корректная оценка, а не баг данных.
- **Что изменено**: в v2 (`verticalEngineV2/components/…/Step2Verticals.tsx`) к пилюле потенциала добавлена подсказка (tooltip): «Потенциал сегмента (0–100) — оценка привлекательности сегмента как рынка для аутрича. Это не прогноз reply%.». Раньше пояснение было только у «факт reply N%».
- **Как теперь работает**: при наведении на процент видно, что это потенциал сегмента (приоритет/привлекательность для аутрича), а не прогноз ответов и не доля рынка; фактический reply rate остаётся отдельной меткой «факт reply N%».

### 4. Репорт Ани: похвалила профиль базы и коммент по качеству («нет ЛПР в базе»)

- **Проблема / репорт**: Аня отметила как удобное: (а) разбивку базы по городам/отраслям/типам компаний, (б) коммент по качеству базы (в её случае — рекреационные бизнесы на юге, услуги в Москве, отсутствие ЛПР).
- **Вердикт**: **положительный фидбек** (не баг). Обе фичи уже работали: разбивка = `geo/industry/company_type/title_distribution`, коммент = `notable_segments` + `data_quality_notes` (стадия `base_analyze`).
- **Что изменено**: сами фичи не трогали. По реплике про «отсутствие ЛПР» уточнён промпт `baseAnalyze.ts` (v2): личные email ЛПР в РФ юридически недоступны (152-ФЗ) — их отсутствие в базе норма, а не ошибка сбора.
- **Как теперь работает**: `data_quality_notes` не вводит в заблуждение — «нет личных почт ЛПР» фреймится как ожидаемое ограничение РФ, а не как дефект конкретной базы.

### 5. Репорт Ани: «в базе есть образование — нужна подсказка про сезон (сентябрь) и актуальность оффера»

- **Проблема / репорт**: Аня предложила: если в базе есть сезонные отрасли (у неё — образование), полезно, чтобы движок сам подсказывал про приближающийся сезон (сентябрь = начало учебного года) и актуальность предложений.
- **Вердикт**: **предложение** (не баг): сезонности не было ни в v1 (её прогон VBI 08-20), ни в v2. Идея дельная, реализовали.
- **Что изменено**: сквозная правка сезонности только в v2 (`verticalEngineV2`):
  - `prompts/baseAnalyze.ts` / `baseAnalyze.en.ts` — в промпт добавлена текущая дата (`СЕГОДНЯ`/`TODAY`) + инструкция отмечать приближающийся сезон в `notable_segments` и давать сезонный угол в `recommended_angles`;
  - `stages/baseAnalyze.ts` — передаёт `today = new Date().toISOString().slice(0,10)` в билдер промпта;
  - `prompts/template.ts` — «ПОВОД»/«REASON» (шаги план и финальные письма, RU+EN) дополнен примером «сезонный пик отрасли → тайминг (образование → сентябрь)», чтобы сезонный факт из анализа базы реально становился поводом письма.
- **Как теперь работает**: если в базе сезонные отрасли, анализ базы сам подсказывает приближающийся сезон относительно текущей даты; этот факт доходит до повода письма («сентябрь близко — у образовательных компаний пик»), а не остаётся только подсказкой в UI.

## 2026-08-22

### 6. Chain (письма) → google/gemini-3.1-pro-preview

- **Проблема / репорт**: письма на gpt-5.5 давали LLM-маркеры — 5/8 чистых на 8 сэмплах.
- **Вердикт**: **улучшение** (внутренний eval, не репорт специалиста).
- **Что изменено**: `HE_MODEL_CHAIN` и `VE_MODEL_CHAIN` → `google/gemini-3.1-pro-preview` (research/bulk остались gpt-5.5).
- **Как теперь работает**: 8/8 писем без LLM-маркеров; латентность ~18s против ~5s, цена ~2.5× за письмо (~$0.023 против ~$0.009).

### 7. Точные цены моделей (MODEL_PRICES)

- **Проблема / репорт**: gpt-5.5 отсутствовал в `MODEL_PRICES` → `cost_usd` падал в фолбэк opus-4-8 и считался неверно.
- **Вердикт**: **реальная** (баг учёта стоимости).
- **Что изменено**: добавлены gpt-5.5 и gemini-3.1-pro-preview в `MODEL_PRICES` (`hypothesisEngine/llm.ts` + `verticalEngineV2/llm.ts`).
- **Как теперь работает**: `cost_usd` в `he_jobs`/`ve_jobs` считается по реальным ценам Requesty, а не по фолбэку.
