## 2026-08-30

### 16. Live VBI: досье показывало размер справочника как будто это объём готовых контактов

- **Проблема / репорт**: в досье вертикали «Частная медицина» было `~31 528`, но
  сбор одной гипотезы дал меньше 2 тыс. строк. Подпись «компаний в директории» создавала
  ложное ожидание, что под гипотезу уже есть примерно 31 тыс. контактов.
- **Вердикт**: **реальная ошибка семантики и несколько дефектов воронки**. Старое число
  считало сырые строки широкого ОКВЭД-среза без дедупликации по ИНН, без фильтров выбранной
  гипотезы и без требования контакта. Затем лимит прогона, конструктор, relevance и
  launch-гейты закономерно уменьшали базу, но UI не показывал эти разные уровни.
- **Что изменено (только v2)**:
  - добавлен отдельный read-only RPC `ve_directory_segment_stats` в миграции
    `20260830_0001_vertical_engine_v2_directory_stats.sql`. Он не меняет общий
    `companies_directory_count_rpc`: возвращает сырые строки, уникальные компании по ИНН
    (строки без ИНН остаются отдельными) и две разные группы contact-счётчиков. Для досье
    `companies_with_*` отвечает на вопрос «известен ли канал хотя бы в одной строке этого
    qualifying ИНН»; для точного среза гипотезы `matched_companies_with_*` считает канал
    только на строках, прошедших его фильтры. Для строк без ИНН обе семантики остаются на
    конкретной matched-строке, чтобы не склеивать одноимённые компании. Опциональные фильтры
    региона, выручки, сотрудников и обязательного email позволяют тем же контрактом оценивать
    точный план одной гипотезы. Некорректные/частичные core-счётчики RPC не приводятся к
    ложному нулю: досье получает `null` и явную причину недоступности статистики;
  - досье показывает отдельно raw/unique/email/phone/any-contact и прямо поясняет, что это
    широкий срез справочника, а не прогноз готовой базы; email ещё не валидированы. Старое
    сохранённое досье не переименовывается задним числом в «уникальные компании»: UI помечает
    его как старый расчёт и предлагает пересобрать;
  - `base_collect` до cap сохраняет в `collect_info.estimate` оценку реестрового среза по
    точным фильтрам гипотезы; contact-ступень этой оценки берётся из matched-row счётчиков,
    а не из более широкого known-any-INN досье. После обработки сохраняются фактические
    `rows_total`, `processed_rows`, `low_relevance`, а `launchable_rows` появляется только
    после полной построчной validation. Шаг 4 показывает эту воронку рядом с выбранным
    лимитом и не складывает несколько пересекающихся реестровых задач в выдуманную сумму;
  - конструктор выполняет `find_emails` при необходимости, затем, если размер базы позволяет,
    один раз обогащает описание компании и только после этого запускает
    `split_emails → dedup_email → validation → cap`.
    Так несколько адресов из одной ячейки становятся отдельными строками со своим статусом,
    но не размножают одинаковые HTTP-запросы `enrich_descriptions`. Сохранённый legacy-
    constructor job без `split_emails` не импортируется: после терминального статуса он один
    раз re-dispatch'ится по текущему контракту;
  - relevance-gate получает title+description закреплённой `base-per-hypothesis` гипотезы,
    а не только широкую вертикаль. Если у привязанной базы контекст гипотезы недоступен,
    все её строки fail-closed помечаются непроверенными; fallback на вертикаль остаётся только
    для legacy-баз без `hypothesis_id`. Отсутствие в строке размера/географии/триггера не
    считается доказательством нерелевантности. После `split_emails` одна компания проверяется
    один раз (ИНН, fallback `company+website`), а verdict fan-out'ится на все её email-строки.
    Хвост сверх лимита relevance-gate и любой сбойный/malformed LLM-батч теперь явно получают
    `_relevance_unchecked`: это отдельная причина, не «низкая релевантность». Такие строки
    fail-closed исключаются и из обычного запуска, и из refill;
  - `launchable_rows` считается тем же каноническим pre-launch фильтром, который использует
    предзапускный аудит #8, но сохраняется только когда constructor завершён и у каждой строки
    есть verification-status. Непокрытые relevance-gate строки в этот итог не входят; рядом
    сохраняются checked/total company coverage и число unchecked-строк. В UI ступень называется
    «Прошли проверки», а не «Готовы к запуску», и неполное покрытие показано отдельным warning;
    при результате больше 2 000 показывается предупреждение о лимите одного запуска. Для
    failed-базы `row_count` больше не подставляется как якобы `processed_rows`.
- **Проверенный пример VBI**: диагностическая воронка конкретной гипотезы на момент live-
  прогона была **8 410 кандидатов под фильтры → cap 2 000 → 1 514 строк после конструктора
  → 651 уникальный email, прошедший проверки**. Поэтому `31 528` из старого широкого досье
  не могло быть прогнозом этой базы.
- **Тесты**: добавлены контракты миграции/RPC/досье UI, оценки и фактической воронки,
  known-any-INN vs matched-row contacts, malformed-RPC fail-safe, re-dispatch legacy-
  constructor, порядок enrich/split, company-level relevance fan-out, complete-validation
  gate, fail-closed unchecked tail/LLM-batches, обычный launch/refill и Step 4 coverage.
  Фактический локальный прогон десяти перечисленных в handoff целевых файлов —
  **10 suites / 46 tests passed**; отдельный прогон `noTransactionMigrations` + `grants` —
  **2 suites / 5 tests passed**; полный VE2 regression — **45 suites / 349 tests passed**.
- **Статус**: код и миграция добавлены в рабочую ветку. Миграция
  `20260830_0001_vertical_engine_v2_directory_stats.sql` **не применялась**; приложение и
  воркер **не развёртывались**. Новые цифры появятся в сохранённом досье после миграции,
  деплоя и ручной пересборки досье.

## 2026-08-28

### 15. Дополнение Ани: сезонность должна определять очередь запусков, включая «мёртвые» периоды

- **Проблема / репорт**: на звонке Аня уточнила исходный пункт #5. Сезонность нужно
  оценивать уже в начале работы по каждой нише: учитывать не только пики спроса, но и
  отрицательные окна (отпуска, отсутствие ЛПР, периоды, когда outreach заведомо хуже).
  Запуски идут не одновременно: текущий наиболее своевременный сегмент должен занимать
  мощность первым, а менее релевантные по сезону — ждать, пока слот освободится.
- **Вердикт**: **реальная продуктовая недостача**. Первая реализация #5 была лишь
  prompt-level подсказкой для текста после анализа базы: она не проверяла факт сезонности,
  не различала позитивные и негативные окна и никак не управляла очередью запусков.
- **Что изменено (только v2)**:
  - на evidence-stage у каждой RU-гипотезы сохраняется проверенная оценка
    `seasonal | neutral | unknown`, уверенность, обоснование и источники с URL+цитатой;
    неподтверждённый вывод становится явным `unknown`, без догадки по названию ниши. Поиск
    разделён на три независимые RU-линии — спрос, доступность ЛПР/отпуска и закупки/бюджеты —
    и может загрузить до двух подтверждающих страниц на каждую, не отдавая весь бюджет одному
    богатому поисковому запросу. У каждого `peak/avoid` собственный проверенный evidence:
    неподтверждённое окно удаляется отдельно и не может «проехать» рядом с валидным;
  - `seasonal` хранит окна `peak` и `avoid`; у `peak` есть `lead_days` — outreach надо
    начать до пика, а не в день его начала. Из годовых окон и московской бизнес-даты
    выводятся состояния `launch_now`, `prepare_now`, `neutral`, `unknown`, `wait`, `avoid`.
    Перед чтением RU-очереди и перед reservation они заново вычисляются из immutable
    seasonality snapshot на текущую дату Москвы; hash проверяется, а plan version меняется
    только при материальном изменении;
  - подготовка кампаний в Instantly по-прежнему создаёт их `PAUSED` и не ограничена
    активной ёмкостью. Один шаблонный запуск, даже если сегментация создала N кампаний,
    записывается как один launch bundle и занимает один слот только при активации;
  - для одного Instantly workspace и пересекающегося набора mailbox действует ёмкость
    `1` bundle. Непересекающиеся mailbox-наборы и другие workspace не блокируют друг друга;
    `activating`, `active` и `uncertain` держат слот, preemption запрещён;
  - после QA специалист активирует bundle вручную из Portal. Сначала атомарно резервируются
    актуальный plan version и слот, затем Portal активирует все дочерние кампании;
    перед checkbox видны названия/сегменты, объёмы и ссылки всех child campaigns. Preflight
    пагинирует точный набор очереди/кампаний и сверяет campaign ID, workspace и immutable
    mailbox snapshot; повтор идемпотентен, частичный/неоднозначный внешний результат остаётся
    `uncertain`;
  - очередь сортируется по подтверждённому ручному порядку, сезонному дедлайну/запасу
    времени, уверенности, потенциалу, возрасту ожидания и стабильному ID. Потенциал и
    сезонность не смешиваются в один непрозрачный score; ручное изменение требует причины
    и автора и не может вытеснить уже активный bundle. Явный audited `wait` исключает bundle
    из head даже при автоматическом `launch_now`; длительность считается по сумме лидов всех
    child campaigns общего mailbox pool;
  - live reconciliation учитывает прямую активацию уже известных кампаний в Instantly как
    отслеживаемый операционный bypass, включая реактивацию ранее `released` bundle.
    `active` требует свежего допустимого статуса у каждого child; partial active+paused остаётся
    `uncertain`. Свежий exact set, где **все** кампании `Completed`, автоматически переводит
    bundle в `released` без manual actor, включая recovery. Иной свежий exact non-sending set
    не доказывает завершение: после settling fence audited manual release допустим только для
    `active | uncertain` и требует mailbox snapshot, reason/actor. `activating`, missing, stale,
    unknown или sending proof слот не освобождают. Portal `released` означает только свободную
    capacity: source cascade допускается лишь для childless `released | skipped | cancelled`,
    а любой tracked remote campaign блокирует delete даже при cached `Completed`;
- **Данные и границы**: миграции
  `20260828_0002_vertical_engine_v2_ru_seasonality.sql` и
  `20260828_0003_vertical_engine_v2_launch_portfolio.sql` добавляют только `ve_*`-данные и
  service-only транзакционные операции. `he_*`, `hypothesisEngine` и ENG не меняются.
- **Тесты**: контракты сезонного календаря/evidence, launch bundle/capacity/release,
  миграций, queue/activation API и UI зафиксированы отдельными тестами. Полный v2-набор:
  **37 suites / 316 tests passed**; целевой seasonality/portfolio-набор:
  **13 suites / 162 tests passed**; strict TypeScript — green.
- **Статус**: реализация и обе миграции находятся только в коде ветки `Sergey`.
  Миграции не применялись, приложение/воркер не развёртывались.

## 2026-08-26

### 12. Хотфикс: multi-hypothesis сбор баз падал с duplicate key (ve_bases_one_collecting_per_vertical)

- **Проблема / репорт**: при сборе баз под несколько гипотез (base-per-hypothesis, #6) вторая база той же вертикали падала с `duplicate key value violates unique constraint "ve_bases_one_collecting_per_vertical"`.
- **Вердикт**: **реальная** (баг #6): legacy-индекс антигонки был уникален на `(vertical_id)` без условия на `hypothesis_id` — запрещал больше одной collecting-базы на вертикаль.
- **Что изменено**: миграция `20260826_0001_vertical_engine_v2_fix_collecting_unique.sql` — индекс переопределён: уникальность на вертикаль оставлена только для `hypothesis_id IS NULL` (легаси/refill); базы с гипотезой защищает `ve_bases_one_collecting_per_hypothesis`.
- **Как теперь работает**: N гипотез → N баз одной вертикали создаются без 23505; антигонка параллельного запуска сохранена на обоих уровнях. Применится при деплое (идемпотентно).

### 13. Хотфикс: ретраи LLM на 5xx/429 — стадия «Генерация гипотез» падала на Requesty 502

- **Проблема / репорт**: прогон упал на стадии «Генерация гипотез»: `Requesty 502: {"error":{"origin":"provider","message":"The provider is currently unavailable (502). Please retry or use a different model"}}`.
- **Вердикт**: **реальная** (транзиентный отказ провайдера, но код его не ретраил). `rawCall` в `verticalEngineV2/llm.ts` делал один запрос; 502 апстрима валил стадию сразу. Ретрай был только на валидацию JSON, не на HTTP-статусы.
- **Что изменено**: `rawCall` ретраит 408/425/429/5xx и сетевые сбои с экспоненциальным бэкоффом (2с → 4с → 8с, итого 4 попытки). Постоянные 4xx (ключ/схема/баланс) падают сразу; отмена задачи (AbortSignal) ретраев не держит. Регрессионный тест `tests/lib/vertical-engine-v2/llmRetry.test.ts`.
- **Как теперь работает**: кратковременный 502/429 пережидается внутри стадии без падения прогона; персистентный отказ (4 попытки подряд) помечает стадию failed с текстом ошибки, как раньше.

### 14. Автоповтор упавшей стадии с бэкоффом — «Повторить» не нужен для транзиентных 502

- **Проблема / репорт**: после падения стадии «Генерация гипотез» (Requesty 502) приходилось жать «Повторить», а он перезапускал весь research с `site_profile` — переплата за уже пройденные стадии.
- **Вердикт**: **реальная** (UX/стоимость). Воркер и так ретраил стадию (pending requeue), но без задержки и всего 3 попытки — три быстрых попытки упирались в недоступного провайдера за секунды.
- **Что изменено**: `verticalEngineV2/jobRetry.ts` — классификация транзиентных ошибок (5xx/429/сеть) против постоянных; `worker/verticalEngineV2.ts` `failJob` ставит отложенный `run_after` с экспоненциальным бэкоффом (30с → 60с → 120с → 120с) и до 5 попыток для транзиентных; постоянные — как раньше (3 быстрых). Регрессионный тест `tests/lib/vertical-engine-v2/jobRetry.test.ts`.
- **Как теперь работает**: упавшая стадия сама пережидает (суммарно ~5 мин окна) и повторяется без кнопки; полный перезапуск с `site_profile` нужен только если провайдер лежит дольше ~5 мин.

## 2026-08-24

### 1. Репорт Ани (VBI): «LLM сужает гипотезы — в „Финансы для МСБ“ нет банков»

- **Проблема / репорт**: прогон VBI. Вертикаль «Финансы для МСБ» содержала только лизинг/факторинг, банки отсутствовали.
- **Вердикт**: **реальная** — подтверждено по данным. Причина тоньше, чем «LLM сужает»: VBI — это маркетинг-агентство, у него был кейс с лизинговой компанией («Интерлизинг»), и LLM заякорился на этом одном кейсе — сгенерировал только «Финансовый лизинг», а соседние подкатегории сектора (банки, МФО, страхование, брокеры) не раскрыл. Плюс единственную финансовую гипотезу потом вручную отклонили → вертикаль в 0%.
- **Что изменено**: промпт стадии гипотез, только v2 (`verticalEngineV2/prompts/hypotheses.ts`):
  - «кейс в секторе = семя для ВСЕГО сектора» — банки/МФО/страхование/брокеры/факторинг/лизинг это отдельные гипотезы;
  - «смежник внутри сектора — не риск/конкурент, а отдельная гипотеза»;
  - самопроверка в конце промпта: «каждый сектор с кейсом разложен на подкатегории полностью».
- **Как теперь работает**: A/B на реальных входных данных VBI (gpt-5.5). Было 1 финансовая гипотеза («Финансовый лизинг»), стало 4 — «Банки для МСБ» 76%, «Лизинг оборудования» 75%, «Страхование и НПФ» 70%, «Факторинг и МФО МСБ» 71%.

### 2. Репорт Ани (VBI): «В цепочке не тот TOV выпал, но есть опция поправить — удобно»

- **Проблема / репорт**: сгенерированная цепочка писем не попала в тон общения (TOV) клиента; при этом «опцию поправить» Аня оценила как удобную.
- **Вердикт**: **частично**. «Не тот TOV» объясним самим прогоном (v1 до брифа): эталона стиля (`style_override`) не было, цепочка писала дефолтным «живым» тоном, а не в голосе клиента — это не баг текущего v2, перепроверить на v2 с заполненным эталоном. «Опция поправить — удобно» — корректная похвала UX (инлайн-редактор письма «✎» + «Перегенерировать» + A/B в Step 3).
- **Что изменено**: ничего не меняли. TOV задаётся эталоном стиля (Step 1 → «Эталон стиля (необязательно)»), отдельно от структурного брифа.

### 8. Репорт Ани (VBI): «как быть уверенной, что школам не полетит РЖД-Медицина, а клиникам — с учениками?»

- **Проблема / репорт**: Аня спрашивает, как ей убедиться перед запуском, что строка из одного сегмента не получит текст другого (школа ← медицина, клиника ← ученики).
- **Вердикт**: **реальная тревога, корень — смешанная база**. В v1 прогон VBI собирал **одну базу на всю вертикаль** «Платные B2C-сервисы»: в одном файле соседствовали медицина (ОКВЭД 86.90.4 санатории, ~47%) и образование (85.41/85.42, ~36%). Отсюда страх: анализ/дефолтный текст/сегментные варианты писались по смеси, и классификатору приходилось раскладывать «школа vs клиника» внутри одного файла.
- **Что уже закрывает**: base-per-hypothesis (#6) убирает первопричину — теперь база собирается **на гипотезу**: в файле «образование» физически нет РЖД-Медицины/клиник, в файле «медицина» нет школ. На уровне данных вопрос «школе полетит медицина» снимается.
- **Что изменено (2026-08-28)**: предзапускный аудит сегментации завершён **в коде ветки `Sergey`**:
  - `POST /templates/[id]/segmentation-audit` сохраняет `pending`-снимок в новой v2-таблице `ve_segmentation_audits` и ставит отдельную асинхронную стадию `segmentation_audit` в `ve_jobs`; повторный POST во время активной проверки идемпотентен, UI получает результат polling-запросом GET;
  - точная launch-аудитория сверяется с лимитом **до** постановки LLM-задачи; audit + job создаются одной транзакцией, а отмена проекта атомарно закрывает job/audit (включая гонку «snapshot уже ready, job ещё running») и переводит уже зарезервированный внешний запуск в `uncertain`; heartbeat/finalize и worker failure-переходы используют CAS, поэтому поздний результат не воскрешает отменённую задачу и не продолжает следующую кампанию;
  - сохранённый снимок содержит стабильный SHA-256 входа, полный массив назначений, сводку и LLM usage. Через GET наружу отдаётся сводка, но не построчные назначения;
  - inline-блок шага 5 до формы запуска показывает точную аудиторию: всего строк и готовых получателей, исключения по низкой релевантности, verification-статусу, невалидному и дублирующемуся email, **все** условия сегментов (включая нулевые), отдельный дефолт и до трёх примеров компаний/строк на группу;
  - специалист обязан сначала дождаться полного актуального аудита, просмотреть раскладку и явно подтвердить её. До этого launch API fail-closed отвечает `409`: `SEGMENTATION_AUDIT_REQUIRED`, `SEGMENTATION_CONFIRMATION_REQUIRED`, `SEGMENTATION_AUDIT_STALE` или `SEGMENTATION_AUDIT_INCOMPLETE`; до прохождения gate внешние кампании не создаются;
  - запуск использует **ровно сохранённые assignments** и не вызывает LLM второй раз. Хэш связывает `templateId`, `baseId`, условия сегментов, точную launch-аудиторию и назначения; изменение шаблона/базы делает аудит stale;
  - строки без ответа классификатора, с неизвестным сегментом или из упавшего batch остаются `unclassified` и блокируют запуск — в дефолт они не подмешиваются;
  - для шаблона без `segment_variants` аудит имеет статус `not_required`: LLM-классификация не запускается (0 batch), все готовые получатели явно входят в default; просмотр и подтверждение точной аудитории перед запуском всё равно обязательны;
  - внешний launch защищён reservation + heartbeat. `launch_info` и terminal-статус фиксируются одной DB-транзакцией по точному reservation ID; неоднозначный/оборванный запуск остаётся `uncertain` и блокирует повтор. На шаге 5 специалист сверяет Instantly и явно фиксирует все campaign ID либо подтверждает отсутствие кампании; устаревшая вкладка и попытка забыть уже известный campaign ID отклоняются.
- **Тесты**: pure-контракт классификатора и reconciliation/hash/groups (`segmentClassify.test.ts`, `segmentationAudit.test.ts`), lease/heartbeat и heartbeat-CAS (`launchReservation.test.ts`), worker-stage/persistence (`segmentationAuditStage.test.ts`), cancel-vs-failure CAS (`jobFailureTransition.test.ts`), POST/GET/PATCH API (`templateSegmentationAudit.test.ts`), атомарная отмена (`projectCancel.test.ts`), fail-closed launch, cancel-mid-launch fence и reuse assignments без второго LLM (`templateLaunchSegmentationAudit.test.ts`), segment preview (`renderPreview.test.ts`) и inline review/confirmation UI (`VerticalEngineV2Step5Template.test.tsx`). Целевой прогон: **12 suites / 70 tests passed**.
- **Статус**: **#8 закрыт в коде**. Миграция `20260828_0001_vertical_engine_v2_segmentation_audits.sql` добавлена в ветку, но здесь не применялась; приложение и воркер не развёртывались.
