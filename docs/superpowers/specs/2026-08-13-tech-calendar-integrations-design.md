# Календарь технички: прокси и балансы сервисов автоматом

Дата: 13.08.2026

Продолжение [календаря технички](./2026-08-13-tech-calendar-design.md). Тот экран
заводят руками; здесь — то, что портал должен узнавать сам.

## Зачем

Прокси покупают пачками и на разные сроки, и вести их руками бессмысленно: на
двух сервисах сейчас 96 штук, даты окончания у них разъезжаются по всему
календарю. Заводить каждую покупку руками никто не станет, а забытый прокси
обнаруживается по упавшему парсеру.

Второе — деньги на счетах сервисов. Остаток видно только внутри чужой панели, и
узнают о нуле post factum: Serper перестал отвечать, аутрич встал. На 13.08.2026
на SpaceProxy лежит $0,38 — на одно продление не хватит.

## Что уже проверено вживую

Все три API опрошены 13.08.2026, ответы настоящие.

| Сервис | Ручка | Что отдаёт |
| --- | --- | --- |
| Serper | `GET https://google.serper.dev/account`, заголовок `X-API-KEY` | `{"balance":22042,"rateLimit":50}` — остаток кредитов |
| proxy.market | `GET https://api.dashboard.proxy.market/dev-api/balance/{api_key}` | `{"balance":"32.00"}` — рубли |
| proxy.market | `POST https://api.dashboard.proxy.market/dev-api/list/{api_key}`, тело `{"type":"all","page":1,"page_size":100,"sort":0}` | `{success, balance, list:{total, data:[{id, ip, expired_at, bought_at, proxy_type, country, tags}]}}` — 15 прокси |
| SpaceProxy | `GET https://panel.spaceproxy.net/api/balance/?api_key=…` | `{"balance":0.38,"partner_balance":0.0}` — доллары |
| SpaceProxy | `GET https://panel.spaceproxy.net/api/proxies/?api_key=…&limit=2000` | `{count, results:[{id, ip, order_id, type, ip_version, country, date, date_end, tags}]}` — 81 прокси, из них живых 11 |

Ограничение SpaceProxy — 50 запросов в минуту; нам хватит одного.

Цены ни один из трёх не отдаёт. Это определяет решение по деньгам ниже.

## Что делаем

### Прокси в календаре — группами по дате

Одна карточка на **сервис + дату окончания + тип + страну**, с количеством в
названии: «SpaceProxy · 3 × IPv4 de». По-другому не годится: строкой на прокси в
день массового продления клетка календаря превращается в простыню, а одной
строкой на сервис не видно, что именно и когда заканчивается. На сегодняшних
данных группировка даёт 62 группы вместо 96 строк, а живых — единицы.

Считаются только **действующие** прокси (`date_end`/`expired_at` в будущем).
Протухшие в календарь не идут: 70 из 81 у SpaceProxy — это история, а не план
платежей.

### Данные

`tech_subscriptions` получает поля:

| Поле | Смысл |
| --- | --- |
| `source` | `manual` (завели руками) / `spaceproxy` / `proxymarket` |
| `external_key` | Ключ группы: `<сервис>:<дата>:<тип>:<страна>`. Уникален вместе с `source` |
| `quantity` | Сколько прокси в группе |
| `synced_at` | Когда последний раз видели в API |

Уникальный индекс на `(source, external_key)` при `source <> 'manual'` — синк
обязан обновлять карточку, а не плодить копии.

Балансы живут отдельной таблицей `tech_provider_balances`: провайдер, значение,
единица (`RUB` / `USD` / `credits`), время снятия, текст ошибки последнего
опроса. Одна строка на провайдера, перезаписывается.

### Правила синхронизации

Раз в три часа, отдельным прогоном (не в десятиминутном — там дедлайны и
напоминания, а поход в три чужих API с их лимитами туда не просится).

1. Тянем список прокси у обоих сервисов и баланс у всех трёх.
2. Группируем действующие прокси, обновляем или создаём карточки.
3. Группа пропала из ответа, а её дата уже прошла — карточку удаляем: прокси
   истёк и не продлён, платить по нему нечего.
4. Группа пропала, но дата ещё впереди — карточку **оставляем** и помечаем
   «пропала из сервиса»: это либо ручное удаление прокси, либо сбой на их
   стороне, и молча стирать запись о будущем платеже нельзя.
5. Сбой опроса не трогает карточки вовсе. Пустой ответ из-за упавшего API
   выглядит так же, как «все прокси удалили», и разница здесь — цена ошибки:
   в первом случае мы сотрём весь календарь.

Сумма и заметка, вписанные человеком, при пересинке **не затираются**. API цен
не отдаёт, поэтому новая карточка заводится с суммой 0 в валюте сервиса, а
дальше её один раз заполняет админ — и синк это уважает, обновляя только дату,
количество и `synced_at`.

### Кнопка «Оплачено — продлить» у автокарточек

Ставит отметку в календаре и всё. API продления (`renew` у SpaceProxy,
`prolong` у proxy.market) **не дёргаем**: обе ручки списывают деньги с баланса
сервиса, и ошибочный клик по кнопке в календаре тратил бы реальные деньги.
Продлевают в панели сервиса, а синк через три часа сам подтянет новую дату.

В карточке при этом честно написано, что дату перезапишет синхронизация — иначе
ручная правка даты выглядит сохранённой, а через три часа тихо откатывается.

### Балансы сверху

Три плитки над календарём: кредиты Serper, рубли proxy.market, доллары
SpaceProxy. Под каждой — время последнего опроса; если опрос сорвался, плитка
показывает прошлое значение и пометку «данные от такого-то часа», а не ноль.
Ноль на месте баланса — это «денег нет», и путать эти два состояния нельзя.

### Оформление

Экран переводится на то же стеклянное оформление, что три дашборда:
`glass-stage` на сцену, `glass-tile` на плитки, `glass-panel` на панель
фильтров, `glass-frame` на таблицы. Сейчас календарь белый и выпадает из общего
вида портала.

### Ключи

`SERPER_API_KEY` уже есть в `.env`. Добавляются `SPACEPROXY_API_KEY` и
`PROXY_MARKET_API_KEY` — туда же, в репозиторий не попадают. Оба присланы в
переписку, поэтому после настройки их надо перевыпустить в панелях сервисов.

## Тесты

- группировка: 96 прокси двух сервисов сворачиваются в ожидаемые группы, протухшие отбрасываются;
- пересинк не плодит дубли (тот же `external_key` — та же строка);
- сумма и заметка, заполненные человеком, переживают пересинк;
- сбой API не удаляет ни одной карточки;
- пропавшая группа с будущей датой остаётся, с прошедшей — удаляется;
- баланс не сбрасывается в ноль при неудачном опросе.

## Что не делаем

- Не продлеваем прокси из портала — см. выше.
- Не тянем историю трафика и статистику: календарь про «что и когда платим».
- Не заводим отдельный экран для прокси: они живут в общем календаре наравне с
  серверами и софтом.
- Не пытаемся угадать цену продления из `new-order-amount`: это цена новой
  покупки, а не продления, и подставлять её в план платежей — врать в цифре.
