# Проверка карточки AMO при передаче проекта

Дата: 25.09.2026. Ветка: `dmitriy_kuladmed_new`. Решения пользователя — из переписки 25.09.2026.

## Зачем

Продажа попадает в дашборд первички и получает деньги, только если карточка сделки в AMO заполнена
(см. `app/src/lib/firstSales/money.ts`, `metrics.ts`, `sources.ts`). Карточки часто недозаполнены — и
это выясняется через месяц, когда деньги «не сходятся». Момент, когда проект передают в работу, — это
сообщение в группе «Продажи Polza» (`-1001852890744`), ветка «Передача проектов» (`message_thread_id`
3781). Бот проверяет карточку по ссылке из этого сообщения и сразу говорит, чего не хватает.

## Поведение

1. Бот — наш бот заявок с сайта (токен `HANDOFF_BOT_TOKEN`). Читает обновления `getUpdates`
   (`message`, `edited_message`) только из чата `-1001852890744`, ветки 3781. Остальное игнорирует.
2. **Сообщение о передаче** распознаётся по шаблону: есть хотя бы два из маркеров «Продажа»,
   «Стоимость:», «Кто завел:», «Откуда лид:», «Ссылка на амо». Прочие сообщения ветки (обсуждения)
   не трогаем.
3. Из сообщения достаём:
   - ссылку `https://<домен>.amocrm.ru/leads/detail/<id>` → `amo_id`;
   - «Стоимость: 259k» / «179 к» / «259 000» / «1,2 млн» → рубли;
   - «Откуда лид: …» → текст.
4. **Нет ссылки на AMO** → ответ реплаем: «⚠️ В сообщении нет ссылки на сделку AMO — добавьте
   «Ссылка на амо: …», иначе проверить карточку нельзя.»
5. **Есть ссылка** → сделка читается из AMO API вживую (`GET /api/v4/leads/<id>`), не из
   `amo_leads`: синк AMO раз в сутки, а передача проверяется сразу. Проверки:
   - сделка найдена;
   - воронка — первичка (`FIRST_SALES_PIPELINE_ID`, 7670334) и статус 142 «Успешно реализовано»;
   - **ИНН**: поле «ИНН» — 10 или 12 цифр; нет другой сделки воронки первички с тем же ИНН
     (иначе платёж станет «спорным» и ни к кому не отнесётся) — по `amo_leads`;
   - **Источник** (поле «Источник») заполнен; если «Откуда лид» уверенно сопоставляется со
     значением справочника (словарь синонимов) и не совпадает — это расхождение. Неизвестное
     «Откуда лид» (например «coldy») не проверяется;
   - **Бюджет** (`price`) > 0; если в сообщении есть стоимость и она отличается от бюджета больше
     чем на 1% — расхождение;
   - **Ответственный** (`responsible_user_id`) задан.
6. **Всё в порядке → бот молчит.**
7. **Есть проблемы** → один ответ реплаем в ветке:
   «⚠️ Сделка не попадёт в первичку / деньги не посчитаются: …» и список конкретных проблем
   («нет ИНН», «бюджет 0 ₽, а в сообщении 179 000 ₽», «сделка на этапе «Встреча проведена + КП
   отправлено», а не «Успешно реализовано»»). Со ссылкой на сделку.
8. **Перепроверка раз в день** (10:00 МСК) всех открытых проблем:
   - исправлено → короткий реплай «✅ Карточка дозаполнена» (единственный «позитивный» ответ —
     чтобы в ветке не висело устаревшее предупреждение);
   - через 3 дня после первого ответа всё ещё есть проблемы → одно напоминание со списком;
   - через 14 дней перестаём проверять.
9. **Правка сообщения** (`edited_message`) → проверка заново; если прежний ответ был о
   проблемах, а их не стало — «✅ Карточка дозаполнена».
10. Старые сообщения задним числом не проверяются — только пришедшие после запуска.

## Устройство

- Воркер `app/worker/handoffCheckBot.ts`, контейнер `worker-handoff-check-bot` (образ
  `portal-worker`), long polling + ежедневный проход по таймеру внутри процесса.
- При старте — `getWebhookInfo`: если у бота стоит webhook, воркер не удаляет его и не читает
  обновления, а шлёт алерт в health-чат (`sendWorkerAlert`) и спит. Если `getUpdates` отвечает 409
  (другой читатель) — тот же алерт.
- `HANDOFF_BOT_TOKEN` пустой → воркер пишет в лог и спит (не падает в рестарт-цикле).
- Таблица `handoff_card_checks`: одна строка на сообщение (`chat_id`, `message_id` — уникальны),
  `thread_id`, `amo_id`, `message_text`, `stated_amount`, `stated_source`, `status`
  (`ok` | `problems` | `no_link` | `resolved` | `expired`), `problems jsonb`, `reply_message_id`,
  `first_checked_at`, `last_checked_at`, `reminded_at`, `resolved_at`.
- Чистая логика отдельно от ввода-вывода: `app/src/lib/handoffCheck/` — `parseHandoff.ts`
  (разбор сообщения), `checkCard.ts` (проверки по данным сделки → список проблем),
  `formatReply.ts` (тексты), `amoApi.ts` (живое чтение сделки и пользователя), `store.ts` (таблица).
- AMO: `AMO_BASE_URL` + `AMO_ACCESS_TOKEN` (уже есть в прод-.env у синка). Названия этапов и
  воронок — из `amo_statuses`; дубли ИНН — RPC `handoff_inn_duplicates(p_pipeline_id, p_inn,
  p_exclude_amo_id)` по `amo_leads` (как `first_sales_payments`: `norm_inn(amo_custom_field_value
  (raw,'ИНН'))`).

## Что нужно при выкладке (делает пользователь)

1. `HANDOFF_BOT_TOKEN` в `.env` на сервере.
2. В BotFather у бота выключить приватность (`/setprivacy` → Disable) или сделать его админом
   группы — иначе он не видит чужие сообщения.
3. Контейнер поднимается `docker compose -p portal … up -d --force-recreate --no-deps
   worker-handoff-check-bot` (новый сервис).

## Вне рамок

- Проверка сообщений до запуска.
- Автоисправление карточки.
- Любые изменения дашборда первички.
