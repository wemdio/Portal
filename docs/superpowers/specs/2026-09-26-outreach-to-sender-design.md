# Автоаутричи → «Рассылка»: дешёвый конвейер, цепочки Gemini 3.1 Pro, портальные почты, заливка по кнопке

Дата: 26.09.2026. Ветка `dmitriy_kuladmed_new`. Решения пользователя — из переписки 26.09.2026.

Затрагивает русский (`app/src/lib/polzaRuOutreach/`, UI `components/polzaRuOutreach/`) и английский
(`app/src/lib/polzaOutreach/`, UI `components/parsers/PolzaOutreach*`) автоаутричи и «Рассылку»
(`app/src/lib/sender/`, `api/tools/sender/`, `components/sender/`).

## 0. Главные решения

| Вопрос | Решение |
|---|---|
| Кто пишет письма | **Как движок вертикалей**: Gemini 3.1 Pro (`google/gemini-3.1-pro-preview`) пишет **цепочку один раз на каждый оффер запуска**; под компанию подставляются проверенные факты. |
| Модель разбора (сайт, вакансия, новости, сегменты) | Дешёвая, как сбор у движка вертикалей: `deepinfra/deepseek-v4-flash-0731` (переопределяется env). |
| Ключи | Отдельные ключи Requesty: `POLZA_RU_OUTREACH_API_KEY`, `POLZA_EN_OUTREACH_API_KEY`. |
| Бюджет | Лимит расхода на ИИ за запуск, по умолчанию **$10**, поле в форме. Цель — **$3–5 за запуск на 500**. |
| Порядок | Дорогое в конце: бесплатные отсевы → почта → дешёвый разбор → оценка → письма только итоговым. |
| Почты | Портальный поиск (`scrapeEmails` + общий кэш `email_scraper_cache`) и портальная SMTP-проверка. Рабочие и catch-all — дальше; «не удалось проверить» — в «спорные»; нерабочие — следующий адрес, иначе отсев. |
| Сбой автопроверки писем | Повтор с замечаниями; снова провал — «спорные» (в рассылку не идут). |
| Подпись | Одна на аутрич: RU — из «Библиотек» (как сейчас), EN — новая настройка в инструменте (по умолчанию «Julia Mira / Account Manager / Polza Agency»). |
| Сендер | Папки «Автоаутрич RU» и «Автоаутрич EN»; каждый запуск по кнопке → новая рассылка в своей папке (или «добавить в существующую»). Запуск рассылки — тоже кнопкой. |
| Интервалы писем | 0 / +1 / +2 / +3 дня (настройка папки). |

## 1. Модели, ключи, учёт денег

Общий клиент аутричей `app/src/lib/outreachLlm/` (один на RU и EN, ключ и модели передаются):
- `callOutreachJson({ lang, role: 'analysis'|'writer', system, user, title, maxTokens }, budget)`:
  ключ — `POLZA_RU_OUTREACH_API_KEY` / `POLZA_EN_OUTREACH_API_KEY`; модель — `role==='writer'` →
  `POLZA_{RU|EN}_WRITER_MODEL` ‖ `google/gemini-3.1-pro-preview`; `analysis` →
  `POLZA_{RU|EN}_ANALYSIS_MODEL` ‖ `deepinfra/deepseek-v4-flash-0731`. Транспорт — Requesty, как
  `lib/openrouter/client.ts` (endpoint `OPENROUTER_ENDPOINT` ‖ router.requesty.ai).
- Стоимость вызова: `usage.cost` из ответа Requesty; нет — оценка по таблице цен (для трёх моделей) из
  `usage.prompt/completion_tokens`. `finish_reason: 'length'` у писателя — один повтор с большим
  `max_tokens` (Gemini тратит токены на размышление).
- `JobBudget` — счётчик запуска: `spentUsd`, `calls`, `limitUsd`. Перед вызовом: `spentUsd >= limitUsd`
  → `BudgetExceededError`. Раннер ловит его и завершает запуск штатно: `stop_reason = 'budget'`, всё
  готовое остаётся. `progress_detail.llm = { spent_usd, calls, limit_usd, by_role }`.
- Ошибка ИИ больше не маскируется под «сайт не открылся»: отдельная причина `LLM_FAILED` (RU) /
  `llm_failed` (EN). 401/403 от Requesty (неверный ключ) — запуск сразу `failed` с текстом «Неверный
  ключ ИИ для RU/EN автоаутрича». Нет ключа — запуск не стартует (ошибка при создании).
- Кэш разбора сайта на 30 дней: `polza_site_analysis_cache(lang, domain, prompt_version, model,
  result jsonb, created_at)` — повторный запуск не платит за ту же компанию.
- Конфиг запуска (оба аутрича): `llm_budget_usd` (1–100, по умолчанию 10).
- EN больше не использует RU-ключ и RU-модель (сейчас `siteProfile.ts` вызывает RU `callJson`).

## 2. Порядок шагов (дорогое в конце)

### RU (`polzaRuOutreach/runner.ts`)
1. Бесплатно: AMO по ИНН → домен (в т.ч. сайт работодателя hh) → AMO по домену, повторы в запуске,
   «уже выгружалась», стоп-лист не нужен ещё (почты нет).
2. **Почта** (бесплатно, см. §3) — нет рабочей почты → отсев `EMAIL_NOT_FOUND` / `EMAIL_INVALID`;
   стоп-лист → `SUPPRESSED_CONTACT`; «не удалось проверить» — запоминаем, строка пойдёт в «спорные».
3. Дешёвый ИИ: карточка вакансии hh + разбор вакансии; разбор сайта (с кэшем); ФНС/новости — как сейчас
   (включены только своими галочками).
4. Бесплатно: фильтры ползунков, выбор оффера, оценка, порог.
5. Сомнения считаются **до писем** (все признаки уже известны; +новый признак «почта не проверена» =
   сразу «очень спорная»). «Очень спорные» писем не получают (кнопка «Написать письма» у строки — позже,
   вне рамок; в выгрузке журнала видно почему).
6. Письма (§4) — только для прошедших, от лучших к худшим, стоп на заказанном числе.

### EN (`polzaOutreach/runner.ts`)
S2 домен → S3 ICP → **новое: повторы между запусками** (компания уже была `ready` в прошлых запусках —
отсев `previously_exported`) → **почта + проверка + стоп-лист** → S4 дешёвый разбор (сайт с кэшем,
вакансия) → оценка → письма (§4) → `ready`, стоп на числе. «Не удалось проверить» → `needs_review`
с причиной `email_unverified`.

## 3. Почты — портальные

- Поиск: `scrapeEmails(url, { locale, maxPages })` из `lib/enrich/emailScraper.ts` через общий кэш
  `email_scraper_cache` (читать/писать так же, как `websiteEnrichmentWorker.ts`: 7 дней удача, 6 часов
  ошибка). Выбор адреса — наши правила (`pickRuEmail`, EN-приоритеты) без изменений.
- Проверка: `validateEmailForAutoPipeline(email, domainCache)` (`lib/jobs/autoPipelineEmailValidation.ts`),
  один `domainCache` на запуск. `ok`/`role`/`catch_all`/`free` → проходит; `invalid`/`disposable` →
  следующий кандидат-адрес с того же сайта (до 3), иначе отсев; `unknown` → «не удалось проверить».
  В строке: `email_verification` = результат проверки.
- Прод: `worker-polza-outreach` получает `SMTP_PROXY_URLS`, `SMTP_PROXY_API_KEY` (как
  `worker-emailvalidation`); без них проверка деградирует до синтаксиса+MX (так устроен wrapper) — на
  экране запуска плашка «SMTP-проверка недоступна».

## 4. Письма: цепочки Gemini 3.1 Pro на оффер

- **Оффер** — RU: `chain_type` (7 типов, включая `automation`); EN: тип главного повода
  (`hiring|yc|launch|tech_stack|none`).
- **Шаблон цепочки** пишется лениво — когда первая компания оффера дошла до писем — одним вызовом
  писателя; хранится в `polza_chain_templates(job_id, lang, offer_key, letters jsonb, status, qa_flags,
  model, cost_usd, attempt, created_at)`; уникален `(job_id, lang, offer_key)`; параллельные компании
  ждут один и тот же промис (не платим дважды).
- Вход писателю: суть оффера и цель каждого из 4 писем (из нынешних шаблонов CEO как образцов тона и
  структуры: RU — `letters/chains.ts`, EN — `buildLetters.ts`), утверждённые формулировки
  (`polza_ru_offer_claims` для RU), правила (без выдуманных цифр; один вопрос на письмо; запретные слова
  из QA; письмо 1 с темой, 2–4 — ответом в той же ветке без темы; обращение RU «Добрый день!», EN «Hi
  there,»), список плейсхолдеров.
- **Плейсхолдеры** (только они меняются от компании к компании): RU `{{бренд}}`, `{{повод}}` (готовая
  фраза-повод из `openingSentence` — детерминированная, из проверенных фактов), `{{кейс}}`,
  `{{гипотеза}}`, `{{подпись}}`; EN `{{company}}`, `{{trigger}}` (`triggerPhrase`), `{{trigger_short}}`,
  `{{case}}`, `{{segments}}`, `{{signature}}`. Писатель выдаёт письмо 1 в двух вариантах — прямое и
  «перешлите ответственному» (общая почта) — и письмо 3 в двух вариантах — с кейсом и без
  (с гипотезой/сегментами). Пустой абзац после подстановки удаляется.
- **Проверка шаблона** один раз: правила нынешнего QA (RU `qa.ts`, EN `guardLetters`) в режиме шаблона
  (разрешены только плейсхолдеры; цифры только из утверждённых формулировок и слов шаблона; ровно один
  вопрос; нет запретных/служебных слов; все обязательные плейсхолдеры на месте). Провал → повтор с
  замечаниями → провал: шаблон `failed`, все компании оффера → «спорные» с причиной «цепочка оффера не
  прошла проверку»; на экране запуска у оффера кнопка «Переписать цепочку» (перегенерировать и
  пересобрать письма этих компаний).
- **Под компанию**: подстановка + дешёвый ИИ только для гипотезы сегментов (RU `buildSegmentsHypothesis`,
  EN сегменты из разбора сайта) + **нынешний QA на готовые письма**; провал → «спорные».
- Сохраняется как сейчас: `letters [{n, subject, body}]` (subject только у письма 1), плюс
  `chain_template_id`. Excel-выгрузки без изменений.
- Экран запуска: блок «Цепочки запуска» — оффер, статус, стоимость, текст шаблона (только чтение).

## 5. «Рассылка»: папки, заливка, запуск

- Таблица `sender_folders(id, key unique, name, timezone, send_hour_from, send_hour_to, send_weekdays,
  gap_seconds, gap_jitter_seconds, step_delays_hours int[], mailbox_ids uuid[], created_at, updated_at)`,
  сид: `auto_ru` «Автоаутрич RU» (Europe/Moscow, 9–18, пн–пт, задержки [24,24,24]), `auto_en`
  «Автоаутрич EN» (America/New_York, 9–17, пн–пт, [24,24,24]). `sender_campaigns` +
  `folder_id`, `source_kind` (`manual|polza_ru|polza_en`), `source_job_id`.
- Логика из роутов выносится в `lib/sender/campaignOps.ts` (роуты вызывают её же):
  `createCampaign`, `replaceSteps`, `importRecipients(rows)` (подавления, дубли, нормализация),
  `startCampaign` (проверки: есть шаги, активные получатели, хотя бы один проверенный ящик в пуле).
- Страховка сендера: если отрендеренное тело шага пустое — шаг не отправляется, получатель завершает
  цепочку (`finished`). Импорт не пускает строку с пустым `email_1`.
- **«Залить в Рассылку»** (кнопка на экране запуска RU и EN; сервер:
  `POST /api/tools/polza-ru-outreach/[jobId]/sender`, `POST /api/parsers/polza-outreach/[jobId]/sender`,
  тело `{ mode: 'new' | 'append', campaignId? }`): создаёт рассылку-черновик в папке («RU · 26.09 ·
  500 компаний»), ящики и расписание — из папки; шаги: 1 — тема `{{subject_1}}`, тело `{{email_1}}`;
  2–4 — пустая тема (ответ в ветке), тело `{{email_N}}`, задержки из папки; получатели — готовые строки
  (RU: `ready` + QA passed + почта; EN: `ready`), `name` = бренд, vars: `subject_1`, `email_1..4`,
  `company`, `domain`; стоп-лист пропускается. Строки аутрича помечаются `sender_campaign_id`,
  `sender_uploaded_at`; повторное нажатие доливает только новые готовые строки. `append` — в
  существующую рассылку этой папки в статусе draft/paused.
- **«Запустить рассылку»** — кнопка там же (и в сендере). Нет ящиков в папке → понятная ошибка
  «Выберите ящики в настройках папки».
- UI сендера: вкладка рассылок сгруппирована по папкам; у папки — «Настройки» (ящики, часы, дни, пояс,
  интервалы).
- Права: как у сендера (внутренние роли).

## 6. Прод и выкладка

- `.env` на сервере: `POLZA_RU_OUTREACH_API_KEY`, `POLZA_EN_OUTREACH_API_KEY` (ключи Requesty создаёт
  пользователь). В compose `worker-polza-outreach` — эти ключи, модели (необязательные), SMTP-прокси;
  сервис пересоздаётся с `--force-recreate`.
- Миграции применяются сами на деплое.
- В настройках двух папок один раз выбрать ящики.

## Проверка

Типы, линтер, существующие тесты (новых тест-файлов нет, CLAUDE.md). Вживую ИИ и SMTP-проверка — только
на проде: первый запуск на 20 компаний, сверить стоимость на экране с кабинетом Requesty.

## Вне рамок

- Письма для «очень спорных» по кнопке.
- Один общий обход сайта для почты и разбора (два обхода остаются, оба бесплатные).
- Автозапуск рассылки без кнопки.
