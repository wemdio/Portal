# Чекбокс «удалить недоступные сайты» после анализа сигналов

**Статус:** draft → ожидает аппрува юзера
**Дата:** 2026-06-22
**Скоуп:** одна правка UI + клиентская пост-обработка. LLM-fallback для пустого
«Профиля» — отдельная доработка, не в этом PR.

## Контекст и проблема

Юзер запустил анализ сигналов на 1000-строчной базе. Результат: 35.3% строк
(353 шт.) вернулись с ошибкой загрузки сайта — «Сайт недоступен»,
«Превышено время ожидания (60с)», DNS не резолвится, SSL и т.п. Эти строки
визуально шумят: юзер хочет видеть «итоговое кол-во сайтов готовых к
аналитике» — то есть только те, по которым сигналы реально собрались.

Текущее поведение `applySignalJobResults` (см. [applySignalJobResults.ts:121-130](app/src/lib/spreadsheet/applySignalJobResults.ts:121)):
для упавшей строки в колонку «Стек» пишется маркер `⚠` (см.
[signalConstants.ts:8](app/src/lib/enrich/signalConstants.ts:8)), в «Профиль» —
текст ошибки. Это единый маркер для **любого** типа провала, не только
двух названных юзером.

## Дизайн

### UI — чекбокс в модалке

Местоположение: в `SignalEnrichmentModal.tsx`, в скроллируемом body — после
блока с превью колонок (line ~374), перед футером (line 438).

Внешний вид:

```
☐ После обработки удалить строки с ошибкой загрузки сайта
   (Сайт недоступен / Превышено время ожидания и т.п.)
```

- **Дефолт:** выключен. Осознанный опт-ин.
- **Доступность:** disable пока `state.isProcessing` (как и остальные контролы
  модалки).

### Состояние

В `SignalEnrichmentModalState` ([SignalEnrichmentModal.tsx:18](app/src/components/SignalEnrichmentModal.tsx:18))
добавить поле:

```ts
removeUnreachableAfterDone: boolean;
```

Параллельно в `DatabaseSpreadsheet`-овском `SignalEnrichmentState` (line 1567)
— то же поле. Инициализация: `false`.

В пропсах модалки добавить handler `onToggleRemoveUnreachable: () => void`.

### Персистентность — localStorage

Существующий код модалки уже лежит в localStorage свои пресеты + последний
выбор экстракторов (line ~7904 useEffect). Туда же добавляем ключ
`signal-enrichment.remove-unreachable` (boolean).

- При открытии модалки — читаем последнее значение.
- При смене чекбокса — пишем.

Если ключа нет — `false`.

### Логика очистки

В `runSignalJobPolling` ([DatabaseSpreadsheet.tsx:7687](app/src/components/DatabaseSpreadsheet.tsx:7687)),
после успешного выхода из polling-цикла (line 7873) и перед
`setSignalEnrichment({isOpen: false})` (line 7879):

1. Прочитать актуальное значение чекбокса из state (через `setSignalEnrichment`
   функциональный update — чтобы не таскать в depsArray useCallback'a).
2. Если `removeUnreachableAfterDone === true`:
   - В рамках `setTabs(prev => ...)` пройти по `tab.data` (где `tab.id === tabId`)
     и оставить только строки где **`row[stackColIndex] !== SIGNAL_ERROR_MARKER`**.
     Строка 0 (header) сохраняется всегда.
   - Посчитать `removedCount = originalLength - newLength`.
3. Положить в `lastAction.message` дополнительный кусок:
   `«Анализ сигналов завершён: N сайтов. Удалено M строк с ошибками загрузки.»`

Сохранение — через существующий autosave (`saveCompressedStateWithCas`),
никаких новых вызовов не нужно: тот же механизм что сейчас сохраняет
изменения после polling-апдейтов сохранит и удаление строк.

### Важно: использовать `⚠`, а не текстовое сравнение

Юзер назвал «Сайт недоступен» и «Превышено время ожидания (60с)», но это
лишь два из ~7 возможных текстов ошибки (см. ERROR_PATTERNS в
[websiteSignalProcessor.ts:79](app/src/lib/enrich/websiteSignalProcessor.ts:79)
и таймаут-сообщение в [websiteEnrichmentWorker.ts:343](app/src/lib/enrich/websiteEnrichmentWorker.ts:343)).

Маркер `⚠` в колонке «Стек» — единственный признак, который ставится для
**всех** типов провала единообразно. Это и **только** это сравнивается.

### Что НЕ делаем

- Не трогаем серверный `applySignalJobResults` — очистка строго клиентская.
  Сервер по-прежнему пишет ⚠ + текст ошибки, как и раньше; удаление
  происходит уже после applies, на стороне клиента.
- Не добавляем серверного флага в job-запись. Если юзер закрыл вкладку пока
  job шёл и вернулся — увидит «Найдена завершённая задача», нажмёт
  «Подключиться», polling добежит до `completed` и сработает та же ветка
  (`removeUnreachableAfterDone` загружен из localStorage).
- Не делаем фильтр-режим (скрыть вместо удалить) — юзер явно выбрал «удалить
  строку целиком».
- Не трогаем 234 «достижимых, но с пустым профилем» строк — это отдельная
  доработка по LLM-fallback для `determineProfile()`.

### Edge cases

- **Юзер вручную написал «Сайт недоступен» в Профиль до запуска job'a**:
  не удалим — мы сравниваем по Стек = `⚠`, а вручную там пользователь
  маркер ставить не должен.
- **Юзер откатил сохранение (Ctrl+Z в spreadsheet)**: undo стека текущего
  компонента; если он там есть для splice — будет работать. Если нет —
  ровно тот же UX что и при удалении строк по любой другой причине.
- **Pre-existing ⚠ строки от прошлого запуска**: тоже удалятся, и это
  правильно — они «не готовы к аналитике» независимо от того, в каком
  именно run'е стали такими.
- **Активный таб поменялся пока job шёл**: polling уже работает по `tabId`
  переданному в `runSignalJobPolling`, не по `activeTabId` — очистка тоже
  должна идти по `tabId`, а не по «текущему активному». Иначе можем
  снести не те строки.
