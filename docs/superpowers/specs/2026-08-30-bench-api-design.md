# Bench API — внешняя витрина инструментов Portal

**Дата:** 30.08.2026
**Статус:** дизайн согласован, готов к планированию реализации
**Повод:** запрос Сергея Лазуткина (переписка 28.08.2026) — дать API по нашим
инструментам внешнему разработчику (Дима), который будет писать улучшения и
собственные скрипты поверх наших парсеров и конструктора баз.

---

## 1. Зачем

Сегодня инструменты студии доступны только через браузер: каждая ручка узнаёт
человека по сессии входа. Снаружи, скриптом, ими пользоваться нельзя.

Нужно отдать наружу набор инструментов так, чтобы:

- внешний разработчик мог запускать парсинг и обогащение из своих скриптов;
- он **физически** не мог тронуть чужие задачи, чужие данные и наши финансы;
- его скрипт не мог выжечь общий пул прокси или бюджет на LLM;
- ключ можно было отозвать за минуту, без деплоя;
- было видно, кто что дёргал.

Отдельная задача-надстройка (высказана Дмитрием в той же переписке) — чтобы это
же основание потом выросло в «настоящее» публичное API сервиса. Дизайн ниже это
учитывает, но в объём текущей работы не входит.

## 2. Объём

**Входит.** Витрина `/api/bench/v1/` над 15 инструментами (см. §5), выдача и
отзыв ключей через админку, лимиты, журнал запросов, документация.

**Не входит.**

- **Крипто-платежи** (`parsers/crypto-payments`). Формально это парсер, но
  сканирует он наш собственный USDT-кошелёк и видит приходы денег от клиентов.
  Финансы студии внешнему подрядчику не отдаём. Решение принято при
  согласовании дизайна.
- **Удаление чего-либо.** Не «запрещено настройкой» — действия удаления в
  витрине не существует.
- Всё, что не перечислено в §5: AMO, клиенты, аутрич, звонилка, отчёты,
  дашборды, задачи команды.
- Публичное API для клиентов студии (отдельный будущий проект).

## 3. Два формата, а не один

Инструменты делятся на два класса, и попытка натянуть один контракт на оба даёт
кривой результат.

**Задачи** — работают долго, встают в очередь, результат забирается позже.
Ручка проверяет параметры и кладёт строку в таблицу задач; тяжёлую работу
делает отдельный воркер. Так устроены все парсеры и конструктор баз.

**Поиск** — отвечает сразу из уже собранных данных. Очереди нет, воркера нет.
Так устроены наша база компаний, 2GIS и «наша база баз».

Витрина даёт им разные, но одинаково простые контракты.

## 4. Контракт

### 4.1. Задачи

| Действие | Запрос |
|---|---|
| Каталог доступного | `GET /api/bench/v1/tools` |
| Поставить задачу | `POST /api/bench/v1/jobs` |
| Статус задачи | `GET /api/bench/v1/jobs/{id}` |
| Результаты | `GET /api/bench/v1/jobs/{id}/results?limit=&cursor=` |
| Остановить | `POST /api/bench/v1/jobs/{id}/stop` |
| Свои задачи | `GET /api/bench/v1/jobs?tool=&status=` |

Постановка задачи:

```
POST /api/bench/v1/jobs
Authorization: Bearer bench_live_...

{ "tool": "yandexmaps", "params": { ... } }
```

Ответ на `POST /jobs` и на `GET /jobs/{id}`:

```
{
  "id": "...",
  "tool": "yandexmaps",
  "status": "running",
  "progress": { "done": 120, "total": 500 },
  "rows_found": 118,
  "error": null,
  "created_at": "...",
  "finished_at": null
}
```

Статусы приводятся к единому словарю: `queued` / `running` / `done` /
`failed` / `stopped`. Внутри инструменты называют их вразнобой (`pending`,
`processing`, `completed`, у Google Maps сразу `queued`) — перевод делает
адаптер, наружу словарь один.

Результаты отдаются страницами, курсором, а не смещением: базы растут во время
выгрузки, и смещение на больших выгрузках теряет и дублирует строки.

### 4.2. Поиск

| Действие | Запрос |
|---|---|
| Найти | `POST /api/bench/v1/search` |
| Посчитать без выдачи | `POST /api/bench/v1/search/count` |

```
POST /api/bench/v1/search
{ "source": "company-base", "filters": { ... }, "limit": 200, "cursor": null }
```

Ответ: `{ "rows": [...], "cursor": "...", "has_more": true }`.

### 4.3. Самоописание

`GET /api/bench/v1/tools` возвращает каталог: какие инструменты открыты
**этому** ключу, к какому классу относятся, какие параметры принимают и какие
поля возвращают.

Это не удобство, а способ не разойтись с документацией. Каталог собирается из
тех же описаний параметров, по которым идёт проверка входа — если параметр
изменился, каталог меняется сам. Новый инструмент появляется в каталоге в тот
же день, когда появляется в коде.

### 4.4. Ошибки

Единая форма: `{ "error": { "code": "...", "message": "...", "details": ... } }`.

| Код | Когда |
|---|---|
| `unauthorized` | ключа нет, ключ не тот, ключ отозван |
| `tool_not_allowed` | инструмент не открыт этому ключу |
| `invalid_params` | параметры не прошли проверку; в `details` — что именно |
| `rate_limited` | превышен лимит; в `details` — когда можно снова |
| `quota_exceeded` | исчерпана суточная норма задач или строк |
| `not_found` | задачи нет **или она чужая** (не различаем намеренно) |
| `conflict` | действие несовместимо с состоянием (стоп уже завершённой) |

`not_found` на чужую задачу вместо `forbidden` — сознательно: иначе перебором
идентификаторов можно выяснить, какие задачи существуют у других.

## 6. Ключи и изоляция

### 6.1. Ключ

Вид: `bench_live_<случайная часть>`. Префикс нужен, чтобы утёкший ключ
опознавался автопоиском по репозиториям и логам.

В базе хранится **отпечаток** ключа, а не сам ключ. Даже с доступом к базе
восстановить ключ нельзя. Показывается один раз в момент выдачи; дальше в
админке видны только метаданные и последние 4 символа.

Сравнение отпечатков — за постоянное время (`safeEqual`, уже есть в
`app/src/lib/crypto/safeEqual.ts`).

Проверка ключа идёт в базу на каждом запросе, без кэширования. «Отозвать за
минуту» должно означать ровно это: следующий же запрос получает отказ. Кэш
проверки, даже на минуту, превращает отзыв в обещание, а не в факт — а отзыв
нужен как раз в тот момент, когда ключ утёк.

### 6.2. Учётка-робот

К каждому ключу привязана учётка-робот — настоящая строка пользователя, но:

- без пароля, войти в браузере под ней нельзя;
- без роли, дающей что-либо в портале;
- помечена как робот и не показывается в списке пользователей админки — иначе
  через полгода никто не вспомнит, что это за «пользователи» без ролей.

Все задачи, поставленные по ключу, принадлежат этому роботу.

### 6.3. Изоляцию сторожит база, а не код

У всех таблиц задач есть владелец (`user_id`), а у таблиц с результатами —
правила уровня базы, отдающие строки только владельцу задачи (проверено на
`yandex_maps_organizations`: политика ходит в `yandex_maps_jobs` и сверяет
`user_id` с текущим пользователем).

Витрина ходит в базу **от имени робота**, а не служебным ключом. Тогда чужие
строки не отдаст сама база — ошибка в коде витрины не превращается в утечку.

Для этого приложению нужен подписной ключ Supabase (`SUPABASE_JWT_SECRET`) —
на сервере он есть, приложению сейчас не передаётся. Витрина выпускает
короткоживущий токен робота и работает под ним.

Дополнительно, поясом поверх подтяжек: все обращения витрины к задачам идут
через один модуль, который всегда подставляет владельца. Тест падает, если
ручка обошла модуль.

### 6.4. Тарифы

Проверки тарифов в инструментах срабатывают только для роли `client`. Робот ею
не является, поэтому тарифные лимиты его не касаются — его сдерживают лимиты
витрины (§7). Это осознанно: тариф — про биллинг клиента, а не про подрядчика.

## 7. Лимиты

Три независимых потолка на ключ, настраиваются при выдаче:

| Лимит | Зачем |
|---|---|
| Запросов в минуту | скрипт в цикле не забивает приложение |
| Новых задач в сутки | не выжигает пул прокси и бюджет LLM |
| Строк результата в сутки | не выкачивает всю базу разом |

Превышение — `rate_limited` или `quota_exceeded` с указанием, когда можно
снова, и заголовками `Retry-After` / `X-RateLimit-*`.

Отдельно — **потолок одновременных задач**, по образцу уже существующего
(`MAX_ACTIVE_JOBS_PER_USER = 6` в конструкторе баз). Робот не должен занять
всю общую очередь воркеров: параллельность обработки общая на всех, и десяток
задач робота отодвинет живых людей.

## 8. Журнал

Каждый запрос: ключ, инструмент, действие, время, код ответа, сколько строк
отдали, длительность. Тела запросов не пишем — там бывают базы клиентов.

Хранение — 90 дней. Видно в админке по каждому ключу.

## 9. Админка

Экран «Ключи API» по образцу существующих админских экранов.

- **Список:** кому выдан, инструменты, лимиты, последнее использование, статус.
- **Выдать:** имя получателя, галочки инструментов, лимиты → ключ показывается
  один раз.
- **Отозвать:** мгновенно, без деплоя. Отозванный ключ перестаёт работать
  сразу.
- **Журнал** по ключу.

Доступ к экрану — только админ.

## 10. Документация

Три слоя, чтобы не расходились:

1. **Файл в репозитории** — источник правды, ревьюится вместе с кодом.
2. **Страница по ссылке** для внешнего разработчика: примеры на `curl` и
   Python, таблица инструментов с параметрами, коды ошибок, лимиты.
3. **`GET /tools`** — машинное самоописание, собирается из кода (§4.3).

## 11. Что меняется в существующем коде

Мало — и это главное достоинство выбранного подхода.

- `app/src/middleware.ts`: `/api/bench/` добавляется в `isPublicApiPath` —
  раздел авторизуется сам, своим ключом.
- Новые таблицы: ключи, журнал. Миграция в `supabase/migrations/`.
- Новая переменная окружения `SUPABASE_JWT_SECRET` (см. §6.3) — вносится
  вручную на проде при деплое.

**Существующие ручки парсеров, конструктора баз и воркеры не трогаем.** Все
инструменты устроены одинаково: ручка проверяет параметры и кладёт задачу в
очередь. Витрина пишет в ту же очередь своими адаптерами, не переиспользуя и не
переписывая код ручек. Рабочий продакшн-код остаётся нетронутым.

## 12. Как проверяем

**Тесты, обязательные к наличию:**

- по каждому инструменту: постановка задачи с валидными параметрами создаёт
  строку с владельцем-роботом;
- по каждому инструменту: невалидные параметры дают `invalid_params`, а не
  битую задачу;
- **изоляция:** ключ A не видит задачу ключа B ни в списке, ни по прямому
  идентификатору, ни в результатах, ни остановкой — по каждому инструменту;
- инструмент вне списка ключа даёт `tool_not_allowed`;
- отозванный ключ даёт `unauthorized` немедленно;
- лимиты срабатывают и отпускают по истечении окна;
- ни одна ручка витрины не ходит в задачи мимо модуля владельца;
- в журнал не попадают тела запросов.

**Приёмка:** Сергей получает ключ через админку и проходит по документации
раньше, чем ключ уходит наружу.

| Кусок | Оценка |

| Проверка ключа, лимиты, журнал, модуль владельца | ~2 дня |
| 12 задачных адаптеров | ~4 дня |
| 3 поисковых адаптера | ~1 день |

Итого ≈ **две недели** чистой работы.

## 14. Решения, принятые при согласовании

| Вопрос | Решение |
|---|---|
| Объём | все инструменты по базам, кроме крипто-платежей |
| Права ключа | смотреть, запускать с лимитами, останавливать своё |
| Удаление | не даём вообще |
| Выдача ключей | экран в админке, отзыв без деплоя |
| Подход | отдельная витрина, а не открытие существующих ручек |
| Имя | Bench (верстак), путь `/api/bench/v1/` |
| Изоляцию сторожит | база, через подписной ключ Supabase |
| Порядок | все адаптеры сразу, без промежуточной сдачи |

По последнему пункту при обсуждении был отмечен риск: замечания Сергея по форме
контракта после сдачи придётся разносить по 15 адаптерам, а не по трём. Решение
принято сознательно.

## 15. Осознанно отложено

- Публичное API для клиентов студии — отдельный проект, это его основание.
- Вебхуки «задача завершилась» вместо опроса статуса.
- Отдельный поддомен для витрины: на старте живёт на основном.
- Крипто-платежи и любые финансовые данные.
- Удаление задач по API.
