# Ответы наших email-кампаний «N. Polza_…» → квалификация → сделка в AMO

Дата: 11.10.2026. Ветка: `dmitriy_kuladmed_new`.

## Зачем

Сделки по нашему email-аутричу (Instantly, кампании «1. Polza_HH_…», «6. Polza_…»)
менеджеры заводят в AMO руками: 173 сделки «Источник = Email Outreach» за 90 дней.
Ответы этих кампаний уже собираются в базу (`instantly_reply_inbox`, с 07.10.2026),
но их никто не квалифицирует: квалификатор Instantly наши кампании пропускает
намеренно (`getPortalLinkedCampaignIds`, решение 06.10.2026).

Нужно: ответ на нашу кампанию → ИИ решает «лид / не лид» → лид сам попадает в AMO
(новой сделкой или примечанием к уже открытой) → сообщение в чат продаж.

## Решения пользователя (10–11.10.2026)

1. **Только наши кампании** «N. Polza_…» (`isOwnAgencyCampaign`). Кампании клиентов —
   никогда (условие от 06.10.2026, см. шапку `lib/crm/dealQueue.ts`).
2. **Дубли не создаём.** Если в AMO уже есть открытая сделка с этой почтой или
   компанией, переписка ложится примечанием в неё, новая сделка не заводится.
3. **Сообщение в чат — на каждого лида:** и «новая сделка», и «переписка добавлена
   к существующей сделке (с этой почтой сделка уже была — дубль не создан)».
   Чат — «Продажи Polza», подчат General (как лиды «Рассылки»).
4. **Новая сделка:** «Воронка - новые лиды» (7670334), этап «Новый лид» (63385358),
   ответственный — Юлия Миронова (10539886).
5. **Поля** — по образцу ручных сделок email-аутрича (разобрано по `amo_leads`
   за 60 дней), «Оффер» оставляем пустым — ссылку на док менеджер вставит сам.
6. **Только ответы после включения.** Историю не прогоняем: на старые ответы
   менеджеры уже реагировали, часть лидов закрыта в AMO отказом.
7. **Управление на экране:** отдельный блок «Instantly · X. Polza» на вкладке
   автоаутрича «Квалификация» — выключатель (по умолчанию выключен), своё правило
   «что считать лидом», история.
8. Новых автотестов не пишем (правило проекта). Проверка — холостой прогон на
   реальных ответах до включения.

## Как устроено

### 1. Источник ответов

`instantly_reply_inbox` (база Instantly) — туда сборщик ответов уже пишет ответы
наших кампаний основного аккаунта (`saveInboxFromPage`) и догружает историю
(`backfillReplyInboxStep`). Новый проход берёт строки, у которых:

- кампания — наша (`isOwnAgencyCampaign` по имени из `instantly_campaign_catalog`);
- `reply_timestamp >= enabled_at` — момент, когда выключатель включили. Фильтр
  именно по времени ответа, а не по `created_at`: догрузка истории пишет старые
  ответы свежими строками, их брать нельзя.
- строки ещё нет в таблице оценок (см. ниже).

Чтение — сервисным клиентом базы Instantly (`supabaseInstantly`), пачками по 20,
по возрастанию `reply_timestamp`.

### 2. Квалификация

`qualifyReply(campaignId, leadEmail, threadId, {...}, 'main')` — тот же
квалификатор, что у «Рассылки»:

- ключ и модель — `SENDER_LEADS_AI_API_KEY` / `SENDER_LEADS_AI_MODEL` (расходы на
  квалификацию уже видны отдельно);
- `briefText: ''` — бриф кампании не ищем, контекст оффера дают наши письма в ветке;
- `leadCriteria` — правило из блока «Instantly · X. Polza» (null → общие правила);
- переписку квалификатор сам читает из Instantly (`fetchThreadContext`) —
  одно чтение на ответ, ответов у наших кампаний единицы-десятки в день.
  Отказ общего лимита чтения (`readInstantlyEmailReadDeferral`) — не ошибка:
  строка ждёт и повторяется на следующем круге без счёта попытки.

Повторы ИИ — как у «Рассылки»: паузы 1/5/15/60 мин, после 5 попыток — `error`.

Один человек — одна передача: если по этой почте (`lower(lead_email)`) уже был
лид, следующие его ответы оцениваются, но в AMO и чат повторно не идут
(переписку менеджер и так видит во встроенной почте AMO — почта в контакте).

### 3. AMO

Если вердикт «лид» — строка в очередь `own_reply_crm_pushes` (основная база),
разбор — общей очередью `processCrmQueue` (`lib/crm/dealQueue.ts`): повторы при
сетевых сбоях AMO, аренда задачи, промежуточные id сохраняются сразу — повтор
не заведёт вторую сделку.

**Данные лида** — `getLeadsByEmail({ email, campaign_id })` из Instantly: имя,
компания, сайт. Не нашлось — работаем с тем, что есть (почта).

**Поиск существующей сделки** (новый шаг перед созданием, в `dealQueue` —
необязательный хук канала `findExistingLead`, TG-аутрич его не задаёт):

1. Контакт в AMO с этой почтой (`findContact` — уже есть) → его сделки
   (`GET /api/v4/contacts/{id}?with=leads`, затем статусы сделок) → первая
   открытая (статус не 142/143) — берём её.
2. Не нашлось и почта корпоративная (домен не из `FREE_PROVIDERS`,
   `lib/emailValidation/shared.ts`) → открытая сделка в зеркале `amo_leads`, где
   домен `contact_email` или `company_website` совпадает с доменом почты.
   Зеркало обновляется синком AMO, поэтому шаг 1 по живому API идёт первым.
3. Нашлась → примечание с перепиской в неё, `action = 'note_added'`.
   Ответственного, этап и поля существующей сделки не трогаем.
4. Не нашлась (нет или только закрытые) → новая сделка, `action = 'created'`.

**Новая сделка:**

| Поле | Значение |
|---|---|
| Название | `<компания или почта> · <название кампании>` |
| Контакт | найти по почте или создать: имя (или почта), почта в стандартном поле Email (встроенная почта AMO подтянет переписку) |
| Воронка / этап | 7670334 «Воронка - новые лиды» / 63385358 «Новый лид» |
| Ответственный | 10539886 (Юлия Миронова) — `responsible_user_id` |
| Источник (1314379, список) | «Email Outreach» |
| Контур (1317011, список) | «Email-outreach» |
| Подысточник (1314381, текст) | «аутрич» — если в наших письмах ветки есть кириллица, иначе «англ аутрич» |
| Ком-й (402805, текст) | название кампании |
| Сайт (402799, текст) | сайт из Instantly, иначе домен корпоративной почты, иначе пусто |
| Оффер (402797) | пусто |
| Тег | «портал» |
| Примечание | переписка целиком: наши письма и ответы, даты МСК (как `buildEmailLeadCard` из f5781ca22) |

Id воронки, этапа и ответственного — константы в коде канала (правило «этапы AMO
только по id», [[amo-stages-by-id]]). Удалят и создадут этап заново — константу
обновить.

Расширения `amoClient`: `createLead` принимает `responsibleUserId` и текстовые
поля (`{ field_id, values: [{ value }] }`); новый `findOpenLeadsOfContact(contactId)`.

Подключение — наша AMO (`'polza'`: `AMO_BASE_URL` + `AMO_ACCESS_TOKEN`), уже
работает для TG-аутрича.

### 4. Сообщение в чат

После того как задача AMO выполнена (`status = 'sent'`) — сообщение тем же ботом
и в тот же чат, что лиды «Рассылки» (`leadTelegramConfig()`: «Polza Site Feedback»,
`-1001852890744`, General; только sendMessage, без кнопок).

- 🟢 **Новый лид с email-аутрича** — кампания, контакт, компания, ответ (без цитаты
  нашего письма, `stripQuoted`), вывод ИИ, ссылка на сделку.
- 🔁 **Переписка добавлена к сделке** «<название>» — то же плюс строка «С этой
  почтой/компанией сделка уже была — дубль не создан», ссылка на сделку.

Задача AMO упала окончательно → сообщение не шлём, ошибка видна в истории блока.
Сбой ТГ повторяется отдельно (до 5 раз), AMO повторно не трогается.

### 5. Экран

Вкладка автоаутрича «Квалификация» (только админ) — новый блок «Instantly · X. Polza»
рядом с блоками папок «Рассылки», в той же вёрстке:

- выключатель «Квалифицировать и заводить сделки в AMO»; при включении
  запоминается `enabled_at`, при выключении новые ответы не берутся;
- правило «что считать лидом» (пусто → общие правила, как у папок);
- одна кнопка «Сохранить» на вкладку ([[one-save-button-per-tab]]);
- история: дата, кампания, почта, вердикт ИИ с причиной, что сделано в AMO
  («сделка создана» / «добавлено к сделке» / ошибка) со ссылкой на сделку,
  ушло ли в чат. Фильтры как у «Рассылки»: всего / лиды / не лиды / в очереди / ошибки.

Подписи короткие, одной строкой ([[ui-captions-short]]).

## Данные (основная база, одна миграция `supabase/migrations/2026101x_…`)

- `own_reply_lead_settings` — одна строка: `enabled`, `enabled_at`, `lead_criteria`,
  `updated_at`, `updated_by`.
- `own_reply_qualifications` — `email_id` PK (id ответа Instantly), `campaign_id`,
  `campaign_name`, `lead_email`, `thread_id`, `reply_timestamp`, `status`
  (pending|lead|not_lead|error|skipped), `ai_reason`, `interest_signals`,
  `criteria_used`, `model`, `attempts`, `next_attempt_at`, `last_error`,
  `qualified_at`, `created_at`, `updated_at`.
- `own_reply_crm_pushes` — колонки общей очереди (`connection`, `pipeline_id`,
  `status_id`, `message_text`, `status`, `attempts`, `next_attempt_at`,
  `amo_contact_id`, `amo_lead_id`, `lead_url`, `error_message`, `sent_at`) +
  `qualification_id` (FK → email_id), `lead_email`, `campaign_name`, `lead_name`,
  `company_name`, `website`, `sub_source`, `action` (created|note_added),
  `tg_sent_at`, `tg_message_id`, `tg_attempts`, `tg_error`.
  Уникальный индекс по `lower(lead_email)` — одна передача на человека.

У всех таблиц — `grant … to service_role` (правило `tests/migrations/grants.test.ts`), RLS включён.

## Где крутится

Новый проход в воркере `worker/senderLeads.ts` (139, круг 60 с): у него уже ключ
ИИ квалификации и токен бота. Добавляется клиент базы Instantly и разбор очереди
AMO. Сбой прохода «X. Polza» не роняет квалификацию «Рассылки» — отдельный try.

Перед выкладкой проверить, что контейнер `worker-sender-leads` видит
`AMO_BASE_URL`, `AMO_ACCESS_TOKEN` и адрес/ключ базы Instantly (общий `.env`
портала на 139).

## Что не делаем

- Не прогоняем историю ответов.
- Не трогаем кампании клиентов и квалификатор Instantly для них.
- Не заполняем «Оффер».
- Не двигаем этап, ответственного и поля уже существующих сделок.
- Не пишем новых тестов.
