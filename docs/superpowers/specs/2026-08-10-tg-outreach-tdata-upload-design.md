# TG Outreach: загрузка аккаунтов из tdata — дизайн

**Дата:** 2026-08-10
**Статус:** согласовано, к реализации
**Основа:** вкладка «Аккаунты» кампании в [TG Outreach](../../../app/src/app/tools/tg-outreach/page.tsx)

## Задача

Портал принимает аккаунты только парами `<имя>.session` + `<имя>.json`. Продавцы
же отдают партии в родном формате Telegram Desktop — папке `tdata`. Сейчас
конвертацию каждой партии делает разработчик руками (партия atol, 04.08.2026:
20 аккаунтов через `opentele`), и без него продажи новую партию не заведут.

Нужно то же, что умеет ТГ Ниндзя: оператор кладёт архивы с `tdata` в загрузчик
и получает готовые аккаунты кампании.

## Почему это не «ещё один формат», а предпочтительный

`tdata` — формат, который создаёт сам Telegram Desktop. Ключ в нём выписан
официальным клиентом с официальным `api_id`, поэтому такие аккаунты живут
дольше и допускают больше действий. Формат `session + json` стандарта не имеет:
каждый продавец регистрирует аккаунты как хочет, часто на своих `api_id`, и
такие аккаунты умирают быстрее. Так что tdata — не альтернативная ветка
загрузки, а та, которую стоит предпочитать.

## Согласованные решения

| Вопрос | Решение |
|---|---|
| Где загрузка | Вкладка «Аккаунты» кампании, та же кнопка «Загрузить файлы» |
| Что принимаем | `.zip` (в дополнение к `.json`/`.session`) |
| Раскладка внутри архива | Папка `tdata` ищется рекурсивно, на любой глубине |
| Много аккаунтов | Много архивов за раз **и** один архив со всеми папками |
| Мультиаккаунт в одной tdata | Забираем все аккаунты из неё |
| Дубли | Пропускаем по **всему порталу**, с указанием кампании |
| Конвертация | Внутри портала, офлайн, `@mtcute/convert` |
| Имя аккаунта | Имя папки, в которой лежит `tdata` (у партии atol — `246630983`) |
| `api_id` / `api_hash` | Официальные Telegram Desktop: `2040` / `b18441a1ff607e10a989891a5462e627` |

## Конвертация: офлайн и без нового входа

Ключ авторизации берётся из `tdata` как есть — это то же, что `UseCurrentSession`
в `opentele`. К Telegram при загрузке не подключаемся вовсе: аккаунт не видит
нового устройства, в его списке сеансов ничего не появляется, повода для
подозрений не возникает.

Технически: `@mtcute/convert` (MIT, 118 КБ) читает `key_datas`, вычисляет
локальный ключ, расшифровывает блок авторизации и отдаёт `authKey` (256 байт),
номер и адрес главного DC и `userId`. Из этого собирается строка сессии в том же
формате, которым портал уже пользуется — тем же байтовым раскладом, что и
`sqliteBufferToSessionString` в `app/src/lib/telegram/sessionUtils.ts`
(`dc_id` + IP + порт + ключ, в base64 с префиксом `1`).

Библиотека по умолчанию тянет крипту из `@mtcute/node`, а тот — нативный
`better-sqlite3`. В образ портала это тащить незачем: `Tdata.open` принимает
свою реализацию крипты, и нужный ей минимум (`sha1`, `sha256`, `pbkdf2`,
`createHash`, AES-IGE) закрывается обёрткой над `node:crypto`. AES-IGE в Node
нет как режима — он собирается из `aes-256-ecb` двумя цепочками XOR, около
тридцати строк.

Проверено на боевой партии: 20 папок из `G:\atol_акки`, все 20 прочитались,
20 уникальных `userId`, 42 мс на аккаунт.

## Что происходит при загрузке

1. Файлы делятся по расширению: `.zip` идёт в новую ветку, `.json`/`.session` —
   в существующую. Кнопка и ручка API остаются одни и те же.
2. Архив читается в память, на диск ничего не пишется. Из него берутся только
   служебные файлы `tdata` (`key_data*`, `<16 hex>*`, `map*`) — они занимают
   единицы килобайт, поэтому кэш и медиа из полной папки Telegram Desktop
   просто не грузятся. Раз портал ничего не пишет, подмена путей внутри архива
   (`zip slip`) невозможна по построению.
3. В дереве архива ищутся все папки с файлом `key_data*` — это и есть `tdata`.
   Глубина вложенности не важна: у партии atol это `<номер>/tdata`, у другого
   продавца может быть иначе.
4. Из каждой `tdata` читается `keyData.count` и порядок аккаунтов, дальше
   каждый аккаунт конвертируется в строку сессии.
5. Собранные `userId` сверяются с `tg_outreach_accounts` по всему порталу.
   Совпавшие пропускаются с указанием кампании, в которой аккаунт уже есть.
   Дубли внутри самой загрузки тоже отсекаются.
6. Оставшиеся вставляются в `tg_outreach_accounts` кампании.

## Что попадает в базу

| Поле | Значение |
|---|---|
| `session_name` | Имя папки, содержащей `tdata` (если `tdata` лежит в корне архива — имя архива); при нескольких аккаунтах внутри — `<имя>_2`, `<имя>_3` |
| `session_data` | Строка сессии, собранная из `tdata` |
| `session_file_path` | `null` — файла `.session` не существует |
| `tg_user_id` | `userId` из `tdata`, известен ещё до подключения |
| `api_id` / `api_hash` | `2040` / `b18441a1ff607e10a989891a5462e627` |
| `phone` | Пусто |
| `proxy_id` | `null`, назначается оператором как и раньше |

`session_file_path` пустой — это штатное состояние, а не пробел: воркер
(`gramClient.ts`) работает строкой сессии, а SQLite-файл читает лишь как
запасной путь для старого формата.

## Телефон

В `tdata` номера нет — его знает только Telegram. Он приходит в ответе на
`getMe()`, и `accountCheck.ts` его уже читает, но ручка проверки аккаунта
сохраняет из ответа лишь `tg_user_id` и `tg_username`, а телефон выбрасывает.
Добавляем его в сохраняемые поля: иначе у аккаунтов из `tdata` колонка
«Телефон» останется пустой навсегда.

Отдельного автоподключения после загрузки не делаем. Аккаунт без прокси пошёл
бы в Telegram с IP прод-сервера — этого нельзя допускать даже разово.
Имя, юзернейм и телефон подтягиваются существующей кнопкой «Проверить», когда
оператор уже раздал прокси.

## Ошибки

Отчёт возвращается построчно, по именам файлов: сколько добавлено, что
пропущено как дубль (и в какой кампании аккаунт уже есть), что не прочиталось.
Одна битая папка не отменяет загрузку остальных.

| Случай | Что видит оператор |
|---|---|
| `tdata` под локальным паролем или битая | «Папка под локальным паролем Telegram либо повреждена — снимите пароль в Telegram Desktop и переупакуйте» |
| В архиве нет `tdata` | «В архиве не найдена папка tdata» |
| Аккаунт уже в портале | «Пропущен: уже загружен в кампанию "…"» |
| Архив не читается | Текст ошибки распаковки с именем файла |

Пароль опознаётся по ошибке библиотеки `Failed to decrypt, invalid password?` —
она же прилетает и на повреждённом `key_data`, поэтому текст для оператора
называет обе причины.

Локальный пароль в первой версии не поддерживаем: у партий, с которыми
работают продажи, его нет, а поле для ввода пароля к чужому архиву — лишний
способ ошибиться. Библиотека это умеет, добавить можно позже.

Архивы, внутри которых лежат `.session` + `.json` вместо `tdata`, не
поддерживаем: такие файлы грузятся как раньше, без архива.

## Чего решение не лечит

Дедуп ловит повторную заливку в портал, но не копию `tdata`, оставшуюся у
продавца или в другом софте. Одним ключом с двух сторон — это `AUTH_KEY_DUPLICATED`
и порванная сессия, тот самый сценарий, из-за которого за две недели осыпалось
около 50 аккаунтов. Показывает такие случаи проверка аккаунта (колонка «чужие
сеансы», миграция `20260810_0001`), а не загрузчик.

## Разбиение кода

Разбор `tdata` — отдельный модуль `app/src/lib/telegram/tdata.ts` рядом с
существующим `sessionUtils.ts`: крипто-обёртка, поиск папок `tdata` в дереве,
конвертация в строку сессии. Ручка загрузки его только вызывает.

Ручка `app/src/app/api/tools/tg-outreach/accounts/bulk-files/route.ts` сейчас
одной функцией разбирает файлы, парсит JSON, вставляет строки и грузит файлы в
хранилище. Добавлять третью ветку внутрь неё нельзя — разведём разбор входа
(`.zip` против пар `.json`/`.session`) и вставку в базу.

## Тесты

Фикстура генерируется синтетически: `@mtcute/convert` умеет и писать `tdata`,
поэтому тест создаёт папку из выдуманного ключа и читает её обратно. Живые
ключи боевых аккаунтов в репозиторий не попадают ни в каком виде.

Покрываем: круговой прогон «строка сессии → `tdata` → строка сессии»,
мультиаккаунтную `tdata`, поиск `tdata` на разной глубине, отказ при `zip slip`
и при слишком большом архиве, отсев дублей (и по базе, и внутри одной загрузки),
раскладку файлов по веткам разбора.
