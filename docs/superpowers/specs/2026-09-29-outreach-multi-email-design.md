# Автоаутрич: до трёх проверенных почт на компанию — дизайн

Дата: 29.09.2026. Ветка: `dmitriy_kuladmed_new`. Касается обоих автоаутричей (EN и RU).

## Зачем

Сейчас у компании в работе ровно одна почта. `findAndVerifyCompanyEmail`
(`lib/outreachEmail/findAndVerify.ts`) идёт по списку адресов с сайта в порядке приоритета
и останавливается на первом, который не `invalid`. Сайт при этом даёт в среднем больше
двух адресов — остальные даже не проверяются.

## Решения пользователя

- Проверяем больше найденных адресов, в работу — **до 3 адресов со статусом OK** в порядке
  приоритета.
- OK нет, а домен catch-all — **один лучший адрес**, как сейчас.
- Ответ, «не пишите», отбой — останавливают **только свой адрес**; остальные адреса компании
  продолжают цепочку.
- Делаем **для EN и RU**.
- (Предложено и принято) Адреса одной компании пишутся **с одного нашего ящика с разницей
  в сутки**, чтобы три одинаковых письма не пришли в компанию в одну минуту.

## Поиск и проверка

`findAndVerifyCompanyEmail` получает режим «собрать несколько»:
- кандидаты — тем же `opts.pick` по приоритету (EN `pickByPriority`, RU `pickRuEmail`), по одному,
  исключая уже проверенные;
- проверяется **не больше 6 адресов** на компанию (новая константа, env-переопределение
  `OUTREACH_EMAIL_MAX_CHECKS`);
- `ok` копятся, пока их не станет 3 или не кончатся кандидаты/проверки;
- `catch_all` у первого проверенного адреса → домен catch-all (он решается на домен и кэшируется
  в `EmailDomainCache`), дальше не проверяем: результат — один этот адрес, как сейчас;
- `unverified` у первого адреса → как сейчас (EN `needs_review`, RU `doubtful`), один адрес;
  `unverified` после уже найденных OK — проверка останавливается, найденные OK остаются;
- `invalid` — пропуск, как сейчас;
- общий лимит времени на компанию (`COMPANY_TIMEOUT_MS`) прежний: вышло время — берём то, что
  уже подтверждено.

Результат — упорядоченный список 1–3 адресов; первый — «главный» (тот, что выбрали бы сегодня).
Главный адрес по-прежнему пишется в прежние колонки, и всё, что от них зависит (отсевы, сомнения
RU, проверка писем, вариант письма 1), продолжает работать без изменений.

## Данные

Новая колонка в обеих таблицах строк — `emails jsonb not null default '[]'`:
`[{ "email", "verification": "ok"|"catch_all"|"unverified"|"crm_contact", "type", "is_routing" }]`,
главный адрес — первым элементом. `type` — как `email_type` таблицы; `is_routing` — нужен ли
вариант письма 1 «перешлите тому, кто отвечает».
- EN `polza_outreach_companies`: главный — `selected_company_email`, `email_type`,
  `email_verification`; `is_routing = email_type = 'generic_company'`.
- RU `polza_ru_outreach_companies`: главный — `recipient_email`, `email_type`, `is_routing`,
  `email_verification`.
- Старые строки (`emails = []`) читаются как «только главный адрес».

## Письма

Цепочка у компании одна; различается только письмо 1 (лично / общий ящик — шаблон уже содержит
оба варианта: `body_direct` / `body_routing`). Строка хранит готовые письма в `letters`; если
среди её адресов есть оба вида, в `letters` сохраняется и второй вариант письма 1
(`letter1_alt` — тот вид, которого нет у главного адреса). Проверка готовых писем
(`guardLetters` EN, проверка RU) проходит для обоих вариантов; провал любого — строка
на ручную проверку, как сейчас.

`regenerate` (кнопка «Переписать цепочку») пересобирает оба варианта.

## Заливка в «Рассылку»

`lib/outreachSender/upload.ts`:
- строка разворачивается в 1–3 получателя: по адресу из `emails` (или главный, если пусто);
  письмо 1 — вариант по `is_routing` адреса; письма 2–4 — общие;
- стоп-лист — по каждому адресу: запрещённый адрес пропускается, строка без единого разрешённого
  адреса не заливается (как сейчас с одним);
- отметка «залито» (`sender_uploaded_at`, `sender_campaign_id`) — по строке целиком, как сейчас:
  компания получает цепочки один раз; сопоставление «получатель → строка» — по адресу из `emails`
  (сейчас по главному);
- уборка после сбоя (`releaseRows`) снимает отметку со строки, только если ни один её адрес
  не остался в рассылке;
- «уже писали» между запусками — по домену, как сейчас (`loadPreviouslyExported`).

## Одна компания — один ящик, по одному адресу в сутки

Новая колонка `sender_recipients.group_key text null` (+ индекс `(campaign_id, group_key)`).
Заливка аутрича ставит в неё id строки компании; ручные рассылки оставляют `null`, и для них
ничего не меняется.

Планировщик (`lib/sender/planner.ts`) для первого шага получателя с `group_key`:
- если у «соседа» по `group_key` в этой рассылке уже закреплён ящик — берём тот же ящик
  (лимит выбран — ждём, как с закреплённым ящиком);
- если сосед получил первое письмо меньше 24 часов назад — первый шаг откладывается до
  «его отправка + 24 ч»;
- следующие шаги у каждого адреса идут по своему расписанию, как сейчас.

Ответ, отписка, отбой останавливают только свой адрес — логика `applyReply` не меняется.

## Экран и выгрузка

- Строка компании остаётся одной; в ячейке почты — список адресов со статусом каждого
  (EN `PolzaOutreachResults.tsx`, `PolzaOutreachStageModal.tsx`; RU `Results.tsx`, `Stages.tsx`).
- Выгрузки XLSX (EN `export/route.ts`, `PolzaOutreachView.tsx`; RU `export/route.ts`):
  колонки «Почта 2», «Почта 3» со статусами рядом с прежними.
- Статус заливки (`getJobSenderStatus`) считает адреса, а не строки, там где речь об адресах
  («в стоп-листе», «уже в рассылке»).

## Вне объёма

Остановка всех адресов компании по ответу одного (решено: не делаем), поиск новых адресов вне
сайта, больше трёх адресов, изменение порядка приоритета адресов.

## Проверка

Новых тест-файлов не пишем. `npm run typecheck:fast`; существующие тесты `findAndVerify`,
планировщика и заливки, если есть, должны остаться зелёными — при необходимости обновляются.
После выкладки: в запуске видны компании с 2–3 адресами; в «Рассылке» у адресов одной компании
один ящик и первые письма с разницей в сутки.
