# TG-outreach: синхронизация диалогов и пометки авторства — Design Spec

**Date:** 2026-07-22
**Status:** Draft → user review
**Scope:** Три связанные фазы, каждая имеет самостоятельную ценность.

## 1. Цель

Убрать три слепые зоны в текущем tg-outreach:

1. **Слепая зона авторства**: мы не различаем «это сообщение отправил наш воркер», «это отправил tg ninja через тот же аккаунт», «это отправил Егор с телефона». Всё исходящее одинаково = `role: 'assistant'`. AI-логика строит контекст на чужих сообщениях → неадекватные ответы.
2. **Слепая зона «уже прочитанного»**: воркер обрабатывает только диалоги с непрочитанными в ТГ. Если tg ninja / оператор прочитал диалог первым — мы его не увидим никогда.
3. **Слепая зона «до подключения»**: если аккаунт работал через tg ninja месяц ДО того, как мы его завели в Portal, эти диалоги невозможно подтянуть в БД.

## 2. Как сейчас (для контекста)

Основной цикл воркера в `campaignLoop.ts:1622`:
```
for dialog of getDialogs():
  if unreadCount == 0: continue      # <-- слепая зона (2)
  history = getMessages(entity, 20)   # только 20 сообщений
  for msg of history:
    role = msg.out ? 'assistant' : 'user'  # <-- слепая зона (1)
  upsertDialog(messages)              # перезаписывает старое поверх, тег теряется
```

Импорт диалогов при подключении аккаунта или ручной по списку — **не существует** ни в API, ни в UI. Слепая зона (3).

## 3. Дизайн решения — 3 фазы

Порядок важен: каждая следующая полагается на предыдущую.

### Phase 1 — Пометки «наше vs чужое»

**Проблема**: при `client.sendMessage()` мы знаем `sent.id` (Telegram message ID). Никуда не пишем — теряем.

**Решение**:
- Новая таблица `tg_outreach_sent_messages(id, campaign_id, account_id, tg_user_id, tg_msg_id, text, sent_at)`. Каждая отправка — insert.
- В типе `DialogMessage` (JSONB в `tg_outreach_dialogs.messages`) добавляем два опциональных поля: `sent_by?: 'portal' | 'external' | 'unknown'` и `tg_msg_id?: number`.
- При отправке (`campaignLoop.ts:941, 1071, 1199`): пишем в `tg_outreach_sent_messages` **до** пуша в JSONB, и в JSONB кладём `sent_by:'portal'`, `tg_msg_id: sent.id`.
- При парсинге истории (`extractMessagesFromHistory`, строка 510): для каждого исходящего msg — ищем `msg.id` в `tg_outreach_sent_messages`. Найден → `sent_by:'portal'`. Не найден → `sent_by:'external'`.
- Все существующие диалоги в БД: одноразовый бэкфилл через миграцию — вся история → `sent_by:'unknown'` (потому что мы не знаем задним числом).

**Эффект**: AI-логика может отличать «наше» от «чужого» и не строить контекст на чужих ответах. Также появляется полноценная аналитика «сколько мы отправили через кампанию X».

**Изменения в AI-логике** (пока минимальные — можно доработать в отдельной задаче):
- Никаких сразу — только сбор данных. Отдельно, после — включим фильтр: «catch-up отвечает только если последнее наше исходящее = portal или unknown, но НЕ external».

### Phase 2 — Пакетный импорт диалогов по списку

**Проблема**: аккаунт работал через tg ninja/руками до подключения к Portal. Есть список @usernames — нужно затянуть их истории.

**Решение**:
- Новый тип job'а в `tg_outreach_jobs.action`: `import_dialogs` (с `payload jsonb` — список usernames/tg_user_ids).
- API-роут `POST /api/tools/tg-outreach/accounts/[id]/import-dialogs` — принимает `{ usernames: string[], tg_user_ids?: number[] }`, создаёт job, воркер подхватит.
- Воркер (`campaignLoop.ts` — новая функция `handleImportDialogsJob`): для каждого username → `getEntity()` → `getMessages(limit=history_limit)` → `upsertDialog()` в кампанию по умолчанию первую этого аккаунта, всё исходящее помечается `sent_by:'external'` (мы знаем что это точно не мы — импортируем задним числом). Между вызовами — задержка 1-2 секунды (флудвейт).
- UI: в `CampaignAccountsTab` кнопка «Импортировать диалоги» рядом с аккаунтом → модалка с textarea (по одному username на строку) → отправка. Прогресс — через логи + статус job'а.

**Эффект**: Егор может выгрузить из tg ninja список контактов, вставить в Portal, и через 3-5 минут все истории будут в БД.

**Ограничения**:
- Только по прямым username/ID. Если username в tg ninja нет — не подтянется.
- Приватные каналы/группы игнорируются (как и сейчас — только `Api.User`).

### Phase 3 — Автосинк при подключении аккаунта

**Проблема**: при подключении нового аккаунта хочется одним движением загрузить всё, что там уже есть, за последние N дней. Не только по клику юзера.

**Решение**:
- Новое поле `tg_outreach_accounts.initial_sync_state text default 'pending'` (значения: `pending`, `running`, `done`, `failed`).
- Новое поле `tg_outreach_accounts.initial_sync_started_at`, `initial_sync_finished_at`, `initial_sync_stats jsonb`.
- Новое поле в `telegram_settings`: `autosync_days_lookback number default 30`.
- При загрузке аккаунта (`accounts/route.ts` POST и `accounts/bulk-files/route.ts`): после успешного `insert` — auto-enqueue job `autosync_dialogs` (или тот же `import_dialogs` со специальным payload).
- Воркер (`handleAutosyncJob`): `getDialogs(limit=200)` → фильтр `dialog.date >= now - N дней` → для каждого `Api.User` без бота: `getMessages(limit=20)` → `upsertDialog`. Обновляет `initial_sync_stats` (сколько нашли, сколько скачали, сколько ошибок).
- UI: в списке аккаунтов чип «Синхронизация: 45/120» пока идёт, «✅ синхронизирован N дней назад» когда done. Кнопка «Пересинхронизировать» вручную.
- Все исходящие в синкнутых диалогах = `sent_by:'unknown'` (не можем точно знать — до Phase 1 tracking'а или после).

**Эффект**: заведение нового аккаунта в Portal автоматически даёт полную картину «что уже писали с этого номера за последний месяц».

**Ограничения**:
- Первый синк — 1-3 минуты для outreach-аккаунта (50-100 диалогов), это блокирует его участие в основной кампании до завершения (иначе рискуем гоняться за флудвейтами). Отражаем это в UI (чип «в процессе»).
- Если аккаунт был в кампании раньше и что-то есть в `tg_outreach_dialogs` — синк не перезаписывает, только добивает недостающее. Дедуп по (campaign_id, account_id, tg_user_id).

## 4. Что НЕ входит в этот план

- **Автосинк на постоянной основе** (снятие фильтра `unreadCount==0`) — риск для стабильности аккаунтов. Отдельная фича, если понадобится.
- **Импорт из архива tg ninja напрямую** (без ручной выгрузки списка) — требует парсинга их структуры, отдельная тема.
- **Merge истории**: если между 20 старыми сообщениями и 20 новыми — есть gap, мы его не подтянем в этом плане. `history_limit` можно увеличить в настройках кампании, но полный merge — за скоупом.
- **Ретро-разметка старых диалогов**: невозможно достоверно определить «это писал наш воркер полгода назад» без сохранённых message_id. Все `messages` до внедрения Phase 1 → `sent_by:'unknown'`.

## 5. Изменения в существующей системе — критический список

- **Миграции**: 3 новые (одна на фазу).
- **`campaignLoop.ts`**: изменения в `extractMessagesFromHistory` (Phase 1), новые функции для jobs (Phase 2/3). Всё аддитивно, existing behavior не ломаем.
- **UI**: две новые модалки в `CampaignAccountsTab`, один чип-индикатор синка. `page.tsx` уже большой — новые компоненты выделим в отдельные файлы если сильно раздуется.
- **RLS-политики**: `tg_outreach_sent_messages` наследует ту же логику что и `tg_outreach_dialogs` (владелец кампании + shared_read).

## 6. Открытые вопросы для юзера

- **Дефолт `autosync_days_lookback`**: 30 дней ок или сразу поставить 60/90? (Больше = дольше первый синк.)
- **Что делать с ботами при автосинке**: пропускать полностью или заводить в БД со статусом `tg_is_bot=true` (как сейчас в основном цикле)?
- **Приоритет фаз**: делать все 3 сразу или сначала Phase 1, посмотреть — потом остальное?
