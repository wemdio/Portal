# Сигнал «ЦА» (client_segment): замена столбца «Клиенты»

Дата: 2026-06-10
Статус: дизайн согласован, ожидает ревью

## Контекст и проблема

В инструменте «работа с базами» (DatabaseSpreadsheet) есть фича «Сигналы» — обогащение
строк данными, спарсенными с сайта компании. Один из сигналов — «Клиенты»
(`customers`): система пыталась выдернуть со страницы названия брендов-клиентов
(logo wall, разделы «Наши клиенты») эвристикой на cheerio + большим набором
junk-фильтров, с LLM-надстройкой как «добивкой».

Столбец отрабатывает плохо: точный список брендов хрупок (мусорные alt у логотипов,
отрасли вместо брендов, иконки оплаты), покрытие низкое.

## Цель

Столбец сохраняет название **«Клиенты»**, но его содержимое меняется: вместо списка
брендов — короткая формулировка *кого компания обслуживает* (сегмент её клиентов),
2-3 слова. Это смысловой вывод, а не точное
извлечение: модель такое делает устойчивее, потому что сегмент почти всегда понятен
из описания на сайте, даже когда конкретный список логотипов вытащить нельзя.

## Зафиксированные решения (из брейншторма)

1. **Смысл ячейки** — сегмент клиентов компании: отрасль + тип, в пару слов.
   Примеры: «стоматологии», «B2B-стройка», «интернет-магазины», «госзаказчики»,
   «производственные предприятия».
2. **Замена содержимого**: столбец и чекбокс остаются с названием «Клиенты», но наполняются
   сегментом ЦА вместо списка брендов. Старый сигнал-список уходит из выбора.
3. **Источник результата — только LLM.** Старого эвристического извлекателя клиентов
   как источника значения быть не должно. Никаких запасных «ручных» путей и пост-фильтров
   списков.
4. **Модель — `gpt-4o-mini`** (через тот же requesty-роутер, что и остальные сигналы).
5. **Вход модели — текст сайта + подписи логотипов** (alt-тексты). Клиентов на b2b-сайтах
   часто видно только логотипами, поэтому подписи к ним передаём модели как материал
   (это подготовка входа, НЕ старый «извлекатель результата»).
6. **Guard**: если по сайту сегмент определить нельзя — прочерк (контракт «нет данных →
   DASH»), модель не выдумывает.

## Поведение (функционально)

Для одной строки (одного URL):
1. Загружается главная страница; если находятся — подстраницы «О компании» (`about`) и
   «Кейсы/Клиенты» (`cases`). (Механизм поиска подстраниц уже существует и переиспользуется.)
2. Со страниц собирается материал для модели: видимый текст + подписи логотипов (alt).
3. Материал отправляется в `gpt-4o-mini` с инструкцией вернуть сегмент клиентов компании
   в 2-3 слова на русском.
4. Ответ нормализуется и пишется в ячейку «ЦА». Если модель/материал ничего не дали —
   прочерк.

Расход на LLM возникает только когда сигнал «ЦА» включён (как у других LLM-сигналов).

## Компоненты

### 1. Новый extractor `clientSegmentExtractor.ts`
Единственный источник значения столбца. Экспортирует `extractClientSegment(mainHtml,
aboutHtml, casesHtml): Promise<string>`.

- **Сбор входа** (внутри модуля, без обращения к legacy customers-коду):
  - видимый текст страниц (strip тегов `script/style/...`, схлопывание пробелов) с главной
    + about + cases, с бюджетом по символам;
  - подписи логотипов: alt-атрибуты `<img>` (приоритетно из секций-кандидатов «клиенты/
    партнёры/logos», но допустимо взять все нетривиальные alt) — отдельным блоком в промпте.
  - Порядок: сперва наиболее релевантное (cases/секции клиентов), затем общий текст —
    под контекст-bias модели.
- **LLM-вызов**: endpoint requesty (как у существующих сигналов), модель из
  env `OPENROUTER_CLIENT_SEGMENT_MODEL` (дефолт `openai/gpt-4o-mini`), ключ
  `OPENROUTER_SIGNALS_API_KEY || OPENROUTER_BRIEF_API_KEY`. `temperature: 0`,
  `response_format: json_object`, ответ `{"segment": "..."}`, `max_tokens` ~ 60.
- **Guard**: если материала почти нет (пустой текст и нет alt) — LLM не вызываем, возвращаем
  `''`. Если модель вернула пусто/воду — `''`.
- **Нормализация**: trim; обрезка по длине (~40 символов); единый вид «B2B/B2C/B2G»;
  без завершающей точки.
- **Надёжность**: best-effort, никогда не бросает исключение — при ошибке/timeout/429
  возвращает `''`.

Черновик system-prompt (RU):
> Ты определяешь, КОГО обслуживает эта компания (сегмент её клиентов), по содержимому её
> сайта. Верни JSON `{"segment": "..."}` — 2-3 слова на русском: отрасль и тип клиентов.
> Примеры: «стоматологии», «B2B-стройка», «интернет-магазины», «госзаказчики»,
> «производственные предприятия», «рестораны и кафе».
> Это НЕ описание самой компании и не её услуги — именно её клиенты.
> Если по сайту понять нельзя — верни `{"segment": ""}`. Не выдумывай. Только JSON.

### 2. Интеграция в конвейер (`websiteSignalProcessor.ts`)
- Добавить ключ `client_segment` в обработку: блок `if (extractors.includes('client_segment'))`
  берёт `main.html`, `subpageHtml.about`, `subpageHtml.cases` → `extractClientSegment(...)`
  → `out.client_segment`.
- **Удаляется** блок `if (extractors.includes('customers'))` (строки ~336-368) и импорт/вызов
  `llmExtractCustomers` — это и есть «старый подход как источник столбца».

### 3. Типы и UI-конфиг (`extractors/types.ts`)
- `ExtractorKey`: добавить `'client_segment'`. `ExtractedData`: добавить `client_segment?: string`.
- `EXTRACTOR_LABELS.client_segment = 'Клиенты'` (по решению заказчика название столбца
  не меняется).
- `EXTRACTOR_TO_SUBPAGES.client_segment = ['cases', 'about']`.
- `ALL_EXTRACTOR_KEYS`, `EXTRACTOR_GROUPS` (группа «Клиенты и кейсы»), `BUILTIN_PRESETS`
  (outreach/audit/all): заменить `customers` → `client_segment`.

### 4. Рендер ячейки (`formatExtraValue.ts`)
- Добавить `case 'client_segment'`: строка/DASH (как `stack`/`profile`).
- `case 'customers'` оставить — чтобы уже существующие выгрузки со старым полем `customers`
  в `result_text` продолжали рендериться.

### 5. UI и сборка джобы
- В местах, где набор сигналов превращается в колонки и заголовки
  (`SignalEnrichmentModal.tsx`, `DatabaseSpreadsheet.tsx`,
  `api/enrich/website/jobs/route.ts`, `websiteEnrichmentWorker.ts`): заменить ссылки на ключ
  `customers` → `client_segment`; заголовок колонки берётся из `EXTRACTOR_LABELS`.
- Кастомные пресеты пользователя (localStorage), где сохранён снятый ключ `customers`:
  фильтровать неизвестные ключи при загрузке, чтобы не падало.

### 6. Что НЕ трогаем
- `customersExtractor.ts` (`extractCustomers`) остаётся в кодовой базе: от него зависит
  отдельный сигнал `enterprise_logos` (вызывает его напрямую). Это вне scope.
- `llmCustomersExtractor.ts` использовался только для столбца customers → удаляется
  (после проверки, что больше нигде не импортируется).

## Поток данных
URL → fetch главной (+ about, cases) → сбор материала (текст + alt) → gpt-4o-mini →
`{"segment"}` → нормализация → `out.client_segment` → `result_text` (JSON) →
`formatExtraValue` → ячейка «ЦА» (или DASH).

## Обработка ошибок
Извлечение best-effort, как все LLM-сигналы: любой сбой (нет ключа, timeout, 429, кривой
JSON) → `''` → DASH в ячейке. Строку/джобу не роняет. Падение fetch страницы — общий путь
ошибок конвейера (как сейчас).

## Тестирование
- Юнит на `extractClientSegment` с моком fetch к requesty:
  - пустой материал → LLM не вызывается, `''`;
  - валидный текст/alt → ожидаемый сегмент;
  - «вода»/пустой ответ модели → `''`;
  - нормализация формата (длина, точка, B2B).
- Юнит на `formatExtraValue('client_segment', …)` — строка/DASH.
- Регресс: старое поле `customers` в `result_text` всё ещё рендерится; `enterprise_logos`
  не сломан.

## Вне scope (YAGNI)
- Фиксированный словарь сегментов — нет, свободная короткая формулировка гибче.
- Многоязычность вывода — нет, только RU.
- Новая колонка в БД — не нужна (всё в `result_text` JSON и в state).
- Переписывание customers-парсинга / enterprise_logos — нет.

## Открытые вопросы
Нет. Заголовок столбца — «Клиенты» (по решению заказчика).

## Заметка про старые данные
Уже заполненные ранее таблицы со старым списком брендов в поле `customers` не
перезаписываются и продолжают рендериться (case `customers` в `formatExtraValue`
сохраняется). Новые запуски сигнала «Клиенты» пишут сегмент в новое поле
`client_segment`. Прочерк в новой ячейке — только когда модель не смогла определить
сегмент по сайту, а не «по умолчанию».
