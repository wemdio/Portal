# Дашборд первички — дизайн

Дата: 2026-07-30
Статус: согласован, готов к плану реализации
Объём этой спеки: **этап 1**. Этапы 2 и 3 описаны рамочно и получают свои спеки.

## Задача

Страница портала с метриками первичных продаж: лиды с источником и стоимостью,
встречи, договоры, средний цикл, средний чек, оборот. Диапазон дат, фильтр по
каналам, группировка по дням / неделям / месяцам.

**Первичка** — воронка AMO «Воронка - новые лиды» (`pipeline_id = 7670334`):
первая продажа новому клиенту. Остальные три воронки в AMO мертвы — последняя
активность в 2024–2025.

Задача парная к [дашборду расходов](./2026-07-30-expenses-dashboard-design.md),
который делается отдельно на тех же банковских данных.

## Что показали данные

Числа собраны запросами к боевой БД 2026-07-30. Они — основание для решений ниже.

**Пять каналов покрывают 38% потока.** Из 1566 сделок воронки новых лидов,
созданных в 2026 году, **969 (62%) не попадают ни в один из пяти каналов**
`detectSummaryChannel`. Причина не в ошибке, а в замысле: канал ставится только
по явной метке «Контур = Маркетинг» (133 сделки) либо по одному из шести значений
«Источник». Всё остальное — Сайт (336), Лидскан (321), TG-посев, Сарафан,
Конференция, Холодная база, SEO — остаётся без канала. Отчёт продаж это устраивает,
он сознательно считает только размеченное. Дашборд с надписью «не определён»
у двух третей строк — нет.

Само поле «Источник» заполнено у ~95% сделок и содержит 21 приличное значение.
Данные есть; нет правила свёртки.

Поле «Подысточник» — свободный текст, ~180 уникальных значений вида «сам в тг»,
«конфа 27.03», ссылка на Google-таблицу. Для агрегатов непригодно.

**Истории переходов нет.** `amo_events` пуста, синк не написан. Известны только
текущий этап сделки и даты `created_at` / `closed_at`.

**Привязка денег к сделкам по ИНН работает.** Из 168 приходов 2026 года
**113 (67%) матчатся** на сделку AMO по ИНН плательщика; ИНН заполнен у 648 из 650
приходов. Матчинг по названию компании бесполезен — совпал 1 приход из 168
(в банке полное юрлицо, в AMO как записал менеджер). Непривязанными остаются
55 платежей на 2.59 млн ₽ — 16% денег, примерно один платёж в неделю на ручную
разметку.

**Банк и AMO дают разные числа, и это нормально.** За 2026: AMO — 96 выигранных
сделок на 16.24 млн ₽, банк — 168 приходов на 16.42 млн ₽. Суммы сошлись, счёт
операций отличается вдвое: в банке каждый транш отдельной строкой, плюс вторичка
от старых клиентов. Следствие: **средний чек по банку без привязки к сделке
посчитать нельзя** — получится средний транш.

**Этапы воронки** (`amo_statuses`, воронка новых лидов):

| sort | Этап |
|---|---|
| 40 | Квалифицированный лид |
| 50 | Назначена встреча |
| 70 | Встреча проведена + КП отправлено |
| 100 | Отправлен счет |
| 110 | Согласование договора |
| 10000 | Успешно реализовано (`status_id = 142`) |
| 11000 | Закрыто и не реализовано (`status_id = 143`) |

## Принятые решения

| Решение | Выбор |
|---|---|
| Что такое первичка | Воронка «Воронка - новые лиды» целиком |
| Разбивка по источникам | Справочник «источник → канал», редактируемый в портале. Не пять каналов отчёта продаж |
| Даты этапов | Синк истории переходов из AMO. Не когортный подсчёт |
| Что такое «лид» | **Все** сделки, созданные в периоде, включая закрытые в минус и лид-магниты |
| Оборот и средний чек | Реальные поступления в банк, привязанные к сделке по ИНН |
| Расходы для стоимости лида | Из парной задачи по расходам. Здесь только маппинг вендор → канал |
| Графики | `recharts` — то же решение, что в спеке расходов |
| Доступ | Схема из спеки расходов: nav-вкладка + серверный гард + RLS без чтения с клиента |
| Порядок | Три этапа, после каждого — работающая страница |

### Почему «лид» считается иначе, чем в отчёте продаж

Отчёт продаж исключает из воронковых метрик мёртвые сделки (`status_id = 143`)
и лид-магниты (сделки с именем на «Бот:»). Для месячного отчёта это разумно —
он показывает живую работу.

Для дашборда это ломает главное свойство отчётности: **прошлое должно быть
неподвижным**. Если майскую сделку закрыли в минус в июле, число «лидов в мае»
уменьшится задним числом, и человек, который смотрел дашборд в июне, увидит
другую цифру. Поэтому лиды считаются все, а «сколько из них дожило до квала» —
отдельная линия на том же графике. Лид-магниты — отдельной полосой, а не
молча выброшены.

Расхождение с отчётом Егора здесь **ожидаемое и объяснимое**. Оно должно
объясняться ровно этими двумя пунктами и ничем больше — это проверяется тестом
сверки (см. «Тесты»).

## Границы: эта задача и парная

Дашборд расходов делает: снятие фильтра «только приход» в `bank_tochka.py` и
`bank_tbank.py`, Brocard, ручной ввод трат, курсы ЦБ, `expense_vendors`,
`expense_rules`, `expense_classifications`, `expenses_v`, очередь разметки.

Дашборд первички **ничего из этого не делает и не дублирует**. На этапе 3 он
добавляет одну таблицу поверх чужой разметки: вендор → канал продаж. Разметка
расходов идёт по оси «вендор и категория» (Instantly → tools, Яндекс.Директ →
marketing); для стоимости лида нужна ось «канал продаж» (Instantly → Аутрич,
Яндекс.Директ → Маркетинг). Это разные оси, и вторая выражается через первую
таблицей на два столбца.

**Зависимость:** этап 3 не может начаться раньше, чем в парной задаче закрыта
фаза «Данные». Этапы 1 и 2 от неё не зависят.

**Общий файл:** обе задачи добавляют индексы на `bank_transactions`. Конфликт
разрешается порядком миграций, пересечения по коду нет — парная задача правит
дебет, эта читает кредит.

# Этап 1

## Определения метрик

Все окна считаются в `Europe/Moscow`; неделя начинается с понедельника. База живёт
в UTC, и без явного приведения понедельник сдвинется на три часа.

**Лиды** — сделки воронки новых лидов с `created_at` в окне. Разрез по значению
поля «Источник», свёртка в канал по справочнику. Без исключений по статусу.
Дополнительные ряды на том же графике: «из них дошли до квала» (первая дата
достижения sort ≥ 40 — любая, не обязательно в окне) и «из них лид-магниты».

**Встречи** — сделки, впервые достигшие sort ≥ 70 («Встреча проведена + КП»),
дата достижения в окне.

**Договоры** — то же для sort ≥ 110 («Согласование договора»).

Ключевая деталь: считается **не переход в конкретный статус**, а первый момент,
когда сделка оказалась на этапе не ниже порога. Менеджеры проскакивают этапы —
двигают сделку из «Первый контакт» сразу в «Отправлен счет». Буквальный подсчёт
переходов в статус 70 такие встречи потеряет.

**Средний цикл** — среднее число дней между `created_at` сделки и датой
достижения `status_id = 142`, по сделкам, оплаченным в окне. Показывается вместе
с медианой: распределение циклов длиннохвостое, одна сделка на 400 дней утащит
среднее.

**Фильтр по каналам** применяется ко всем метрикам одинаково — через канал сделки
из справочника.

## Архитектура данных

Принцип наследуется из `20260706_0003_create_external_sync_tables.sql`: сырьё
остаётся честным, трактовки живут отдельно. Ночной синк переливает сырьё и
физически не может затереть ручную разметку.

### `lead_source_channels` (новая)

Справочник свёртки. `source` (значение поля «Источник» AMO, нормализованное:
trim + lower + `ё→е`), `channel`, `display_name`, `sort_order`, `updated_by`,
`updated_at`. Уникальный индекс по `source`.

`channel` — фиксированный список через CHECK: `marketing`, `smm`, `outreach`,
`partners`, `tg_outreach`, `inbound`, `referral`, `events`, `unassigned`.
Расширяется миграцией.

Первичное наполнение — только бесспорное: `email outreach` и `аутрич` → outreach,
`партнер` → partners, `telegram outreach` → tg_outreach, `smm` и
`личный бренд (инст /ютуб)` → smm. Спорное (Лидскан, Сайт, Сарафан, Конференция,
SEO, Холодная база, TG-посев — 969 сделок за 2026) заводится со значением
`unassigned` и раскладывается Егором с Никитой через UI до запуска.

Сделка без заполненного «Источник» (~5%) и источник, которого нет в справочнике,
попадают в `unassigned` и видны отдельной строкой со счётчиком.

Сделки с «Контур = Маркетинг», но без «Источник», относятся к `marketing`:
явная ручная метка команды приоритетнее пустого поля. Это единственное правило
поверх справочника, и оно живёт в коде расчёта, а не в данных.

### `amo_events` (существующая, наполняем)

Схема уже есть: `amo_deal_id`, `event_type`, `changed_at`, `changed_by`,
`from_value`, `to_value`, `payload`, уникальный ключ
`(amo_deal_id, event_type, changed_at)`. Пишем события смены этапа.

Уникальный ключ делает повторный прогон синка идемпотентным.

### `amo_lead_stage_dates` (новая)

Производная таблица: на сделку — `amo_deal_id` (PK), `first_qualified_at`,
`first_meeting_at`, `first_invoice_at`, `first_contract_at`, `won_at`,
`history_complete boolean`, `computed_at`.

Пересчитывается после каждого синка событий. Правило «проскок этапа
засчитывается» живёт здесь в одном месте; страница читает готовые даты и не
занимается археологией на каждый клик.

`history_complete = false` — для сделок, созданных раньше глубины, на которую
AMO отдаёт события. Такие сделки исключаются из метрик встреч, договоров и цикла,
а не считаются нулём (см. «Ошибки»).

## Изменения в синке

`services/portal-external-sync/`:

Добавляется **один** источник — `sources/amo_events.py`, класс `AmoEventsSync`,
внутри две фазы:

1. **Забор событий.** `GET /api/v4/events` с фильтром по типам смены этапа,
   страницами. Инкрементально: от времени последнего успешного прогона минус
   нахлёст 2 суток. Upsert в `amo_events`.
2. **Пересчёт дат.** `amo_lead_stage_dates` из `amo_events` + `amo_statuses`,
   в том же прогоне, сразу после первой фазы.

В `main.py` источник встаёт в `SOURCES` строго после `AmoSync` — ему нужны
свежие `amo_statuses` для порогов `sort`.

Именно один источник, а не два — из-за CHECK-констрейнта на
`external_sync_runs.source` (`…_0003_…sql:183`): он перечисляет допустимые имена,
и незарегистрированное имя роняет **логирование** прогона, а не сам прогон.
То есть отвалилась бы ровно наблюдаемость, самым неочевидным способом. Имя
`amo_events` в констрейнте уже разрешено, поэтому при одном источнике миграция
на констрейнт не нужна вовсе. Пересчёт дат — не отдельный внешний источник,
а завершение той же работы, так что дробить нечего.

**Разовый бэкфилл** — скрипт `app/scripts/`, тянет события за всю доступную
глубину. Прогон тяжёлый, запускается руками, не в штатное окно.

### Спайк до кода

Первым делом — проверить на живом API, за какой период AMO отдаёт события смены
этапа, и все ли переходы в выдаче. Результат меняет обещание пользователю
(«данные с такой-то даты»), но не архитектуру. Узнать это в первый день, а не
в последний.

Если глубина окажется меньше года — этап 1 не отменяется: страница честно
показывает доступный период, а `history_complete = false` отсекает остальное.

## Код метрик

Новая папка `app/src/lib/firstSales/`:

- `sourceChannels.ts` — чтение справочника, нормализация значения «Источник»,
  правило «Контур = Маркетинг»;
- `metrics.ts` — чистые функции расчёта по строкам + обёртки с запросами;
- `buckets.ts` — границы дней / недель / месяцев в МСК, раскладка по корзинам.

Чистая часть отделена от запросов — так же, как в `salesReport/metrics.ts`, чтобы
считать тесты на фикстурах без БД.

**Отчёт продаж эта задача не трогает.** `salesReport/` и `leadsReport/` остаются
как есть и продолжают сходиться с ручным отчётом. Какое-то время правило «что
такое канал» живёт в двух местах — это осознанный долг, зафиксированный в
«Открытых вопросах», а не недосмотр. Ломать сходимость с ручным отчётом ради
единообразия кода сейчас — плохая сделка.

## UI

Страница `/analytics/first-sales`, компоненты в `components/first-sales/`,
графики на `recharts`.

**Шапка** — период (этот месяц / прошлый / 30 дней / квартал / год / произвольный),
переключатель группировки день–неделя–месяц, мультифильтр по каналам.

**KPI-строка** — лиды, встречи, договоры, средний цикл (среднее и медиана) за
период, у каждого Δ к предыдущему периоду того же размера. Отдельным блоком —
«без канала: N сделок», и рядом дата последнего успешного синка.

Оба служебных показателя стоят в одном ряду с метриками, а не в углу: пока
«без канала» большое, остальным числам верить нельзя.

**График по времени** — bar с шагом по выбранной группировке, стек по каналам.
Поверх — линии «дошли до квала», «встречи», «договоры».

**Разбивка по источникам** — горизонтальные бары и таблица под ними: источник,
канал, лиды, доля, дошли до квала, встречи, договоры, Δ к прошлому периоду.
Клик по строке раскрывает сделки со ссылками в AMO — чтобы можно было проверить,
откуда взялась цифра.

**Справочник источник → канал** — отдельный экран: слева источники из AMO с числом
сделок, справа выбор канала. Источники в `unassigned` — сверху, с подсветкой.

Новые строки интерфейса заводятся в `lib/globalTranslations.ts` парами ru→en,
как принято в проекте.

## Доступ

Схема берётся из парной спеки расходов — два соседних дашборда обязаны
закрываться одинаково.

**Навигация.** В `ALL_NAV_TAB_IDS` добавляется `nav-first-sales`, в `navItems` —
пункт «Первичка». Nav-вкладки по умолчанию выключены, поэтому вкладка невидима,
пока её не выдали точечно в модалке пользователя. Флаг `adminAlwaysOn` — как у
`nav-expenses`.

**Данные.** `lead_source_channels` и `amo_lead_stage_dates` получают RLS без
select-политики для `authenticated`; читает серверный код под `service_role`.
Все запросы идут через API-роуты, каждый первым делом зовёт
`requireFirstSalesAccess`: роль `admin` → доступ; иначе — строка
`user_tool_visibility(tool_id='nav-first-sales', enabled=true)`.

**Порядок с парной задачей:** обе вводят `adminAlwaysOn` в `NavTabConfig`. Кто
первым — тот и добавляет флаг; вторая задача его переиспользует. В плане это
отмечается явной проверкой, чтобы не получить два конфликтующих изменения одного
типа.

## Ошибки и крайние случаи

**История глубже, чем отдаёт AMO.** Сделки с `history_complete = false`
исключаются из встреч, договоров и цикла. Страница пишет «данные о переходах —
с такого-то числа», периоды раньше показывают прочерк. **Не ноль**: ноль читается
как «встреч не было» и является худшим видом вранья в отчётности.

**Синк упал ночью.** Дата последнего успешного прогона (`external_sync_runs`)
выводится в KPI-строку. При отставании больше суток — предупреждающая плашка.
Тихо устаревшие цифры хуже отсутствующих.

**Источник без канала, сделка без источника.** Отдельная строка `unassigned`
со счётчиком в KPI и в разбивке. Ничего не прячем.

**Сделка достигла этапа до окна.** Метрика привязана к дате первого достижения;
сделка, дошедшая до встречи в июне, в июльское окно не попадает, даже если в июле
она двигалась дальше. Это осознанно: иначе одна сделка считается несколько раз.

**Пустой период.** Ноль сделок — валидный ответ, график рисует пустые корзины,
а не схлопывается.

**Часовые пояса.** Все границы — в МСК. Проверяется тестом на переходе через
границу месяца.

## Тесты

Jest (`app/tests`), по образцу `app/tests/lib/salesReport/metrics.test.ts`:

- свёртка источника в канал: нормализация регистра и `ё`, неизвестный источник →
  `unassigned`, пустой источник → `unassigned`, «Контур = Маркетинг» без источника
  → `marketing`;
- «дошёл до этапа»: проскок этапа засчитывается, откат назад не сбрасывает первую
  дату, повторный проход не считается дважды;
- границы группировки день / неделя / месяц в `Europe/Moscow`, включая переход
  через границу месяца и начало недели с понедельника;
- средний цикл: медиана и среднее на длиннохвостом распределении, пустая выборка
  не даёт `NaN`;
- `history_complete = false` исключает сделку из встреч / договоров / цикла, но
  оставляет в лидах;
- идемпотентность синка событий: повторный прогон не плодит строк;
- гард доступа: админ проходит; пользователь с `enabled=true` проходит;
  без строки и с `enabled=false` — 403;
- Δ к предыдущему периоду для периодов разной длины.

**Сверка с ручным отчётом.** Отдельная проверка вне Jest: прогнать дашборд за
июль 2026 и сравнить с отчётом Егора. Расхождения обязаны объясняться ровно двумя
принятыми решениями — мёртвые сделки и лид-магниты считаются иначе. Любое третье
расхождение — баг, а не особенность.

# Этапы 2 и 3 — набросок

Каждый получает свою спеку. Здесь — только рамка и известные риски.

**Этап 2. Деньги.** Привязка приходов `bank_transactions` к сделкам AMO по ИНН
плательщика: 67% автоматически, остальное — экран ручной доразметки (≈55 платежей
в год). Таблица привязок отдельно от сырья, ручная привязка не перезаписывается
пересчётом. Даёт оборот первички и средний чек.

Известные сложности: транш против сделки (одна сделка — несколько платежей);
отделение вторички от первички (плательщик уже был клиентом); ИНН заполнен только
у 274 сделок, для остальных матч идёт от банка к сделке и может не найтись.
Существующая пустая таблица `attribution_payment_project` привязывает платёж к
проекту, а не к сделке — надо решить, расширять её или заводить свою.

**Этап 3. Стоимость лида.** Таблица `vendor_sales_channel`: вендор из
`expense_vendors` парной задачи → канал продаж. CPL = расход канала за период,
делённый на лидов канала за тот же период.

Зависимость: начинается после фазы «Данные» парной задачи. Открытый вопрос —
что делать с расходами, которые не относятся ни к одному каналу (ФОТ продаж,
общие инструменты): включать ли их в CPL и по какому правилу разносить.

## Открытые вопросы

1. **Раскладка спорных источников по каналам** — Лидскан, Сайт, Сарафан,
   Конференция, SEO, Холодная база, TG-посев, Телеграм, ТГ-канал, ТГ Бот.
   969 сделок за 2026. Решают Егор и Никита, до запуска, через UI справочника.
2. **Глубина истории в AMO** — спайк прогнан на проде 2026-07-30.

   **Форма события подтверждена:** id статуса лежит в
   `value_before[0].lead_status.id` и `value_after[0].lead_status.id`, рядом —
   `pipeline_id`. Плюс `entity_type = 'lead'`, `entity_id`, `created_at` в unix,
   `created_by`. Разбор в синке пишется по факту, а не по догадке.

   Аккаунт отдаёт 16 типов событий; нужный называется именно
   `lead_status_changed`.

   **Глубина:** события есть в окнах 2024-06, 2025-06 и 2026-06; в 2023-07 нет.
   При этом сам аккаунт AMO начался в январе 2024 — самая старая сделка в
   `amo_leads` от 2024-01-15. То есть отсутствие событий в 2023 объясняется
   отсутствием аккаунта, а не удержанием AMO. Точная нижняя граница уточняется
   добивочной пробой по началу 2024; если события найдутся с января,
   `history_complete` будет true практически у всех сделок и прочерков на
   дашборде не будет вообще.

   Попутно: образец события оказался переходом **в статус 143**. Терминальные
   статусы в событиях реально встречаются — верхняя граница `sort < 10000`
   во view защищает от живого случая, а не от гипотетического.
3. **Перевод отчёта продаж на справочник и на историю этапов** — зафиксированный
   долг. После него уйдёт двойное определение канала и отчёт начнёт считать
   встречи по датам, а не когортно. Отдельная задача, требует согласования с
   продажами: цифры в привычном отчёте изменятся.
4. **Список каналов** — предложен `marketing` / `smm` / `outreach` / `partners` /
   `tg_outreach` / `inbound` / `referral` / `events` / `unassigned`. Нужен
   подтверждающий взгляд от продаж вместе с пунктом 1.
