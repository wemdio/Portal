# Расхождение пятничного отчёта продаж с ручным (24.07–31.07)

Дата расследования: 03.08.2026. Источник: прод-БД (`amo_leads`, `amo_events`,
`amo_statuses`, `meeting_deal_links`, `external_sync_runs`).

## Проблема

Автоотчёт `leadsReportSummaryCron` за 24.07–31.07 и ручной отчёт Егора за
25.07–31.07 разошлись по всем пяти каналам.

## Причина 1 (главная) — отчёт посчитан по данным суточной давности

`amo_leads` синкается **раз в сутки в 13:30 UTC (16:30 МСК)**, отчёт бежит в
**14:00 UTC (17:00 МСК)**. 31.07 синк упал:

```
external_sync_runs: source=amo_leads, started_at=2026-07-31T13:30:01Z,
status=error, error="Server disconnected without sending a response."
```

Последний удачный прогон — `2026-07-30T17:15:13Z` (20:15 МСК четверга). Отчёт
считался по снимку, устаревшему на ~21 час: четверг после 20:15 и вся пятница
в него не вошли.

Отказ не разовый: с 01.07 по 03.08 — **8 error из 52 прогонов** `amo_leads`,
все с той же ошибкой.

## Причина 2 — «Лид» ловит выброшенные сделки

`app/src/lib/leadsReport/metrics.ts`: лид = `sort` текущего этапа ≥ `sort`
этапа «Квалифицированный лид» (40). У AMO «Закрыто и не реализовано» имеет
`sort = 11000`, «Успешно реализовано» — `10000`. Значит **любая закрытая
сделка проходит порог**, даже если её выбросили с «Первого контакта».

По истории переходов (`amo_events`): из 15 закрытых сделок окна **14 никогда
не достигали этапа 87397290 «Квалифицированный лид»**. Все 14 посчитаны
лидами.

Намерение бизнес-правила («дошёл до квала и умер — всё равно лид») корректно;
неверна реализация — она не отличает «умер после квала» от «умер до квала».
Данные для правильного расчёта есть: `amo_events` хранит переходы этапов.

## Причина 3 — встречи считаются по этапу карточки, а не по факту

Автоотчёт: «Было» = текущий этап ≥ «Встреча проведена + КП отправлено» (70),
исключая 142/143. «Запланировано» = текущий этап ровно «Назначена встреча».

По записям разговоров (`meeting_deal_links` + `tg_video_transcripts`) за окно
прошло **20 встреч**; из них 5 — со сделками, пришедшими в этом же окне.
Автоотчёт показал 3, ручной — 7.

Показательный случай: 34397653 `Заявка: venyoo-agency.ru` — встреча 30.07
15:54 UTC, перевод карточки на этап 70 в **31.07 14:30 UTC, через 30 минут
после отчёта**. У нас ушла в «Запланировано».

Дашборд первички (`app/src/lib/firstSales/metrics.ts`) эту проблему уже решил —
считает встречи по записям разговоров, а не по этапу. Отчёт продаж — нет.

## Причина 4 — окно и непокрытые источники

* Окна не совпадают: авто — пт 17:01 → пт 17:00 (`weekWindow.ts`), ручной —
  25.07–31.07 по календарю. Три сделки вечера 24.07 есть только у нас, вся
  пятница 31.07 после 17:00 — только у него.
* Из 68 сделок окна **12 не попали ни в один канал** (`detectSummaryChannel`
  вернул `null`): `портал (outreachos)` ×2, `холодная база` ×3, `сайт` ×2,
  `seo`, `тг бот`, `тг-канал`, `tg-посев`, `сарафан`. Две сделки
  `портал (outreachos)` — автоаутрич (в названии «Автоаутрич»), должны были
  попасть в Аутрич; это часть дельты 10 против 11.

## Что делать

1. **Свежесть данных.** Гнать синк AMO непосредственно перед отчётом и падать
   с алертом, если он не прошёл; либо в самом сообщении писать возраст данных.
   Молча отправлять отчёт по вчерашнему снимку — недопустимо.
2. **Лид по истории переходов.** Считать лидом сделку, у которой в
   `amo_events` есть переход на этап с `sort ≥ 40` и `sort < 10000`, либо
   текущий этап в этом диапазоне.
3. **Встречи по записям разговоров** — переиспользовать логику
   `firstSales/meetings.ts` вместо этапа карточки.
4. **Карта источников** — как минимум `портал (outreachos)` → Аутрич; остальные
   непокрытые источники согласовать с продажами.

Пункты 1 и 2 дают основную часть расхождения.
