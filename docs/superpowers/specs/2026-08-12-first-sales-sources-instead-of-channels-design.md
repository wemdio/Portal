# Дашборд первички: источники вместо каналов

Дата: 12.08.2026. Постановка — Дмитрий Кулага.
Источник цифр ниже — прод-БД (`amo_leads`, `amo_lead_stage_dates_v`,
`lead_source_channels`), выборка по воронке первички `pipeline_id = 7670334`.

Отменяет решение из `2026-07-30-first-sales-dashboard-design.md` о слое
«канал». Само по себе оно было не ошибочным, но требовало согласования, которое
за две недели не состоялось и в текущей организации работы не состоится.

## Почему

Плашка «Без канала» показывает 240 из 380 лидов за 14.07–12.08. Читается это
как «продажи не разметили сделки». Разбор показал обратное.

| | сделок |
|---|---|
| «Источник» в AMO заполнен, но портал не знает, в какой канал его класть | 230 |
| «Источник» в AMO действительно пустой | 10 |

96% «неразмеченных» размечены в AMO. В `lead_source_channels` 16 источников
заведены миграцией как `unassigned` — сознательно, до согласования раскладки
Егором и Никитой. Согласование не сделано: у всех строк справочника
`updated_by = null`, `updated_at = 31.07.2026 11:15` — момент заливки миграции.
Руками справочник не трогали ни разу.

Механика воспроизведена на боевых данных до штуки: 380 лидов, 240 без канала,
153 лид-магнита — совпадает с дашбордом.

**Диагноз.** Плашка обвиняет продажи в долге портала. Пока раскладка не
сделана, дашборд врёт; а раскладка требует решения, которого никто не
принимает, потому что оно ни для кого не приоритет.

**Решение.** Убрать слой, который требует этого решения. Таксономию источников
ведут продажи в AMO — поле «Источник» там `select` (`field_id = 1314379`) с
фиксированным списком значений. Портал должен группировать сделки по этому
списку, а не заводить у себя второй.

## Что меняется в поведении

**Источники берутся из сделок.** Портал не хранит своего списка. Новое значение
в AMO появляется на дашборде в тот же день, без правок кода. Сегодня такое
значение молча падало бы в «без канала» — так случилось с «ТГ-АДС», заведённым
06.08 (2 сделки).

**Фильтр — выпадающий список с галочками и поиском** вместо ряда чипов-каналов.
В списке только источники, встречавшиеся в выбранном периоде, по убыванию числа
сделок; за последний месяц это 15 значений, за год — 22. Плюс пункт «Без
источника». Выбор нескольких источников суммирует их в плашках, воронке и
графике — так же, как сегодня работает выбор нескольких каналов.

**Плашка «Без канала» → «Без источника».** За период это 10 сделок, за 2026 год
— 78. Плашка кликабельна и открывает список сделок со ссылками в AMO: разовая
ручная выгрузка от 12.08 становится живой, продажи могут забирать свежий список
сами.

**Таблица разбивки — минус одна колонка.** Колонка «Источник» в ней уже есть,
убирается вторая, «Канал»: было 7 колонок, станет 6. Оттуда же уходит метка
«нет в справочнике» — справочника нет, отсутствовать не в чем.

**Названия источников показываются как в AMO.** Сегодня в колонке «Источник»
всё в нижнем регистре («email outreach», «тг-канал», «личный бренд (инст
/ютуб)») — потому что нормализованный текст служил ключом сопоставления со
справочником. Ключом он больше не служит, и названия показываются как заведены.

## Ключ группировки — `enum_id`, не текст

Группировка идёт по `custom_fields_values[].values[0].enum_id` — стабильному
номеру значения в справочнике AMO, а название берётся из сделки с наибольшим
`created_at` среди сделок с этим `enum_id` (при равенстве — с наибольшим
`amo_id`, чтобы результат не зависел от порядка строк в выборке).

Разница проявится при переименовании пункта в AMO («Партнер» → «Партнёрка»).
`amo_leads.raw` — снимок на момент последней синхронизации сделки, поэтому у
старых, давно не менявшихся сделок останется старое написание. Группировка по
тексту разрежет историю одного источника на две строки; группировка по `enum_id`
сохранит её одной. Проверено: сегодня у всех 22 значений ровно по одному
написанию, так что мера профилактическая и на текущие цифры не влияет.

Ключ строки, он же значение параметра `source` в API:

- `<enum_id>` — обычный источник;
- `text:<нормализованный текст>` — защитный случай, значение без `enum_id`
  (поле `select`, такого быть не должно, но потеря сделки хуже лишней ветки);
- `none` — «Источник» не заполнен.

Числовой `enum_id` с литералами `none` и `text:` не сталкивается.

## Что удаляется

- Таблица `lead_source_channels` — миграцией `drop table`.
- Экран-редактор справочника `SourceMapEditor.tsx` и ручка
  `api/analytics/first-sales/source-map/route.ts`.
- `FIRST_SALES_CHANNELS`, `CHANNEL_LABELS`, `FirstSalesChannel`,
  `resolveChannel`, `buildSourceIndex` в `lib/firstSales/sourceChannels.ts`.
  Файл переименовывается в `sources.ts` — от него остаётся извлечение источника
  из сделки. Тест `sourceChannels.test.ts` → `sources.test.ts`.
- Правило «источник пуст, но Контур = Маркетинг → маркетинг». За весь 2026 год
  оно не сработало ни разу: сделок с пустым источником и `Контур = Маркетинг`
  ноль из 78. Единственные две сделки, которых оно касалось, — «ТГ-АДС», и у них
  источник заполнен, после правки они встанут под своим именем.

## Затрагиваемые файлы

| Файл | Что делаем |
|---|---|
| `lib/firstSales/sourceChannels.ts` → `sources.ts` | вырезаем каналы, оставляем извлечение источника + ключ строки |
| `lib/firstSales/metrics.ts` | `SourceBreakdown` без `channel`/`known`; `unassignedLeads` → `noSourceLeads`; группировка по ключу |
| `lib/firstSales/params.ts` | параметр `channel[]` → `source[]`, без проверки по списку значений |
| `components/first-sales/FiltersBar.tsx` | чипы → выпадающий список с галочками и поиском |
| `components/first-sales/SourceTable.tsx` | минус колонка «Канал» и метка «нет в справочнике» |
| `components/first-sales/KpiRow.tsx` | «Без канала» → «Без источника», плашка кликабельна |
| `components/first-sales/FirstSalesView.tsx` | проводка нового фильтра, снятие `SourceMapEditor` |
| `api/analytics/first-sales/summary/route.ts` | новый параметр фильтра |
| `api/analytics/first-sales/leads/route.ts` | drill-down по ключу источника; фильтр каналов уходит |
| `supabase/migrations/20260812_0001_drop_lead_source_channels.sql` | `drop table lead_source_channels` |

Список источников для фильтра приходит в ответе `summary` отдельным полем
`availableSources` и считается **до** применения фильтра. Переиспользовать для
этого `bySource` нельзя: она уже отфильтрована, и, выбрав один источник,
пользователь получил бы список из одного пункта — добавить второй стало бы
нечем. Ошибка вида «фильтр съедает сам себя», поэтому оговаривается явно.

`availableSources` строится по тем же сделкам, что и разбивка, но до отсева по
источнику, и включает пункт «Без источника», когда такие сделки в периоде есть.

Ручка `leads` принимает один `source` и больше не принимает фильтр: строка, в
которую пользователь проваливается, уже прошла фильтр, второй раз применять его
незачем.

- Сверка на боевых данных перед мержем: сумма лидов по всем источникам за
  14.07–12.08 равна 380, «Без источника» равно 10.

## Что не входит

- Отчёт продаж (`lib/salesReport/`) и его понятие канала не трогаем.
- `lib/cisLeads/channelResolver.ts` — другой «канал» (соцсети лида), не связан.
- Схлопывание шести телеграм-источников в один. Если понадобится «телеграм
  всего» одной цифрой — это делается объединением пунктов в самом AMO силами
  продаж. Прямое следствие выбранного подхода: у списка один владелец.
- Этапы 2 и 3 дашборда (оборот, стоимость лида) — как были, не начаты.
