# Дашборд расходов по сервисам — дизайн

Дата: 2026-07-30
Статус: согласован, готов к плану реализации

## Задача

Отдельная вкладка портала с расходами компании: сумма за период с группировкой
по дню / неделе / месяцу и разбивкой по сервисам. Три источника денег:

- **Точка** — расчётный счёт, приезжает автоматом (API уже подключён);
- **Brocard** — виртуальные карты для оплаты зарубежных SaaS, есть API, доступы будут выданы позже;
- **личная карта CEO** — «свободная трата», API нет.

Задача парная к дашборду первички (доходы/лиды), который делается отдельно на тех же банковских данных.

| Точечная выдача вкладок | `user_tool_visibility` + `ALL_NAV_TAB_IDS` | nav-вкладки **по умолчанию выключены** (`UserProvider.tsx:115`, `api/admin/users/[id]/tools/route.ts:65` — оба `?? false`) |
| Модалка пользователя в админке | `app/admin/users/page.tsx:1886` (инструменты), `:1921` (вкладки) | инструменты уже свёрнуты в `<details>`, вкладки — плоский `<ul>` |

Ключевой факт: **расходов в базе сейчас нет ни одной строки**. Это не «подключить
UI к данным», а сначала завести сами данные.

## Принятые решения

| Решение | Выбор |
|---|---|
| Что такое «сервис» | Два уровня: вендор (OpenAI, Instantly, Яндекс.Директ) внутри категории (маркетинг, инструменты, ФОТ, налоги, операционка) |
| Как размечается транзакция | Словарь правил + ручной хвост. Разметка руками в UI сразу становится новым правилом |
| Валюта | Всё приводится к рублям по курсу ЦБ на дату операции. Прошлые месяцы не пересчитываются |
| Метод учёта | Кассовый: расход попадает в тот день, когда ушли деньги. Годовая подписка целиком падает в месяц оплаты |
| Хранение | Сырьё по источникам + отдельный слой разметки поверх (вариант A) |
| Графики | Добавляем `recharts` |
| Размещение | Отдельная вкладка, не внутри `/finance` |
| Доступ | Админы видят всегда; остальным выдаётся точечно тумблером в модалке пользователя |
| Ввод трат с личной карты CEO | Форма ручного ввода в портале, вендор выбирается сразу при создании |
| Внутренние перемещения | Отдельная категория `transfer` — видны в списке, в сумму расходов не входят |

## Архитектура данных

Принцип — тот же, что уже принят в репозитории (см. шапку
`supabase/migrations/20260706_0003_create_external_sync_tables.sql`): сырьё
остаётся честным, связи и трактовки живут в отдельных таблицах. Здесь это даёт
конкретную гарантию: ночной синк переливает сырьё каждый день, но физически
не может затереть разметку, сделанную руками, — она лежит в другой таблице.

### Слой сырья

**`bank_transactions` (правим существующую)** — снимаем фильтр «только приход».
Дебетовые строки и есть расходы. `is_revenue` / `exclude_reason` относятся только
к приходу; для дебета пишем `NULL`, классификатор `classify_revenue` на них не
вызываем. Для дебета заполняются `payee_name` / `payee_inn` (получатель), которые
сейчас всегда `NULL`.

**`brocard_transactions` (новая)** — сырьё виртуальных карт: внешний id, карта и
держатель, дата, сумма в валюте операции, валюта, сумма списания со счёта (если
API её отдаёт), мерчант, MCC-категория, статус, `raw jsonb`.

**`manual_expenses` (новая)** — всё, чего нет в API, и в первую очередь личная
карта CEO: дата, сумма, валюта, плательщик, комментарий, автор записи. Вендор
здесь **не хранится** — см. ниже.

Валюта здесь не декоративная: личной картой оплачивается в том числе зарубежный
SaaS, поэтому поле работает так же, как для Brocard, и пересчёт в рубли идёт по
тому же курсу ЦБ на дату операции.

### Слой разметки

**`expense_vendors`** — вендор и его категория. Категории фиксированным списком:
`payroll` (ФОТ), `marketing`, `tools` (сервисы и подписки), `taxes`,
`operations`, `transfer` (внутренние перемещения), `other`. Список задан
CHECK-констрейнтом, расширяется миграцией.

Категория `transfer` нужна для корректности итога, см. «Двойной счёт» ниже.

**`expense_rules`** — правило «поле + тип совпадения + образец → вендор».
Поле: `payee_name` / `payee_inn` / `purpose` / `merchant`. Тип: `exact` / `contains`.
Плюс приоритет и необязательное ограничение по источнику. Уникальный индекс по
`(match_field, match_type, lower(pattern), coalesce(source,''))` не даёт плодить
дубли правил.

**`expense_classifications`** — какая транзакция каким вендором размечена:
`(source, source_ref)` уникальны, плюс `vendor_id`, `method` (`rule` | `manual`),
ссылка на правило, автор и время.

Здесь же структурная защита ручной работы: пересчёт правил делает
`INSERT … ON CONFLICT (source, source_ref) DO UPDATE … WHERE
expense_classifications.method = 'rule'`. Строка, размеченная человеком,
правилом не перезаписывается никогда — это условие в SQL, а не договорённость
между разработчиками.

`manual_expenses` намеренно не держит `vendor_id` у себя: ручные траты
размечаются через ту же `expense_classifications` (`source = 'manual'`). Одна
таблица разметки — один код очереди разметки, один код применения правил, один
вид в отчёте.

**`fx_rates`** — `(rate_date, currency) → rate` (рублей за единицу валюты),
источник `cbr`. Строки исторические и неизменяемые, поэтому рублёвый эквивалент,
посчитанный на лету, задним числом не плывёт — фиксировать его отдельной
колонкой не нужно.

ЦБ не публикует курс в выходные и праздники, поэтому берётся ближайший курс на
дату **не позже** даты операции (LATERAL-подзапрос, не прямой join по равенству).

### Витрина

`expenses_v` — view: UNION четырёх источников (дебет Точки, дебет Т-Банка,
Brocard, ручные), LEFT JOIN разметки и вендора, LEFT JOIN курса. Отдаёт строку
на трату: дата, источник, контрагент/мерчант, сырое назначение платежа, сумма в
валюте операции, сумма в рублях, вендор, категория.

LEFT JOIN, а не INNER — неразмеченная трата обязана быть видна в отчёте как
«без категории», а не тихо исчезнуть из суммы. Строка без курса валюты видна
там же и по той же причине.

### Двойной счёт

Три источника пересекаются по одним и тем же деньгам, и без отдельного правила
дашборд будет завышать расходы:

- **Пополнение Brocard.** Деньги уходят дебетом с Точки на баланс виртуальных
  карт, а потом списываются по картам у мерчантов. Один и тот же рубль виден
  дважды, и это не редкий случай, а каждое пополнение.
- **Возмещение подотчёта.** CEO платит личной картой, запись заводится руками;
  затем компания возвращает ему ту же сумму с Точки — и она приходит дебетом.
- **Переводы между своими счетами** — Точка и Т-Банк.

Все три случая — не расход, а перемещение уже учтённых денег. Решаются
существующим механизмом, без новых сущностей: заводятся вендоры вида
«Пополнение Brocard», «Возмещение подотчёта», «Перевод между счетами» с
категорией `transfer`, и обычные правила разметки ловят эти платежи по
получателю или ИНН.

Строки категории `transfer` видны в списке транзакций и в очереди разметки, но
исключены из итога расходов, из графика по времени и из разбивки по сервисам.
Прятать их нельзя: если перемещение исчезнет совсем, сумма по дашборду перестанет
сходиться с банковской выпиской, и проверить дашборд станет нечем.

Отдельно на дашборде показывается строка «перемещения: X ₽» — рядом с итогом,
чтобы расхождение с выпиской объяснялось на месте, а не в переписке.

**Что это не решает.** Возмещение и исходная трата остаются двумя независимыми
записями, и никто не проверяет, что каждой ручной трате соответствует ровно одно
возмещение. Если CEO забудет внести трату, но возмещение с Точки пройдёт —
расход просто не будет виден. Сверка «подотчёт закрыт» в объём не входит.

## Доступ

Данные чувствительные (ФОТ, налоги), поэтому доступ закрывается на двух уровнях.

**Навигация.** В `ALL_NAV_TAB_IDS` добавляется `nav-expenses`, в `navItems` —
пункт «Расходы» с `navTabId: 'nav-expenses'`. Так как nav-вкладки по умолчанию
выключены, вкладка невидима, пока её не выдали.

Одного этого мало: текущий фильтр в `Sidebar.tsx:99` и `TopNav.tsx:36` про роли
ничего не знает, поэтому без строки в БД вкладку не увидит и админ. Добавляем в
`NavTabConfig` флаг `adminAlwaysOn` и включаем его **только** для `nav-expenses`
— поведение существующей вкладки «Доска» при этом не меняется.

**Данные.** Скрытый пункт меню — это не защита. Новые таблицы получают RLS
без select-политики для `authenticated`, читает их только серверный код под
`service_role`. Все запросы дашборда идут через API-роуты, каждый из которых
первым делом зовёт общий гард `requireExpensesAccess`: роль `admin` → доступ;
иначе — строка `user_tool_visibility(tool_id='nav-expenses', enabled=true)`.

Это отличается от `/finance`, который читает Supabase прямо с клиента. Для
расходов такой путь закрыт сознательно.

### Модалка в админке

Блок «Отображение вкладок в Header-е» (`app/admin/users/page.tsx:1921`)
оборачивается в `<details>` — точно так же, как соседний блок «Отображение
инструментов» (`:1886`): заголовок, chevron с `group-open:rotate-90`, состояние
в DOM без React-стейта. Внутри — «Доска» и «Расходы», у каждой строки
description из `NAV_TABS_CONFIG`.

## Изменения в синке

`services/portal-external-sync/`:

1. **`sources/bank_tochka.py`** — убрать `Credit`-фильтр, раскладывать обе
   стороны: для кредита плательщик из `DebtorParty` (как сейчас), для дебета
   получатель из `CreditorParty` в `payee_name` / `payee_inn`.
2. **`sources/bank_tbank.py`** — то же самое: сейчас берутся только входящие.
3. **`sources/brocard.py`** (новый) — адаптер к тому же слою. Пока нет
   `BROCARD_API_KEY`, поднимает `NotImplementedError` — существующий обработчик
   в `main.py:84` пишет прогон как `partial` и идёт дальше, весь остальной синк
   не ломается.
4. **`sources/fx_cbr.py`** (новый) — курсы ЦБ за даты, для которых есть операции
   в валюте.
5. **`sources/expense_rules.py`** (новый) — применение правил к неразмеченным
   строкам. Идёт последним, после всех источников.
6. **`main.py`** — новые источники в `SOURCES`, порядок важен.

**Подводный камень:** `external_sync_runs.source` — CHECK-констрейнт с
перечислением допустимых имён (`…_0003_create_external_sync_tables.sql:183`).
Новые имена (`brocard`, `fx_cbr`, `expense_rules`) без миграции на этот
констрейнт уронят логирование прогона, а не сам прогон — то есть отвалится
именно наблюдаемость, самым неочевидным способом. Констрейнт расширяется в той
же миграции.

**Бэкфилл:** `PERIODS` в обоих банковских источниках тянут с 2023 года, и
снятие фильтра добавит дебет за всю историю разом. Прогон разовый и тяжёлый —
запускается вручную, не в штатное окно.

**Индексы:** сейчас проиндексирован только плательщик. Добавляются индексы по
`payee_inn`, `lower(payee_name)` и `(direction, occurred_at desc)`.

## API

Все под `requireExpensesAccess`, читают `expenses_v` через `supabaseAdmin`:

| Роут | Назначение |
|---|---|
| `GET /api/expenses/summary` | ряд по времени + KPI. Параметры: `from`, `to`, `groupBy=day\|week\|month`, `source`, `category` |
| `GET /api/expenses/vendors` | разбивка по вендорам за период с Δ к предыдущему периоду |
| `GET /api/expenses/transactions` | drill-down по вендору, с пагинацией |
| `GET /api/expenses/unclassified` | очередь разметки |
| `POST /api/expenses/classify` | разметить транзакцию; опционально создать правило и применить ко всем похожим |
| `POST /api/expenses/vendors` | создать вендора |
| `GET /api/expenses/manual` | список ручных трат за период |
| `POST /api/expenses/manual` | создать ручную трату (сразу с вендором) |
| `PATCH /api/expenses/manual/[id]` | исправить ручную трату |
| `DELETE /api/expenses/manual/[id]` | удалить ручную трату |
| `GET /api/expenses/export` | выгрузка периода в xlsx (пакет `xlsx` в проекте есть) |

Границы дня, недели и месяца считаются в `Europe/Moscow` — том же поясе, в
котором работает синк и в котором люди смотрят отчёт.

## UI

Страница `/expenses`, компоненты в `components/expenses/`, графики на `recharts`.

**Шапка** — период (этот месяц / прошлый / 30 дней / квартал / год /
произвольный), переключатель группировки день–неделя–месяц, фильтры по источнику
и категории.

**KPI-строка** — всего за период, среднее в день, Δ к предыдущему периоду того же
размера, отдельным блоком «не размечено: N операций на X ₽» и рядом
«перемещения: X ₽» (категория `transfer`, в итог не входит).

Последнее — не украшение. Пока эта цифра большая, остальным числам верить нельзя,
поэтому она стоит в одном ряду с итогом, а не прячется в углу.

**График по времени** — stacked bar с шагом по выбранной группировке, стек по
категориям, переключатель на разбивку по источникам.

**Разбивка по сервисам** — горизонтальные бары топ-15 вендоров и таблица под
ними: вендор, категория, сумма, доля, число операций, Δ к прошлому периоду.
Клик по строке раскрывает транзакции вендора с сырым назначением платежа —
чтобы можно было проверить, откуда взялась цифра.

**Ручная трата** — форма для личной карты CEO: дата, сумма, валюта (по умолчанию
рубли), вендор из существующих или новый прямо здесь, комментарий. Вендор
выбирается сразу, поэтому запись приходит уже размеченной и в очередь разметки
не попадает.

Список ранее внесённых трат — рядом с формой, со строкой поиска и возможностью
исправить или удалить запись. Опечатка в сумме — обычное дело для ручного ввода,
и чинить её через SQL никто не будет: без редактирования в интерфейсе форма
превращается в append-only свалку с неверными числами.

В каждой записи хранится автор (`created_by`), и он виден в drill-down рядом с
суммой. Создавать может любой, у кого есть доступ к вкладке; редактировать и
удалять — автор записи либо админ.

**Очередь разметки** — отдельный экран: неопознанные операции, по каждой видно
сырьё (получатель, ИНН, назначение или мерчант), выбор существующего вендора либо
создание нового и галка «запомнить правило и применить ко всем похожим». Один
клик закрывает и текущую операцию, и все будущие такие же.

Новые строки интерфейса заводятся в `lib/globalTranslations.ts` парами ru→en,
как принято в проекте.

## Порядок работ

1. **Данные.** Миграции, дебет в Точке и Т-Банке, курсы ЦБ, правила и
   классификация. Проверка на реальной выписке: сумма дебета за месяц из
   `expenses_v` должна сойтись с выпиской Точки до рубля.
2. **Доступ.** `nav-expenses` в реестре и навигации, `adminAlwaysOn`, гард
   `requireExpensesAccess`, `<details>` в модалке админки.
3. **Дашборд.** API-роуты, страница, графики, очередь разметки, форма ручной
   траты со списком и редактированием, экспорт.
4. **Brocard.** Адаптер включается, когда придут ключи. Остальное к этому моменту
   уже работает.

Каждая фаза самодостаточна: после первой можно считать расходы SQL-запросом,
после второй — вкладка появляется у нужных людей, после третьей — дашборд живой
на Точке и личной карте CEO, даже если Brocard ещё не подключён.

Форма ручного ввода стоит в третьей фазе, а не отдельной последней: без неё
расходы на личной карте не видны вообще, и дашборд запускается заведомо неполным.

## Тесты

Jest (`app/tests`):

- матчинг правил: приоритет, `exact` против `contains`, регистр, ограничение по
  источнику;
- ручная разметка не перезаписывается пересчётом правил;
- подбор курса: выходные и праздники берут ближайший предыдущий, отсутствие курса
  даёт видимую строку без рублёвой суммы, а не ноль;
- границы группировки день/неделя/месяц в `Europe/Moscow`, включая переход через
  границу месяца;
- Δ к предыдущему периоду для периодов разной длины;
- гард доступа: админ проходит; пользователь с `enabled=true` проходит;
  пользователь без строки и с `enabled=false` получает 403;
- категория `transfer` не входит в итог, в график и в разбивку по сервисам, но
  присутствует в списке транзакций и в отдельном показателе «перемещения»;
- ручная трата: сумма строго больше нуля, дата не в будущем, валюта без курса
  не роняет форму; редактировать и удалять может автор или админ, посторонний
  получает 403.

## Открытые вопросы

1. **Список категорий** — предложен `payroll` / `marketing` / `tools` / `taxes` /
   `operations` / `transfer` / `other`, нужен подтверждающий взгляд от финансов.
2. **Старая вкладка «Расходы» в `/finance`** — оставить как есть или убрать после
   запуска. Две разные цифры в двух местах — источник вопросов, но выпиливание в
   объём этой задачи не заложено.

## Замеченное рядом, вне объёма

`/finance` не имеет ролевого гейта (`lib/navigation.ts:30` — ни `leadOnly`, ни
`adminOnly`): страницу видит любой авторизованный сотрудник. Пока там данные из
localStorage одного человека, это не утечка. Стоит закрыть отдельной задачей —
особенно если старую вкладку расходов решат оставить.
