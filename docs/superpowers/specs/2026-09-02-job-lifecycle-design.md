# Единый жизненный цикл фоновых задач (lease / checkpoint / handoff)

Дата: 2026-09-02. Статус: дизайн утверждён, ждёт плана внедрения.

## Проблема

Деплой останавливает воркеры, и фоновые задачи (парсинги, кампании, обогащение)
встают; часть из них не продолжается. Причина — единого механизма нет, у каждого
из ~30 воркеров своя схема:

- Захват задачи — везде CAS `UPDATE … WHERE status='pending'`, но признак
  «исполнитель жив» разный: `started_at` (конструктор баз), `updated_at`
  по триггеру (ЯКарты, транскрибация), ничего (`parser_jobs` HH/ATS,
  TG-парсер, ИНН).
- Восстановление после рестарта — почти везде «при старте перевести все
  `running` в `pending`». Это корректно только для одной реплики; у
  `worker-enrich` их девять, и вторая реплика при старте отбирает живые
  задачи у первой.
- Продолжение с места есть у ЯКарт, конструктора баз, обогащения, валидации
  почт, ИНН-lookup. TG-парсер, HH/ATS, поиск, архив чатов начинают с нуля
  (архив чатов явно обнуляет `dialogs_done`).
- TG-аутрич, обзвон (ai-caller), LinkedIn держат ход кампании только в
  памяти процесса; деплой «ставит кампанию на паузу и кладёт команду старт»
  через `drain-worker.sh`.
- `drain-worker.sh` держит захардкоженные списки из 12 таблиц и 23
  контейнеров, которые отстали от `docker-compose.prod.yml`: около десятка
  воркеров (enrich-2..9, byo-*, sales-*, hypothesis-engine, vertical-engine-v2,
  client-report-exports, base-constructor вне списка) убиваются `docker rm -f`
  (SIGKILL) без SIGTERM, и `stop_grace_period` в compose для них декоративен.

Границы этой работы: только задачи. Простой самого портала (2–3 минуты,
один контейнер на фиксированном порту, два холодных старта за деплой)
решается отдельно.

## Цель

1. Ни одна задача не теряется из-за деплоя или падения контейнера.
2. Задача продолжается с сохранённого места, а не с нуля.
3. Один механизм на все воркеры; новый воркер получает его подключением
   библиотеки, без правок в скриптах деплоя.
4. Скрипт деплоя не лезет в базу и не хранит списки контейнеров.

## Решение

### 1. Общие колонки в каждой таблице задач

Одна миграция в `supabase/migrations/`, только `add column if not exists`,
статусы и существующие поля не меняются:

| Колонка       | Тип          | Назначение |
|---------------|--------------|------------|
| `lease_until` | timestamptz  | До какого момента задача арендована исполнителем. Истекла — задачу можно перехватить. |
| `run_token`   | uuid         | Жетон владения, выписывается при каждом захвате. Все записи исполнителя в строку ограничены `and run_token = <свой>`. |
| `worker_id`   | text         | Имя исполнителя (`<kind>-<pid>-<ts>`), для диагностики. |
| `checkpoint`  | jsonb        | Сохранённый прогресс. Структура своя у каждого воркера. |
| `attempts`    | int default 0| Число попыток выполнения. |

Индекс: `(status, lease_until)` на каждую таблицу — под запрос «истёкшие
аренды».

Таблицы (по воркерам): `base_constructor_jobs`, `tg_parser_jobs`,
`parser_jobs`, `hh_archive_jobs`, `yandex_direct_jobs`, `search_parser_jobs`,
`sales_chat_archive_jobs`, `sales_chat_sync_runs`, `yandex_maps_jobs`,
`yandex_maps_catalog_discovery_queue`, `tg_outreach_campaigns`,
`tg_outreach_warmup_runs`, `tg_outreach_jobs`, `ai_campaigns`,
`ai_caller_jobs`, `li_campaigns`, `website_enrichment_jobs`,
`brief_scoring_jobs`, `crypto_payment_jobs`, `email_validation_jobs`,
`inn_enrich_jobs`, `website_inn_lookup_jobs`, `tg_scan_jobs`,
`tg_transcribe_jobs`, `client_report_export_jobs`, `he_jobs`, `ve_jobs`,
`client_manual_score_runs`. У `base_constructor_jobs` уже есть `run_token` —
переиспользуется.

### 2. Библиотека `app/src/lib/jobs/lifecycle.ts`

Один модуль, подключаемый каждым воркером вместо самописных
`claim*`/`recover*`/`resetStuck*`. Лежит в `app/src/lib`, а не в
`app/worker`, потому что библиотечный код (`app/src/lib/**`) тоже должен
уметь продлевать аренду и писать чекпойнт.

Публичный интерфейс:

```ts
createJobRunner<Row, Checkpoint>({
  table: 'tg_parser_jobs',
  workerId: 'tg-parser-1234-...',
  statuses: { pending: 'pending', running: 'running', done: 'done', failed: 'error' },
  leaseSeconds: 180,          // аренда; продление каждые leaseSeconds/3
  maxAttempts: 3,
  concurrency: 1,
  orderBy: 'created_at',      // порядок захвата pending
  select: 'params',           // id, checkpoint, attempts, run_token читаются всегда
  manageTerminalStatus: true, // false — терминальный статус пишет сам run()
  claimPatch: () => ({ started_at: new Date().toISOString() }),
  failedPatch: (reason) => ({ error_message: reason }),
  log,
  run: async (job, ctx) => { … },
}) => { pollOnce(): Promise<boolean>; shutdown(): Promise<void>; activeJobIds(): string[] }
```

`ctx` внутри `run`:

- `ctx.saveCheckpoint(data)` — записать `checkpoint = data`, продлить аренду и
  обнулить `attempts` (прогресс возвращает бюджет попыток). Возвращает `false`,
  если запись не прошла фильтр `run_token` (строку уже перехватили): воркер
  обязан прекратить работу над задачей. `true` означает «владение сохранено»;
  запись — best-effort после трёх попыток, поэтому терять состояние из памяти
  по одному `true` нельзя.
- `ctx.checkpoint` — чекпойнт с прошлого захвата или `null`.
- `ctx.signal: AbortSignal` — взводится при SIGTERM/SIGINT; передавать в
  fetch/паузы, чтобы задача прерывалась между шагами, а не дожидалась
  SIGKILL.
- `ctx.shouldStop()` — то же флагом, для циклов.
- `ctx.log` — логгер с префиксом задачи.

Поведение раннера:

1. **Захват.** Сначала `pending` → `running` с новыми `run_token`,
   `worker_id`, `lease_until = now()+lease`, CAS по `status='pending'`.
   `attempts` при захвате не растёт — счётчик считает потери, а не запуски
   (см. п. 3). Если pending нет — `running` с истёкшей (`lease_until < now()`)
   или обнулённой (`lease_until is null`) арендой, CAS по тому же условию.
   Обнулённая аренда — чистая передача при остановке, попыткой не считается;
   истёкшая — падение исполнителя, `attempts+1`. Pending
   приоритетнее, чтобы новые задачи не ждали за резюмами. Через PostgREST,
   без RPC — тот же паттерн, что уже работает в конструкторе баз.
2. **Продление.** Пока `run` выполняется, `setInterval` каждые
   `leaseSeconds/3` пишет `lease_until = now()+lease` с фильтром `run_token`.
   После `markShuttingDown()` продления не пишутся (см.
   `app/src/lib/workerShutdown.ts`, инцидент 11.08.2026).
3. **Завершение.** `run` вернулся → `status=done`, `lease_until=null`,
   `run_token=null`. Бросил исключение → если `attempts < maxAttempts`,
   `status=pending`, `lease_until=null` и поля из `failedPatch`; иначе
   `status=failed`. Терминальные записи идут с тремя попытками и коротким
   ожиданием: одна сетевая осечка не должна оставить готовую задачу в работе.
   Отмена по `ctx.signal` не считается ошибкой: строка остаётся `running` с
   обнулённой арендой (п. 4). При `manageTerminalStatus: false` статус пишет
   сам `run`, а библиотека только отпускает аренду.
4. **Остановка (SIGTERM/SIGINT).** Синхронно `markShuttingDown()`, прерывание
   `ctx.signal`, затем для всех своих задач `lease_until = null` с фильтром
   `run_token`, дважды с паузой в секунду (перебивает продление, ушедшее в
   PostgREST до сигнала), и контрольное чтение строки: если аренда всё-таки
   ожила, отпускаем ещё раз. Потом ждёт завершения `run`-промисов до
   `shutdownGraceMs` (по умолчанию 10 с, потолок 12 с — чтобы всё уложилось в
   `docker stop --timeout 15`) и выходит. Новая реплика перехватывает задачу на
   первом же опросе.
   Захват, случившийся уже во время остановки, немедленно отпускается: задача
   не стартует.
5. **Восстановление при старте — отсутствует.** Никаких «running →
   pending» при загрузке. Брошенная задача определяется только истёкшей
   арендой. Это делает механизм корректным при любом числе реплик.
6. **Жёсткое убийство (SIGKILL, OOM).** Аренда истекает сама через
   `leaseSeconds`; задача перехватывается без участия людей. Порог задачи
   «зависла» для монитора здоровья не меняется (20 минут без прогресса).
7. **Недоступная база.** Сбой записи не считается потерей владения (все записи
   и так ограждены жетоном), но исполнитель следит за собственной арендой по
   часам: если она провисела дольше срока — прерывает работу сам, до следующего
   запроса. Иначе при зависшем соединении два исполнителя делали бы одну задачу,
   и внешние действия (отправка в Telegram, платные API) не ограждены ничем.

Контракт для `run`: обязан слушать `ctx.signal`, продолжаться с последнего
чекпойнта и переживать ситуацию, когда соседняя реплика начала ту же задачу
раньше, чем он остановился.

Не входит: приоритеты, отложенный запуск (`run_after` у HE/VE остаётся их
локальной надстройкой поверх захвата), распределённые блокировки.

### 3. Воркеры с запусками в памяти

TG-аутрич (кампании и прогрев), обзвон, LinkedIn: строка кампании со
статусом «идёт» сама становится задачей раннера. `run` — это существующий
цикл кампании, `ctx.signal` прерывает его между лидами. Аренда на строке
кампании; истекла — новая реплика поднимает кампанию. Команды пользователя
(`tg_outreach_jobs` с action start/stop, `ai_caller_jobs`) остаются как есть:
они меняют статус кампании, а раннер уже реагирует на статус. Хак
«поставить на паузу и положить команду старт» из `drain-worker.sh`
удаляется. Спящий сторож осиротевших стартов (`reclaimOrphanedStartJobs`)
и карантин зависших кампаний у TG-аутрича остаются.

### 4. Деплой

`.semaphore/scheduled-deploy.yml`, шаг 5: вместо `force_rm_svc` +
`drain-worker.sh` — `docker compose stop --timeout 15 ${WORKER_TARGETS}`
(параллельно средствами compose), затем `up -d --no-deps --force-recreate`.
`force_rm_svc` остаётся запасным ходом после `stop`, только для контейнеров,
которые не остановились. 15 секунд достаточно: освобождение аренды занимает
около двух секунд, дожидаться завершения задачи не нужно — она продолжится
с чекпойнта.

`drain-worker.sh` на переходный период сохраняет правку статусов только для
таблиц, чьи воркеры ещё не переведены, и удаляется на последнем этапе.
Списки контейнеров из него уходят сразу: compose сам знает контейнеры
сервиса.

`stop_grace_period` в compose приводится к 30 с для всех воркеров на
библиотеке; значения 2–3 часа (HH, eng-hiring, client-report-exports)
убираются — они компенсировали отсутствие чекпойнта.

### 5. Порядок внедрения

Каждый этап — отдельная ветка, план и выкладка.

1. Библиотека, миграция колонок, два пилота: конструктор баз (уже ближе
   всех: `run_token`, `started_at`-heartbeat, чекпойнт по шагам — заменить на
   `lease_until`/`checkpoint`) и TG-парсер (сейчас стартует с нуля, получит
   чекпойнт «последний обработанный чат/оффсет»). Деплой переводится на
   `compose stop`; `drain-worker.sh` пропускает переведённые таблицы.
2. Парсеры, стартующие заново: HH/ATS/eng-hiring (`parser_jobs`,
   `hh_archive_jobs`, `yandex_direct_jobs`), поиск, архив чатов, каталог
   ЯКарт (`yandex_maps_jobs` уже с чекпойнтом — только замена механики
   восстановления; убрать перевод в `failed` при старте).
3. Воркеры с памятью: TG-аутрич и прогрев, обзвон. LinkedIn рассмотрен и
   намеренно оставлен вне механизма — причина ниже.
4. Остальные: обогащение (9 реплик — главный выигрыш), валидация почт,
   ИНН, ИНН-lookup, транскрибация и сканы, экспорт отчётов, движки гипотез
   HE/VE, sync-runs чатов, ручной скоринг, крипто-платежи.
5. Удаление `drain-worker.sh` и всех локальных `recover*`/`resetStuck*`,
   выравнивание `stop_grace_period`.

Вне плана (остаются как есть): `instantly-leads`, `outreach` (Bugor/Nash),
`autopipeline` (уже с heartbeat), `bob-scorer`, cron-процессы 2ГИС и
внешнего sync — у них нет таблицы задач или уже есть эквивалент.

**LinkedIn-аутрич (`li_campaigns`) — решение от 03.09.2026: не переводим.**
Не потому, что «руки не дошли», а потому что аренда здесь не выражает нужный
запрет. Взаимное исключение у LinkedIn идёт **по аккаунту**, а не по кампании:
воркер группирует кампании по `account_id`, внутри группы гонит их строго
по очереди, а группы — параллельно. Две рассылки с одного аккаунта разом
разгоняют дневной счётчик приглашений и ловят анти-бот. Аренда же выдаётся на
строку кампании — она не запрещает двум кампаниям **одного** аккаунта идти
одновременно, то есть не защищает ровно от того, от чего надо. Настоящий
эквивалент — аренда на строку аккаунта, а это другой механизм и другая работа.

Терять при перезапуске тоже нечего: состояние воркера — одно число (когда был
последний проход), проход короткий и ограниченный, прогресс по каждому лиду
пишется в базу по ходу, восстановления при старте нет, и `drain-worker.sh` эту
очередь никогда не трогал. Единственное, что дал бы перевод, — разделение между
репликами, которого при одной реплике и так достаточно.

Пересмотреть это решение стоит, если появится вторая реплика воркера: тогда
внутрипроцессная очередь по аккаунту перестанет быть исключением, и понадобится
аренда **на аккаунт**.

### Рецепт перевода воркера

1. Убрать локальные `claim*`, `recover*`, `resetStuck*`, watchdog по
   `updated_at`/`started_at`.
2. Завести `createJobRunner` с таблицей и статусами воркера.
3. Тело обработки перенести в `run(job, ctx)`; в местах естественных
   границ (страница, чат, шаг) звать `ctx.checkpoint`; при старте читать
   `job.checkpoint` и продолжать с него; в паузы и запросы передавать
   `ctx.signal`.
4. Убрать SIGTERM-обработчики воркера, оставить `runner.shutdown()`.
5. Добавить таблицу в список пропуска `drain-worker.sh`.
6. **Сверить спецификацию монитора здоровья** (`JobMonitorSpec` в
   `services/health-check/main.py`) для этой таблицы — два поля, оба
   ломаются молча:
   - `updated_column`. Перевод на библиотеку добавляет в строку регулярный
     UPDATE, которого раньше не было: продление аренды раз в `lease/3`.
     Сама библиотека пишет только `lease_until`/`run_token`, но если на
     таблице висит безусловный триггер `before update … updated_at = now()`,
     то у живого исполнителя `updated_at` свеж ВСЕГДА — и алерт «Долго
     висит» для этой очереди выключается насовсем. Поэтому перед переводом:
     `grep -i "on public.<таблица>" supabase/migrations/*.sql` рядом с
     `create trigger`. Есть безусловный триггер — `updated_column` убрать,
     простой считать по отпечатку `progress_columns` (так уже сделано для
     `yandex_maps_jobs`, `yandex_direct_jobs`, `hh_archive_jobs`). Тот же
     эффект даёт heartbeat самого воркера, штампующий `updated_at` по
     таймеру независимо от прогресса: он превращает алерт в проверку
     «процесс жив», и если это не то, что нужно, менять надо не спеку, а
     heartbeat.
   - `active_statuses`. Статус «в работе» у воркеров называется по-разному
     (`running` против `processing`), и при переводе он задаётся заново в
     `statuses:` раннера. Спека, разошедшаяся со статусом, не даёт ложных
     тревог — она просто НИКОГДА не видит выполняющиеся задачи: строки не
     попадают в выборку монитора вовсе. Сверять с `statuses:` раннера и с
     check-констрейнтом таблицы.

   Заодно убедиться, что колонки из `progress_columns` двигаются во время
   работы, а не только в терминальной записи: неподвижный отпечаток даёт
   гарантированную ложную тревогу на любой задаче длиннее
   `HEALTH_JOB_STUCK_MIN`.
7. Во всех операторских маршрутах «возобновить / перезапустить» обнулять
   `attempts` рядом с `error_message`. `attempts` — бюджет неудач, а не
   счётчик запусков: строка, возвращённая в `pending` со счётчиком 2,
   получает одну попытку вместо трёх и уходит в `failed` при первой же
   осечке. Чекпойнт бюджет возвращает, но только когда задача до него
   дошла, — а рано падающая задача как раз не доходит. Известные случаи
   (фаза 2, вместе с переводом самих воркеров):
   `app/src/app/api/parsers/crypto-payments/jobs/[id]/resume/route.ts`,
   `app/src/app/api/parsers/hh/execute/route.ts`,
   `app/src/app/api/parsers/yandexmaps/[jobId]/collect-links/route.ts`,
   `app/src/app/api/parsers/yandexmaps/[jobId]/parse/route.ts`.

## Тесты

Один новый файл `app/tests/lib/jobLifecycle.test.ts` на виртуальных часах
(`jest.useFakeTimers`), без реальных пауз, с мок-клиентом Supabase.
Сценарии: два экземпляра берут одну pending-задачу — побеждает один;
истёкшая аренда перехватывается, живая — нет; продление и чекпойнт с чужим
`run_token` не проходят и возвращают `false`; SIGTERM обнуляет аренду
только своих задач и глушит продления; исключение в `run` ниже
`maxAttempts` возвращает задачу в pending, выше — в failed. Согласовано с
пользователем 02.09.2026 как исключение из правила «новых тестов не пишем».

## Риски

- Переходный период: часть таблиц под новым механизмом, часть под
  `drain-worker.sh`. Список пропуска в скрипте — единственное место, где
  они пересекаются; ошибка там означает лишний перевод `running → pending`
  на переведённой таблице. Это безопасно: раннер увидит `pending` и возьмёт
  задачу заново с чекпойнта.
- Монитор здоровья (`services/health-check/main.py`) считает «зависание» по
  своим полям прогресса; после перевода таблиц ему можно дополнительно
  показывать `lease_until`, но это не требуется для работы механизма.
- Realtime-подписка `pollLoop` слушает только `status=eq.pending`; перехват
  истёкших аренд идёт по fallback-опросу (30 с). Для деплоя это приемлемо:
  освобождённая аренда подхватится не позже 30 с после старта новой реплики.
