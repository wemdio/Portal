# Прогрев: настройки нагрузки и переезд чатов — дизайн

**Дата:** 2026-08-12
**Статус:** согласовано, к реализации
**Основа:** надстройка над [прогревом](./2026-08-03-tg-outreach-warmup-design.md) и
[активностью в публичных чатах](./2026-08-07-tg-warmup-public-chats-design.md)

## Задача

Прогрев работает, но нагрузка зашита в константы `types.ts` с env-override.
Оператор не может ни посмотреть, ни изменить её из портала: в интерфейсе крутится
только число дней и галочка «Активность в чатах». Чтобы понизить нагрузку, нужно
править `.env` на проде и перезапускать воркер — то есть звать разработчика.

При этом сама потребность реальна: пул прокси бракует часть аккаунтов, партии
приходят разного качества, и «сегодня жмём осторожнее» — обычное операторское
решение, а не исключение.

Вторая часть задачи — чаты. Сейчас они живут на отдельной вкладке кампании, а
числа, управляющие активностью в этих чатах, будут жить в настройках прогрева.
Разносить по разным экранам список чатов и нагрузку по ним незачем.

## Согласованные решения

| Вопрос | Решение |
|---|---|
| Вкладка «Чаты» | Убирается. Содержимое переезжает в секцию «В публичных чатах» на вкладке «Прогрев» |
| Переписка между своими | Две ручки: переписок в день на аккаунт и сообщений в одной переписке |
| Публичные чаты | Две ручки: сообщений в день и реакций в день на аккаунт |
| Чатов на аккаунт | Тоже выносим в настройки (сейчас зашито 3) |
| Способ настройки | Простой режим «первый день → потолок» плюс галочка «задать по дням» с таблицей |
| Хранение | Новая колонка `warmup_settings` у кампании, подставляется в каждый следующий запуск |
| Идущий прогрев | Правки подхватываются со следующего дня; план текущего дня не пересчитывается |
| Разгон в простом режиме | Остаётся привязан к `RAMP_DAYS` (7), а не к выбранной длине прогрева |

## Почему разгон по-прежнему за 7 дней

Это единственное решение, которое стоит объяснить отдельно, потому что оно
выглядит как недоделка. Кривая уже была привязана к длине прогрева — и это
чинили: прогрев на 4 дня выходил втрое агрессивнее недельного, аккаунт получал
6 сообщений в первый день и 80 в четвёртый. Просьба «поставить меньше дней»
означает «пусть суммарно уйдёт меньше», а не «пусть разгон будет резче» —
потолок для свежего номера один и тот же независимо от того, сколько дней его
греют.

Поэтому простой режим держит ту же механику: день N даёт одну и ту же нагрузку
при любом `days`, а `days` решает, на каком дне остановиться. Кому нужен другой
разгон — таблица по дням даёт его явно, и это уже осознанный выбор оператора, а
не побочный эффект поля «дней».

## Модель настроек

Один объект, живущий в двух местах: в кампании (что применится к следующему
запуску) и в снимке прогона (по чему идёт текущий).

```jsonc
{
  "mode": "curve",              // "curve" | "manual"
  "ramp_days": 7,               // за сколько дней кривая доходит до потолка
  "public_chats": true,         // этап активности в чатах включён
  "chats_per_account": 3,
  "curve": {
    "conversations":  { "first": 2, "peak": 8  },  // переписок в день на аккаунт
    "messages":       { "first": 3, "peak": 10 },  // сообщений в одной переписке
    "chat_messages":  { "first": 1, "peak": 5  },  // сообщений в день в чатах
    "chat_reactions": { "first": 3, "peak": 12 }   // реакций в день в чатах
  },
  "per_day": [
    { "conversations": 2, "messages": 3, "chat_messages": 1, "chat_reactions": 3 },
    { "conversations": 3, "messages": 4, "chat_messages": 2, "chat_reactions": 5 }
  ]
}
```

`public_chats` сохраняет имя из текущего снимка прогона — это тот же флаг, что
раньше ставила галочка в полосе управления, и переименовывать его значило бы
сломать чтение уже идущих прогонов.

`per_day` заполняется всегда, когда оператор включает ручной режим, и хранится
даже после возврата в `curve` — но не читается. Это нужно, чтобы случайное
переключение галочки туда-обратно не стирало работу; при возврате в ручной режим
интерфейс предупреждает, что покажет сохранённое, а не свежую кривую.

### Разложение в дневные нормы

Единственная функция, которую спрашивает планировщик:

```
dailyLimits(settings, day) -> {
  conversations, messages, chatMessages, chatReactions
}
```

- `mode: "curve"` — линейная интерпретация между `first` и `peak` за `ramp_days`,
  ровно та же формула, что сейчас в `rampValue`. Дни за пределами разгона держатся
  на потолке.
- `mode: "manual"` — берётся строка `per_day[day - 1]`. Если строки нет (прогрев
  длиннее таблицы), берётся последняя строка: продолжение на достигнутой нагрузке
  безопаснее, чем возврат к кривой, которую оператор уже отверг.

Значения по умолчанию — нынешние константы `types.ts`. Это делает первый запуск
после релиза неотличимым от последнего запуска до него.

Настройки, пришедшие из БД, проходят через `normalizeSettings`: недостающие поля
добираются дефолтами, числа зажимаются в разумные границы. Прогон, записанный до
релиза, не имеет ни одного из новых полей и должен читаться без ошибок.

## Границы значений

| Поле | Мин | Макс | Ноль значит |
|---|---|---|---|
| Переписок в день | 0 | 30 | в этот день своим не пишем |
| Сообщений в переписке | 2 | 40 | — (переписка из одной реплики не переписка) |
| Сообщений в чатах | 0 | 30 | в этот день в чатах не пишем |
| Реакций в чатах | 0 | 60 | реакции не ставим |
| Чатов на аккаунт | 1 | 10 | — |
| Дней | 1 | 14 | — |

Ноль — допустимое значение, а не ошибка ввода: «в первый день только реакции» —
осмысленный сценарий. Потолки нужны не как рекомендация, а как защита от опечатки:
случайный лишний ноль в поле реакций отправит партию в бан.

## Где хранится и когда применяется

Настройки живут в новой колонке `tg_outreach_campaigns.warmup_settings` (jsonb,
default `'{}'`). Кнопка «Сохранить» пишет туда.

При старте прогрева настройки копируются в `tg_outreach_warmup_runs.settings` —
снимок, по которому идёт прогон. Так уже устроен флаг `public_chats`, и причина
та же: перезапуск воркера посреди прогрева должен видеть то же решение, что
принял оператор.

Если прогрев идёт, сохранение пишет **в оба места**. Воркер и сейчас перечитывает
прогон на каждой итерации цикла (`getActiveRun`), так что новые числа он увидит
сам. Но план дня строится один раз — значит, правки вступают со следующего дня.
Это не компромисс ради простоты, а нужное поведение: у запланированных на сегодня
переписок уже проставлено время, часть выполнена, и пересчёт превратил бы
статистику дня «сделано X из Y» в прыгающую цифру.

Интерфейс говорит об этом прямо, а не оставляет оператора гадать.

## Интерфейс

Вкладка «Прогрев» после переезда:

```
полоса управления (статус, «дней», старт/стоп)
▾ Настройки прогрева                        ← новый блок, свёрнут во время прогрева
    Между своими        · 2 пары полей + предпросмотр по дням
    В публичных чатах   · переключатель секции
                          2 пары полей + «чатов на аккаунт»
                          список чатов, ввод ссылок, «Проверить»
    ☐ задать по дням вручную  →  таблица День 1…N × 4 колонки
    [Сохранить]
метрики
аккаунты · переписки/активности
логи
```

Решения по интерфейсу:

- **Блок свёрнут по умолчанию, пока прогрев идёт** — но раскрывается и правится.
  Оператор открывает вкладку во время прогрева, чтобы смотреть, а не настраивать;
  экран и так плотный.
- **Поле «дней» остаётся в полосе управления.** Оно управляет запуском, а не
  нагрузкой; в шапке блока настроек показывается справочно, чтобы таблица по дням
  не выглядела оторванной от их числа.
- **Предпросмотр под полями простого режима** («день 1 · 2×3 → день 2 · 3×4 …»).
  Без него два числа «2 → 8» ничего не говорят о том, что случится в среду.
- **Таблица предзаполняется кривой.** Ручной режим — это «поправить пару клеток»,
  а не «заполнить двадцать полей с нуля».
- **Текущий день подсвечен** в таблице во время прогрева, с пометкой, что правка
  этой строки уже ни на что не повлияет.
- **Галочка «Активность в чатах» уезжает** из полосы управления и становится
  переключателем секции: включение этапа и его настройка — одно место.
- Предупреждение про единственный рабочий чат и счётчик непроверенных
  переезжают вместе со списком.

## Крайние случаи

| Случай | Поведение |
|---|---|
| Меняем «дней» с 4 на 7 при заполненной таблице | Недостающие строки дозаполняются кривой |
| Меняем «дней» с 7 на 4 | Лишние строки остаются в `per_day`, не читаются; вернёте 7 — снова заработают |
| Прогон, начатый до релиза | `normalizeSettings` добирает дефолты, прогрев идёт как раньше |
| Кампания без сохранённых настроек | Дефолты из констант, поля предзаполнены ими же |
| `public_chats` включён, а чатов нет | Как сейчас: предупреждение в лог, этап пропущен |
| Ручной режим, вся строка нулевая | Допустимо: день без активности |
| Сохранение во время прогрева | Пишем в кампанию и в прогон, показываем «вступит со следующего дня» |

## Проверка

Тесты на `settings.ts` — основная защита, потому что вся арифметика фичи там:

- дефолтные настройки в режиме `curve` дают ровно нынешние нормы для дней 1…7
  (регрессия: если релиз тихо изменит нагрузку, это заметит тест, а не Telegram);
- дни за пределами `ramp_days` держатся на потолке;
- ручной режим отдаёт строку таблицы как есть;
- день за пределами таблицы берёт последнюю строку;
- `normalizeSettings` на пустом объекте, на `null`, на снимке старого формата и
  на мусоре с числами вне границ;
- `curveToPerDay` даёт ровно то, что покажет предпросмотр.

Тесты планировщиков (`warmupSchedule`, `warmupChatSchedule`) переводятся с
`targetOverride`/`repliesOverride` на явную передачу норм — они и сейчас
проверяют планирование при подставленных числах, меняется только способ подставить.

Отдельно — тест на то, что `assignChats` получает `chats_per_account` из настроек,
а не константу.

## Что осознанно не делаем

- **Не даём настраивать паузы между репликами и активное окно суток.** Оператор
  их не просил, а неверно выставленное окно ломает прогрев тише всего.
- **Не пересчитываем план текущего дня.** Разобрано выше.
- **Не делаем шаблоны «осторожный/обычный/быстрый».** Обсуждали, отказались:
  цифры для таких режимов пришлось бы придумать, а прямая настройка их заменяет.
- **Не переносим настройки между кампаниями.** Копирование настроек — отдельная
  задача, если возникнет спрос.
