# Автоматизация отчётов продаж (маркетинг + аутрич + общий саммари) — Design Spec

**Date:** 2026-07-22 (rev. 2026-07-22 — вернули отчёт 3)
**Status:** Draft → user review
**Scope:**
- **Phase 1 (MVP)** — раз в сутки берём новые сделки из AMO и добавляем строки в две Google-таблицы (маркетинг и аутрич). Ничего умного — только копипаст данных из AMO.
- **Phase 2 (после MVP)** — общий еженедельный саммари продаж по 5 каналам (Маркетинг / SMM / Аутрич / Партнёрка / TG Outreach), автоматически отправляется в личку Егору пятничным TG-ботом. Ручной труд Егора выведен.

Что по-прежнему **не автоматизируется** — качество лида, статус, «на чём остановились», комментарии, «Лидов» в саммари (зависит от разметки качества). Всё это остаётся сейлзам.

## 1. Цель

Убрать ручной труд двух ролей:
- **Максим (маркетолог)** — вручную копирует лидов из TG-чата «Продажи Polza → General» в маркетинг-таблицу
- **Нина и другие спецы аутрича** — вручную копируют лидов в аутрич-таблицу при передаче сейлзу

Оба процесса — просто копипаст данных из AMO в Google Sheet. Все сделки уже в AMO (см. [[amo-single-source-of-truth]]), значит ручную часть можно снять полностью.

**Что остаётся сейлзам** (не автоматизируем):
- Качество лида, статус лида, «на чём остановились», комментарии — это ручная работа сейлза, LLM не заменяет.
- Пятничный саммари Егора (общий по 5 каналам) — Егор продолжает писать сам.

## 2. Что делаем

**Один ночной воркер, два конфига:**

- Раз в сутки в 3:30 МСК (после того как в 2:00 отработал существующий AMO-синк `services/portal-external-sync/sources/amo.py`)
- Читает `amo_leads`, применяет фильтр по каждому из двух конфигов
- Для каждого нового лида собирает строку из данных, которые уже есть в AMO
- Пишет через Google Sheets API в соответствующую таблицу, вкладка «Лиды»
- Дедуплицирует по `amo_id` — при повторном прогоне не добавляет ту же сделку дважды

**Два конфига:**

| Отчёт | Google Sheet (MVP — тестовые копии) | Фильтр AMO |
|---|---|---|
| **Маркетинг** | [тестовая копия](https://docs.google.com/spreadsheets/d/1kKDO-vqpjqOIC9OQogwQrhxs1s1-eC_IBzrZqU9ZvUs/) (`1kKDO-vqpjqOIC9OQogwQrhxs1s1-eC_IBzrZqU9ZvUs`) — прод: [таблица Максима](https://docs.google.com/spreadsheets/d/1RIlIcheJoFzp63t0QPVWnGc8e7GKDzCGKhIz8-UO0xg/) | `Источник ≠ 'Email Outreach'` (всё, кроме аутрича) |
| **Аутрич** | [тестовая копия](https://docs.google.com/spreadsheets/d/14Kg75x91STU3RFLbVGf5WeNxpQUoBUth-Gm0fEVDRCU/) (`14Kg75x91STU3RFLbVGf5WeNxpQUoBUth-Gm0fEVDRCU`) — прод: [таблица Нины](https://docs.google.com/spreadsheets/d/1SdY-4mq3_PcYCSrIZmlvU5UkuqvGmMOunoQWGH8b9QM/) | `Источник = 'Email Outreach'` |

MVP настраиваем и запускаем на тестовых копиях. При переходе на прод — только замена `spreadsheetId` в конфиге, кода не меняем.

## 3. Какие колонки заполняем

### Маркетинг-таблица

| Колонка | Значение | Источник |
|---|---|---|
| Ссылка на лид в AMO | `https://<домен>.amocrm.ru/leads/detail/<amo_id>` | `amo_leads.amo_id` |
| UTM (5 строк: source/medium/campaign/content/term) | Как в текущей таблице у Максима | `amo_leads.raw` custom-поля |
| Площадка | Органика / Я.Директ / HH / Инстаграм / VS | правилами из UTM (см. §5.2) |
| Дата | Дата поступления заявки | `amo_leads.created_at` |
| Телефон | Телефон контакта | `amo_leads.contact_phone` |
| Email | Email контакта | `amo_leads.contact_email` |
| Имя | Имя контакта | `amo_leads.name` |
| Кто обрабатывает | Менеджер | `amo_users.name` по `responsible_user_id` |
| Категория «источник для…» | Лиды Директ / Лиды копирайт / Заявки органика | правилами из площадки |

**Не заполняем** (сейлз сам): дата последнего контакта, качество лида, на чём остановились, свободные комментарии.

### Аутрич-таблица

| Колонка | Значение | Источник |
|---|---|---|
| Имя | Имя контакта | `amo_leads.name` |
| Контакт | Телефон | `amo_leads.contact_phone` |
| Email | Email | `amo_leads.contact_email` |
| Организация | Название компании | `amo_leads.company_name` |
| Сайт | Сайт компании | `amo_leads.company_website` |
| Дата передачи | Дата создания сделки в AMO | `amo_leads.created_at` |
| Статус | Текущий этап воронки | `amo_leads.status_name` |

**Не заполняем** (сейлз/спец сам, если нужно): Оффер (это внутренний артефакт), Сфера деятельности (нет в AMO), Из какой кампании (в Instantly, договорились не лезть), Ком-й, статус справа (квалификация).

## 4. Что уже готово, что надо доделать

### Готово (используем как есть)

| Возможность | Где |
|---|---|
| AMO CRM ingestion | `services/portal-external-sync/sources/amo.py` → `amo_leads` + `amo_users` + `amo_statuses`. Ночной APScheduler 2:00 МСК |
| Google service account | `GOOGLE_SERVICE_ACCOUNT_EMAIL`, `GOOGLE_PRIVATE_KEY` в env — уже используется в `app/src/app/api/reglament/import-google-doc/route.ts` (Drive readonly) |
| `googleapis` npm пакет | `app/package.json:75` (v144) |
| Воркер-паттерн | `app/worker/_shared.ts` (`pollLoop`), пример — `app/worker/salesAiAnalysis.ts` |
| Semaphore CI/CD | `.semaphore/semaphore.yml` + `scheduled-deploy.yml` |
| Observability | таблица `external_sync_runs` |

### Надо доделать

1. **Google Sheets writer** — новый модуль `app/src/lib/googleSheets/writer.ts`. Auth: тот же service account JWT + добавить scope `https://www.googleapis.com/auth/spreadsheets`. Методы: `appendRows()`, `readColumn()` (для дедупликации).
2. **UTM extractor** — модуль `app/src/lib/leadsReport/extractUtm.ts`. Извлекает UTM из `amo_leads.raw` (custom-поля / текст заявки). Используется только маркетинг-конфигом.
3. **Площадка mapper** — `app/src/lib/leadsReport/platformMapper.ts`. Правила «UTM → Площадка» + «Площадка → категория» для отчёта 1.
4. **Конфиги** — `app/src/lib/leadsReport/config.ts`: два объекта (marketing, outreach) с фильтром AMO + список колонок.
5. **Row builder** — `app/src/lib/leadsReport/rowBuilder.ts`. По конфигу собирает финальный массив ячеек.
6. **Оркестратор** — `app/src/lib/leadsReport/report.ts`. Читает БД → строит строки → пишет в Sheet.
7. **Cron воркер** — `app/worker/leadsReport.ts` + `leadsReportCron.ts`. Раз в сутки в 3:30 МСК, прогоняет оба конфига.
8. **Мелкая миграция** — добавить `leads_report_marketing`, `leads_report_outreach` в check-constraint `external_sync_runs.source`.

## 5. Ключевые детали

### 5.1. Извлечение UTM

UTM бота заявки хранятся внутри `amo_leads.raw` jsonb. Возможные места (проверяются последовательно):
- `raw.custom_fields_values[]` с `field_name` содержащим `utm_*`
- Текст в поле «Комментарий» / примечании сделки (regex `utm_source:\s*(\S+)` и т.д.)

Если не нашли ни там, ни там — колонки UTM остаются пустыми (лид всё равно попадает в таблицу).

**Замечание:** точное место посмотрим один раз через Portal DB MCP на нескольких свежих сделках — тогда упростим цепочку.

### 5.2. Маппинг UTM → Площадка

Правила (в порядке проверки):

```
if utm_source == 'yandex' && utm_medium == 'cpc'   → 'Я.Директ'
if utm_source in ('polzaagency','hh')              → 'HH'
if utm_source == 'inst'                            → 'Инстаграм'
if utm_source == 'vs' or campaign contains 'vs'    → 'VS'
if utm пусты                                        → 'Органика'
else                                                → 'Другое (' + utm_source + ')'
```

Категория «источник для…»:
```
Я.Директ, VK, Инстаграм → 'Лиды Директ'
HH                       → 'Лиды копирайт'
Органика                 → 'Заявки органика'
```

Хранятся в коде с unit-тестами. Расширяются PR-ом при появлении новых источников.

### 5.3. Как читать custom-поле «Источник»

`amo_leads.raw.custom_fields_values[]` — массив объектов вида `{field_id, field_name, values[]}`. Helper `extractCustomField(raw, name)` берёт первое значение поля с `field_name == 'Источник'`. `field_id` можно захардкодить в конфиг (найти разово через Portal DB MCP), это ускорит поиск.

### 5.4. Отправка в Google Sheet

**Auth:** тот же service account JWT, что для Drive. Добавляем scope `https://www.googleapis.com/auth/spreadsheets`. Владельцы обеих таблиц (маркетинг + аутрич) шарят **Editor**-доступ на service-account email (`GOOGLE_SERVICE_ACCOUNT_EMAIL`).

**Дедупликация:** храним `amo_id` в служебной колонке (например, в конце таблицы — «AMO id»). При каждом прогоне читаем `amo_id` через `sheets.values.get`, пропускаем те, что уже есть. Новые — `append` в конец.

**Порядок:** новые лиды в конце. Сортировка по дате остаётся ручной (Sheets sort) — сейлзы делают как удобно.

## 6. Обработка ошибок и observability

Логируем в `external_sync_runs`. Источники:
- `leads_report_marketing` — прогон по маркетинг-конфигу
- `leads_report_outreach` — прогон по аутрич-конфигу

Каждый прогон: `started_at`, `finished_at`, `status`, `records_upserted`, `error`, `meta` (в meta — `{new_leads: N, skipped_dedup: N, sheet_id: '...'}`).

**Failure modes:**
- Google Sheets API 401/403 → job = 'error', понятный текст (скорее всего забыли шарить таблицу).
- Google Sheets API rate limit (60 req/min per project) → retry с backoff. Лимит не грозит — десятки строк в день.
- AMO sync ещё не прошёл (крон запустился раньше 2:00) → пустой прогон, warning в meta.
- Custom-поле «Источник» пустое → лид попадает в маркетинг-фильтр (по умолчанию), помечается в meta.

1. **Одноразовые проверки через Portal DB MCP:**
   - `SELECT DISTINCT` по «Источник» на свежих сделках — понять реальные значения (Email Outreach, Партнёрка и т.п.) и `field_id`.
   - Посмотреть на нескольких сделках, где лежат UTM в `raw`.
2. **Миграция:** добавить `leads_report_marketing`, `leads_report_outreach` в `external_sync_runs.source` check-constraint.
3. **Google Sheets access:** расшарить обе **тестовые** таблицы на service account email (`GOOGLE_SERVICE_ACCOUNT_EMAIL`) с правами **Editor**. При переходе на прод — то же самое для боевых таблиц.
4. **Реализация** модулей в порядке: writer → config → extractUtm → platformMapper → rowBuilder → report → cron. Каждый под тестами.
5. **Semaphore CI:** вписать в `.semaphore/semaphore.yml` и `scheduled-deploy.yml` ([памятка про CI](../memory/ci-is-semaphore.md)).
6. **Dry-run на dev:** прогон против тестовых копий обеих таблиц.
7. **Deploy на прод** (делает пользователь, [регламент](../memory/prod-deploy-ownership.md)).
8. **Первый прогон:** ручной триггер по каждому конфигу, проверка что Максим и Нина видят все свои лиды.
9. **Мониторинг 1-2 недели:** `external_sync_runs`, фидбек команды.

**Оценка:** ~5-7 рабочих дней.

## 9. Открытые вопросы

### #1 Точные значения `Источник` в AMO

Известно: `Email Outreach`. Остальное найдём одним `SELECT DISTINCT` через Portal DB MCP. Никаких блокеров.

### #2 Точное место UTM в `raw`

Тоже одним запросом через MCP. Не блокирует — extractor делаем защитным.

### #3 Куда воткнуть служебную колонку `AMO id` в таблицах

В конце (после всех колонок Максима/Нины) или в самом начале (A) — согласовать с ними, чтобы не мешало их привычному виду. Скорее всего в конце и скрытая.

### #4 Порядок первого backfill

При первом прогоне подтянуть только новые (за последние N дней) или все исторические? Первое — быстро, второе — полная синхронизация. Скорее «за последние 30 дней», а исторические — по запросу.

## 10. Phase 2 — общий еженедельный саммари в TG-бот

Инкремент над Phase 1: собираем метрики по всем 5 каналам продаж (Маркетинг / SMM / Аутрич / Партнёрка / TG Outreach) в единое TG-сообщение по шаблону Егора, отправляем в личку админам и подписчикам. Ручной труд Егора выведен.

### 10.1. Модель доступа

TG-бот с чувствительными данными по лидам — нельзя открывать всем, кто найдёт бота. Модель:

- **Админы** — прописаны в env `LEADS_REPORT_TG_ADMIN_IDS=833825243,475474557` (chat_id через запятую). Получают саммари автоматически. Могут управлять списком подписчиков.
- **Подписчики** — хранятся в БД (таблица `leads_report_subscribers`). Админ добавляет их командой бота.
- **Кто угодно ещё** — бот отвечает «нет доступа», данные не сливает.

### 10.2. Команды бота

| Команда | Кому | Что делает |
|---|---|---|
| `/start` | всем | если ты админ/подписчик — «будешь получать саммари». Иначе — «нет доступа, скинь свой chat_id `<id>` админу». |
| `/whoami` | всем | показывает свой chat_id и статус (admin/subscriber/none). |
| `/add <chat_id>` | только админы | добавляет подписчика. |
| `/remove <chat_id>` | только админы | убирает подписчика. |
| `/list` | только админы | список всех подписчиков + админов. |

### 10.3. Метрики (SQL шаблон)

Единый шаблон, параметризуется фильтром канала:

```sql
-- Пришло
SELECT COUNT(*) FROM amo_leads
WHERE {channel.amoFilter}
  AND created_at >= :week_start AND created_at < :week_end;

-- Встреч запланировано (текущий статус = 'Назначена встреча')
SELECT COUNT(*) FROM amo_leads
WHERE {channel.amoFilter}
  AND status_name = 'Назначена встреча'
  AND updated_at >= :week_start AND updated_at < :week_end;

-- Встреч было (текущий статус ≥ 'Встреча проведена + КП отправлено', не считая won/lost)
SELECT COUNT(*) FROM amo_leads
WHERE {channel.amoFilter}
  AND status_id IN (
    SELECT status_id FROM amo_statuses
    WHERE pipeline_id = 7670334
      AND sort >= (SELECT sort FROM amo_statuses
                   WHERE pipeline_id = 7670334
                     AND status_name = 'Встреча проведена + КП отправлено')
      AND status_id NOT IN (142, 143)
  )
  AND updated_at >= :week_start AND updated_at < :week_end;
```

Ограничение (то же, что для Sheets): «встреч было» считается по факту прохождения этапа за неделю. Если сделка прошла встречу ранее, а `updated_at` изменился сейчас — засчитается неверно. Точная история — только через `amo_events` (не в этой спеке).

### 10.4. Фильтры по каналам

| Канал | Фильтр по «Источник» |
|---|---|
| Маркетинг | `NOT IN ('Email Outreach', 'Telegram Outreach', 'Партнёрка', 'SMM')` |
| SMM | `= 'SMM'` (уточнить точное значение через `SELECT DISTINCT`) |
| Аутрич | `= 'Email Outreach'` |
| Партнёрка | `= 'Партнёрка'` (уточнить точное значение) |
| TG Outreach | `= 'Telegram Outreach'` |

### 10.5. Формат сообщения

```
📊 Отчёт продаж — неделя 15.07-21.07

Маркетинг
Пришло — 47 | Лидов — 12 | Встреч (Было/Запланировано) — 6/9

SMM
Пришло — 8 | Лидов — 3 | Встреч (Было/Запланировано) — 1/2

Аутрич
Пришло — 12 | Лидов — 5 | Встреч (Было/Запланировано) — 3/4

Партнёрка
Пришло — 5 | Лидов — 2 | Встреч (Было/Запланировано) — 2/1

TG Outreach
Пришло — 9 | Лидов — 4 | Встреч (Было/Запланировано) — 1/3
```

**«Лидов»** считаем по тому же принципу, что и «Встреч было»: сделки с текущим этапом `sort ≥ sort("Квал-лид")` (кроме won/lost). Ключевое требование от бизнеса (Егор, 23.07.2026): в AMO создаётся новый этап «Квал-лид» между «Первый контакт» и «Назначена встреча». Всё что на нём и дальше — считается как «Лид».

**Опорный этап хардкодится в конфиг:**
```
QUAL_LEAD_STATUS_NAME = 'Квал-лид'  // точное имя уточнит Егор при создании этапа
```

Если Егор ещё не создал этап на момент запуска саммари — метрика «Лидов» = 0 по всем каналам (SQL просто не находит опорную точку). После создания — начнёт считаться автоматически, ничего в коде менять не надо.

### 10.6. Технические компоненты

- **Резидентный воркер** `leadsReportBot.ts` — long polling через Telegram Bot API (`getUpdates`), обрабатывает команды, пишет в `leads_report_subscribers`. По аналогии с `sales-chat-logger` — контейнер живёт постоянно.
- **Пятничный крон** `leadsReportSummaryCron.ts` — one-shot запуск в 15:00 UTC пятницы (= 18:00 МСК). Считает метрики по 5 фильтрам, форматирует, шлёт всем получателям через `sendMessage`. Логирует в `external_sync_runs`.
- **Миграция**: таблица `leads_report_subscribers` + расширение `external_sync_runs.source` (`leads_report_summary`).

### 10.7. Идемпотентность

Если крон запустился повторно в ту же пятницу — шлём заново каждому получателю (Telegram сам не дедуплицирует, но получатели увидят повтор — это не критично, крон не запускается чаще раза в день по расписанию). Более сложную защиту (сохранять `message_id` и `editMessageText` при повторе) — не делаем на MVP.

## 11. Не в скоупе

- LLM-подсказки (качество лида, «на чём остановились»).
- Пятничный саммари в отдельные вкладки таблиц (в Sheet — не пишем, только в TG).
