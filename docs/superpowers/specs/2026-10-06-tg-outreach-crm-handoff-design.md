# TG-аутрич: лиды при передаче падают в CRM (amoCRM)

Дата: 06.10.2026. Статус: дизайн согласован с Дмитрием К.

## Зачем

Лиды TG-аутрича сейчас передаются только карточкой в Telegram-чат. В AMO их
заводят руками, а по правилу «каждая сделка в AMO» ([[amo-single-source-of-truth]])
без этого лид не попадает в отчёты продаж. Нужно: при передаче лида сделка
сразу создаётся в CRM. Куда именно, выбирается в кампании: в нашу AMO
(Polza) или в amoCRM клиента, если кампания ведётся для клиента.

## Решения

| Вопрос | Решение |
|---|---|
| Какие CRM | Только amoCRM: наша и клиентская. Bitrix24 и вебхук не делаем |
| Кто подключает клиентскую AMO | Наши сотрудники в TG-аутриче. Клиентский кабинет не трогаем |
| Воронка и этап | Выбираются в кампании из списков, которые портал подтягивает из AMO. Для нашей AMO по умолчанию «Первичные продажи», первый этап |
| Какие передачи идут в CRM | Лиды, переданные и кнопкой, и автоматически (по интересу). «Кандидаты в партнёры» не идут |
| «Компания» | Название кампании (`Polza_Старые аккаунты`), это просто подпись. Сущность «Компания» в AMO не создаём |
| Оффер | Тег сделки + строка в комментарии |
| Переписка | Комментарий (примечание) к сделке, текстом карточки передачи |

## Что видит сотрудник

**Раздел «Подключения CRM»** в TG-аутриче (рядом с настройками кампаний):

- «Наша AMO (Polza)» — встроенная строка, ключ берётся из `AMO_ACCESS_TOKEN` сервера, редактировать нечего.
- «Добавить amoCRM клиента»: название, адрес (`client.amocrm.ru`), долгосрочный токен.
  При сохранении портал сразу проверяет подключение (запрос списка воронок).
  При ошибке подключение не сохраняется, а под формой показывается одна строка с причиной.
- Токен после сохранения не показывается. Его можно заменить новым, подключение можно удалить.
  Если подключение используется в кампаниях, перед удалением портал спросит подтверждение и выключит у этих кампаний блок CRM.

**Блок «Передавать в CRM»** в настройках кампании (вкладка «Настройки», после «Чат для пересылки (+)»):

- переключатель вкл/выкл;
- подключение: «Наша AMO» или одно из клиентских;
- воронка и этап: выпадающие списки, загружаются из выбранного подключения.

Подписи короткие, одной строкой ([[ui-captions-short]]).

**Карточка диалога** показывает статус отправки в CRM рядом со статусом передачи:

- «В CRM ✓» со ссылкой на сделку;
- «В CRM: в очереди»;
- жёлтая строка «CRM: <ошибка>» и кнопка «Отправить в CRM ещё раз».

## Что попадает в AMO

На каждую передачу лида создаётся одна запись в очереди и одна сделка:

1. **Контакт.** Ищем `GET /api/v4/contacts?query=<ник без @>` и берём точное совпадение: имя `@<ник>` или ник в поле Telegram контакта (правило поля — как у ночного синка, `_tg_from_contact`). Регистр не учитываем.
   - Нашли контакт — сделку привязываем к нему.
   - Не нашли — создаём контакт с именем `@<ник>` и ником в поле Telegram. Поле — стандартное «Мессенджеры» (код IM, вариант TELEGRAM), а если его нет — текстовое поле с Telegram/ТГ в названии (`GET /api/v4/contacts/custom_fields`, кеш на процесс). Нет и такого — ник остаётся только в имени.
   - Если ника нет, имя контакта `TG ID <tg_user_id>`; поиск в этом случае тоже идёт по этой строке.
2. **Сделка** — `POST /api/v4/leads`:
   - `name`: `@<ник> · <название кампании>`
   - `pipeline_id`, `status_id` — из настроек кампании
   - `_embedded.tags`: `[{name: <оффер>}]`, если оффер известен
   - `_embedded.contacts`: `[{id: <контакт>}]`
   - **только для нашей AMO**: поле «Источник» (`field_id 1314379`) = enum со значением `Telegram Outreach`.
     `enum_id` ищем по тексту через `GET /api/v4/leads/custom_fields/1314379` и кешируем в памяти процесса.
     Если значение не найдено, сделку всё равно создаём, а в `error_message` пишем предупреждение. Отправка от этого не падает.
3. **Комментарий** — `POST /api/v4/leads/<id>/notes`, `note_type: common`, `params.text` = текст карточки передачи (шапка, ник, оффер, источник-чат, переписка). Текст тот же, что уходит в Telegram.
   Длинную переписку режем на куски примерно по 8000 символов, по границе строк. Каждый кусок — отдельное примечание.

Повторная передача того же диалога вторую сделку не создаёт (см. «Идемпотентность»).

## Как устроено

### Данные

**`crm_connections`** — клиентские подключения:

- `id uuid pk`, `name text not null`, `kind text not null default 'amocrm' check (kind = 'amocrm')`
- `base_url text not null` (нормализованный `https://<sub>.amocrm.ru`)
- `secret_encrypted text not null` (AES-256-GCM через `lib/cryptoGcm.ts`, ключ `CRM_CRED_KEY` в env)
- `status text` (`ok` / `error`), `last_verified_at`, `last_error`
- `created_by uuid`, `created_at`, `updated_at`
- RLS включён. Таблица без политик для `authenticated`: все чтения и записи идут через API-роуты под service_role, наружу отдаются колонки без `secret_encrypted`.
- `grant ... to service_role` (иначе упадёт `grants.test.ts`).

Нашу AMO в таблицу не кладём: она адресуется значением `'polza'` и берёт `AMO_BASE_URL` / `AMO_ACCESS_TOKEN` из env, так же как остальной код портала.

**`tg_outreach_campaigns.crm_settings jsonb`** (null = выключено):

```json
{ "enabled": true, "connection": "polza" | "<uuid crm_connections>",
  "pipeline_id": 7670334, "status_id": 123 }
```

В PUT `campaigns/[id]` добавить `crm_settings` в белый список полей.

**`tg_outreach_crm_pushes`** — очередь:

- `id`, `campaign_id → tg_outreach_campaigns on delete cascade`, `dialog_id → tg_outreach_dialogs on delete cascade`
- `connection text not null` (`'polza'` или uuid); `pipeline_id`, `status_id` — снимок настроек на момент постановки
- `username`, `tg_user_id`, `offer`, `campaign_name`, `message_text` — снимок карточки
- `status text check in ('pending','sent','failed')`, `attempts int default 0`, `next_attempt_at timestamptz default now()`
- `amo_lead_id bigint`, `amo_contact_id bigint`, `lead_url text`, `error_message text`
- `created_at`, `sent_at`
- уникальный частичный индекс `(dialog_id) where status in ('pending','sent')` — защищает от дублей;
  индекс `(status, next_attempt_at) where status = 'pending'` — для опроса
- RLS на select для `authenticated` (как у `tg_outreach_lead_forwards`), запись — только service_role; гранты.

### Когда ставится задача

Задача ставится, только если у кампании `crm_settings.enabled = true` и `kind = 'lead'`. Ставим её в момент, когда лид действительно передан, а не когда нажали кнопку. Так отменённая по ошибке передача («Отменить отправку») в CRM не попадает.

- **Кнопка:** в `lib/tgOutreach/leadForward.ts`, в `sendLeadForward` после перевода строки в `sent`. Если передача окончательно ушла в `failed`, задачу тоже ставим: лид настоящий, просто не дошёл до чата.
- **Автопередача:** в `campaignLoop.ts` `handleChat`, после попытки `forwardToTargetChat` (успешной или нет) — там же, где пишется `auto_forwarded_at` / `auto_forward_error`.

Постановка — один общий хелпер `enqueueCrmPush(db, {campaign, dialog, messageText, …})` в новом `lib/tgOutreach/crmPush.ts`. Он делает `insert … on conflict do nothing` (по уникальному индексу) и не бросает исключений: сбой постановки пишется в лог и не мешает передаче.

### Кто отправляет

Отправляет процесс `worker-tg-outreach`: в `main()` добавляется таймер `crmPushTimer` уровня процесса (раз в 15 с), рядом с `usernameCheckTimer`. Он не зависит от того, запущена ли кампания: у AMO нет телеграм-сессии, держать кампанию запущенной незачем.

Шаг опроса:

- берёт до 10 `pending` с `next_attempt_at <= now()`;
- для каждой: клиент AMO (`polza` или расшифрованное подключение) → контакт → сделка → примечания → `status='sent'`, `amo_*`, `lead_url = <base>/leads/detail/<id>`;
- каждый HTTP-запрос под таймаутом 30 с;
- ошибки:
  - сеть, 5xx, 429 → `attempts+1`, `next_attempt_at = now()+5 мин`; после 5 попыток → `failed`;
  - 401/403 (неверный или отозванный токен) → сразу `failed` с понятной причиной; у клиентского подключения ставим `status='error'`, `last_error`;
  - 400 (например, этапа больше нет) → сразу `failed` с текстом от AMO.
- Если сделка создана, а примечание не легло, `amo_lead_id` уже записан. При повторе сделку заново не создаём, только дописываем примечание.

Повторная отправка («Отправить в CRM ещё раз»): API-роут переводит `failed` → `pending`, `attempts=0`, `next_attempt_at=now()`. Снимок настроек берётся текущий из кампании, чтобы исправленный этап или токен подхватились.

### Клиент AMO

Новый `lib/crm/amoClient.ts`: `createAmoClient({baseUrl, token})` с методами `listPipelines`, `findContactByName`, `createContact`, `createLead`, `addLeadNotes`, `getEnumId(fieldId, value)`. Логику переиспользует нормализацию `baseUrl()` из `handoffCheck/amoApi.ts`, но клиент отдельный: тот модуль только читает и завязан на env. Лимит AMO — 7 запросов/с; опрос идёт последовательно, этого хватает.

### API-роуты (под `authenticateRequest` TG-аутрича)

- `GET/POST /api/tools/tg-outreach/crm-connections` — список (с встроенной `polza`) / создание с проверкой.
- `PUT/DELETE /api/tools/tg-outreach/crm-connections/[id]` — замена токена или названия / удаление.
- `GET /api/tools/tg-outreach/crm-connections/[id]/pipelines` — воронки и этапы (`id='polza'` для нашей).
- `POST /api/tools/tg-outreach/dialogs/[id]/crm-push` — «Отправить в CRM ещё раз».
- В выдаче диалогов добавить последнюю задачу CRM по диалогу (статус, ссылку, ошибку).

## Что нужно на сервере

- В прод-`.env` добавить `CRM_CRED_KEY` (32 байта, hex). Его читают web-приложение (шифрует при сохранении) и `worker-tg-outreach` (расшифровывает). Оба читают `.env` через `env_file`, compose править не нужно.
  `AMO_BASE_URL` и `AMO_ACCESS_TOKEN` в `.env` уже есть.
- Миграция применяется автоматически на деплое (`supabase/migrations`).

## Проверка

Новых тестов не пишем (правило проекта). После выкладки:

1. В нашей тестовой кампании включить блок, выбрать «Первичные продажи → первый этап».
2. Передать один диалог кнопкой и проверить в AMO: контакт `@ник`, сделка `@ник · кампания`, тег оффера, «Источник = Telegram Outreach», примечание с перепиской, ссылка на карточке диалога.
3. Передать тот же диалог ещё раз → вторая сделка не создаётся.
4. Подключение с заведомо неверным токеном не сохраняется, причина видна под формой.

## Вне объёма

Bitrix24 и вебхуки; подключение CRM клиентом из своего кабинета; обратная синхронизация (статусы сделок из CRM обратно в портал); передача «кандидатов в партнёры»; привязка кампании к проекту портала.
