# Календарь технички

Дата: 13.08.2026

## Зачем

Оплаты за техничку — прокси, серверы, API, софт — сегодня нигде не собраны. Экран
«Расходы» показывает их постфактум: деньги ушли, категория `tools` проставлена,
но узнать «что и когда спишется на следующей неделе» по нему нельзя. Ответ живёт в
головах и личных заметках, поэтому сервисы то продлевают вслепую, то теряют.

Ровно эту задачу для email-подписок решает «Календарь почт» (`/billing-calendar`,
таблица `email_subscriptions`): месячная сетка с датами списаний, автоматический
переход в «ожидает решения» за неделю до даты, решение «оставить/отменить» и
кнопка «оплатить». Техничке нужен такой же экран со своими полями и своими
правами доступа.

## Что делаем

Новая страница `/tech-calendar` — «Календарь технички». Только для админов. Своя
таблица в базе. Календарь почт не трогаем: он работает, и его переделка ради
соседней фичи — лишний риск.

### Данные

Таблица `tech_subscriptions`:

| Поле | Тип | Смысл |
| --- | --- | --- |
| `id` | UUID PK | |
| `service_name` | TEXT NOT NULL | Название сервиса: «Bright Data», «Hetzner CX32» |
| `service_type` | TEXT NOT NULL | `proxy` / `server` / `api` / `software` / `other` |
| `amount` | NUMERIC(12,2) NOT NULL | Сумма списания |
| `currency` | TEXT NOT NULL | `RUB` / `USD` |
| `billing_cycle` | TEXT NOT NULL | `monthly` / `quarterly` / `yearly` |
| `next_billing_date` | DATE NOT NULL | Дата следующего списания |
| `status` | TEXT NOT NULL | `active` / `pending_review` / `keep` / `cancel` |
| `decision_by` | UUID → profiles | Кто принял решение |
| `decision_at` | TIMESTAMPTZ | Когда |
| `decision_notes` | TEXT | Комментарий к решению |
| `notes` | TEXT | Свободная заметка |
| `created_by` | UUID → profiles | |
| `created_at` / `updated_at` | TIMESTAMPTZ | `updated_at` через триггер |

Индексы по `next_billing_date`, `status`, `service_type`.

Валюта ограничена `RUB`/`USD` через CHECK, а не свободной строкой: итог месяца
считается по каждой валюте отдельно, и третья валюта, залетевшая опечаткой, дала
бы молча потерянную строку в сумме.

Статуса `expired` — в отличие от почт — нет. Там он остался от прежней логики и
сейчас не выставляется ничем; переносить мёртвое состояние в новую таблицу незачем.

Привязки к проекту нет: техничка студийная, общая. Если однажды понадобится
делить по проектам, поле добавится миграцией — сейчас оно было бы пустым в 100%
строк.

### Доступ

Календарь почт ходит в базу прямо из браузера, а RLS у `email_subscriptions`
разрешает чтение любому залогиненному. Для технички так нельзя: экран админский, а
суммы по инфраструктуре — не то, что должен видеть клиент или подрядчик, даже
залезая в обход интерфейса.

Поэтому таблица запирается: RLS включён, политик для `authenticated` нет,
`service_role` получает GRANT (без него линт грантов в `app/tests/migrations/`
справедливо ругнётся). Все операции идут через серверные ручки, каждая начинается
с `requireAdmin` из `app/src/lib/adminAuth.ts`.

Три уровня, как у остальных админских экранов:

1. `app/src/lib/navigation.ts` — пункт меню с `adminOnly: true`;
2. `app/src/middleware.ts` — редирект на `/` для не-админа на `/tech-calendar`;
3. `layout.tsx` страницы — проверка `isAdmin(userRole)` на клиенте.

### Ручки

`app/src/app/api/tech-calendar/`:

- `GET /api/tech-calendar/subscriptions` — список. Перед выдачей сервер переводит
  в `pending_review` всё, у чего до даты ≤ 7 дней и статус `active`. Отдельный
  робот не нужен: экран открывают руками, а вычисление идемпотентно.
- `POST /api/tech-calendar/subscriptions` — создать.
- `PATCH /api/tech-calendar/subscriptions/[id]` — отредактировать.
- `DELETE /api/tech-calendar/subscriptions/[id]` — удалить.
- `POST /api/tech-calendar/subscriptions/[id]/renew` — продлить: принимает
  необязательные `next_billing_date` и `amount`; если их нет, дата считается
  сдвигом на цикл. Сбрасывает `status` в `active` и обнуляет решение.
- `POST /api/tech-calendar/subscriptions/[id]/decision` — решение `keep`/`cancel`
  с комментарием; пишет `decision_by`/`decision_at`.

Продление отдельной ручкой, а не через `PATCH`: это не «поправить строку», а
переход цикла со сбросом решения. Разными ручками эти два намерения не путаются, и
кнопка «Оплачено» не может случайно затереть решение, принятое пару минут назад.

### Расчёт дат

Чистый модуль `app/src/lib/techCalendar/dates.ts`, отдельно от UI, потому что
именно тут прячутся ошибки:

- сдвиг на цикл: месяц / 3 месяца / год;
- если в целевом месяце нет такого числа — берётся последний день месяца
  (31 января + месяц = 28 или 29 февраля). В почтах это место написано на
  `new Date(dateStr)` и уезжает в часовых поясах — здесь считаем по компонентам
  даты, без превращения в момент времени;
- `daysUntil(date)` — целое число дней до даты по местной дате, без часов.

### Интерфейс

`app/src/app/tech-calendar/` — страница, и `app/src/components/tech-calendar/` —
части. Не один файл на всё: календарь почт разросся до 1761 строки, и это ровно
тот случай, который не хочется повторять.

- `TechCalendarView.tsx` — состояние, загрузка, склейка;
- `StatsRow.tsx` — четыре плитки;
- `TypeBreakdown.tsx` — фильтр по типу и разбивка сумм;
- `MonthGrid.tsx` — сетка месяца с попапом дня;
- `UpcomingList.tsx` — «ближайшие 7 дней»;
- `SubscriptionModal.tsx` — создание / редактирование / продление / решение;
- `app/src/lib/techCalendar/stats.ts` — чистые функции подсчёта.

Плитки сверху:

1. **Активных сервисов** — статусы `active`, `pending_review`, `keep`.
2. **Ожидают решения** — `pending_review`; жёлтая, когда больше нуля.
3. **За этот месяц** — сумма списаний, чья дата попадает в показываемый месяц,
   **двумя строками: ₽ и $ раздельно**. Конвертации нет намеренно: курс в базе не
   хранится, а сложить разные валюты по выдуманному курсу — соврать в цифре, на
   которую смотрят при планировании. (Календарь почт именно так и делает: рисует
   `$` над суммой любых валют.)
4. **Решений на ближайшие 7 дней** — сколько сервисов упрётся в дату в течение
   недели и ещё не имеет решения.

Отменённые (`cancel`) в суммы месяца и в число активных не входят.

Фильтр по типу переключает и сетку, и плитки, и список ближайших. Рядом —
разбивка «сколько уходит на каждый тип за месяц», тоже ₽ и $ раздельно.

Сетка месяца: в клетке дня — сервисы с датой списания в этот день, точка статуса,
название, сумма. Клик по дню — попап со списком и итогом за день по валютам. Клик
по сервису — карточка с кнопками «Оплачено — продлить», «Оставить», «Отменить»,
«Редактировать», «Удалить».

Цвета статусов — те же, что в почтах, чтобы два календаря читались одинаково:
активна — синий, ожидает решения — жёлтый, оставить — зелёный, отменить — красный.

Окно продления показывает предрассчитанную дату и текущую сумму, оба поля можно
поправить: цены на прокси и серверы меняются от продления к продлению, и чаще
всего именно в этот момент их и правят.

Решение «Отменить» оставляет сервис в календаре красным, а не прячет: пока техник
реально не отключил сервис, деньги продолжают списываться, и строка должна мозолить
глаза.

## Тесты

`app/tests/lib/techCalendar/`:

- сдвиг даты по циклам, включая 31 января → конец февраля и 29 февраля
  високосного года → 28 февраля следующего;
- `daysUntil` на границах (сегодня = 0, вчера = −1);
- суммы месяца: две валюты не смешиваются, `cancel` не считается, чужие месяцы не
  попадают;
- счётчик «решений на неделю»: порог ровно 7 дней, вчерашние просрочки считаются,
  уже решённые — нет;
- перевод `active` → `pending_review` идемпотентен и не трогает `keep`/`cancel`.

`app/tests/api/tech-calendar/` — не-админ получает 403 на каждой ручке, включая
`GET`.

## Что не делаем

- Не переписываем календарь почт и не объединяем таблицы.
- Не связываем техничку с экраном «Расходы»: там факт списания из банка, здесь
  план платежей. Сведение одного с другим — отдельная задача, не эта.
- Не шлём уведомления в Telegram: сначала экран, поведение по напоминаниям станет
  понятно после недели использования.
- Не считаем историю продлений: сейчас нужен ответ «что платим и когда», а не
  журнал изменений.
