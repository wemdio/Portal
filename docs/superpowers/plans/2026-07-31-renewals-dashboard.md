> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development или executing-plans.

**Goal:** Третий дашборд портала — `/analytics/renewals`: сколько продлений, на какую сумму, средний чек, средний цикл, табличка проектов.

**Architecture:** Продления живут в `projects` с `project_type = 'Продление'` — отдельной сущности заводить не надо. Расчёт — чистые функции в `app/src/lib/renewals/`, по образцу `firstSales/`. Страница переиспользует приёмы дашборда первички.

## Принятые решения

| Решение | Выбор | Почему |
|---|---|---|
| Что такое продление | `projects.project_type = 'Продление'` | Поле заполнено у 128 из 139, других кандидатов нет |
| Дата продления | `payment_date` | 27 из 32 против 17 у договора |
| Проекты без даты | Отдельной строкой «без даты оплаты», не прячем | 4 проекта; молча выкинуть — соврать |
| Будущие даты | Считаются планом, не фактом; в метрики за прошедшие периоды не попадают | Иначе оборот покажет деньги, которых ещё нет |
| Оборот и средний чек | `budget`, парсится защитно | Сейчас все 32 — чистые числа, но колонка текстовая и однажды получит мусор |
| Средний цикл | Конец прошлого периода → `contract_date` | Решение пользователя. Работает только у проектов с историей периодов |
| Фильтр по KPI | Числовой факт, 27 из 32 | Единственный из трёх запрошенных фильтров, у которого есть данные |
| Фильтры «канал» и «сфера» | **Не делаем** | Канал заполнен у 3 из 32, поля сферы нет вообще. Вопрос задан Егору; добавим, когда появятся данные |

## Границы

**Средний цикл будет тонким.** История периодов есть у 11 проектов из 139, и не факт что это продления. Метрика покажет прочерк там, где истории нет — не ноль. Ноль читался бы как «продлили мгновенно».

**Фильтров по каналу и сфере в первой версии нет.** Это осознанный отказ, а не забывчивость: строить фильтр на трёх заполненных значениях из тридцати двух — значит показать инструмент, который врёт при каждом использовании.

## Task 1: Расчёт метрик

**Files:**
- Create: `app/src/lib/renewals/metrics.ts`
- Test: `app/tests/lib/renewals/metrics.test.ts`

Правила:

1. **Продление** — строка `projects` с `project_type = 'Продление'`. Сравнение регистронезависимое с обрезкой пробелов: поле текстовое и заполняется руками.
2. **Дата** — `payment_date`, строго формат `YYYY-MM-DD`. Всё, что не парсится, идёт в счётчик `withoutDate`, а не молча пропадает.
3. **Оборот** — сумма `budget`. Парсинг защитный: пробелы-разделители разрядов убираем, всё остальное нечисловое — в счётчик `withoutBudget`. `parseFloat` по грязной строке даст неверное число и не скажет об этом, поэтому проверяем строку целиком регуляркой до преобразования.
4. **Средний чек** — среднее и **медиана**. Распределение длиннохвостое: в выборке есть 45 000 и 600 000 рядом, среднее без медианы обманет.
5. **Будущие даты** — продления с датой позже «сегодня» в метрики периода не попадают, но считаются отдельно как `planned`. На дашборде это полезная цифра «сколько ждём», а не мусор.
6. **Цикл** — дни от `period_end` предыдущего периода проекта до `contract_date` продления. Нет истории периодов или нет даты договора → сделка в цикл не попадает; если таких большинство, флаг `cycleReliable = false` и UI показывает прочерк.
7. **Группировка по месяцам** — через `bucketKey` из `firstSales/buckets.ts`. Не копировать: границы МСК уже решены там, вторая реализация разъедется.

Тесты обязаны покрыть: тип с пробелами и другим регистром; бюджет с пробелами внутри числа; бюджет-мусор попадает в счётчик, а не в сумму; будущая дата не в обороте, но в `planned`; медиана на длинном хвосте; пустая выборка без NaN.
