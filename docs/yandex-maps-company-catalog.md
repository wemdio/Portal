# Общий каталог компаний Яндекс.Карт

Каталог хранится отдельно от результатов конкретного запуска парсера. Ключ записи —
стабильный ID организации из выгрузки Яндекс.Карт, поэтому повторное появление компании
в региональной и рубричной разбивке не создаёт новую карточку. Непустые поля объединяются,
а источники и число появлений сохраняются для контроля качества импорта.

## Откуда берутся страна, город и ссылка

В 13 269 xlsx-файлах **нет колонки «Страна»** — она есть только в 4 корневых CSV
(Абхазия, Армения, Молдова, Таджикистан). Импортёр достаёт страну из пути файла:

```
Разбивка по регионам\<Страна>\<Регион>\<Город>.xlsx
Разбивка по регионам\<Страна>\<Город>.xlsx
Разбивка по рубрикам\<Страна>\<Рубрика>\<Подрубрика>.xlsx
```

Колонка из файла всегда приоритетнее пути — путь только закрывает пробелы. Файл, названный
так же, как его папка (`Алтайский край\Алтайский край.xlsx`), — это сводка региона:
город из него не выводится, иначе «Алтайский край» попал бы в список городов.

Ссылки на карточку в xlsx тоже нет — она собирается из ID: `https://yandex.ru/maps/org/<id>`.
Яндекс открывает организацию по одному идентификатору, слаг не нужен.

## Поиск из интерфейса

Выбор страны, города и рубрики обслуживается каталогом и **не обращается к Яндексу**.

`yandex_maps_catalog_fill_job()` делает один `insert ... select` из каталога в
`yandex_maps_organizations`, поэтому строки не покидают Postgres.

**Почему сбор дольше поиска.** Это разные операции: поиск отдаёт страницу
найденного, сбор копирует каждую найденную строку в таблицу результатов. Замер на
100 000 организаций (локальный NVMe, прогретый кэш):

| Шаг | Время |
|---|---:|
| Найти 100 000 организаций | 0,48 с |
| Записать их в `yandex_maps_organizations` | 3,17 с |
| **Итого `fill_job`** | **3,28 с** |

Поиск — десятая часть, остальное копирование: 18 текстовых колонок, три индекса
(включая уникальный `(job_id, card_url)`) и uuid на каждую строку. На боевом сборе в
сотни тысяч строк с сетевого диска это и есть наблюдаемые минуты.

**Крупный сбор идёт порциями.** Замер на бою: 14 699 организаций — 7 с, 83 466 — 52 с,
то есть около 1650 строк в секунду, и время пропорционально объёму. Одним запросом
человек всё это время смотрит на пустой экран. Воркер вместо этого вызывает `fill_job`
лесенкой — 5 000, 20 000, 80 000, 320 000 — и после каждой порции пишет в задачу
`processed_organizations`. Первые тысячи ложатся за пару секунд, форма их сразу
показывает, дальше счётчик растёт на глазах.

Порции держатся на том, что `fill_job` вставляет с `on conflict do nothing` и возвращает
размер прибавки: следующий шаг видит уже вставленное и добавляет только новое. Курсора
и состояния не нужно. Последним всегда идёт вызов с настоящим потолком задачи — он
ничего не добавит, если всё собрано, но гарантирует полноту: выводить её из «прибавка
меньше порции» нельзя, потому что одна карточка может встретиться в каталоге дважды и
вставиться один раз.

Лишняя работа от лесенки невелика: шаги перечитывают уже вставленное, но не пишут его
заново, а поиск — около десятой части времени сбора.

Ссылки при сборе **не пишутся**: `yandex_maps_links` нужна живому парсингу, где их
собирают отдельным этапом и правят руками. Здесь она получала точную копию `card_url`
каждой строки — 1,47 с из 4,25 с и 56 МБ против 110 МБ у самих организаций
(миграция `20260810_0001`).

Радикально быстрее станет, только если перестать копировать вовсе и читать результаты
запуска прямо из каталога по сохранённым фильтрам — тогда сбор станет мгновенным, как
поиск. Это затрагивает результаты, экспорт и тарифный подсчёт строк, поэтому вынесено в
отдельное решение (пункт D в
[`yandex-maps-catalog-search-performance.md`](./yandex-maps-catalog-search-performance.md)).

Раньше это делал воркер: просыпался, читал каталог страницами по 2000 строк через
PostgREST и теми же страницами писал обратно — данные дважды шли по сети ради переноса
из одной таблицы базы в соседнюю.

**По умолчанию забирается всё, что нашлось.** Потолок был (50 000 строк) и держался на
том, что сбор был медленным; после индексов по токенам и настройки базы искусственная
отсечка не нужна: раз выбраны места и сферы, нужны все организации, а не произвольные
пятьдесят тысяч из них.

Поле «сколько забрать» — **необязательное ограничение**: указал число, заберём столько;
оставил пустым, заберём всё, хоть миллион. В кабинете клиента объём, наоборот,
обязателен — он списывается с тарифа, и «без ограничения» там превращается в остаток по
тарифу.

Где выполняется сбор, решается **по запрошенному объёму, без предварительного счёта**:

| Что запросили | Что происходит |
|---|---|
| число до `CATALOG_INLINE_LIMIT` (20 000) | Собирается прямо в запросе, API возвращает задачу уже `completed` с готовыми результатами |
| число больше порога **или** без ограничения | Задача заводится `pending`, её доделывает воркер. В форме она видна как выполняющаяся и закрывается сама |

Логика простая: `limit N` останавливается, набрав N строк, поэтому небольшое N всегда
быстрое. А без потолка объём заранее неизвестен, и держать на нём открытый запрос от
браузера нельзя. Воркер слушает realtime по `yandex_maps_jobs`, так что очередь добавляет
не минуты ожидания, а секунду.

**Сбор ходит в Postgres напрямую, мимо PostgREST и Kong.** Шлюз рвёт соединение через
60 секунд — и неважно, кто зовёт, API или воркер: `supabaseAdmin` в обоих случаях идёт по
HTTP. 09.08.2026 на этом упал сбор «Москва и область × Товары для дома и дачи» уже из
воркера. Гонять такую операцию через REST нечего: это один `insert ... select` внутри
базы, ни одна строка не покидает Postgres. Адрес берётся из `SUPABASE_DB_URL`
(`app/src/lib/parsers/yandexMapsCatalog.ts`); без переменной код молча работает через RPC
как раньше, с прежним ограничением по времени. Воркеру `worker-yandexmaps` эта переменная
добавлена в `docker-compose.prod.yml`.

**Предпросчёта «сколько найдётся» в форме больше нет.** Он уходил на каждое изменение
фильтра и стоил полного прохода по всем подходящим строкам: счёт обязан досмотреть
выборку до конца, в отличие от сбора. Объём каждого места и каждой рубрики виден в самих
списках — он берётся из заранее посчитанных справочников и не стоит ничего.
`countYandexMapsCatalog` осталась в коде для разовых проверок и скриптов.

Полей «URL поиска» и «организаций на 1 запрос» в форме больше нет: запуск — это один
запрос к своей базе, а не тысячи заходов в выдачу.

Живой парсинг по URL никуда не делся на стороне воркера — им пользуются
reputation-finder и гипотезы, — просто в этой форме его больше не завести.

Списки в форме строятся из справочников `yandex_maps_catalog_places` (4 777 записей) и
`yandex_maps_catalog_rubrics` (2 628), которые пересчитываются из самого каталога
функцией `yandex_maps_catalog_refresh_dictionaries()`. Благодаря этому на экране не может
появиться город или рубрика, за которыми в базе ничего нет.

Поиск сверяет выбранное место **и с городом, и с регионом**: в выгрузках Яндекса города
федерального значения (Баку, Москва) часть организаций держат на уровне региона с пустым
городом, и фильтр только по городу терял бы их десятками тысяч.

Рубрика сверяется **точным токеном**, а не подстрокой: `yandex_maps_rubric_tokens()`
разбирает `categories`/`subcategories` теми же правилами, что и пересчёт справочников,
а обслуживают отбор составные GIN «токены + город» и «токены + регион» (миграция
`20260807_0004`). Поэтому число рядом с рубрикой в форме и предпросчёт «сколько найдётся»
показывают одно и то же, а «Кафе» больше не приводит за собой «Интернет-кафе» и
«Антикафе» — они выбираются отдельными пунктами. Почему так и что это дало по времени —
[`yandex-maps-catalog-search-performance.md`](./yandex-maps-catalog-search-performance.md).

### Как устроен выбор мест и сфер

Списки занимают весь верх формы двумя высокими колонками, потому что выбирать
приходится из тысяч пунктов: 4,8 тыс. мест и 2,6 тыс. рубрик. На широком экране пункты
раскладываются в две-три колонки, длинный хвост догружается кнопкой, а не прячется
за жёстким лимитом отрисовки.

Высота задана на ряду, а списки добирают остаток через `flex-1`, подписи прижаты к низу
через `mt-auto`. Раньше высота стояла на каждом списке отдельно и подгонялась руками под
то, что над ним (у сфер сверху ещё поле ключевого слова) — любая правка сверху ломала
выравнивание, и колонки переставали совпадать по нижней границе.

| Что | Зачем |
|---|---|
| «Весь регион» в заголовке группы | Кладёт в запрос **один** регион вместо сотен городов. Поиск сверяет и с `city`, и с `region`, поэтому так забираются и организации региона без города |
| Чипы выбранного | Выбор виден и снимается по одному; раньше о нём говорил только счётчик |
| «Только с контактами» | Прячет рубрики, где телефона и сайта нет ни у кого: скамейки (554 тыс.), детские и мусорные площадки, велопарковки. Порог — 15% организаций с контактом |
| Процент у рубрики | Доля организаций с телефоном, сайтом или почтой — из `with_contacts` справочника |
| Быстрый выбор сферы | Только в кабинете клиента. В форме оператора убран: те же рубрики стоят первыми в самом списке, он отсортирован по охвату, и плашки над ним лишь дублировали их |
| Сортировка и «показать выбор» | По охвату, по алфавиту, по доле контактов; отдельный режим — показать только выбранное |

Массовый выбор рубрик ограничен 50 пунктами: каждая рубрика добавляет в условие
`like '%…%'` по двум колонкам, и «выбрать все 2 600» превратилось бы в запрос, который
база не досчитает. Города сверяются равенством по индексу — там потолка нет.

### Почему функции поиска собирают запрос текстом

`yandex_maps_catalog_search` и `yandex_maps_catalog_count` формируют условия через
`format('%L')` и выполняют `execute`. Это не небрежность, а замер: вариант с постоянным
набором условий вида «параметр пуст ИЛИ совпадает» шёл 11 секунд, тот же запрос
с подставленными значениями — 1 секунду. Такая дизъюнкция неиндексируема, база обязана
проверить каждую из 9,9 млн строк. Значения экранируются, подстановка кода невозможна.

## Фоновое пополнение новыми организациями

Механизм ищет **новое**, а не освежает старое.

1. Из очереди `yandex_maps_catalog_discovery_queue` берётся пара «место × рубрика».
2. Делается обычный поиск по Яндекс.Картам, собираются ссылки выдачи.
3. ID организации виден прямо в ссылке — известные отсеиваются запросом к своей базе,
   без обращений к Яндексу.
4. Карточки открываются **только у новых**, результат пишется в каталог.
5. Последним шагом — уборка: отметки «видели» и «кажется, закрылась».
6. Пара возвращается в очередь: нашлось новое — через 14 дней, пусто — через 60.

**Уборка идёт последней и её неудача ничего не стоит.** Раньше она стояла первым
шагом и роняла всё задание: 11.08.2026 на бою 343 пары из 20 000 висели в «упало»
с `Не удалось отметить организации: The upstream server is timing out`, и ни одной
новой организации по ним не собралось — среди них вся Москва, четвёртые сутки
подряд. Теперь ошибка пометки уходит в лог
(`parser.yandexmaps.catalog.mark_seen_failed`), найденное остаётся в каталоге, а
пара возвращается в очередь по обычному расписанию, а не через сутки как упавшая.

**Пометка ходит в Postgres напрямую**, как и сбор: через PostgREST её рвал Kong на
60 секундах (`app/src/lib/parsers/yandexMapsCatalog.ts`, адрес из `SUPABASE_DB_URL`).

Обход выполняется **в фоне относительно цикла опроса воркера**, а не внутри его
итерации. Пока он вызывался под `await`, цикл на нём стоял: круг обхода — это живой
поиск по Яндексу на минуты, и пользовательская задача, пришедшая секундой позже, ждала
его окончания (10.08.2026 — две минуты ожидания на пустой очереди). Новый круг не
начинается, пока выполняется хоть одна пользовательская задача; уже начатый доживает
свой круг.

Очередь заполняется `yandex_maps_catalog_seed_discovery_queue(мест, рубрик)`;
по умолчанию 200 крупнейших мест × 100 рубрик = 20 000 заданий.

**Приоритет — размер места × размер рубрики с поправкой на долю организаций с контактами.**
Поправка обязательна: «Скамейки» — вторая по величине рубрика каталога (554 тыс.), но
телефон есть у 20 записей из них, то есть у 0%. Мусорные площадки — 0%, велопарковки — 0%,
детские площадки — 1%. Против 86% у «Бизнеса» и 83% у «Красоты». Без поправки обход начал
бы с объектов карты, бесполезных для аутрича.

Пропавшие организации помечаются попутно и бесплатно: если выдача оказалась исчерпывающей
(Яндекс вернул меньше, чем запрошено, — значит показал всё), то наши организации этого
города и рубрики, которых в списке нет, получают `missing_streak + 1`. `closed_suspected_at`
ставится после двух промахов подряд — один ничего не доказывает.

**Слову «выдача исчерпывающая» веры нет.** «Меньше, чем запрошено» бывает и когда
поиск оборвался: на бою 11.08.2026 «Москва × Бизнес» вернула 20 ссылок при 65 321
организации в каталоге, «Воронежская область × Услуги» — ноль при 3 343. По прежним
правилам все они пошли бы в пропавшие, а на втором таком обходе — в «закрылась»;
механизм, задуманный ловить закрытые точки, записывал бы в них живые компании
тысячами. Поэтому у уборки есть потолок: показал Яндекс N организаций — усомниться
можно максимум в **2N + 20** (`missingMarkBudget`, миграция `20260811_0002`). Не
сошлось — выдача была неполной, не трогаем ничего. Побочно это ограничивает и объём
работы: минутных переписываний десятков тысяч строк, на которых рвался шлюз, больше
не бывает.

Практическое следствие: отметка «кажется, закрылась» теперь ставится редко — только
там, где выдача действительно покрывает базу. Это честное состояние: с потолком в
250 ссылок на поиск проверить крупную пару целиком нечем.

Ожидаемый объём — **сотни новых организаций в сутки, не тысячи**: база залита свежая, и
почти всё, что Яндекс показывает, в ней уже есть. Дневной потолок обращений — 15 000,
но упирается механизм не в него, а в то, сколько реально открылось нового.

## Повторный импорт снапшота

```powershell
cd G:\PycharmProjects\Portal\app
npm run build:yandex-maps-catalog
```

Запуск через обёртку, которая сама перезапускает импорт с контрольной точки при падении.
Строка подключения передаётся параметром и в файлы не пишется:

```powershell
.\scripts\yandex-maps-catalog\run-full-import.ps1 -DatabaseUrl "<URL основной БД>"
```

Импорт пишет контрольную точку по файлам, поэтому после падения продолжает с нужного
места, а не перечитывает миллионы строк. Продолжение вручную — флагом `-Resume`.

Заливка идёт около 4 часов и упирается в скорость чтения xlsx. Строку подключения лучше
брать на ту же машину, где база: заливка в облачный Postgres через домашний канал шла
в 15 раз медленнее.

После импорта обязательно пересчитать справочники, иначе форма покажет старые списки:

```sql
select * from public.yandex_maps_catalog_refresh_dictionaries(20);
select public.yandex_maps_catalog_seed_discovery_queue(200, 100);
```

## Порядок применения миграций

Индексы на каталоге строятся **до** деплоя и **отдельно** от миграций:

```bash
docker run --rm --network host --env-file .env <образ portal> \
  node scripts/db/buildYandexMapsRubricTokenIndexes.js
```

Обычный `create index` держит на таблице `SHARE` — запись запрещена на всё время
постройки, а это минуты на 9,9 млн строк. Миграции идут в транзакции с
`lock_timeout = 30s`, и в каталог непрерывно пишет фоновый обход, поэтому такая
миграция гарантированно не возьмёт блокировку: 08.08.2026 деплой на этом и встал
([`docs/incidents/2026-08-08-yandex-maps-index-migration-lock.md`](./incidents/2026-08-08-yandex-maps-index-migration-lock.md)).
Скрипт строит те же индексы через `create index concurrently` — дольше, но записи
не мешает; он идемпотентный, готовые пропускает, недостроенные пересобирает.

`20260807_0004` после этого только проверяет, что индексы на месте, и на боевом
объёме останавливает деплой с подсказкой, если их нет. На маленькой базе
(локальная разработка) строит сама — там секунды.

`20260807_0001` строит индексы прямо в миграции и держит блокировку записи несколько
минут. Применять её во время идущего импорта нельзя — импорт встанет.
