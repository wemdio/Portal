# Team — доступ и жизненный цикл ревью

Актуально с 1 августа 2026 года. Документ фиксирует обязательные инварианты страницы `/team`, API статистики и ревью сотрудников.

## Модель доступа

Вся страница `/team`, включая нагрузку, статистику и ревью, доступна только руководящим ролям:

- `lead`;
- `director`;
- `admin`.

Demo-профили не имеют доступа независимо от сохранённой роли. Изменение доступа к Team не меняет signup: самостоятельная регистрация остаётся клиентской, внутренние роли назначаются через административный контур.

Защита реализована на нескольких уровнях:

1. Навигация скрывает ссылку «Команда» от остальных ролей.
2. Middleware для `/team` всегда читает актуальные `role` и `is_demo` из профиля.
3. API `/api/team/statistics` и `/api/team/reviews*` повторно проверяют сессию и профиль.
4. RLS разрешает чтение `employee_reviews` и `team_project_history` только руководству.
5. Запись ревью выполняется сервисным API; прямых прав записи у браузера нет.

### Cookie роли не является источником прав

`x-portal-role` используется как кэш для обычной навигации, но не является авторитетным источником доступа к `/team`. На этом маршруте middleware намеренно обращается к профилю даже при cache hit.

Проверка работает fail-closed: ошибка чтения профиля, исключение проверки сессии или отсутствие Supabase-конфигурации закрывают `/team`, а не пропускают запрос дальше. Это правило нельзя заменять graceful-degradation fallback без отдельного security review.

## Жизненный цикл ревью

У ревью два состояния и только один допустимый переход:

```text
scheduled → completed
```

Обратный переход запрещён одновременно API-валидацией и триггером базы данных, чтобы устаревший конкурентный запрос не вернул завершённое ревью в планы.

### Запланированное ревью

Обязательны:

- дата;
- сотрудник.

Причина или повестка необязательна и ограничена 500 символами. Итоги, проблемы и рекомендации должны оставаться пустыми.

### Завершённое ревью

Обязательны непустые основные итоги. Проблемы и рекомендации необязательны. В историю ревью попадает только после сохранения завершённого состояния.

Существовавшие до введения lifecycle записи считаются завершённой историей и при миграции получают `completed`.

## Совместимость API

Новый интерфейс планирует ревью через `POST /api/team/reviews` без полей результатов. Такой запрос создаёт `scheduled`.

Старый интерфейс отправлял дату, сотрудника и результаты одним POST-запросом. Для обратной совместимости запрос с любым из полей `outcomes`, `problems` или `recommendations` трактуется как создание `completed`. При этом `outcomes` обязателен, а все переданные тексты сохраняются — молчаливая потеря заметок недопустима.

`PATCH /api/team/reviews/:id` проверяет итоговое состояние с учётом уже сохранённых полей. Завершить встречу без итогов или добавить результаты, оставив статус `scheduled`, нельзя.

## UI-инварианты

- запланированные встречи показываются отдельно и сортируются от ближайшей даты;
- просроченная встреча без итогов получает статус «Ожидает итогов»;
- история сортируется от новых встреч к старым;
- запланированные и завершённые ревью можно редактировать;
- завершение переносит запись из планов в историю только после успешного ответа API;
- элементы управления сохраняют доступный фокус, touch-target не меньше 44 px, а анимации учитывают `prefers-reduced-motion`.

## Основные точки реализации

- `app/src/middleware.ts` — авторитетная и fail-closed проверка `/team`;
- `app/src/lib/auth/internalGuard.ts` — leadership guard для API;
- `app/src/app/api/team/reviews/` — чтение, создание и обновление ревью;
- `app/src/components/team/TeamReviewsPanel.tsx` — планирование, завершение и история;
- `supabase/migrations/20260801_0001_team_reviews_lifecycle_and_acl.sql` — lifecycle, защита перехода и RLS.
