# Team — доступ, ревью и план активностей

Актуально с 8 августа 2026 года. Документ фиксирует обязательные инварианты страницы `/team`, API статистики, ревью сотрудников и HR-плана активностей.

## Модель доступа

Страница `/team` доступна всем внутренним сотрудникам без demo-профиля. Состав вкладок зависит от полномочий:

- «Загрузка» доступна всем внутренним сотрудникам;
- «Статистика» и «Ревью» доступны ролям `lead`, `director` и `admin`;
- «Активности» доступны только профилю с явным признаком `is_hr = true`.

Роль руководителя или администратора сама по себе не открывает HR-план. Demo-профили не получают закрытые возможности независимо от роли и HR-признака. Изменение доступа к Team не меняет signup: самостоятельная регистрация остаётся клиентской, а внутренние роли назначаются через административный контур. Отдельного UI для выдачи HR-доступа пока нет: признак меняется только доверенной миграцией или серверной операцией с обязательной проверкой конкретного профиля.

Защита реализована на нескольких уровнях:

1. Навигация показывает ссылку «Команда» только внутренним сотрудникам.
2. Middleware для `/team` всегда читает актуальные `role` и `is_demo` из профиля.
3. API `/api/team/statistics`, `/api/team/reviews*` и `/api/team/activity-plan*` повторно проверяют сессию и актуальный профиль.
4. RLS разрешает чтение `employee_reviews` и `team_project_history` только руководству.
5. RLS разрешает чтение `team_activity_plan_items` только HR-профилю; роль `readonly` не имеет доступа к этой таблице.
6. Запись ревью и плана активностей выполняется сервисным API; прямых прав записи у браузера нет.

### Cookie роли не является источником прав

`x-portal-role` используется как кэш для обычной навигации, но не является авторитетным источником доступа к `/team`. На этом маршруте middleware намеренно обращается к профилю даже при cache hit.

Проверка работает fail-closed: ошибка чтения профиля, исключение проверки сессии или отсутствие Supabase-конфигурации закрывают `/team`, а не пропускают запрос дальше. Ошибка проверки отдельной закрытой вкладки не должна открывать её по умолчанию. Это правило нельзя заменять graceful-degradation fallback без отдельного security review.

## План активностей

План хранится помесячно, но плановая дата отдельной активности может находиться за границей выбранного месяца. Это позволяет сохранить фактическую структуру рабочего плана, например включить итоговое мероприятие 31 июля в план августа.

Для активности обязательны периодичность и название. Формат, примечание, сумма и комментарий к бюджету необязательны. Для времени выбирается один вариант: точная дата с необязательным временем, свободное текстовое расписание или «без даты»; дата и расписание одновременно не сохраняются. Статус принимает одно из трёх значений: `planned`, `completed` или `cancelled`. Автоматическая просрочка рассчитывается только для запланированной активности с точной прошедшей датой; свободное расписание не считается просроченным автоматически.

Создание и редактирование выполняются непосредственно в таблице без модального окна. Изменение и удаление используют `updated_at` как optimistic-lock: устаревшая вкладка получает конфликт, не перезаписывает свежие данные и сохраняет пользовательский черновик для повторной отправки.

### Порядок выкладки и отката

1. Сначала применить миграцию и дождаться обновления schema cache, затем выкладывать приложение.
2. После миграции проверить, что HR-признак установлен ровно у согласованного профиля Алины; под её сессией API плана отвечает успешно, а под обычным admin без признака возвращает отказ в доступе.
3. При срочном откате сначала вернуть предыдущую версию приложения. Таблицу, колонку и накопленные записи не удалять: они обратно совместимы и не видны старому коду.
4. Удаление схемы допускается только отдельной последующей миграцией после экспорта или подтверждённого отказа от накопленных данных.

## Жизненный цикл ревью

У ревью два состояния и только один допустимый переход:

```text
scheduled → completed
```

Обратный переход запрещён одновременно API-валидацией и триггером базы данных, чтобы устаревший конкурентный запрос не вернул завершённое ревью в планы.

### Запланированное ревью

Обязательны:

- дата;
- сотрудник.

Причина или повестка необязательна и ограничена 500 символами. Итоги, проблемы и рекомендации должны оставаться пустыми.

### Завершённое ревью

Обязательны непустые основные итоги. Проблемы и рекомендации необязательны. В историю ревью попадает только после сохранения завершённого состояния.

Существовавшие до введения lifecycle записи считаются завершённой историей и при миграции получают `completed`.

## Совместимость API

Новый интерфейс планирует ревью через `POST /api/team/reviews` без полей результатов. Такой запрос создаёт `scheduled`.

Старый интерфейс отправлял дату, сотрудника и результаты одним POST-запросом. Для обратной совместимости запрос с любым из полей `outcomes`, `problems` или `recommendations` трактуется как создание `completed`. При этом `outcomes` обязателен, а все переданные тексты сохраняются — молчаливая потеря заметок недопустима.

`PATCH /api/team/reviews/:id` проверяет итоговое состояние с учётом уже сохранённых полей. Завершить встречу без итогов или добавить результаты, оставив статус `scheduled`, нельзя.

## UI-инварианты

- запланированные встречи показываются отдельно и сортируются от ближайшей даты;
- просроченная встреча без итогов получает статус «Ожидает итогов»;
- история сортируется от новых встреч к старым;
- запланированные и завершённые ревью можно редактировать;
- завершение переносит запись из планов в историю только после успешного ответа API;
- элементы управления сохраняют доступный фокус, touch-target не меньше 44 px, а анимации учитывают `prefers-reduced-motion`.

## Основные точки реализации

- `app/src/middleware.ts` — авторитетная и fail-closed проверка `/team`;
- `app/src/lib/auth/internalGuard.ts` — leadership guard для API;
- `app/src/app/api/team/reviews/` — чтение, создание и обновление ревью;
- `app/src/components/team/TeamReviewsPanel.tsx` — планирование, завершение и история;
- `supabase/migrations/20260801_0001_team_reviews_lifecycle_and_acl.sql` — lifecycle, защита перехода и RLS.
- `app/src/app/api/team/activity-plan/` — защищённый CRUD плана активностей;
- `app/src/components/team/TeamActivityPlanPanel.tsx` — месячный план и inline-редактирование;
- `supabase/migrations/20260808_0001_team_activity_plan.sql` — HR-признак, схема плана и RLS.
