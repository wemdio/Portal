# VE2: отправители по тегам и запас до синхронизации аналитики

28.09.2026. Продолжение `2026-09-28-ve2-delivery-rate.md`. Ветка задачи
`codex/ve2-preview-recovery-scale`, публикация в `Sergey` по поручению пользователя.
Production в этой работе только читался; миграций нет.

## Причины и исправления

- Расчёт темпа отвергал любую другую активную кампанию с `email_tag_list`, даже
  если её почты не пересекались с текущим профилем. Теперь объединение тегов
  разрешается через `/accounts?tag_ids=...` с полной пагинацией и ограниченными
  пачками тегов. После уточнения пользователя пересечение учитывается только
  информационно: общие почты допустимы, Instantly соблюдает их суммарные лимиты.
  Ошибка/повтор курсора/повтор почты в одной выборке не считаются
  отсутствием занятых почт. Таймаут чтения включает тело ответа.
- После первой загрузки каталог может ещё содержать `new_leads_contacted_count:
  null`. Прогноз доставки по-прежнему не считает неизвестное нулём; отдельный
  `DELIVERY_ANALYTICS_PENDING` объясняет ожидание синхронизации. Подтверждённые
  факты готового запаса, загрузок за день/всего и неопределённых результатов
  показываются независимо от прогноза, по ledger и блоклисту, в часовом поясе
  закреплённого запуска. Загрузка при неполной аналитике остаётся заблокирована.
- Кнопка «Подготовить следующий запуск» переименована в «Выбрать другую базу для
  запуска». Действие прежнее: переход к выбору баз, без создания кампании или
  повторной отправки. Для ежедневной дозаливки текущей базы она не нужна.

Документация фильтра `tag_ids` (OR):
[Instantly List account](https://developer.instantly.ai/api-reference/account/list-account).

## Проверенные production-факты

Read-only SSH, SQL `BEGIN READ ONLY`, прямые GET Instantly/PostgREST; без
application GET/reconciliation и платных проверок.

- StaffLine `523affe8-01fe-4b1e-a584-b4f6415c33f3`: ledger accepted **50**, ready
  **724**, supply plan active без ошибки. Это число загруженных, не отправленных.
- Кампания `ba5b0ce7-e336-4c15-b458-474a49d108ef`: GET на **12:35:24 UTC** вернул
  **Paused (2)**. В каталоге ещё Draft (0), first-contacted и analytics sync null.
  Предыдущая проверка на 12:19 UTC подтверждала активацию; свежий API важнее
  старого локального статуса. Затем пользователь подтвердил, что поставил паузу
  сам для проверки подготовленной кампании; это не сбой.
- Все **20 из 20** выбранных отправителей входят в другие Active/RunningSubsequences
  кампании через прямой выбор или теги. Прежний вывод о необходимости освободить
  почты был ошибочным: совместное использование разрешено провайдером. Расчёт
  исправлен — совпадение больше не обнуляет мощность, но дневной темп считается
  верхней границей, а не гарантированной долей общего лимита. Кампании, профили
  и паузы production в этой работе не менялись.

## Исправление после уточнения пользователя

- Подготовка кампаний и разрешение отправки разделены. Основная кнопка теперь
  «Подготовить кампании в Instantly»; созданные кампании ждут отдельного
  подтверждения в «Очереди запусков». Повторный проход воркера не активирует их.
- До подтверждения контакты хранятся в резерве Portal. Отдельная активация
  разрешает первую загрузку и отправку по расписанию. Уже работающие запуски
  сохраняют состояние; ручную паузу StaffLine код не отменяет.
- Проверено 45 тестов в 7 существующих наборах, включая сохранение ручной паузы,
  отсутствие автоактивации при повторном проходе, общие почты и теги. Полная
  строгая типизация, ESLint и сборка worker прошли. Новых test-файлов и миграций нет.

Официальное правило общих лимитов:
[Instantly account and campaign limits](https://help.instantly.ai/en/articles/6248612-account-and-campaign-limits).

Следующий шаг после выпуска: проверить расчёт темпа в панели; специалист сам
решает, когда возобновлять поставленную им паузу. Деплой её не отменяет.
