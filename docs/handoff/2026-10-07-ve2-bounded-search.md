# VE2: ограниченный поисковый добор и общая очередь

## Запрос и граница релиза

Пользователь согласовал до **$3 в сутки на все проекты VE2 суммарно** и проверки
в существующих тестовых файлах. Ручная работа специалистов должна сохранять
доступность. Изменения подготовлены в `codex/ve2-preview-recovery-scale` для
отправки в `Sergey`. Это не отчёт о production: деплоя, миграции на сервере,
включения функции, платных API и production-нагрузки в этой работе не было.

Контекст: у Profit Gateway нулевой результат узкой гипотезы не доказывал
отсутствие рынка. Старые реестровые/каталожные источники перестали давать прирост,
а поисковая выдача не была подключена как источник обнаружения компаний VE2.
Исследование сохранено локально в `~/.codex/handoffs/ve2-profit-adult-diagnostic-20261007`.

## Поведение

- После остановки обычных источников ниже цели допускается проба: один запрос
  по названию исходной гипотезы, одна страница, максимум 10 сайтов. Следующая
  страница допускается только после прироста проверенных контактов. Максимум
  три страницы на сочетание гипотезы, запроса и языка; продолжение той же
  гипотезы не покупает уже выполненную страницу повторно.
- Проба не генерирует дополнительные запросы моделью, не использует браузер,
  не обходит каталоги и не ищет почты внутри поискового парсера. Сайты проходят
  обычный конструктор, проверку email и релевантности VE2. Сайт из выдачи не
  считается готовым контактом. Гарантии достижения 500 нет.
- Непродуктивный старый источник сохраняет закладки и результаты, но не
  запускается вновь вместе с поисковой пробой. Старый deferred-список также
  не превращается в новую платную волну. Ошибка провайдера или режим проверки
  только сохранённых данных не являются поводом покупать такую пробу.
- Кэш содержит только публичную выдачу автоматических проб, с точным совпадением
  запроса/языка/страницы, до 30 дней для другой гипотезы. Результаты ручных
  поисков специалистов не используются. Пробы скрыты из списка ручного парсера.

## Деньги и нагрузка

- `ve_search_control`: выключено по умолчанию, лимит 3 USD. CHECK не допускает
  значения выше 3. Бюджет — скользящие 24 часа, поэтому на границе полуночи
  нельзя потратить два дневных лимита подряд.
- `ve_search_spend`: атомарное предварительное резервирование перед HTTP,
  единое для проектов и процессов. SERP-страница резервирует $0.10; это
  консервативный резерв, **не заявленная цена страницы**. Без отчёта провайдера
  о стоимости в USD резерв не уменьшается, в том числе после таймаута.
- В тот же лимит включены последующие учитываемые платные вызовы VE2 для базы,
  использовавшей пробу: классификация/проверка, поиск подтверждений, очистка
  названий и анализ. Допуск проверяет защищённую таблицу, а не сбрасываемый JSON
  checkpoint. Обычные базы и ручной поисковый инструмент этот бюджет не тратят.
- Верхняя оценка модельного запроса использует известный тариф, размер всех
  сообщений и схемы ответа, максимальный вывод и запас. Неизвестный тариф
  останавливает автоматический расход. Если провайдер сообщает стоимость выше
  резерва, новые расходы блокируются до проверки тарифа. Внезапное изменение
  цены внешним провайдером не является тем, что локальный код может гарантировать.
- При исчерпании бюджета задача откладывается на час без расходования попыток
  и потери результатов; ожидающая поисковая задача не считается трёхчасовым
  зависанием парсера. Сбой чтения поисковой очереди повторяется через минуту.
- Общая DB-очередь допускает не больше пяти исполняемых поисковых задач, из них
  не больше одной автоматической. Ожидающий ручной поиск имеет приоритет.
  Очередь автоматических проб ограничена 20 задачами. Уже исполняемый ручной
  поиск не прерывается ради автоматики.

## Восстановление и совместимость

Все исполнители (`worker/search`, `worker/index`, прямой вызов DFYB) проходят
один `search_claim_job`. Lease на пять минут продлевается каждые 30 секунд;
потеря heartbeat прекращает новые запросы/записи. Запись прогресса и результатов
проверяет token и статус в той же транзакции. Операции очереди ограничены
десятисекундным ожиданием, Serper HTTP — 30 секундами.

Перезапуск не сбрасывает здоровые задачи других процессов. Неопределённый
результат уже начатой автоматической SERP-пробы не повторяется автоматически.
Удаление базы сохраняет расход в общем бюджете; осиротевшая проба не может
превратиться в обычный неограниченный ручной парсер. DFYB повторяет enqueue с
одним детерминированным ID. Ручной поиск сохраняет выбранную глубину и обогащение;
возобновляет только непрерывный завершённый префикс запросов, дедуплицирует
повторно сохранённые домены и не считает ошибку сохранения успешным завершением.

`hypothesisEngine`, `he_*` и ENG не изменялись. Нужна миграция
`20261007_0070_search_queue_ve_budget.sql` **до** запуска новых воркеров. Следует
обновить все исполнители поискового парсера одной версией: старый код не знает
новый протокол lease. Legacy running без lease учитываются в общей ёмкости;
после трёх часов они становятся доступны для восстановления.

## Проверки

- VE2 + парсер + GRANT: 51 файл, 525 passed, 1 ранее skipped, около 20 секунд.
- После дополнительных правок восстановления: 115 проверок в шести файлах;
  заключительный точечный прогон — 39 passed.
- `npm run typecheck:strict`, ESLint изменённых исходников, сборка трёх
  затронутых воркеров. `typecheck:fast` локально недоступен: нет typescript-7.
- Настоящий SQL миграции выполнен в локальном PGlite: приоритет, общая ёмкость,
  fencing, отмена, повторная запись, резерв/списание, удаление базы, кэш,
  недоступность RPC для anon/authenticated. Это односессионная проверка SQL,
  **не** измерение пропускной способности production и не многопроцессный тест.
- Артефакты: `~/.codex/handoffs/ve2-search-budget-20261007`.

## После согласованного деплоя

Сначала read-only проверить миграцию/права, версии всех исполнителей и работу
обычной очереди. Флаг `ve_search_control.enabled` останется false: автоматическая
покупка поисков сама от деплоя не включится. Включение — отдельная production-запись
по явному разрешению пользователя, с `daily_usd=3` и без `blocked_reason`.
Существующие завершённые базы сами не перезапускаются. Возобновление конкретной
базы и реальный платный пробный сбор требуют отдельного поручения. Не менять
параметры ручного парсера и не повышать лимит при проверке.
