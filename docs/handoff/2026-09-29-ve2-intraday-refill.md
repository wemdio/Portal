# VE2: дозагрузка поздно готовых контактов в тот же день

Дата: 2026-09-29. Основа — Sergey `4511006ec`, test `75e5867c2` уже включён. Production в этой задаче не изменяли.

## Запрос и причина

Пользователь попросил исправить ситуацию: из дневного плана загружена только доступная часть, новый сбор завершился позже, но оставшиеся контакты ждут следующего рабочего дня. Нужна дозагрузка в пределах общего дневного плана, с теми же защитами от повторов, паузы и превышения цели.

Причина: существующая reservation-функция возвращала replay для дня с уже завершённой попыткой, даже если его исходная дневная квота заполнена лишь частично. Перезапускался только пустой день `no_ready_rows` без истории попыток.

## Изменение

Миграция `20260929_0061_ve_intraday_contact_refill.sql` добавляет закрытую SQL-функцию и вызывает её из существующего public reservation wrapper только после replay. Замена wrapper проверяет ожидаемый участок установленной функции; повторное применение идемпотентно. Функция недоступна service_role напрямую: рабочий вызов проходит через прежние проверки темпа, согласования, лимита workspace и восстановления.

- Используется тот же дневной run и тот же журнал контактов/попыток. Новая партия увеличивает cumulative reserved/effective counters, не удаляя историю.
- Максимум новых мест: меньший из исходного дневного плана, исходной мощности и текущей мощности минус уже выделенные в этот день места. Суммарный лимит общий для всех запусков проекта. Увеличение темпа не создаёт вторую квоту; снижение ограничивает ещё не выделенный остаток.
- Например, при плане 360 и первоначальной партии 100 последующие партии смогут занять ещё максимум 260 мест.
- Принятые, пропущенные, неизвестные и возвращённые из попытки контакты консервативно сохраняют выделенные места. Это предотвращает обход дневного лимита через ошибки; неизвестный результат не подменяется нулём. Explicit retry/recovery управляет прежними идентификаторами отдельно.
- Перед новой партией проверяются текущий статус проекта/периода, остаток цели, уже загруженный и неизвестный остаток. Новые строки выбираются только из проверенного ready-резерва активных кампаний с актуальным состоянием Instantly.
- Если ответ БД о резервировании второй партии потерян, повтор получает те же pending строки. Наличие старых завершённых попыток больше не делает эту новую партию недоступной. Во время незавершённого provider request новая партия не выделяется.
- Пауза одной гипотезы не мешает пополнить другую активную. Pause в Instantly и устаревшее наблюдение запрещают новый отбор для соответствующей кампании.
- Если после восстановления старой неизвестной загрузки освободилось место до общей цели, ранее записанный `awaiting_delivery` пересматривается в тот же день.

Не менялись: старт только в Instantly, алгоритм/качество сбора, двухдневный запас, API отправки, платежи, ENG, исходная цель. Изменены только SQL и существующий executable SQL smoke.
