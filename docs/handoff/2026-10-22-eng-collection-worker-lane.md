# ENG: отдельный воркер для сборов

22 октября 2026. Ветка назначения `Sergey`. Пользователь: «сделай отдельный
воркер для ENG-сборов, чтобы они не ждали за русскими исследованиями; RU и VE2
по поведению не меняй, письма не запускай; деплой сделаю сам».

## Что было

Один процесс `portal-worker-hypothesis-engine` вёл всё: проверенные ENG-сборы
клиентов делили два параллельных слота, а любая другая стадия — в том числе
исследования RU-инструмента `/tools/hypothesis-engine` — шла одна. 22.10 сбор
HST Insurance carriers простоял ~50 минут за стадией `evidence` RU-проекта
«Нержавейка»: найденные почты (11 OK + 15 catch-all) не попадали в базу, пока
воркер не освободился (его освободил деплой).

## Что сделано

- `lib/hypothesisEngine/heWorkerLane.ts`: переключатель `HE_WORKER_LANE`.
  Не задан или `all` — прежний единственный процесс, без изменений. `serial` —
  все стадии, кроме проверенных ENG-сборов (`readHeEngCollectionScope`,
  `parallelEligible`). `eng_collections` — только они. Неизвестное значение —
  отказ старта, а не тихий `all`.
- `worker/hypothesisEngine.ts`:
  - очередь берёт только задачи своей полосы; чужая задача не барьер;
  - один проект — одна полоса за раз: задача не берётся, пока у её проекта
    есть `running`-строка другого процесса (учёт расходов проекта сериализован
    только внутри процесса, `engProjectUsage.ts`);
  - `resetStuckJobs` на старте возвращает в очередь только строки своей полосы
    (раньше — все `running`: второй процесс перезапускал бы оплаченную стадию
    первого); строка с непрочитанной полосой остаётся до рестарта владельца;
  - служебные проходы (блокировки аккаунтов, «не писать», автозапуск) — только
    в полосах `all` и `serial`.
- `docker-compose.prod.yml`: у `worker-hypothesis-engine` —
  `HE_WORKER_LANE=serial`; новый `worker-hypothesis-engine-eng` того же образа
  с `HE_WORKER_LANE=eng_collections`, тем же томом кэша Companies House
  (блокировка импорта — каталог в томе, работает между контейнерами), теми же
  лимитами (2 ГиБ, 0,5 CPU), healthcheck и `stop_grace_period: 5m`.
- `.semaphore/select-deploy-targets.sh`: новый сервис в списке воркеров (тест
  `exportWorkerWiring` требует совпадения со списком compose).
- `drain-worker.sh`: ветка Hypothesis Engine останавливает оба сервиса одной
  командой (параллельно), срок — больший StopTimeout из существующих
  контейнеров.

RU-задачи идут по-прежнему одна за другой в своём процессе; разница одна — они
больше не ждут, пока доработают ENG-сборы. VE2 не затронут. Миграций нет.

## Выпуск

Правка `docker-compose.prod.yml` по правилам деплоя выкатывает все воркеры
(`select-deploy-targets.sh`, ветка `*`) с `up -d --force-recreate` — новый
контейнер создаётся этим же шагом. После деплоя проверить: оба контейнера
healthy; в логе основного «Lane serial…», нового — «Lane eng_collections…»;
ENG-сбор и RU-стадия могут быть `running` одновременно.

Риск, оставленный сознательно: между проверкой «проект занят другой полосой»
и клеймом есть миллисекундное окно. Автозапуск ENG (сейчас выключен,
`HE_ENG_AUTO_LAUNCH=0`) в полосе `serial` больше не ждёт окончания сборов
другого процесса; собирающаяся база в автозапуск не попадает.

## Проверки

TypeScript core, ESLint, `bash -n drain-worker.sh`, разбор compose, тесты
проводки деплоя (5 наборов), полный Jest, `npm run build:workers`. Офлайн-проверка
правил полос: каждая задача ровно в одной полосе, неверное значение — отказ.
