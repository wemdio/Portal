## Установленная причина остановки

Сохранённая ошибка — `ENG base budget: unavailable`. Ограничитель расходов
остановил работу при неуспешном обращении к своей БД, а не при исчерпании $5.
Старая реализация теряла исходный код ошибки и не повторяла временный сбой.
Точную причину соединения/БД по имеющимся журналам восстановить нельзя.
Периодические перезагрузки схемы PostgREST видны, но причинная связь не доказана.

Все 587 заявок общего журнала завершены: 40 ранних проверок и 547 обращений
к модели при проверке компаний. Общий резерв нулевой, блокировки нет.
Последний расчёт модели на 176 микродолларов совпадает с локальной заявкой 547.
Следующая локальная заявка 548 сохраняет `inFlight` и резерв 2566 микродолларов,
но не имеет соответствующей заявки общего журнала. Вместе с проверенным
порядком «резерв в БД до HTTP к модели» это указывает на остановку до оплаты
следующего запроса. Это отдельный вывод для данного исторического состояния,
а не разрешение автоматически обнулять любые неизвестные запросы.

Обычное повторное включение задания небезопасно для качества: старый
`inFlight` приводит к `model_response_unavailable` для оставшихся компаний.
Нельзя просто нажать повторный сбор или создать ещё одну базу.

## Подготовленное исправление

Только три ENG-модуля:

- `engBaseBudgetLedger.ts`: до трёх попыток одного и того же обращения к
  журналу расходов при известных временных ошибках. ID и аргументы неизменны;
  повторы не распространяются на HTTP-запрос модели. Повтор использованного
  резерва по-прежнему останавливает оплату. Отмена, ошибки доступа и постоянные
  ошибки не повторяются. В ошибке сохраняются только RPC, безопасный код,
  HTTP-статус, категория и число попыток, без исходного текста/секретов.
- `engBaseBudget.ts`: текущая ошибка резерва получает непереносимое через JSON
  свидетельство в памяти процесса, что этот физический запрос к модели ещё
  не отправлен. Это не освобождает общий резерв и не снимает блокировки.
- `engCompanyQualification.ts`: только для такого свидетельства локальная
  заявка закрывается с нулевой оплатой, сохраняется checkpoint без `inFlight`,
  затем ошибка ограничителя пробрасывается дальше. Здесь строго один вызов
  `callLLMText`, `transportRetries: 0`, без переключения модели/исправления схемы.
  Исторический маркер, неизвестная оплата, ошибка после HTTP или ошибка
  сохранения checkpoint остаются консервативно заблокированными.

Проверено бесплатно: 49 сценариев журнала и 25 независимых сценариев
реального пути qualification → LLM transport → budget с подменёнными внешними
вызовами. Проверены потерянный ответ резерва, повтор расчёта, отмена, предел,
неизвестная оплата, сохранение уже оплаченных решений, поддельный маркер,
историческая заявка 548 и отказ сохранения. TypeScript core, ESLint трёх
файлов, сборка HE и `git diff --check` прошли. Новых `*.test.ts` нет.
Это проверки кода, не успешный повторный сбор на production.

## Продолжение текущей Fund-базы — пока только план

Подготовлен, независимо просмотрен, **не выполнен**:
`/private/tmp/portal-eng-hst-resume-plan-20261021/resume-existing-fund.sql`.
Нужны выкладка пользователем и отдельное согласие на эту запись в production.

План продолжает то же задание и ту же базу. Он проверяет точные ID, состояние,
время изменения, общий журнал, отсутствие других задач этой базы и запусков
писем, а также сохранённую структуру бюджета. Меняет только историческую
локальную заявку 548 на нулевой расход, удаляет её `inFlight`, возвращает
базу/задание в collecting/pending и очищает старые времена/ошибку завершения.
534 решения и восемь подготовленных материалов сохраняются; общий журнал,
лимит $5, attempts и накопленные расходы не меняются. Подготовленный JSON
прошёл настоящую функцию чтения/сверки бюджета. SQL на production не запускался.
Перед исполнением повторить чтение состояния; при изменении любого условия
остановиться и заново разобрать его, а не ослаблять проверки.

## Качество ещё не доказано

Широкие финансовые отрасли в PDL дают много нецелевых компаний. Ранее
подготовленный приоритет названий услуг решает только небольшую часть этой
проблемы; новый сбор с ним ещё не проверен. Сам классификатор в этом цикле
не менялся.

Независимое чтение сохранённых материалов пяти предварительно допущенных
компаний: у четырёх услуги подтверждены хорошо, одна погранична — реальное
хранение цифровых активов не доказывает точный выбранный подтип услуг фондов.
Это не установленный ложный допуск и не основание исключать всю категорию.
Ранее рассмотренные три спорных отказа также остаются неподтверждёнными:
лишние условия в объяснении модели найдены, но бесспорная ошибочность полного
итогового отказа по сохранённым выдержкам не установлена. Не приписывать
компании услуги прежнего работодателя её руководителя. Не считать все
ошибки DNS доказательством закрытия сайта.
