## 3. Как устроен отбор

12 сигналов (`signals.ts`): 6 «потоковых» (общий телефон, форма заявки, отдел продаж, целевые
вакансии, большой поток, сеть офисов) + 6 скоринговых (юр./бухгалтерская/консалтинговая
релевантность, CRM-коллтрекинг, калькулятор-тарифы, работа с ИП/ООО/МСБ). В `signalsCount`
входят ТОЛЬКО первые шесть — фильтр edu/remont не зависит от скоринговых.

Скоринговые сегменты (legal, accounting, consulting) фильтруются взвешенным скором 0–100
(`scoring.ts`, веса дословно из ТЗ клиента, сумма 100): порог 35, грейды A 75+ / B 55+ / C 35+.
Ниже порога — компания архивируется, но в конструктор не идёт.

Дедуп отбора, по порядку: `seen` (залитые — навсегда) → архив проверок
(`RECHECK_AFTER_DAYS = 30`) → cross-segment (первый по приоритету забирает) → OutreachOS 45 дней.

**Важное свойство архива:** он же 30-дневный замок. Прогон, умерший ПОСЛЕ записи архива, но ДО
заливки, уносит проверенные компании из пула на месяц. Так 12.08 заперлись 500 компаний edu —
их вернули удалением строк, бэкап в таблице `gis_signal_company_signals_bak_20260812`.

Берём только карточки **с сайтом**: вся квалификация — проверка сайта, без него компания
получит 0 баллов. Карточек «почта есть, сайта нет» в наших нишах 115 и 39 против ~14 000
с сайтом — решено не брать (18.08).

## 5. Инцидент 12.08 и что из него сделано

Потерян весь день: три прогона подряд не довели ни одной заливки.

**Первопричина, подтверждённая и починенная — битый UTF-16 в jsonb.** Сниппет-evidence режется
по индексу UTF-16 (`snippetAround` / `clip`) и границы среза попадали в середину surrogate pair
эмодзи с сайта. Осиротевшая половинка сериализуется в непарный `\udXXX`, и Postgres отвергает
ВЕСЬ пакет upsert'а: `invalid input syntax for type json` (DETAIL: Unicode low surrogate must
follow a high surrogate). Проверено на боевой БД: `SELECT '{"a":"\ud83d"}'::jsonb` даёт ровно эту
ошибку. Косвенное подтверждение: в архиве за 12.08 ровно 500 строк — первый чанк прошёл,
следующий снёс всё.

Фикс — коммит `92048f907` (в main): общий примитив `app/src/lib/jsonbSafe.ts`
(`stripUnstorableJsonChars` + `sliceWholeChars`), срез по целым символам в `clip`/`snippetAround`,
санитизация перед ВСЕМИ jsonb-записями (архив, сетка конструктора, патч run-строки — иначе
падала бы и сама запись «прогон упал»). +6 регрессий, все падают на коде до фикса.
Подтверждение в бою: 13 и 14.08 «Архив: ok за 0s/1s» на пакетах в 2000 строк, ни одной ошибки.

**Вторая версия — «редеплои убивают прогон» — НЕ подтверждена.** Проверено 13.08: автоматики,
пересоздающей контейнеры, на хосте нет (в crontab деплоя нет, единственный деплой — Semaphore
05:00 МСК и он SHA-gated). Прямых улик не осталось: `docker events` вымылись из буфера демона,
а journald хранит меньше суток (самая старая запись была 12.08 21:30 при аптайме с 23.07) —
**это отдельная проблема: при следующем инциденте улик снова не будет.**
Более прозаичная версия для дневных ручных перезапусков: `docker exec` без `-d` привязан к
ssh-сессии, а канал до 139 рвётся постоянно. Для утреннего прогона причина неустановлена —
смерть процесса и зависание постфактум неразличимы.

**Сторож** (коммиты `756ad4653` + `5bdf73f82`, в main; крон поставлен 13.08 03:31). Каждые 15
минут в том же контейнере: процесс жив → молчит; строка `running` без живого процесса старше
10 мин → failed + TG-алерт; перезапуск дня только буднями в окне 06:40–13:00 МСК, если нет
успешного прогона и всего прогонов за сутки < 3. Отдельно ловит «крон вообще не отработал».
Время считается явно в `Europe/Moscow` (в контейнерах TZ=UTC). `/proc` недоступен → считаем
прогон живым (fail-safe).

## 6. Операционные заметки

- **SSH:** обычный `ssh` даёт Connection timed out — ходить через `plink` (креды в `.env.servers`,
  не коммитить), и оборачивать в retry: примерно каждый второй-третий вызов флапает
  «Network error». `gh` в сессиях не авторизован.
- **Ручные прогоны — только `docker exec -d`**, иначе обрыв ssh убивает процесс молча.
- **Деплой** — Semaphore, старт **05:00 МСК**, гейт по SHA `main` (если main не двигался — выходит,
  ничего не трогая). Имя пайплайна «Scheduled Deploy (3 AM)» историческое, на него не смотреть.
  Чтобы фикс уехал ночью, он должен быть в main с запасом на сборку образов (30–60 мин).
- **Ветки:** работаем только в `Sergey`, промоушен `Sergey → test → main`. Отдельных фикс-веток
  не заводить. Мерж в test/main и деплой — только по явному «да» владельца.
- **Разовые скрипты** запускаем из `/tmp` контейнера (исчезают при пересоздании): сборка
  esbuild как `build:workers`, запуск `docker exec -d … sh -c 'node /tmp/x.js > /tmp/x.log 2>&1'`.
- **Новый воркер** нужно добавлять В ДВА списка: `build:workers` в `app/package.json` И
  esbuild-строку в `Dockerfile.worker` — иначе бандла нет в образе. На это есть страж
  `app/tests/migrations/workerBundleEntries.test.ts`.
- При ручном запуске пометить stale:
  `UPDATE gis_signal_runs SET status='failed', finished_at=now(), error='…' WHERE status='running'`.
