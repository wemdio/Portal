# «Не лид» в карточке ручной передачи

## Поведение

- Новые карточки ручной передачи содержат «Передать клиенту», «Изменить ответ», «Не лид».
- Кнопка отказа доступна ответственному специалисту и лиду проекта, если для него включено разрешение. Проверяются подпись callback, секрет webhook, чат и привязка Telegram.
- Для автоматической передачи кнопки отказа нет. Нажатие старой ручной карточки также проверяет текущий `projects.handoff_auto_send`: при включённой автопередаче отказ запрещён.
- При ручной передаче кандидат сохраняется внутренне, но не показывается клиенту до `instantly_pending_handoffs.status = 'sent'`. Исходящие письма и способ отправки не меняются.
- «Не лид» атомарно сохраняет `status = 'rejected'`, время, Telegram ID автора и снимок исходного ответа, причины ИИ и строки базы. Ничего не отправляет и не вызывает модель. Первоначальная квалификация ИИ остаётся неизменной для последующего сравнения с решением человека.
- Повторное нажатие не дублирует решение. Отправка, редактирование и отказ используют одну строку `instantly_pending_handoffs`; уже начатую отправку отклонить нельзя, отклонённую — отправить нельзя. Если открыт редактор, сначала нужно отменить редактирование.

## Клиентская таблица

Публичные GET/PATCH/DELETE и импорт используют отфильтрованное, обновляемое представление `project_client_lead_board_rows`. Внутренние кандидаты остаются в `project_lead_board_rows`; API не отдаёт их клиенту, в том числе по угаданному ID. Экспорт страницы строится из тех же опубликованных строк.

`specialist_review_required` ставится до появления карточки, поэтому задержка очереди передачи не публикует кандидата преждевременно. Ошибка чтения режима проекта запрещает публикацию. Очередь передачи повторно сохраняет кандидата до показа карточки, если первая запись не удалась.

Исторические строки с незавершённой ручной передачей также скрываются новым представлением. Уже переданные лиды, автоматические передачи, проекты без настроенной передачи и ручной импорт остаются доступны. Исторические Telegram-сообщения не редактируются и новые сообщения по ним автоматически не рассылаются; кнопка появится на новых карточках.

Дополнительный ответ в уже отклонённом треде сохраняется внутренне, но не возвращает строку клиенту. Автоматического пересмотра человеческого отказа нет.

## Выкладка

Нужны обычная выкладка Portal и `worker-instantly-leads`, а также миграция операционной Instantly DB `supabase/instantly-migrations/20260926_0001_handoff_not_lead.sql`. Это не миграция аналитического `instantly_dataset` и не основной Portal DB. Миграция должна примениться до запуска нового API/воркера; при её отсутствии API не откатывается к выдаче скрытых строк.

Разработка и проверки выполнены локально. Production-миграции, отправки, перезапуски и платные API в рамках задачи не запускались.

## Проверка

Локальные проверки SQL выполняют настоящую миграцию в PGlite: скрытие до решения, публикация после передачи, отказ и повторный отказ, обе последовательности гонки отправки/отказа, старые ручные строки, автоматические строки, архив, открытый редактор, клиентское изменение/удаление и импорт, права ролей. Runtime-проверки вызывают настоящие функции подписи, Telegram-клавиатуры, авторизации, отказа и отправки с подменёнными внешними API.
