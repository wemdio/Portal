# VE2: подготовка кампаний в Portal, ручной Start в Instantly

Дата: 28 сентября 2026. Ветка задачи `codex/ve2-preview-recovery-scale`, публикация в `Sergey`.

## Решение пользователя

Это решение заменяет прежнее требование второго подтверждения в «Очереди запусков» из `f1c8c9ed3` и handoff `2026-09-28-ve2-rate-tags-and-stock.md`.

- Portal создаёт кампании, письма, точную привязку к выбранному проекту и первую дневную порцию контактов без запуска отправки.
- Специалист проверяет получившуюся кампанию и нажимает Start только в Instantly. В Portal нет очереди/второго разрешения на отправку.
- Новые кампании: `Клиент · Гипотеза · [Сегмент] · YYYY-MM-DD`, без HE/auto; `open_tracking=false` независимо от пресета. Настройки ENG не меняются.

## Реализация и условия

- `contactDeliveryActivation.ts` теперь только наблюдает GET-состояние Instantly. Старое имя экспорта сохранено для внутренних зависимостей. `launchActivation.ts` возвращает 409 с предложением перейти в Instantly; provider activation API в VE2 больше не вызывается.
- Миграция `20260928_0005_ve_manual_instantly_start.sql` обязательна вместе с кодом. Применять её до запуска нового worker. Она также блокирует старые RPC резервирования активации для старых вкладок/версий worker. Никаких автоматических Start или массового восстановления при миграции нет.
- `ve_observe_manual_campaigns` проверяет полную фиксацию запуска/аудита, привязку проекта, актуальное согласование пополнения, полный набор кампаний. Worker проверяет ID и состав отправителей через GET. Историческое поле queue.status=active означает разрешение на доставку контактов; реальную отправку показывает remote_status.
- Первый пакет разрешён только для пустого, ранее не запускавшегося Draft/Paused с нулевым журналом принятых/неопределённых загрузок. После первой загрузки ждём ручного Start. Пауза после запуска блокирует дальнейшую загрузку; резерв повторно проверяется непосредственно перед попыткой.
- Наблюдения старше 5 минут блокируют новую загрузку/новый поиск. Поиск пополнения разрешён только для конкретных гипотез с подтверждённым состоянием Active/Completed/Running subsequent. Уже выполнявшийся сбор не отменяется автоматически.
- После Start можно повторить пустой резерв в тот же день. Уже выполненные/неопределённые попытки не переоткрываются. Суточный лимит, дедлайн, аналитика фактических первых контактов, блоклист и дедупликация сохранены.
- Completed может принять следующую порцию без provider Start со стороны Portal. Автоматическое возобновление отправки самой платформой не подтверждено; при необходимости специалист управляет ею в Instantly.
- Интерфейс показывает последнее подтверждённое состояние кампании и время проверки. GET статуса не вызывает reconciliation или provider mutations.
