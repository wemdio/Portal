# Хотфикс публичного ключа (anon), 14–15 октября 2026

## Коротко

Публичный ключ Supabase (anon) лежит в каждом браузере, который открывает портал.
После июльского восстановления базы скрипт `deploy/main-db-prod/fix-roles.sql` выдал
этому ключу полный доступ ко всем таблицам, последовательностям и функциям схемы
`public`. Любой, кто достал ключ из страницы, мог читать и менять таблицы без
защиты строк (RLS) и вызывать опасные служебные функции, например
`agent_query_readonly(text)`, которая выполняет любой SELECT.

В ночь с 14 на 15 октября 2026 мы вручную применили на проде два SQL-файла из этой
папки. Они закрыли публичный ключ, не дожидаясь релиза. Через деплой хотфикс не
проходил, поэтому строки в `public.portal_migrations` у него нет.

Это временная заплатка. Постоянное исправление — миграции `20261015_0030` … `20261015_0036`
в `supabase/migrations/`. Миграция **0036 заменяет хотфикс** и закрывает то, до чего он
не дотянулся (подробнее ниже).

## Когда и как применено

- Снимки прав «до» (`anon-acl-before.tsv`, `rpc-acl-before.txt`) сняты 14.10.2026
  около 20:00 UTC (около 00:00 15.10 по UTC+4).
- Применено в ночь на 15.10.2026 с «да» владельца: 14.10 около 21:50 UTC (00:50 15.10
  по МСК, 01:50 по UTC+4); проверка снаружи и по журналам — 21:56 UTC. Вручную через
  psql на прод-базе (контейнер `main-postgres` на сервере 139.60.162.24). Перед
  применением права сняты повторно и совпали со снимками «до».
- Каждый файл — одна транзакция (`begin … commit`), ожидание блокировок ограничено
  3 секундами (`lock_timeout`).
- Оба файла в конце сами проверяют результат и откатываются целиком, если
  проверка не сошлась. Раз они применились, проверка прошла.

## Что сделали

### 1. `hotfix-anon-tables.sql`: таблицы и последовательности

- У anon отобраны все права на все таблицы, представления и последовательности
  `public`. До хотфикса у него были права на 295 объектов: 241 таблицу, 6
  представлений и 48 последовательностей. Полный список с исходными правами — в
  `anon-acl-before.tsv`.
- Намеренно оставлены три объекта:
  - `reglament_documents`: чтение (политика RLS показывает только опубликованное);
  - `companies_directory`: чтение;
  - `database_review_row_marks`: чтение и добавление.
- Проверка в конце файла: anon не читает ничего, кроме этих трёх.

### 2. `hotfix-rpc-anon.sql`: 25 функций SECURITY DEFINER

Такие функции выполняются с правами своего владельца, суперпользователя, и обходят
RLS. Для 25 функций:

- у `PUBLIC` и anon отобрано право вызова;
- `service_role` получил явное право вызова, чтобы не потерять его вместе с `PUBLIC`.
  Все воркеры и API-роуты вызывают эти функции под `service_role`;
- у `authenticated`, то есть у любого вошедшего пользователя, включая клиентов,
  право вызова тоже отобрано. Исключения — `copilot_dialog_stats(uuid)` (её вызывает
  браузер сотрудника) и `tg_outreach_swap_proxy(uuid,uuid,uuid,text,integer)` (её
  оставили, пока не проверили всех вызывающих);
- в список вошли `agent_query_readonly`, четыре `cleanup_*`,
  `drain_enrich_results_buffer`, `instantly_acquire_token`,
  `mailganer_acquire_score_token`, `tg_parser_increment_usage`,
  `tg_transcribed_chat_topic_counts` и 13 функций `yandex_maps_catalog_*`. Права до
  хотфикса — в `rpc-acl-before.txt`.

## Чего хотфикс не сделал

Это закрывает серия миграций 0030–0036:

- **Остальные функции SECURITY DEFINER.** Хотфикс закрыл 25 функций из списка.
  Остальные функции этого типа в `public` anon и вошедшие пользователи могут
  вызывать по-прежнему (их показывает запрос V4 в `verify.sql`). Закроет 0036.
- **Права по умолчанию для новых объектов.** Хотфикс их не менял. Новая функция,
  созданная миграцией, снова доступна `PUBLIC`, а значит и anon. Новый объект,
  созданный ролью, у которой `fix-roles.sql` прописал права по умолчанию для anon,
  снова получит права anon. Закроет 0036.
- **Вошедшие пользователи.** Любой клиент и любой, кто сам зарегистрировался в ENG,
  по-прежнему видит профили всех пользователей и читает и пишет в таблицы без RLS
  или с открытыми политиками. Закроют 0030–0035.
- **Представления с правами владельца** (`sender_threads`, `sender_mailbox_stats`,
  `v_sales_ai_stale_transcripts` и другие) обходят RLS. У anon доступа к ним больше
  нет. Права остальных ролей на них хотфикс не трогал. 0036 забирает эти
  представления и у anon, и у `authenticated`.
- **Схему `storage`** хотфикс не трогал. У anon там по-прежнему полный доступ к
  `storage.objects` (тот же `fix-roles.sql`). Закрытые бакеты `briefs` и `knowledge-base`
  закроет 0035: для вошедших — свои файлы клиента в `briefs/brief-scoring/`, для anon —
  ничего в этих двух бакетах, даже если на проде есть политика «TO public» на них.

## Как проверить

Файл `verify.sql` в этой папке только читает и ничего не меняет. Запускать с
согласия владельца:

```sh
cd docs/security/2026-10-15-anon-hotfix
ssh -i /Users/cybermart/.ssh/portal_hostkey_mac_ed25519 -o IdentitiesOnly=yes \
  -o StrictHostKeyChecking=yes root@139.60.162.24 \
  'docker exec -i main-postgres psql -U postgres -d postgres -X -v ON_ERROR_STOP=1' < verify.sql
```

Что должно получиться, пока хотфикс применён, а 0036 ещё нет:

| Запрос | Ожидание |
|---|---|
| V1. Объекты, доступные anon | ровно 3 строки: `companies_directory` (чтение), `database_review_row_marks` (чтение и добавление), `reglament_documents` (чтение) |
| V2. Последовательности, доступные anon | 0 строк |
| V3. 25 функций хотфикса | все на месте; anon не может вызвать ни одну, `service_role` может все; `authenticated` может только `copilot_dialog_stats` и `tg_outreach_swap_proxy` |
| V4. Другие функции SECURITY DEFINER, доступные anon | строки ожидаемы: это остаток, который закроет 0036. После 0036 — 0 строк |
| V5. Строки серии 0030–0036 в `portal_migrations` | пока строк нет, действует только хотфикс |

После 0036 меняется одно: в V3 `tg_outreach_swap_proxy` больше не вызывается под
`authenticated`.

Проверка снаружи, через API, если под рукой есть публичный ключ:
`curl -s -o /dev/null -w '%{http_code}\n' "$SUPABASE_URL/rest/v1/tasks?select=id&limit=1" -H "apikey: $ANON_KEY"`.
Ожидается `401` (permission denied). До хотфикса здесь был `200`.

## Как откатить

**Откат снова открывает базу публичному ключу.** Делать его только по явному решению
владельца и только если хотфикс что-то сломал.

Откат каждого файла восстанавливает права ровно такими, какими они были в снимках
«до». Файлы независимы, откатывать можно по одному. Сначала функции, потом таблицы:

```sh
cd docs/security/2026-10-15-anon-hotfix
SSH='ssh -i /Users/cybermart/.ssh/portal_hostkey_mac_ed25519 -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes root@139.60.162.24'
PSQL='docker exec -i main-postgres psql -U postgres -d postgres -X -v ON_ERROR_STOP=1'

# 25 функций: вернуть вызов PUBLIC, anon и authenticated, как в rpc-acl-before.txt
$SSH "$PSQL" < hotfix-rpc-anon.rollback.sql

# 295 таблиц, представлений и последовательностей: вернуть права anon, как в anon-acl-before.tsv
$SSH "$PSQL" < hotfix-anon-tables.rollback.sql
```

Узкий откат вместо полного. Если сломался один вызов, лучше вернуть одно право:

```sql
grant execute on function public.<функция>(<аргументы>) to authenticated;  -- или to anon
grant select on table public.<таблица> to anon;
```

### Если 0036 уже применена

- **Не запускать `hotfix-*.rollback.sql`.** Они откроют anon то, что закрыла 0036.
  Для отката 0036 есть свой файл
  `supabase/operator-sql/20261015_0036_anon_definer_view_lockdown.rollback.sql`. 0036
  в своей транзакции записывает права каждого объекта дважды: до себя и после себя.
  Откат возвращает права «до» только тем объектам, которые 0036 изменила и которые с
  тех пор никто не трогал. Так база возвращается в состояние хотфикса, а не в открытое
  состояние до него.
- Если права объекта после 0036 поменяла более поздняя миграция или кто-то руками,
  откат этот объект не трогает и перечисляет его в предупреждении (`WARNING`). Иначе
  откат молча отменил бы более позднее закрытие. Решать по таким объектам вручную.
  Вернуть и их к состоянию «до 0036» можно только явно: перед запуском отката
  выполнить `set lockdown.rollback_0036_force = 'on';` (или запустить psql с
  `PGOPTIONS='-c lockdown.rollback_0036_force=on'`).
- Посмотреть заранее, что изменит откат (только чтение), — запрос в шапке файла
  отката: он показывает по каждому объекту права «до», «после 0036» и «сейчас».
- **Не запускать `hotfix-*.sql` повторно.** `hotfix-rpc-anon.sql` снова выдаст
  `authenticated` вызов `tg_outreach_swap_proxy`, а 0036 у него этот вызов забирает
  (все вызывающие работают под `service_role`). Повтор `hotfix-anon-tables.sql`
  ничего не испортит, но и ничего не добавит.

## Связь с миграциями 0030–0036

Хотфикс применён до серии, поэтому серия ложится поверх него. Он не обязателен:
0032, 0033 и 0036 сами отбирают права anon и от хотфикса не зависят. Но и не мешает.
Серию проверили в PGlite на схеме из репозитория и на трёх вариантах эмуляции прода:
без хотфикса, с обоими хотфиксами и с обоими хотфиксами без «чужих» грантодателей.
Все проверки прошли.

15.10.2026 серию перенесли на `origin/main` (все миграции, применённые на проде деплоем
13:02 UTC) и проверили ещё раз, в том числе на четвёртом варианте: права, политики и
флаги RLS скопированы с прода (снимок только для чтения, 15.10 ~13:15 UTC). Этот
вариант нашёл два расхождения с репозиторием, оба исправлены в файлах серии:

- 0030. На проде у `profiles` есть самодельные политики «Admins can update profiles» и
  «Admins can insert profiles», которые внутри себя снова читают `profiles`. Вместе с
  подзапросом `(select auth.uid())` в новой политике 0030 PostgreSQL падал бы с 42P17
  («infinite recursion detected in policy») на любом изменении профиля через JWT:
  сотрудник не смог бы сохранить свой профиль, клиент — сменить язык. Теперь политика
  вызывает `auth.uid()` и `is_internal_staff()` напрямую, без подзапросов (на проде 77
  профилей, разницы в скорости нет), а самопроверка 0030 пробует UPDATE и INSERT от
  имени сотрудника и клиента.
- 0035. На проде у бакета `briefs` только самодельные политики «briefs read own» (чтение
  своих файлов) и «briefs uploads by authenticated» (загрузка), поэтому сотрудник видит
  не все файлы бакета, а только свои. Самопроверка 0035 ждала «сотрудник видит всё» и
  откатила бы файл (на проде: 0 из 937); теперь она сравнивает видимость сотрудника до и
  после фильтра.

Номера `20261015_0030` и `20261015_0031` совпадают с VE-миграциями
`20261015_0030_ve_hypothesis_preparation_pause.sql` и
`20261015_0031_ve_preparation_launch_pause_guard.sql`, которые уже применены на проде.
Раннер применяет файлы по имени, поэтому на пустой базе порядок такой: 0030 профили,
0030 VE, 0031 помощники, 0031 VE, 0032…0036. Этот порядок тоже проверен. На проде
VE-файлы уже в `portal_migrations`, и серия идёт после них.

| Миграция | Что делает | Откат (`supabase/operator-sql/`) |
|---|---|---|
| 0030 | профили: клиент видит только себя, сотрудник видит всех; изменения профилей через JWT работают как раньше; `agent_query_readonly` закрыта для anon и `authenticated` | `20261015_0030_profiles_read_lockdown.rollback.sql` |
| 0031 | вспомогательные функции `is_internal_staff()` (теперь PARALLEL SAFE) и `is_api_robot()` | `20261015_0031_staff_gate_helpers.rollback.sql` |
| 0032 | 59 таблиц без RLS: RLS включён, доступ только сотрудникам (клиенту — только свои строки `user_tool_visibility`) | `20261015_0032_no_rls_tables_lockdown.rollback.sql` |
| 0033 | 115 таблиц с политиками, открытыми любому вошедшему: доступ только сотрудникам, с узкими исключениями (свои ручные прогоны клиента, `pdl_companies` для Bench-робота). `pdl_count_estimate` и `search_pdl_companies` становятся SECURITY DEFINER со своей проверкой вызывающего, чтобы поиск сотрудника по названию компании остался на триграммном индексе | `20261015_0033_open_policies_staff_gate.rollback.sql` |
| 0034 | остальные таблицы с RLS: только сотрудники, а клиенту — свои задания и результаты там, где ими пользуется клиентская часть. Список таблиц берётся из каталога, поэтому сюда попадает и `tg_outreach_proxy_lists` с политиками «для всех вошедших» из `20261015_0008` | `20261015_0034_rls_tables_staff_or_own_gate.rollback.sql` |
| 0035 | бакеты `briefs` и `knowledge-base`: сотрудникам — как сейчас (на проде это свои файлы в `briefs` и весь `knowledge-base`), клиенту только свои файлы в `briefs/brief-scoring/`, anon — ничего | `20261015_0035_storage_private_buckets_gate.rollback.sql` |
| 0036 | anon, все функции SECURITY DEFINER, представления, права по умолчанию; **заменяет этот хотфикс**. Новые функции в `public` больше не получают право вызова через `PUBLIC`; его явно получают `authenticated`, `service_role` и прямые логины `readonly`, `nick_ro`, `supabase_auth_admin`, `supabase_storage_admin` (если они есть и не суперпользователи). Любой другой роли, которая будет вызывать новую функцию, право выдаётся в той же миграции | `20261015_0036_anon_definer_view_lockdown.rollback.sql` |

- Проверки перед применением, только чтение:
  `supabase/operator-sql/20261015_lockdown_preflight.sql` (вся серия) и
  `supabase/operator-sql/20261015_0030_profiles_read_lockdown.preflight.sql` (профили).
  Проверку «логины, которые наследуют anon», на которую ссылается шапка 0031, делает
  запрос Q3 в `20261015_lockdown_preflight.sql`.
- Откат серии строго в обратном порядке: 0036 → 0035 → 0034 → 0033 → 0032 → 0031 → 0030.
  Строки миграций в `portal_migrations` не удалять: иначе следующий деплой применит
  их снова. Исправление выпускать новой миграцией.
- Откаты 0032, 0033 и 0034 сначала разом берут эксклюзивную блокировку на все свои
  таблицы, дочерние раньше родительских (как и сами миграции). Ожидание каждой
  блокировки — не больше 3 секунд, вся фаза блокировок — не больше 30 секунд; если не
  уложились, файл откатывается целиком и ничего не меняет. Запускать с остановленными
  воркерами (VE2/HE, tg-outreach, парсеры), не в 06:00 и 18:00 UTC (pg_dump) и не в
  22:00 UTC (зеркало портала).
- Известное ограничение, которое чинится кодом, а не миграцией. Bench-робот ищет по
  `pdl_companies` прямым запросом к таблице (`lib/bench/tools/companyBase.ts`). Под
  ограничением 0033 его поиск по названию не может использовать триграммный индекс и
  на 19,5 млн строк упрётся в таймаут. Инструменту нужно перейти на
  `search_pdl_companies`. Правка `companyBase.ts` для этого сделана вместе с серией. Пока
  она не выйдет через Sergey, поиск роботов по названию медленный.
  Роботы этим поиском пользуются: на 15.10 за 30 дней было 43 поиска `company-base`, всего
  у Bench 4 677 вызовов с 2 ключей, последний 05.10. Счётчик входов (`last_sign_in_at`)
  у роботов всегда 0: их токены выпускаются без входа. Нагрузку смотреть в
  `bench_api_requests` (P6b в preflight 0030).
  Поиск по базе знаний для сотрудников (`kb_search_chunks`) тоже теряет индекс, но там
  это миллисекунды на сотнях тысяч фрагментов, поэтому функция осталась как есть.
- Схема `storage` тоже открыта через PostgREST, а 0036 снимает право вызова
  definer-функций только в `public`. `storage.delete_leaf_prefixes` может вызвать
  anon. Сегодня вызов падает, потому что `storage.prefixes` на проде нет; даже рабочая,
  функция удаляет только пустые записи префиксов. После обновления storage-api
  проверить definer-функции в `storage` (runbook ночи, раздел 10).
- Права anon не возвращает ни один откат 0030–0035. Откат 0036 возвращает их к
  состоянию хотфикса. Открыть всё, как было до 14.10, можно только откатом самого
  хотфикса (см. выше).
