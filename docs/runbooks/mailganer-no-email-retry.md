# Mailganer: повторный поиск почты для уже скоренных доменов

## Назначение

Повторно найти и валидировать корпоративные адреса у ранее положительно
скоренных доменов с исходом `no_email`, передав только
прошедшие действующие проверки контакты в настроенные score-кампании.
Повторная попытка остаётся в исходном журнале и экспорте с пометкой
`no_email_retry`, но не увеличивает клиентскую воронку новых скорингов.
Подтверждённые Instantly контакты остаются в ledger и метриках кампаний.

## Граница выпуска

Коммит и push ветки не запускают обработку. Перед новым продовым запуском
нужны отдельные подтверждения на миграцию, деплой app/worker и постановку
точного набора пакетов в очередь; не выполнять их по одному общему «сделай».
Именно в этом порядке: сначала миграция с `is_no_email_retry` и отчётным RPC,
потом app/worker, затем новый read-only план и его проверка, и лишь затем
одобренная постановка в очередь. Если код app появится до миграции, клиентский
отчёт намеренно не покажет потенциально завышенную воронку (fail closed).

## Read-only план

На Mac с проверенным SSH из `docs/ssh-access.md`:

```sh
node app/scripts/no-email-retry/plan.mjs <client-user-uuid>
node app/scripts/no-email-retry/prepare-enqueue.mjs <output-directory>
```

Первый скрипт выполняет только `BEGIN READ ONLY` SQL на текущем Portal DB и
создаёт временный локальный каталог: `manifest.json` и файлы по максимум
100 доменов. Второй сверяет хеш/уникальность и готовит
`enqueue-after-approval.sql`, но **не исполняет** его. Он не вызывает Mailganer
или Instantly. В Git не добавлять список доменов и SQL с данными клиента.

Правила выборки: действующий кэш скоринга `>1000`, прошлый исход `no_email`,
зоны `.ru/.su/.рф`, отсутствие ранее найденной почты/маршрутизации, принятых
контактов и прошлых `no-email-retry` попыток. Планировщик убирает встроенные
исключённые бренды по кэшированному имени; worker перед передачей повторно
проверяет встроенные и дополнительные regex по нескольким вариантам имени.
Домены, где адрес уже находили, но он не прошёл email-валидацию, не входят
в повторный поиск: это отдельная категория, исключённая пользователем.

## Перед одобренной постановкой

1. Подтвердить, что продовая миграция и worker/app с этим кодом уже работают.
2. Повторно построить read-only план; проверить объём, SHA-256, отсутствие
   активных/дублирующих `no-email-retry` запусков и текущие настройки кампаний.
3. Проверить текст локально сгенерированного SQL: ровно один run на файл,
   `route_to_instantly=true`, `is_no_email_retry=true`, максимум 100 строк на
   run; повторное применение отклонит уникальный индекс по source filename.
4. Только после отдельного разрешения выполнить SQL на текущем DB. Мониторить
   `client_manual_score_runs`, `client_manual_score_rows`,
   `client_campaign_append_batches` и `client_campaign_contact_ledger`.
   `accepted` означает добавление в кампанию, не отправку письма.
5. При failed run не создавать его заново вслепую: проверить ошибку и
   частично подтверждённые append identities. Отчёт должен показывать
   retry-строки отдельно и не увеличивать `scoredCompanies`/ранние ступени.

Автоматический worker последовательно берёт `pending` прогоны. Исторические
ручные прогоны удаляются штатной 30-дневной уборкой, а клиентский ledger и
domain snapshots сохраняют результаты. Без миграции и деплоя не ставить
новые retry-партии: старый worker не знает флаг и смешает повторы с новыми
скоринговыми компаниями в отчёте.

## Безопасная остановка worker (подготовлено 2026-10-13)

Изменение требует отдельного одобрения миграции
`20261013_0001_manual_scoring_worker_lease.sql` и деплоя worker. Коммит/push
не применяют его к production и не восстанавливают текущие пакеты.
Сначала миграция, затем worker: без RPC новый worker останавливается,
не возвращаясь к старому небезопасному `SELECT pending` + `UPDATE processing`.

Worker берёт pending только после записи всех `unique_count` строк,
затем атомарно занимает один run с уникальным token и пятиминутной lease,
продлеваемой каждые 30 секунд. Сохранение строки и изменения run проверяют
token в одной транзакции. Повтор после временного HTTP/network-сбоя пишет
тот же результат и `processed_at`, не вызывает повторно Mailganer, scrape
или валидацию; CAS/readback не позволяют затереть уже сохранённую строку.
Постоянная ошибка записи остаётся ошибкой, а не успешным результатом.
После первой ошибки pool перестаёт брать новые строки и ждёт завершения
всех уже начатых, прежде чем фиксировать failed и переходить к другому run.

При SIGTERM worker перестаёт брать новые строки, сохраняет начатые и только
затем возвращает **свою** scoring-lease в pending. Уже начатая reconciliation
должна закончить append receipts, snapshots и итоговый статус. Drain даёт
до 600 секунд и проверяет фактический ExitCode=0; SIGKILL/137, старый
worker с ExitCode=143 и неизвестный итог прекращают deploy **до** force_rm.
Daemon получает `docker stop --timeout -1`: предел 600 секунд ограничивает
только локальное ожидание, не включает принудительный SIGKILL контейнера.
Первый переход со старого worker нельзя считать автоматически безопасным:
он не умеет этот checkpoint-контракт, поэтому нужен отдельно согласованный
план остановки в idle/проверки сохранённых результатов. Увеличение timeout
не является разрешением принудительно убивать worker после его истечения.

После аварии автоматически подбирается только истёкшая lease нового
scoring-phase run. Исторические processing без token и все failed остаются
неизменными: массового восстановления или миграционного backfill нет.
Перед внешним append phase становится routing. Истёкший routing блокирует
новые claims: возможный внешний успех без полной identity-receipt нельзя
безопасно переотправлять. Проверить read-only snapshots, append batches и
ledger; дальнейшее восстановление требует отдельного разрешения. Pending
не доказывает остановку, а отсутствие batch не означает accepted=0.

Офлайн-проверка SQL (только синтетическая in-memory БД, без `.env`/SSH):
`node app/scripts/no-email-retry/verify-worker-lease.mjs --pglite <path-to-pglite-module>`.
Существующий retry marker, правила ready-only routing/дедупа и ранее
подтверждённые accepted identities этой защитой не заменяются.

Маркер `is_no_email_retry` сохраняется в metadata неизменяемого domain
snapshot. Отчёт, экспорт и повторный отбор используют этот маркер и
зарезервированный префикс файлов `no-email-retry-`, поэтому удаление
временного прогона через 30 дней не возвращает попытку в новые скоринги и
не делает её повторно доступной для очереди. Миграция
`20261009_0002_client_no_email_retry_retention.sql` заменяет отчётный RPC
с учётом этой очистки; обе миграции применяются обычным деплоем.

Миграция `20261010_0001_client_no_email_retry_live_email_counts.sql` также
обязательна перед массовым повторным поиском. Она выравнивает промежуточный
расчёт почт с основным/rollup-отчётом: одна найденная почта при отсутствии
второй не теряется из retry delta из-за NULL; пустые и одинаковые адреса
нормализуются так же, как в исходной воронке. Уже сохранённые snapshots и
контактный ledger не изменяются. Read-only проверка фактического SQL на
синтетических данных: `node app/scripts/no-email-retry/verify-reporting-sql.mjs --ssh-read-only`.
