# Mailganer: повторный поиск почты для уже скоренных доменов

## Назначение

Повторно найти и валидировать корпоративные адреса у ранее положительно
скоренных доменов с исходом `no_email`/`no_valid_email`, передав только
прошедшие действующие проверки контакты в настроенные score-кампании.
Повторная попытка остаётся в исходном журнале и экспорте с пометкой
`no_email_retry`, но не увеличивает клиентскую воронку новых скорингов.
Подтверждённые Instantly контакты остаются в ledger и метриках кампаний.

## Граница выпуска

Коммит и push ветки не запускают обработку. Перед новым продовым запуском
нужны отдельные подтверждения на миграцию, деплой app/worker и постановку
точного набора пакетов в очередь; не выполнять их по одному общему «сделай».
Именно в этом порядке: сначала миграция с `is_no_email_retry` и отчётным RPC,
потом app/worker, затем новый read-only план и его проверка, и лишь затем
одобренная постановка в очередь. Если код app появится до миграции, клиентский
отчёт намеренно не покажет потенциально завышенную воронку (fail closed).

## Read-only план

На Mac с проверенным SSH из `docs/ssh-access.md`:

```sh
node app/scripts/no-email-retry/plan.mjs <client-user-uuid>
node app/scripts/no-email-retry/prepare-enqueue.mjs <output-directory>
```

Первый скрипт выполняет только `BEGIN READ ONLY` SQL на текущем Portal DB и
создаёт временный локальный каталог: `manifest.json` и файлы по максимум
100 доменов. Второй сверяет хеш/уникальность и готовит
`enqueue-after-approval.sql`, но **не исполняет** его. Он не вызывает Mailganer
или Instantly. В Git не добавлять список доменов и SQL с данными клиента.

Правила выборки: действующий кэш скоринга `>1000`, прошлый email-failure,
зоны `.ru/.su/.рф`, отсутствие ранее валидной почты/маршрутизации, принятых
контактов и прошлых `no-email-retry` попыток. Планировщик убирает встроенные
исключённые бренды по кэшированному имени; worker перед передачей повторно
проверяет встроенные и дополнительные regex по нескольким вариантам имени.

## Перед одобренной постановкой

1. Подтвердить, что продовая миграция и worker/app с этим кодом уже работают.
2. Повторно построить read-only план; проверить объём, SHA-256, отсутствие
   активных/дублирующих `no-email-retry` запусков и текущие настройки кампаний.
3. Проверить текст локально сгенерированного SQL: ровно один run на файл,
   `route_to_instantly=true`, `is_no_email_retry=true`, максимум 100 строк на
   run; повторное применение отклонит уникальный индекс по source filename.
4. Только после отдельного разрешения выполнить SQL на текущем DB. Мониторить
   `client_manual_score_runs`, `client_manual_score_rows`,
   `client_campaign_append_batches` и `client_campaign_contact_ledger`.
   `accepted` означает добавление в кампанию, не отправку письма.
5. При failed run не создавать его заново вслепую: проверить ошибку и
   частично подтверждённые append identities. Отчёт должен показывать
   retry-строки отдельно и не увеличивать `scoredCompanies`/ранние ступени.

Автоматический worker последовательно берёт `pending` прогоны. Исторические
ручные прогоны удаляются штатной 30-дневной уборкой, а клиентский ledger и
domain snapshots сохраняют результаты. Без миграции и деплоя не ставить
новые retry-партии: старый worker не знает флаг и смешает повторы с новыми
скоринговыми компаниями в отчёте.
