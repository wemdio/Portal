# VE2: доступ к балансу Requesty

Автовосстановление после ошибки оплаты проверяет баланс бесплатными GET-запросами
Requesty. Проверки не обращаются к модели.

## Отдельный ключ для проверки баланса

Если рабочий ключ отвечает `403` на `/v1/manage/org`, можно сохранить его и
подключить отдельный ключ **той же организации**:

- `VE_REQUESTY_MANAGEMENT_API_KEY` — новый ключ с `manage: read`;
  для него достаточно `completions: none`.
- `OPENROUTER_HYPOTHESIS_ENGINE_API_KEY` и его fallback
  `OPENROUTER_BRIEF_API_KEY` остаются ключами запросов к моделям.

Не заменяйте рабочий ключ ключом чтения баланса. Не публикуйте значения ключей в
чате, логах, документации или Git. Создание нового ключа и изменение production
конфигурации выполняются только в согласованном объёме.

Публичный Requesty API позволяет задать `permissions` при создании ключа.
Изменение прав существующего ключа публично не документировано. Если интерфейс
предлагает только переключатель `Admin Permissions`, это ещё не подтверждает
наличие только `manage: read`: права созданного ключа нужно проверить через
`GET /v1/manage/apikey/self`.

## Как работает проверка

1. Баланс организации читается новым ключом через `GET /v1/manage/org`.
2. Идентификатор, разрешение на запросы к моделям и месячный лимит рабочего ключа
   читаются **рабочим ключом** через `GET /v1/manage/apikey/self`.
3. Новый ключ должен прочитать этот же идентификатор через
   `GET /v1/manage/apikey/{id}`. Согласно контракту Requesty, доступ разрешён к
   ключам своей организации. Несовпадение, отказ или отсутствие ответа блокируют
   восстановление.

Отпечаток ошибки оплаты остаётся привязан к рабочему ключу. Положительный баланс
чужой организации или свободный лимит нового ключа не разрешает восстановление.
Для ключей с неизвестным бюджетом группы восстановление остаётся заблокированным.

Если переменная не задана, сохраняется прежний путь: два GET-запроса рабочим
ключом. При заданном отдельном ключе выполняются три запроса без повторов,
с общим таймаутом 8 секунд. Проверка выполняется штатным циклом раз в пять минут,
только когда есть ожидающие восстановления задания.

## Подключение после выпуска кода

Сохраните секрет `VE_REQUESTY_MANAGEMENT_API_KEY` в штатном production `.env`,
который уже подключён к `worker-vertical-engine-v2` через `env_file`.
Не меняйте ключи моделей, лимиты или конфигурацию ENG. Значение переменной
появится в процессе после согласованного пересоздания VE2-воркера штатным
деплоем; простой перезапуск существующего контейнера не обновляет окружение.

Проверка результата: `/org` отвечает `200`, рабочий ключ имеет доступный лимит,
проверка принадлежности проходит; затем штатный цикл восстановления продолжает
тот же job/base с сохранёнными результатами. Сам по себе `200` ещё не доказывает,
что сбор продолжился: проверьте статус и обновление checkpoint.

Не вызывайте RPC возобновления вручную ради проверки автоматики. Пауза/отмена
специалиста и ограничения повторного восстановления после новой `402`
продолжают действовать.
