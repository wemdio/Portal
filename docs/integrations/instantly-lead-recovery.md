# Повторная квалификация ответов Instantly

## Разбор очереди после сбоя (2026-09-07)

Пополнение Requesty восстанавливает API, но не обрабатывает накопленные ответы
само по себе. Сохранённый `AI API 402` может относиться к прошлой попытке (`ai_reason`
сохраняет первоначальную причину), а не к текущей недоступности провайдера. Нужно смотреть
`updated_at`, текущий `error_message` и движение всей очереди, не только одного проекта.

Раньше основной повторный разбор выполнялся максимум по пять ответов раз в
15 минут на процесс для всех проектов. После сбоя сотни ответов могли ждать часами.
Теперь между обычными циклами — две минуты; не более пяти последовательных
попыток за цикл. Свежие ответы по-прежнему обрабатываются первыми в основном poll.

| Настройка | Значение по умолчанию | Назначение |
|---|---:|---|
| `INSTANTLY_OWNERSHIP_RETRY_INTERVAL_MS` | 120000 | Интервал обычных повторных циклов |
| `INSTANTLY_OWNERSHIP_RETRY_BATCH` | 5 | Максимум попыток за цикл, верхний предел 5 |
| `INSTANTLY_OWNERSHIP_RETRY_BACKOFF_MS` | 900000 | Минимальная пауза перед повтором той же неудачной записи |
| `INSTANTLY_OWNERSHIP_RETRY_TIME_BUDGET_MS` | 45000 | Мягкий бюджет цикла: после него не начинаются следующие записи |
| `INSTANTLY_OWNERSHIP_RETRY_PROVIDER_BACKOFF_MS` | 300000 | Пауза recovery после новой временной ошибки провайдера |
| `INSTANTLY_OWNERSHIP_PAGE_BUDGET_RETRY_INTERVAL_MS` | 900000 | Отдельный интервал сложных проверок владельца |
| `INSTANTLY_OWNERSHIP_PAGE_BUDGET_RETRY_BACKOFF_MS` | 21600000 | Пауза перед повтором той же сложной проверки владельца |

Истёкший мягкий бюджет не прерывает уже начатую обработку и не бросает запись
в состоянии `processing`. Один такой запрос может длиться дольше бюджета.
Начальный `getEmail` в recovery ограничен 20 секундами и не повторяет 429 внутри
HTTP-клиента: запись возвращается в надёжную очередь.

При **новой** ошибке 402/429, временной ошибке API или сети текущая запись
возвращается на повтор, оставшиеся записи не захватываются. Оба recovery-направления
делают паузу. Историческая ошибка в `ai_reason` сама по себе паузу не включает.
Уведомления в Telegram и обычный приём свежих ответов этим предохранителем не выключаются.
Пауза и защита от пересечения циклов локальны процессу; между процессами сохранён CAS.

Ускорение не меняет критерии лида, проверку принадлежности проекта, идентификаторы
квалификаций, защиту от дублей, срок автоматических попыток и правила ручной проверки.
Сложная ownership-очередь остаётся отдельной: по одной записи раз в 15 минут.

## Проверка после согласованного выпуска

- Миграции БД не требуются. Уже ожидающие подходящие записи подхватываются автоматически.
- Явные значения env имеют приоритет: старое `INSTANTLY_OWNERSHIP_RETRY_INTERVAL_MS=900000`
  оставит прежний интервал. Изменение env работающего сервера — отдельное согласованное действие.
- В логах есть `qualification recovery: active=..., page-budget=...` и сообщение о паузе
  после новой ошибки провайдера. Следить за возрастом самой старой ожидающей записи и 429.
- Две минуты — интервал планирования, не SLA доставки. Время poll, вызовов API,
  мягкий бюджет и неудачные попытки снижают фактическую пропускную способность.
- Общий Instantly rate limiter может быть выключен и работает fail-open;
  он не является гарантией доступной квоты. Нельзя без проверки увеличивать batch
  или число процессов, рассчитывая только на этот limiter.
