# Передача лида: неопределённый результат отправки

Область: `handoffSender.ts`, ручная кнопка/редактор Telegram и автоматическая
передача Instantly. Это защита от повторного письма, не гарантия доставки во
входящие и не автоматическая починка старых передач.

## Состояния

- Новая запись получает `send_attempt = {version: 1, phase: "ready"}`.
- Sender перечитывает запись и атомарно захватывает попытку. Ручной захват
  сохраняет проверки пользователя, сессии редактирования, текста и срока.
- Перед внешним POST сохраняется `request_started`. Ошибка сохранения
  запрещает POST. Один и тот же handoff нельзя отправить конкурентно.
- Успех `/emails/reply` требует ID письма в ответе. Receipt, `sent_at` и
  `status=sent` сохраняются одним обновлением. Повторяется только это
  идемпотентное обновление БД (до трёх попыток), не отправка письма.
- Сетевой обрыв, таймаут, 5xx или неполный ответ оставляют `unknown`.
  Автоматический повтор POST запрещён. Активную попытку первые пять минут
  проверяют повторно без отправки; затем нужна ручная сверка. Пять минут —
  техническое окно для статуса «выполняется», не SLA доставки.
- Явные HTTP 400/401/403/404/422 — `refused`. Нужна проверка причины.
  Только подтверждённый 400 «not part of campaign» разрешает прежний Others
  fallback. Таймаут fallback так же блокирует повтор. HTTP 429 или ошибка,
  доказанно возникшая до POST, разрешают новую попытку после безопасного
  снятия только своей блокировки. Отмена редактора сохраняет исходный текст.
- При неуспехе сохранения receipt возвращается `publicationPending`.
  Блокировка остаётся; предупреждение появляется в чате, ID ответа сохраняется
  также в runtime-логе `instantly.handoff.confirmation_not_saved`.

## Выкладка и совместимость

1. Только в отдельно согласованной фазе релиза применить
   `supabase/instantly-migrations/20261031_0001_handoff_send_attempt.sql` к
   **операционной БД Instantly**, не аналитическому датасету и не основной БД.
2. Согласованно заменить app **и** worker Instantly. Не допускать одновременно
   работающего старого автоматического sender и нового: старый код не знает
   о журнале и может повторить POST. Не откатывать worker на старый sender
   при наличии незавершённых попыток без отдельного плана сверки.
3. Без колонки новый код отказывает безопасно до отправки, а worker — до
   создания новой карточки передачи. Это не совместимость с немигрированной
   схемой: миграция обязательна до включения новой версии.

Миграция только добавляет nullable-колонку. Нет backfill, переквалификации,
сброса блокировок, перепубликации таблиц или отправки старых писем. Legacy
автоматические `pending/failed` без журнала требуют проверки: старый процесс
мог умереть после POST. Не считать их пустой журнал доказательством неотправки.
Старые ручные pending без захвата можно отправить лишь явным нажатием с
действующими правами; захваченные и failed не перезапускаются.

## Проверка неопределённого результата

Проверить точное исходящее в Instantly: отправляющий ящик, получателя,
обязательных клиентов в CC (для Others — в To), родительское письмо, время,
ID/статус исходящего и текст. Одного thread_id или пустого поиска по canonical
lead недостаточно. Изменённый вручную поздний текст требует отдельной проверки;
это не доказательство успеха первоначального POST.

Этот релиз не ищет старые исходящие автоматически и не принимает отсутствие
письма в неполной истории за разрешение повторить отправку. Коррекция состояния
Portal после подтверждённой внешней отправки — отдельное согласованное действие.
При одновременном полном отказе БД и процесса/логов receipt может быть потерян;
write-ahead блокировка предотвращает дубль, но не устраняет необходимость сверки.
