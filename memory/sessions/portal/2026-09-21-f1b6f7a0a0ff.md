## Запрос и уточнение пользователя

- Пользователь уточнил, что около 98% кампаний создаются вручную непосредственно в Instantly. Поэтому защита только в Portal create/edit UI не покрывает реальный рабочий процесс.
- Резервные теги `неименные почты` и `неименные maildoso` являются инвентарным пулом, а не проектом и не доказательством владельца кампании.
- Пользователь запросил проектную настройку: при новом квалифицированном лиде по желанию тегать в Telegram не только специалиста, но и сотрудника из поля `Лид (PM)`.

## Реализованное решение

- Ветка/снимок: рабочая ветка `Sergey`, поверх `a9cec24ab` до финального коммита этой задачи.
- `replyOwnershipResolver` проверяет sender scope в Instantly только при конфликте владельцев одного ящика. Кампании с `email_tag_list`, содержащим резервный тег `неименные …`, исключаются из mailbox ownership evidence. Метаданные тегов/кампаний кэшируются 10 минут; обычный бесконфликтный путь не получает дополнительных API-вызовов. При ошибке API остаётся прежнее fail-closed поведение.
- Добавлена колонка проекта `tag_project_lead_in_telegram boolean NOT NULL DEFAULT false`, флажок в настройках проекта и отдельная строка `Лид проекта` в Telegram-карточке. PM не получает право отправки лида и не добавляется в in-app уведомления специалиста. Совпадение PM со специалистом не создаёт дубль.
- PM пока резолвится по точному регистронезависимому совпадению `projects.manager` с `profiles.full_name`; при нуле/нескольких совпадениях упоминание безопасно пропускается с warning.

## Открытый операционный вопрос

Portal не может запретить неверный выбор тега внутри интерфейса Instantly до сохранения. Текущая правка защищает маршрутизацию ответов, но не останавливает саму неверно настроенную рассылку. Для полной превентивной защиты нужен периодический аудит Instantly и решение пользователя: только уведомлять администратора или автоматически ставить такие активные кампании на паузу.
