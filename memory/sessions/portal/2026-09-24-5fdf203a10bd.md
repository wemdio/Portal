Пользователь после диагностики долгого деплоя спросил «что делать то?». Подготовлена исправленная CI-логика в .semaphore/scheduled-deploy.yml для Sergey, без остановки/перезапуска текущего workflow и без production-записей.

Основа — актуальный файл origin/main fd01e2b3d, включая ранее чужое исправление bf03337ad (sender fail-open и health alert). В рабочей Sergey его ещё не было, поэтому переносится только этот релевантный CI-файл, без остальных изменений main. Новый sender phase ограничен бюджетом300с (плюс до10с на принудительное завершение команды). SSH/SCP под GNU timeout; preflight/setup могут повториться дважды. Login ограничен30с; compose pull180с на удалённой машине, самаSSH-сессия240с, без повторной попытки. Pull и up разделены, поэтому после потери SSH скачивание не продолжится автоматически в перезапуск контейнера.

Учтено stop_grace_period:2m из deploy/sender/docker-compose.yml: up не начинается, если осталось<210с бюджета. В таком случае образ может быть скачан, но старый контейнер сохраняется и есть явное сообщение. У up есть180с на удалённой машине/210с наSSH, --pull never, одна попытка; неопределённый результат не повторяется вслепую. Sender failure не останавливает Portal. Уже существующему health alert добавлены connect/max timeouts и корректный текст о неподтверждённом результате. На будущий отдельный sender retry остаётся прежнее ограничение fail-open: после записи last_deploy_sha sender не выбирается без новых релевантных изменений; текущая правка не обещает самостоятельный повтор.

Проверено без сетевых/production-команд: YAML parse, bash -n всей команды job; существующие54 проверки select-deploy-targets;7 локальных сценариев выполнения извлечённого настоящего sender shell-блока со stub-командамиSSH/timeout (success, unreachable, copy failure, pull failure/timeout, недостатокбюджета передup, неизвестныйup). Во всех отказах shell продолжаетPortal, послеpull failure нетup, неизвестныйup не повторяется. Временный стенд /tmp/check-sender-phase.cjs, не добавлялись тестовые файлы врепозиторий.
