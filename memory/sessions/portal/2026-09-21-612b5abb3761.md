## Behavior

- Status reads distinguish query/transport failures from confirmed non-running status. Transient PGRST connection errors, 408/429/5xx and network/timeouts retry with a fresh query and abort signal, five total attempts, 1/2/4/8 second backoff, 15 second per-attempt timeout.
- Exhaustion or permanent error fails explicitly, not as a cancellation. The cache run retains its durable cursor for a later resume instead of being invalidated by an unavailable status read.
- Failure-status persistence uses the same bounded retry and a `status=running` filter; progress writes also require running status. A confirmed prior cancellation is not reset at runner entry. Cancellation during a failure-write retry cannot be overwritten.
- If even the failure-status write remains unavailable through all retries, the runner rejects to the worker's error logger. This does NOT guarantee that a terminal status can be recorded during a prolonged total DB outage. No runtime stale-job reaper or automatic requeue was introduced.
