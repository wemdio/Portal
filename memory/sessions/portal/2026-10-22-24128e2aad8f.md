Пользователь уточнил поведение после проверки языка TG-аутрича: если ответ не отправился, перегенерировать; напротив ответа красный «!» с настоящей причиной при наведении. Это корректировка прежнего решения «не отправлять без UI-диагностики» из memory/sessions/portal/2026-10-22-9e833ae319a0.md.

Реализовано локально в dmitriy_kuladmed_new: подготовка ответа в handleChat имеет максимум две генерации на одно входящее (одна перегенерация). Во вторую передаётся реальная причина первого отказа. Проверяются язык, пустой/бессмысленный ответ, повтор, вопросы при передаче; qualification/referral/interest не сбрасываются и передача возможна только после успешной отправки. Неуспех перевода теперь различает пустой ответ и оставшийся кириллический текст, исключения API сохраняют исходное сообщение. Ошибки ограничены 1000 символами, ключ LLM/Bearer редактируются.

Подготовлена миграция основной БД 20261022_0060_tg_outreach_reply_failure.sql: отдельная JSONB-колонка reply_failure в tg_outreach_dialogs. Черновик не входит в messages/контекст/счётчики/экспорт. Поля text/reason/timestamp/incomingKey/attempts/retrying/delivery. Хеш последнего входящего ограничивает две генерации на одно сообщение, не на каждый круг; retrying=1 attempt может продолжиться после прерывания. После подтверждённой отправки ошибка очищается. Перед SendMessage фиксируется delivery=unknown: при обрыве/рестарте не допускаем автоматический дубль. RPC-отказ хранится not_sent и передаётся внешнему обработчику FLOOD/прокси, сетевой таймаут — unknown; история Telegram может снять неопределённость. Отказ записи диагностики не маскирует исходный RPC-отказ.

UI: FailedReplyBubble/ReplyFailureIndicator — красный значок в списке диалогов и напротив неотправленного черновика, hover/focus tooltip содержит настоящую причину; retrying подписан «перегенерация…», unknown — «Отправка не подтверждена». Открытая видимая вкладка обновляется каждые 15 секунд. Для выкладки сначала применять миграцию, затем портал и TG worker; старый worker совместим с добавленной nullable-колонкой. Новому worker нужна колонка. Документация: docs/tg-outreach-reply-failures.md и docs/portal-db-mcp-guide.md.

Проверено: 17 существующих Jest-проверок leadForward/timeout/dialog ownership/base filter/grants; core TypeScript и scoped TypeScript всей TG-страницы/нового UI; esbuild worker. Временные offline harnesses app/.next/cache/check-tg-reply-regeneration.mjs и check-reply-failure-storage-ui.mjs: реальное тело handleChat с I/O doubles, success после неудачного перевода, остановка после двух ошибок и на следующем круге, новое входящее/возобновление, positive/negative/CRM, fallback/qualification, исключения API/пустые ответы, Telegram RPC/unknown. PGlite выполнил настоящую миграцию дважды, SETOF RPC возвращает новую колонку, обновление messages не стирает ошибку. SSR-проверка нового компонента подтвердила title/aria и экранирование текста. Постоянных тестов не добавлено; реальных отправок/ожиданий нет.

Production не изменялся, миграция не применялась, push/deploy требуют отдельного подтверждения. Новая ошибка восстанавливает только последнюю попытку на диалог, не отдельный полный журнал отправок. Не является полной транзакционной outbox с восстановлением всей CRM/forward-финализации после падения между доставкой и отметкой лида.
