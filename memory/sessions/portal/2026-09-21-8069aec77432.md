## Причина

Ошибка возникла в сохранённой конфигурации кампаний «Вороной»: вместо второго проектного тега `Вороной` в `email_tag_list` был выбран общий резервный тег `неименные почты`. Поскольку резервный тег остаётся на временно выданных ящиках разных проектов, любой такой ящик становился sender-кандидатом кампаний «Вороной». Для ящика с дополнительным тегом другого клиента resolver видел кампании двух Portal-проектов и корректно останавливался на неоднозначной принадлежности.

Код ручного создания кампании позволял эту ошибку: один выбранный тег одновременно использовался как фильтр списка ящиков и как динамический sender selector. Автор/интерфейс конкретного выбора по API не устанавливается.

## Полный read-only аудит

- Срез `instantly_dataset` до 2026-09-20 23:19 UTC: четыре текущие кампании на резервном теге, все относятся к «Вороной».
- Для 38 текущих кампаний, созданных или обновлённых после среза, выполнен прямой GET live Instantly; после внешней коррекции ни одна не использует резервные теги.
- Все девять кампаний «Вороной» были переключены внешним действием между 2026-09-21 15:28 и 15:31 UTC: теперь каждая использует только проектный тег `Вороной`, резервных тегов нет.
- Изменение выполнил не этот агент.

## Вывод

В проверенном текущем наборе активных/приостановленных кампаний ошибка была только у проекта «Вороной» и сейчас в live Instantly устранена. Коммит `b9d2d8041` после деплоя предотвращает повторение через Portal: скрывает и серверно запрещает теги `неименные …` как sender selector.
