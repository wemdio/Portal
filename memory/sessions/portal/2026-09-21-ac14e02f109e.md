# Instantly recovery: isolate reply-local failures from provider outages

- User approved fixing the queue delay diagnosed in `sessions/portal/2026-09-21-a0abe214faa8.md`. Implementation stays on the Sergey task line; no production action or historical replay was authorized/performed.
- Root cause: `reprocessOwnershipReviewRows` reused the broad retry-eligibility regex for its shared five-minute provider circuit breaker. `AI classification failed after retries: outbound history unavailable` therefore stopped the remaining candidates and later recovery lanes, despite being specific to one reply. Fresh intake is a separate loop; this did not stop all inbound processing.
- Fix: separate provider/network/billing signals from generic local retry markers. Missing history, invalid/truncated AI output and per-reply budget exhaustion retain their durable pending/backoff but do not start the shared provider pause. Genuine 402/429/503, Requesty 412 spend-limit rejection, network failures and response timeouts still pause recovery. AI checkpoint/read-admission exclusions are preserved; final paid-budget exhaustion is explicitly excluded too.
- No model, prompt, Requesty route, token/request limit, paid checkpoint, per-row retry schedule, ownership decision, notification path, persisted no-backfill cutoff or 24-hour automation window changed. Instantly read quotas remain a separate throughput constraint; this patch is not proof that production queue latency is solved.
- Expanded one existing worker test, with no new test file or `it()` block: same-batch continuation, fresh-lane continuation, failed-row backoff preservation, real provider pause and automatic resume. It fails under the old circuit-breaker condition (one attempted row instead of two) and passes after the fix. Eight local-failure cases and seven provider/network cases run with a simulated clock and mocked I/O.
- Validation: 232 suites / 2,527 tests passed in 64.528 seconds; ESLint on both changed TypeScript files and dedicated `worker/instantlyLeads.ts` esbuild passed. No real emails, Telegram alerts, paid model calls or production writes were used to verify the fix.
- Full-project `tsc --noEmit` did NOT pass validation: default 4 GiB Node heap exhausted after about 147 seconds. A local-only retry with an 8 GiB heap was still computing after about five minutes without diagnostics and was stopped; do not describe that check as passed. No repository/production memory settings were changed. This is a validation limitation, not a demonstrated type error in the patch.
- Follow-up after the user's normal deployment: verify the running revision and measure fresh queue age/count, local-read-quota share and recovery logs. Do not start recurring monitoring or replay old replies; user previously explicitly declined both.
