# Search parser adaptive website routes

User approved a focused implementation, verification and push to Sergey; no production deployment. Company names must remain required alongside emails. Prior diagnosis: `sessions/portal/2026-09-23-52d9e0031272.md`.

## Change

- Only `searchParserWorker.ts` opts into `fetchWebsiteEmails({ adaptiveRoutes: true })`. Other consumers retain the legacy policy by default; proxyPool configuration and workers/DB/queue are unchanged.
- The first attempt stays RU-priority. On failure, up to two alternate routes run within one retry window (direct and another proxy group). First usable HTML wins; a quick HTTP error cannot beat success. The losing request is aborted. Successful route reuse is confined to one origin in one crawl, never a cross-job/global cache.
- Ordinary 404/410 pages are not retried through other routes. Existing contact/about discovery and browser fallback remain; finding an email does not disable name discovery. No blanket site deadline, worker scaling or shortened page budget.
- Existing regression scenario expanded, no new test files or it blocks. Coverage includes direct recovery, alternate proxy recovery despite direct 403, cache reuse/isolation, name lookup after finding email, opt-out behavior, cancellation, and retained homepage data with two timeout windows when all contact-page routes stall.
