Запрос пользователя: проверять банковские поступления раз в 10 минут и уведомлять продажи через существующий @PolzaSiteFeedbackBot. Пользователь явно выбрал группу -1001852890744 и новую ветку «Оплаты» 29718 (https://t.me/c/1852890744/29718); бот пятничных сводок для этого не используется.

Реализовано локально на dmitriy_kuladmed_new поверх 9fc9fd72a: отдельный BANK_SYNC_CRON=*/10 для Точки и всех счетов/токенов Т-Банка, окно текущего дня МСК + три дня перекрытия, session advisory locks между full/recent. Полная история, AMO, Метрика и крипта сохраняют пять ежедневных запусков. Короткие банковские записи не подавляют startup catchup полного pipeline перед отчётом продаж. Последняя дата полной выписки вычисляется на каждом прогоне, а не только при импорте модуля.

Новый закрытый журнал bank_income_notifications: уникальность по банковской операции, baseline создаётся до первого включённого pull, ранее загруженные операции не отправляются. Новые backfill-операции старше начала дня активации также исключены. Уведомления только для положительных credit/is_revenue Точки/Т-Банка с ИНН длиной 10/12 цифр, без крипты. Поля: название, ИНН, сумма/валюта, банк, исходные дата/время при наличии и время обнаружения МСК, назначение без AI-догадок. В T-Банке текущий legacy API отдаёт raw.date, не operationDate; дата без времени явно подписана. Проверка getMe требует ровно PolzaSiteFeedbackBot; webhook бота не трогается.

Telegram 429 повторяется по next_attempt_at до 10 попыток; явный отказ — failed. Timeout/5xx/неподтверждённый ответ или перезапуск с sending — unknown без автоматического повтора, потому что сообщение уже могло быть принято. Ошибки требуют проверки ветки и поднимают существующий health alert только с ID операций. Недоступные уведомления не останавливают банковский синк. Токены/URL запросов в новых ошибках не печатаются.

Проверки: существующий Python suite 240 passed; migration grant/transaction Jest suites 16 passed; временные offline harnesses проверили форматирование, точность дат, адресата, bot identity, статусы Telegram, lifecycle scheduler и блокировки. На изолированной in-memory PostgreSQL (PGlite, без production подключения) применена миграция и исполнены реальные SQL из dispatch_income: baseline, дедуп, фильтры, позднее появление ИНН, NULL-коррекции, 429 delay, restart quarantine, повторная проверка классификации при claim, запрет anon на чтение журнала. py_compile, diff --check и docker compose config --quiet прошли; compose сообщил ожидаемые отсутствующие локальные env для других сервисов. Новых постоянных тестов не добавляли по CLAUDE.md.
