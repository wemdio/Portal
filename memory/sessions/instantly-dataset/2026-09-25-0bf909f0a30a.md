# Passive proposal-inbox routing fix

## Request and decision
After the read-only diagnosis in 2026-09-25-dbd667257628.md, the user asked to fix the false positive. A reply consisting solely of permission to send a generic commercial proposal to an inbox should not be treated as expressed buyer interest. Other email addresses alone must not veto genuine requests. No replay of old mail or notifications.

## Implementation
Task worktree Sergey, base 5ebf828262e2d5de757e1fe23debac09285555e5 (the remote's new VE2 memory-only commit was fast-forwarded without touching its content).
Only source changed: app/src/lib/instantly/leadQualifier.ts.
- Added a narrow whole-authored-answer guard for Russian permission-only proposal/email routing before commercial-keyword positive overrides. Thus both model-positive and model-contact_routing seeds remain not_lead for the reported case.
- Locally unwrap markdown emphasis around signature lines and normalize CRLF, without changing shared signature/contact parsing.
- Questions/personal requests, concrete prices or quantity, explicit agreement, additional buyer content and buyer postscripts bypass the shortcut.
- A competing proposal question in the latest actual outbound also bypasses the shortcut, preserving an answer accepting our offer to send a proposal.
- Model-confirmed positive project criteria and the existing standalone shared-email custom criterion retain priority. Machine, sarcasm and intro-request vetoes retain priority.
- Prompt distinguishes permission-only inbox routing from a real request after a substantive offer.
No changes to project ownership, queues, models, retry budgets, sends, handoffs, table extraction or deployment.
