# Internal-only, unique name resolution for lead notifications

## Request and scope
User authorized the previously diagnosed safety fix only if client notifications remain intact. Implemented on Sergey after fast-forward to 1b2e1bde2. No deployments, production writes, old-reply replay or live test notifications.

## Fix
- Specialist fallback in leadQualificationWorker now queries profiles only in INTERNAL_ROLES and requires exactly one match per free-text name; query errors fail closed with a diagnostic. Existing specialist_user_id routing retains priority and is unchanged.
- Optional project-lead Telegram mention excludes client profiles before checking uniqueness.
- The matching PM handoff authorization uses the same internal-role restriction, so a same-name client neither gains edit/send permission nor blocks a legitimate employee.
- Client reply notifications remain separately routed via projects.client_user_id or self-serve campaign access, then enabled client_reply_telegram_links. No role restriction was applied to this path.
- VE2 client account creation, campaign/project ownership, classifier and handoff email sending were not changed.

## Verification
207 existing tests / 7 suites passed (20.033s): lead qualification worker, campaign owner resolver, VE2 launch client API, managed user provisioning, immutable preset binding, no-period launch and client reply bot.
No permanent test cases added; the existing PM fixture now states role=lead.
Offline one-off verification executed actual notification and authorization functions with an in-memory DB and mocked delivery. 44 cases passed, including all seven internal roles, client-only and ambiguous names, DB errors, linked-ID precedence, PM edit/send permissions, same-person dedup, case-insensitive PM match and wildcard exact-name guard. Sixteen combinations covered managed/self-serve client delivery, enabled/disabled and leads_only settings. Three prior bugs reproduced against HEAD: client included as specialist, client-name collision suppressing PM, and client selected as PM. No network or real messages.
Core TypeScript, focused ESLint, diff whitespace check and production worker bundle succeeded.

## Read-only production impact check
2026-09-25: 59 projects outside completed status (23 in work, 6 preparation, 30 testing); no text-only specialist fallback or client-name collision on those projects. The one enabled PM mention outside completed status resolves to a unique internal profile. One completed legacy project has a text-only name matching client profiles; this change intentionally prevents that unsafe match. No project data repaired or reassigned.

## Limits and next step
This protects name-based internal routing, not arbitrary changes to explicit specialist IDs or a universal notification delivery guarantee. Ambiguous internal names deliberately do not receive a guessed recipient; assign the exact employee in the project selector. Client-account creation alone still does not subscribe it to Telegram.
Push the focused commit to Sergey; user controls merge/deployment. Production impact above is a point-in-time read, not evidence of this patch already running.
