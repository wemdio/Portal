Incident: Event&Marketing Group / dental clinics 3+ chairs, base 289954d8-bff0-4153-b408-40e598e06119, job 89d3d0f2-a245-44e5-b2f5-2f01798c7441. Earlier logs prove the invocation actually failed at11:02:23 after metering journal writes failed, and failure finalization itself failed11:02:49 due fetch failed. The process was healthy and continued other jobs. The old pool released the failed invocation, and startup-only recovery could not run again until restart.

Fix: worker keeps the base/project queue lock while retrying bookkeeping, with backoff5/10/20/30seconds and bounded database requests. Retrying failure finalization preserves one attempt increment, fences by started_at, recognizes a committed transition whose response was lost, and does not resurrect cancellation or overwrite a newer claim. Base/project error writes are checked and protected against a newer updated_at. Success finalization retains the paid stage result in memory and retries its write instead of rerunning the stage; a committed done is recognized, enqueue reads/writes are checked, and the same invocation increments its project usage aggregate at most once. Startup recovery must succeed before claims start; a temporary database outage there no longer silently skips recovery. Shutdown stops retrying and leaves the saved checkpoint for restart.

Metering journal errors remain terminal for arbitrary/non-checkpointed stages. Only base_collect with a validated, nonempty relevance checkpoint gets bounded retry (up to5 failed attempts, usual backoff). The relevance gate reuses saved admissions and has its existing bounded recovery for an interrupted semantic review. This does not promise zero extra cost for the last unknown provider response: an unfinished check may be retried under that existing bounded policy; confirmed saved checks are reused. No global invalidation of paid caches, change to targeting rules, legacy ENG code or database schema.
