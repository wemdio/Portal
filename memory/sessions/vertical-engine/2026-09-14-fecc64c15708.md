Пользователь пополнил Requesty, нажал продолжение VBI и спросил, почему всё стоит
в очереди вместо параллельной работы. На production VE2 действительно выполнял
одну основную задачу за раз («Аврора»), но VBI не ожидал в настоящей очереди:
worker упал по V8 heap OOM между UPDATE базы и INSERT новой base_collect-задачи.

Read-only SSH 139.60.162.24: рестарт 14 сентября 22:41:47 UTC; память контейнера
512 MiB, heap около 259 MiB. База VBI a7d6c650-05f7-480d-8d87-196459c7b12f
сохранила 213/500 готовых контактов, collecting с 22:41:33.975 UTC, прежняя
задача done с 08:23:59 UTC. Подготовка перешла в error. В 22:59 UTC активен
только evidence «Аврора», задачи VBI нет. Точное место OOM не установлено,
разрыв записи состояния и очереди подтверждён. Это уточняет готовность после
редеплоя из sessions/vertical-engine/2026-09-14-996523d97f9c.md.

В коде добавлены два параллельных проекта в одном VE2 worker, запрет одновременных
стадий одного проекта, scoped AsyncLocalStorage для отмены LLM, drain при
остановке. Координатор читает только лёгкое состояние базы; resume не получает
снова тяжёлый collect_info из UPDATE. До создания задачи сохраняется pending
намерение продолжения. Оборванное продолжение collecting после старого done
чинится идемпотентно; failed/cancelled без запроса пользователя не повторяются.
Compose worker: RAM 2 GiB, heap 1536 MiB, CPU 1.0, concurrency 2.

Дополнительный скриншот пользователя показал противоречие: сверху подготовка
остановлена, снизу spinner по старому relevance_review_requested. В автоаутриче
сводка и строка базы теперь используют один расчёт статуса. Старый checkpoint
без активной задачи не означает работу; остановка/очередь без spinner.
Кнопка продолжения добавлена в карточку ошибки даже при base=collecting,
действие оставляет пользователя на шаге базы. Просмотр/скачивание сохранены.

Проверены 213 suites / 2402 tests за 54.245 s, TypeScript, ESLint, esbuild,
YAML. Реальная PostgREST JSON-проекция проверена read-only. ENG не изменён.
Локальная браузерная проверка реальных PreparationProgress/BaseRow с фикстурой:
остановка → очередь → работа; desktop 1100/mobile 390 px без переполнения и
ошибок JavaScript. Production POST не выполнялся.
Production-изменений, платных тестов и ручной постановки задач агентом не было.
Подробности и идентификаторы: docs/incidents/2026-09-15-ve2-resume-oom-and-parallel-projects.md.

Нужен пользовательский релиз Portal+VE2 worker с пересозданием контейнера,
затем «Продолжить подготовку» для текущего VBI error. Проверить реальное
совместное продвижение, отсутствие OOM и сохранение контактов после релиза.
Несколько контейнеров не запускать: resetStuckJobs пока глобальный, решение
предусматривает один процесс. Падение процесса может прервать обе активные
задачи; сохранённые checkpoint и startup recovery остаются механизмом возврата.
