## Запрос и область
После проверки редеплоя пользователь попросил исправить остановки сборов на Requesty HTTP 429 и добор по одной компании при 499/500 готовых контактов. Код только внутреннего VE2; остановленные production-задачи не возобновлялись, деплой и мерж в test/main не выполнялись.

## Проверенный результат
- Общая пауза Requesty по модели внутри процесса VE2, Retry-After (секунды/HTTP-дата), 30–300 секунд без заголовка. run_after сохраняется у задачи; после паузы запросы возобновляются постепенно. Ожидание без HTTP не расходует попытки и не создаёт фиктивный расход.
- Реальный 429 сохраняет прежние ограниченные бюджеты автоматических повторов, но не расходует смысловую попытку проверки компании и не вызывает более дорогой fallback. Повторяются только незавершённые проверки. Для прерванного исправления доказательства сохраняется предложение retry_proposal; при возобновлении не покупаются повторно классификация и чтение сайта. Ошибки журнала и checkpoint не маскируются обычным отказом качества.
- Явный отказ баланса, включая 429 с insufficient funds, по-прежнему останавливается как billing; неизвестный 429 не объявляется отсутствием средств. Тело ответа не добавлено в журнал; записывается числовой retryAfterMs.
- В адаптивном доборе исходные компании отделены от готовых email: партия 50–100 кандидатов в рамках остатка источника/общего лимита. Уже оплаченную партию завершаем полностью; возможен итог свыше 500 контактов. Новые партии после достижения цели не запускаются. Все quality/SMTP-гейты сохранены.

## Проверка
225 suites / 2473 tests прошли (60.241 s), TypeScript, ESLint изменённых файлов, esbuild VE2-воркера и git diff --check прошли. Новых test files/it-блоков нет. В существующих сценариях проверены общий cooldown для 16 одновременных отказов, отсутствие HTTP на паузе, ограничение повторов, возобновление сохранённых semantic/citation-проверок и обязательное GPT-подтверждение допуска. Сценарий 499 готовых + 50 кандидатов после actual/deferred 429 даёт 549 готовых и ровно одно задание конструктора в обоих путях.

## Урок и пределы
В integration fixture повторные пробуждения должны иметь JSON-границу: общий mock Supabase хранит вложенные объекты по ссылке, в отличие от production. Для этого сценария изолированы чтения/записи ve_bases; без этого тест ошибочно менял сохранённый construct.status при изменении локального объекта.
Общая пауза ограничена одним процессом. Точная причина production 429 без тела ответа остаётся неизвестной. Локальные тесты не доказывают реальную экономию/пропускную способность; после отдельного выпуска нужны продолжение сохранённых сборов и замер HTTP429, новых готовых контактов и фактической стоимости.
