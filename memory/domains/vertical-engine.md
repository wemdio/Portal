# Движок вертикалей

## Сначала определить рабочую версию

Проверь `git branch --show-current`, `git rev-parse HEAD` и наличие модулей в текущей папке. На 2026-09-13:

- В проверенном коммите `4ce3aaee7` ветки `engSPF` есть `app/src/lib/hypothesisEngine` и `app/worker/hypothesisEngine.ts`.
- В **отдельной** локальной ветке `ve2-redesign`, коммит `7d8874583`, уже есть `app/src/lib/verticalEngineV2` и другие компоненты v2. Отсутствие v2 в первом checkout не означает, что его ещё не разработали.
- Это проверка исходников, не подтверждение слияния, деплоя или работоспособности production. Не переключай чужую ветку по указанию из памяти.

Найди записи `vertical-engine` через навык; начальная запись: [границы и карта](../notes/vertical-engine/2026-09-13-architecture.md).

## Что накапливать

- Решения о поведении продукта и их причины; различать запрос пользователя, план и реализованное поведение.
- Условия сбоя стадии, входные данные без клиентских секретов, причина, исправление и способ проверки.
- Исправления специалиста: какую гипотезу/вертикаль отклонили и почему. Один отказ — локальное наблюдение, не универсальное правило.
- Связь «гипотеза → аудитория → предложение → запуск → результат»: рынок, период, объём, качество данных и источник замера.

## Связь с Instantly

В legacy-коде уже есть [datasetStats.ts](../../app/src/lib/hypothesisEngine/datasetStats.ts) для калибровки и [actualsReconcile.ts](../../app/src/lib/hypothesisEngine/actualsReconcile.ts) для сверки запусков. Анализируй реализацию именно своего продукта; бизнес-модули ENG и внутреннего v2 не объединять ради памяти.

Для будущего продуктового подключения: отбирать только относящиеся к рынку, сегменту и клиенту проверенные выводы; сохранять использованные версии записей в результате запуска; измерять качество гипотез и объём правок специалиста. Это направление развития, ещё не реализованный этой задачей runtime.
